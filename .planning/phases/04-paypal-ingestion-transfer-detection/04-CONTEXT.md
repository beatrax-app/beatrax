# Phase 4: PayPal Ingestion + Transfer Detection - Context

**Gathered:** 2026-05-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 4 lands PayPal as the project's fourth ingestion source (after ASN CSV / CAMT.053 / MT940 and ICS PDF) and lights up the two cross-account features the prior phases deferred: `pair_transaction_id` linking between paired own-account moves (ASN ↔ ICS settlement, PayPal → bank sweep) and a first-pass income detector that distinguishes genuine inflows from internal transfers.

The user can: upload a PayPal Activity Download CSV through the existing two-step wizard (issuer→format picker, with PayPal as the new third issuer group) and see one canonical transaction per logical payment — fees, currency-conversion rows, and any holds/authorizations rolled up or filtered rather than landing as duplicate rows; see ASN→ICS bulk-iDEAL settlements appear as a paired `transfer_out` (on ASN) / `transfer_in` (on ICS) joined via `pair_transaction_id`, with neither side counted as expense or income; see PayPal→ASN sweeps appear as a paired `transfer_out` (on PayPal) / `transfer_in` (on ASN) the moment both sides are in the ledger; and see every other positive inflow appear as `type='income'` (with a manual reclassification path on the transaction detail page) so monthly totals stop double-counting moves between own accounts.

The PayPal Reporting API path (ING-09) is **deferred to backlog** for this phase: PayPal's Transaction Search is gated behind a business account and the user is on a personal account. CSV remains the only supported PayPal ingestion path in Phase 4; the API path moves to REQUIREMENTS.md "Future / business-upgrade trigger" and ROADMAP.md Phase 4 wording is tightened accordingly during planning.

This phase does NOT add chain resolution (PayPal-charge → underlying funder, ICS bulk-settlement decomposition) — those are Phase 5. It does NOT add recurring detection, drift alerts, forecasting, or what-if. Those are Phases 8–10. The transfer-pair detector intentionally stops at "deterministic IBAN/synthetic-account-key match"; any candidate the detector cannot match deterministically remains a regular row (no review queue ships in Phase 4 — that surface lands with Phase 5's chain resolver, which reuses the same UX).

## Implementation Decisions

### PayPal CSV Format + Wave 0

- **D-57:** **PayPal Activity Download CSV is the canonical input format.** The user uses PayPal's default "Activity Download" CSV (Activity → Statements → Custom report → "Activity download" / "All transactions"). One row per event (payment / fee / currency conversion / hold / transfer). Comma-separated UTF-8. Includes `Transaction ID` and `Reference Txn ID` columns — these are the rollup keys per `research/PITFALLS.md` Pitfall 3. The legacy "Statement of Account" report and any business-only variants are NOT supported in Phase 4.
- **D-58:** **User has a real recent Activity Download export available for Wave 0.** Mirrors the Phase 2 / Phase 3 enablement-wave pattern: the raw CSV stays under `local/paypal/` (gitignored — see Phase 3's `local/ics/` precedent); Wave 0 anonymises it and commits the redacted result as `Modules/Ingestion/tests/fixtures/paypal/paypal-sample-1.csv`. Anonymisation is OUR job, not the user's. Redaction targets: email addresses → `kaarthouder@example.test`-style placeholders, names → `KAARTHOUDER`, IBANs → `NL00ASNB0000000000` (the same anonymised IBAN form Phase 2's CAMT fixture uses), Transaction IDs → fixed-length zero-padded synthetic IDs that preserve `Reference Txn ID` parent-child links, addresses dropped, ZIPs zeroed; **dates / amounts / currencies / event-type strings / merchant strings preserved verbatim** so the rollup parser is exercised against truth.
- **D-59:** **Wave 0 fingerprints the CSV language from the header row.** PayPal localises both column headers and event-type values (e.g. `Express Checkout Payment` vs `Express Checkout-betaling`, `Currency Conversion` vs `Valutaomrekening`). User is unsure which language their export shipped in (the account may have switched at some point). Wave 0 detects language by header-row token match and locks the empirical token vocabulary into a `PaypalCsvLanguageProfile` (parallel to Phase 2's `AsnCsvHeaderProfile` / Phase 3's `IcsPdfHeaderProfile`). If a future export ships under an unrecognised language, the adapter raises an explicit `UnsupportedPaypalCsvLanguageException` rather than silently mis-parsing. Phase 4 implements **whichever language Wave 0 finds in the committed fixture**; supporting both EN and NL is a follow-on if a second-language sample arrives.
- **D-60:** **Wave 0 empirical reporting set (mirrors Phase 3 Wave 0).** The Wave 0 plan reports back on:
  (a) language profile (EN / NL / other) and the empirical column-header tokens used,
  (b) the empirical event-type vocabulary present in this user's history (which subset of `Express Checkout Payment` / `Currency Conversion` / `Refund` / `General Withdrawal` / `Transfer to bank` / `Hold` / `Authorization` / `Reversal of General Account Hold` / `Mass Pay` / `Subscription Payment` etc. actually appears, in the user's language),
  (c) `Reference Txn ID` chain shapes (depth, fan-out — does a single payment have one fee child or many? Are currency-conversion pairs always two rows with a shared `Reference Txn ID`?),
  (d) presence/absence of explicit `Funding Source` column (research/ARCHITECTURE.md flagged this label has changed over time),
  (e) FX representation (single row with both legs vs two paired rows under a shared `Reference Txn ID`),
  (f) "Transfer to bank" row shape (counterparty IBAN populated? bank name? memo line carrying the destination IBAN?),
  (g) one-period reconciliation check: `sum(net_amount) == closing_balance - opening_balance` per `research/PITFALLS.md` Pitfall 3 — surface mismatch as a Wave-0 finding before any adapter code is written.

### Transaction ID Rollup Contract

- **D-61:** **Rollup is keyed by `Transaction ID`; children walk via `Reference Txn ID`.** For each unique `Transaction ID`, the row whose `Reference Txn ID` is null (or self-equal) is the **parent**; rows whose `Reference Txn ID` equals another row's `Transaction ID` are **children** that enrich the parent. The canonical `SourceTransactionDto` for the group carries the parent's `posted_at` / `booked_at` / merchant / counterparty and rolls up child rows into the dual-amount pair (native + settled) and into the rawPayload-stored event manifest. Orphan child rows whose parent is NOT in the file (cross-period boundary case) become standalone canonical rows under their own `Transaction ID` — the adapter logs them via `import_runs.extras.orphanChildCount`. This is the contract `research/PITFALLS.md` Pitfall 3 names directly.
- **D-62:** **Filtered event types — skip at the adapter boundary.** `Hold`, `Authorization`, `Reserve`, `Reversal of General Account Hold` are filtered entirely; they never become canonical rows. The skipped-row count surfaces via `import_runs.extras.skippedHoldCount` so the wizard can show "X hold rows skipped" in the import summary (Phase 5's existing 4-state preview UI gains no new state — these rows simply never enter the pipeline). Wave 0 confirms the exact set of skipped event-type strings in the user's language (D-60 (b)). The decision rationale lives at `research/PITFALLS.md` Pitfall 3 "Filter event types".
- **D-63:** **Currency Conversion pairs roll up into one canonical row.** When a foreign-currency payment generates a `Currency Conversion` sibling (out of foreign currency + in to settlement currency, both sharing a `Reference Txn ID`), the adapter folds the pair into the same canonical row's dual-amount fields: `amountMinor` / `currency` from the foreign-currency leg, `settledAmountMinor` / `settledCurrency` from the EUR leg, `fxRateUsed` derived per Phase 3's D-39 contract (`settled / native`). This honors `LED-03` (multi-currency preservation) and reuses the Phase 3 NormalizeStage substitution unchanged. If Wave 0 finds the conversion encoded as a single row with both legs in two columns, the adapter handles that shape directly without the pair-walk step.
- **D-64:** **`source_format = 'paypal-csv'`; `source_ref = Transaction ID`.** Every canonical row's `source_ref` is the parent `Transaction ID` — Phase 2's enrichment-rank contract makes `paypal-csv` rank below the ASN formats (it never enriches ASN rows; the rank function gains a new line `'paypal-csv' => 1`, same band as `asn-csv`). PayPal rows never collide with ASN/ICS rows under the v3 fingerprint tuple (different `account_id` always; cross-source dedup is the deliberate-design Phase 5 chain-resolution layer, NOT a fingerprint concern).
- **D-65:** **rawPayload stores the per-canonical-transaction event manifest.** Discriminator: `{ "format": "paypal-csv", "events": [ { "type": "Express Checkout Payment", "row": <raw_row_dict> }, ... ] }`. The parent + all children for that `Transaction ID` are preserved in order. Memory cost: ~1–3 KB per row in the worst case (5-event chain). Honors the Phase 3 D-49 rawPayload convention (own-row-only, never duplicate the entire statement). The skipped Holds/Authorizations are NOT stored in rawPayload — they're dropped at the adapter boundary (D-62), not after rollup.

### PayPal Account Modeling

- **D-66:** **One Account row of `kind='paypal'`, `default_currency='EUR'`, synthetic IBAN `'PAYPAL'`.** Mirrors Phase 3's `'ICS-CARD'` synthetic IBAN pattern (D-36, D-37). The single account holds all PayPal transactions regardless of currency-of-charge; native/settled column pair preserves every non-EUR row exactly the way ICS does. PayPal balances are inherently multi-currency, but **one Account row** keeps the schema simple and the wizard simple; the dashboard's per-currency mode (Phase 3 D-46) already renders multi-currency PayPal cleanly without further plumbing.
- **D-67:** **Wizard prompts to name the PayPal Account on first upload.** Mirrors Phase 3's D-38 ICS naming step: the trigger is "no Account of `kind='paypal'` exists yet". Suggested default: `'PayPal'`; user can override. The PreviewWizard step lands as a small extension to the existing ICS-naming branch (already proven in `Modules/Import/Internal/Http/Livewire/PreviewWizard.php`) — generalise the trigger from `kind='ics_card'` to "the appropriate-kind account for the declared format".
- **D-68:** **Multi-currency PayPal balance is implicit, not modeled.** No `paypal_balances` subtable; the account's net by currency is derivable from `SELECT SUM(amount_minor) GROUP BY currency` at query time. Phase 4 does NOT introduce a "current PayPal balance by currency" surface. If a later phase wants it (Phase 8 recurring detection over PayPal-funded subs? Phase 10 forecasting?), add it then.

### Wizard + Routing

- **D-69:** **Three-issuer wizard: ASN / ICS / PayPal.** Phase 3's two-step grouped picker (D-33) gains a third issuer group `PayPal`. Leaf format key: `paypal-csv`. `HeaderSniffer::sniffPaypalCsv()` extends the existing CSV-header-sniff pattern (it inspects the first row tokens against the language-profile registry from D-59) — the existing `paypal-csv` validator extension reads `'in:asn-csv,asn-camt053,asn-mt940,ics-pdf,paypal-csv'`. Mimes validator already accepts `csv`. No `paypal-api` slot in the picker — ING-09 is deferred; surfacing a greyed-out future option is premature noise.
- **D-70:** **SourceAdapterRegistry maps `'paypal-csv' => PaypalCsvAdapter::class`.** Adapter lives at `Modules/Ingestion/Internal/Adapters/Paypal/PaypalCsvAdapter.php`. Composition: `PaypalCsvLanguageProfile` (D-59) + `PaypalCsvEventTypeMap` (D-62) + `PaypalAmountParser` (US-locale: dot decimal, comma thousands — distinct from `AsnAmountParser` which is nl_NL) + `PaypalDateParser` (US-locale, distinct from `IcsDateParser`'s Dutch month abbreviations). All under `Modules/Ingestion/Internal/Adapters/Paypal/`.
- **D-71:** **`PaypalCsvAdapter` is stateful like the CAMT/MT940/ICS-PDF adapters.** After iteration, `lastStatementSummary(): ?StatementSummaryData` exposes a `StatementSummary` row that captures period start/end (derived from min/max booked_at across rolled-up canonical rows — same pattern as Phase 3 D-51 revised), and the four totals (openingBalance / closingBalance / totalInflow / totalOutflow). Wave 0 confirms whether the Activity Download CSV has explicit opening/closing balance rows; if not, the adapter computes opening = closing − sum(net) per Pitfall 3's reconciliation check. The single-statement-per-CSV assumption holds (Wave 0 verifies).

### Transfer-Pair Detection (LED-04)

- **D-72:** **`pair_transaction_id` is added in Phase 4 — schema migration ships with this phase.** Self-referential nullable foreign key on `transactions.pair_transaction_id` → `transactions.id` (ON DELETE SET NULL). No CHECK constraint that the pair's amounts sum to zero (the cross-currency case — Phase 3 multi-currency rows mean a PayPal→ASN sweep can carry FX rounding); the **invariant is enforced in the listener that writes the pair**, not at the DB layer. Migration: `2026_05_15_010002_add_pair_transaction_id_to_transactions.php` (the timestamp after the existing latest migration of the same date is left for the planner to lock in). No fingerprint-version bump — `pair_transaction_id` is NOT in the v3 tuple, so adding it doesn't break dedup.
- **D-73:** **Deterministic layer first, tolerant fallback for review only.** Layer 1 (deterministic, auto-link): match candidates whose `counterparty_iban` equals another `Account.iban` the same user owns AND whose `amount_minor` is equal and opposite (signed sum = 0 in same currency) AND `booked_at` falls within a ±3-day window. Synthetic IBANs (`'ICS-CARD'`, `'PAYPAL'`) participate as ordinary `Account.iban` values for matching — the ASN row whose counterparty_iban is `'ICS-CARD'` matches the ICS row whose account is `'ICS-CARD'`, same for PayPal. Layer 2 (tolerant fallback): if Layer 1 misses, NO auto-link in Phase 4 — the row stays singleton-typed; surfacing tolerant candidates to a review-queue UI is Phase 5's job (reuses the same Phase 5 chain-resolver review surface).
- **D-74:** **Half-pair state is observable: row is typed `transfer_out` / `transfer_in` immediately, `pair_transaction_id` stays NULL until partner lands.** When the ASN import has a row whose counterparty_iban matches a known own-account IBAN but the partner row doesn't exist yet, the row is still classified `transfer_out` (so it never inflates expense totals) and `pair_transaction_id` is NULL. When the partner import lands, the post-load listener (D-75) finds the orphan via a query keyed on `(account_id, amount_minor, currency, booked_at +/- 3 days, pair_transaction_id IS NULL, type IN ('transfer_in', 'transfer_out'))` and atomically writes both sides' `pair_transaction_id` foreign keys in one DB transaction. Honest "eventual consistency" shape.
- **D-75:** **Pair detection runs as a post-load event listener.** ImportPipeline already fires `TransactionImported` per persisted row (Phase 1 wiring — verify in code during planning). A new `PairTransferCandidates` listener under a new bounded module `Modules/Transfers/Internal/Listeners/` runs the deterministic Layer-1 match inside the same DB transaction as the listener's outer event-dispatch frame. The module's `Public/` surface stays empty in Phase 4 — only the listener is needed. This keeps `ImportPipeline` clean of cross-module concerns; matches `research/ARCHITECTURE.md` "enrichment via events" pattern.
- **D-76:** **Typing during import: `transfer_out` / `transfer_in` is decided BEFORE pair detection runs.** Specifically: a new `ClassifyTransactionType` step in `NormalizeStage` (or a small pre-Load step) classifies every row's `type` based on (a) source-format event-type mapping for PayPal (`Express Checkout Payment` → `expense`, `Refund` → `refund`, `General Withdrawal` / `Transfer to bank` → `transfer_out`, etc.), and (b) for ASN/ICS rows, the existing `counterparty_iban_matches_own_account` predicate flips the type from `expense` / `income` to `transfer_out` / `transfer_in`. The pair-detection listener then links the typed rows; it does NOT re-type them. Decoupling typing from pairing means a half-pair never silently miscounts.

### Income Detection (LED-05)

- **D-77:** **v1 income detector: positive `amount_minor` AND NOT `transfer_in`/`transfer_out` AND NOT `refund` AND NOT `fee` → `type='income'`.** Applied during `ClassifyTransactionType` (D-76). Refunds preserve their source-derived type (PayPal `Refund` event type → `type='refund'`; ASN refund rows already classify as `refund` from Phase 1's mapper — verify in the existing pipeline). The detector is intentionally simple-subtractive — counterparty-heuristic salary detection / recurring-income clustering is **Phase 8** (REC-04 is explicitly scoped there). LED-05 demoability test: a manually-typed refund/transfer NEVER appears in the "income" rollup on the dashboard; a salary-shaped positive inflow DOES.
- **D-78:** **Manual override on transaction detail page.** The Phase 3 transaction-detail Livewire SFC (`/transactions/{id}`) gains a "Reclassify" action: dropdown of allowed types (the `Transaction::TYPES` constant), confirm → updates `type` and (if needed) clears `pair_transaction_id`. UI-SPEC pass during planning locks the exact surface. The override is per-row and persistent. Reclassifying one side of a pair to non-transfer breaks the pair (sets `pair_transaction_id` to NULL on BOTH rows) — keeps the invariant honest.

## Specific Ideas

- **Wave 0 fixture anonymisation reuses the Phase 2 / Phase 3 protocol.** User hands over their raw PayPal Activity Download CSV; we run the anonymiser; the redacted CSV becomes the committed Wave 0 fixture. The raw CSV stays under `local/paypal/` (gitignored). Anonymisation preserves event-type strings / dates / amounts / currencies verbatim; redacts emails / names / IBANs / full Transaction IDs to fixed-length synthetic equivalents that preserve parent-child `Reference Txn ID` linkage. The Phase 2 IBAN check-digit re-anonymisation pattern (CAMT mod-97 valid synthetic IBANs) applies: where IBANs surface in PayPal CSV rows (e.g., "Transfer to bank" memo lines naming the destination IBAN), they become mod-97-valid placeholder IBANs.
- **Transaction-ID rollup is the headline complexity of this phase.** A 5-row PayPal "purchase + fee + currency conversion (out) + currency conversion (in) + memo" group must collapse to ONE canonical `SourceTransactionDto`. The contract is fully specified in `research/PITFALLS.md` Pitfall 3; the implementation walker (D-61) is single-purpose and independently testable. Test datasets (`spatie/pest-plugin-snapshots` + Pest datasets) drive parser-correctness from real examples.
- **`pair_transaction_id` is symmetric.** When the listener links row A to row B, BOTH rows get `pair_transaction_id` written in the same transaction: A.pair_transaction_id = B.id, B.pair_transaction_id = A.id. Reading from either side surfaces the other. Reclassifying one side via the manual override (D-78) breaks BOTH sides atomically. Defensive: a `BoundaryArchTest` rule asserts that whenever the listener writes one side, it writes the other; a Pest feature test exercises both directions.
- **Half-pair state is honest, not broken.** A PayPal sweep imported in May whose ASN counterparty doesn't land until June stays typed `transfer_out` (so it never inflates May's expenses) but has `pair_transaction_id = NULL` until June. When the ASN row lands, the May row gets its pair attached. The "orphan transfer" state is observable on the detail page (small "unpaired" indicator) — and disappears on its own as soon as the partner shows up.
- **The income detector is intentionally simple.** Subtractive rule (D-77): any positive amount not classified as transfer/refund/fee is income. The user expects the system to be useful even before recurring detection lands in Phase 8 — and the most common false-positives (PayPal refunds, ASN→ICS settlements) are handled by their own classifier paths. Counterparty-heuristic salary detection / payer-clustering is explicitly Phase 8 work.
- **No review queue ships in Phase 4.** Tolerant-window pair matching (Layer 2) is a Phase 5 surface — the Phase 5 chain resolver already needs a review queue, so PayPal's tolerant transfer-pair candidates simply use that same queue. Phase 4 stops at deterministic auto-link, which already covers the ASN→ICS settlement axis (synthetic-IBAN match) and the PayPal→ASN sweep axis (real ASN IBAN in PayPal CSV's memo).
- **`Modules/Transfers/` exists as a future home, not as substantial Phase 4 surface.** The Phase 4 listener + service provider are the entire module. When Phase 5's chain resolver wants to query "is row X paired?", it asks `Modules/Transfers/Public/Services/PairLookup.php` (added then). Postponing the public surface is consistent with the Phase 1/2 "promote to Public when a second consumer arrives" pattern.
- **ROADMAP.md SC #2 needs editing during plan-phase.** Phase 4 ships CSV-only (ING-09 deferred). The plan-phase agent writes the SC #2 edit alongside the REQUIREMENTS.md "Deferred" entry — same atomic-commit posture as Phase 3 used when ICS reversed from CSV to PDF.
- **Reconciliation soft-warning is the operationally-honest gate.** When `sum(net) ≠ closing - opening` on a real upload, the wizard surfaces the mismatch as a soft warning ("PayPal reconciliation: expected €X but rolled-up sum is €Y — possible parser gap or boundary edge"). Doesn't block ingestion (single-user, the user can always investigate); does flag the wizard summary so a silent regression in our rollup walker doesn't go undetected.
