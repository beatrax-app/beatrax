<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→Livewire wire snapshot | The sidebar's `$isDeveloper` value is server-computed but reaches the browser inside the Livewire wire snapshot. A tampered client cannot flip the value (the server re-renders on every wire call), but the **rendered HTML for a non-developer must not contain the Dev block markup at all** — see T-16-01. |
| theme tokens → CSS | Tokens are baked into the served stylesheet. No user input flows into the token values. No injection vector. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-01 | Information Disclosure | AppSidebar Blade view | mitigate | The Dev block is wrapped in `@if ($isDeveloper) ... @endif` so the markup is server-side absent for non-developers. Task 1 test #1 asserts the rendered HTML does NOT contain `side-dev-block` for a non-developer. Without this gate a non-developer would learn the Dev Console exists. |
| T-16-02 | Tampering | Livewire `$isDeveloper` property | accept | Livewire properties round-trip through the server on every action — a tampered wire snapshot is re-validated by `CurrentUser` on the next request. Sidebar is render-only with no destructive actions; even if a client flipped a property in memory, the next route navigation would re-compute it from the DB. |
| T-16-03 | Information Disclosure | account caption "developer · local" | accept | The caption reveals developer status to the developer themselves (who already knows). It is never rendered for non-developers (`$isDeveloper === false → "local"`). No cross-user leak. |
</threat_model>
