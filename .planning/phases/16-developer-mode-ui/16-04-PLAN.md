<objective>
Land the entire artisan runner end-to-end: the SAFE + DESTRUCTIVE command whitelist registered against the DevCommandRegistry interface, the Symfony Process spawn + SSE stream + cancel pipeline, the triple-gate modal (server-side enforced), the spatie/laravel-activitylog audit pipeline with 8KB excerpt cap, the Queue::looping worker heartbeat, the Advanced-toggle-reset-on-login listener, the /dev/artisan timeline UI with run cards, the /dev/audit filter page, and the manual prune command. Every component of DEVUI-02 (SAFE-tier streaming + history + cancel) and DEVUI-03 (DESTRUCTIVE-tier triple-gate + audit log via spatie) ships in this single plan because they share the same audit pipeline + process pipeline + SSE infrastructure.

Purpose: This plan establishes the AuditWriter concrete (`SpatieAuditWriter`), the Process+SSE pipeline (`CommandSpawner` + `RunRegistry` + `ArtisanStreamController`), the triple-gate primitive (`TripleGateModal`), the worker heartbeat (`WriteWorkerHeartbeat` listener), and the `run-card` Blade component that downstream Wave 5 plans (16-05 log tailer, 16-06 queue inspector, 16-07 doctor/sql) all reuse: the log tailer mounts the same SSE controller pattern, the queue inspector's bulk-delete uses the same triple-gate, the doctor panel wraps the same Process+SSE pipeline around `beatrax:doctor`, the SQL panel writes through the same SpatieAuditWriter. After this plan ships, Wave 5 is mostly composition.

Output: A working `/dev/artisan` page where a developer can run any of the 9 SAFE-tier commands (D-12) one-click with live stdout streaming, or any of the 6 DESTRUCTIVE-tier commands (D-13) through the triple-gate modal; a `/dev/audit` filterable history page; a `dev_mode_audit` table populated per run; the `dev_mode.queue_worker_heartbeat` cache key updating on every queue tick; an Advanced session toggle that resets on every login. Three of the eight previously-disabled dev sidebar items (Artisan + Audit) become enabled (Doctor stays disabled until 16-07).

## Phase Goal

**As a** developer in the Dev Console, **I want to** click `db:backup` in the artisan runner and watch live stdout stream into a run card, click Cancel on a long-running command and see it die, run a DESTRUCTIVE command like `db:restore` only after passing the triple-gate (Dev Mode ON + Advanced ON + typing `beatrax`), and review every command I've run from the /dev/audit page with filters and tier coloring, **so that** the rest of Phase 16's panels can compose this audit + streaming + triple-gate machinery instead of re-implementing it.

NO ANALOG IN REPO for the SSE controller — see PATTERNS.md § Missing patterns. Use RESEARCH § Pattern 2 (full reference implementation) as the seed:
- `response()->stream($cb, 200, ['Content-Type' => 'text/event-stream', 'Cache-Control' => 'no-cache', 'X-Accel-Buffering' => 'no'])`.
- Inside the closure: `while ($process->isRunning()) { $chunk = $process->getIncrementalOutput() . $process->getIncrementalErrorOutput(); if ($chunk !== '') { echo "data: " . $this->redact($chunk) . "\\n\\n"; @ob_flush(); @flush(); } if (connection_aborted()) break; usleep(150_000); }`.
- After loop: `echo "event: done\\ndata: " . $process->getExitCode() . "\\n\\n";` + audit-log write.
- RESEARCH Pitfall 4 mitigation: set `X-Accel-Buffering: no`, ini_set output_buffering, ob_flush() + flush() per chunk.

`CommandSpawner::start(string $command, array $args, int $callerUserId): string`:
- Generates `run_id = (string) Str::uuid()`.
- Constructs `new Process(array_merge(['php', 'artisan', $command], $this->flattenArgs($args)), base_path())`.
- `setTimeout(null)` — the SSE controller owns the time budget (RESEARCH Open Q3: 24h cache TTL on `pid` + `run_id`).
- `start()` (non-blocking).
- `$this->registry->store($run_id, $process->getPid(), $command, $args, now(), $callerUserId, $tier)`.
- Returns `$run_id`.
- The `flattenArgs($args)` helper formats the args per Symfony Process expectations: positional args first, then `--key=value` for options. The ArgSpec DTO tells the spawner which is which.

`RunRegistry` (cache-backed per D-16):
- Methods: `store(string $runId, int $pid, string $command, array $args, CarbonInterface $startedAt, int $callerUserId, string $tier): void`, `find(string $runId): ?RunRecord`, `markFinished(string $runId, int $exitCode, ?CarbonInterface $finishedAt): void`, `markCancelled(string $runId): void`.
- Storage: cache key `dev_mode.run.{runId}` with TTL 24h (per RESEARCH Open Q3 recommendation).
- `RunRecord` is a small DTO: `runId`, `pid`, `command`, `args`, `startedAt`, `callerUserId`, `tier`, `status` (running|done|cancelled|failed), `exitCode?`, `finishedAt?`.

`ArtisanStreamController` (`__invoke(string $runId): StreamedResponse`):
- Verifies the request user is `is_developer === true` via CurrentUser DI (defense-in-depth — the route already has `ensureDeveloperMode` but the controller checks again because SSE long-lived connections are a juicy target).
- Resolves RunRecord from RunRegistry; 404 if absent.
- Rehydrates the live Process object from the PID (Symfony Process supports adopting an existing PID via `Process::fromShellCommandline()` — actually no, Symfony Process does not directly support rehydrating from PID. ALTERNATIVE: store the Process instance in a request-scoped singleton during the lifetime of the spawning request — but the spawning request and the SSE request are separate. CORRECT APPROACH per RESEARCH Pattern 2 line: the spawn happens INSIDE the SSE controller, not as a separate request. The Livewire component dispatches a "run" event → the controller spawns + streams in a single HTTP request. Cancel is a separate POST endpoint that reads the PID from cache and sends SIGTERM via `posix_kill($pid, SIGTERM)` or `Process::stop()` on a Process re-created with `Process::fromPid()` (verify the exact API)).
- Actually re-read RESEARCH Pattern 2 in 16-RESEARCH.md once during execution to confirm the exact rehydration model. The two viable architectures are:
  (a) Spawn-in-controller: the Livewire component POSTs to `/dev/artisan/run` which spawns + redirects-to-SSE-stream-route. The stream route owns the Process for its lifetime.
  (b) Spawn-separately: the Livewire component POSTs to `/dev/artisan/spawn` which spawns + returns run_id; the SSE route adopts the PID via `posix_kill` (Unix) checks for liveness + tails stdout/stderr from a separate file the spawner redirected to.
  Architecture (a) is simpler and matches RESEARCH Pattern 2; architecture (b) is more robust for page-refresh reconnect. **Recommendation:** Architecture (a) for v1. Page-refresh-reconnect (D-16) is satisfied by re-reading the audit log row (which always exists) — the user sees the cached output of a completed run, not the live stream of a still-running one. Document this trade-off in the SUMMARY.
- Loop body per RESEARCH Pattern 2 (see above).
- On loop exit: write the dev_mode_audit row via SpatieAuditWriter (`recordCommandRun(...)`); call `RunRegistry::markFinished(...)`.

`ArtisanCancelController` (`__invoke(string $runId, ?CurrentUser $user): JsonResponse`):
- Resolves RunRecord; 404 if absent.
- Reads the PID; sends `posix_kill($pid, SIGTERM)` (PHP function; check `extension_loaded('posix')` first — fallback to `shell_exec("kill -TERM $pid")` only if posix is unavailable). Wait 3 seconds; if still running, `posix_kill($pid, SIGKILL)` (matches Process::stop's grace pattern).
- Writes cancel marker to RunRegistry; writes an audit row with `status: cancelled` (or omits the audit and lets the SSE controller's done-handler do it — pick one).
- Returns `204 No Content`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /dev/artisan | EnsureDeveloperMode gates entry. Inside, the Livewire component dispatches command-run events that flow into the controller. Every command is from the locked whitelist (D-12/D-13); no free-form shell-out is possible. |
| browser → /dev/artisan/cancel/{runId} | Controller resolves the PID from cache; sends SIGTERM. If the runId is forged the cache lookup fails → 404. Cannot kill arbitrary PIDs because the cache key is namespaced + scoped per run. |
| arg form → Symfony Process | Args pass through Laravel `validate()` (per ArgSpec rules) before being assembled into the Process command array. Process receives args as an array (no shell interpolation possible — `Process::fromShellCommandline()` would be the dangerous variant; we use the array form). |
| spatie activity log → DB | Excerpts pass through RedactionExcerptCap BEFORE write (basic Bearer + JWT regex; OAuth scrub-set added in 16-05). |
| triple-gate confirm → command spawn | Three independent server-side checks (DevModeFlag, session.advanced, hash_equals('beatrax', typed)) before the spawn fires. UI-only gates would be insufficient. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-02 | Tampering | Destructive command run by mis-click or by tampered Livewire payload | mitigate | Triple-gate enforced server-side in `TripleGateModal::confirm()`. Three independent checks (DevModeFlag, session.advanced, hash_equals app name). UI-only gates are insufficient — server re-validates every gate on the confirm request. Tested in TripleGateTest. |
| T-16-11 | Tampering | Artisan command injection via arg form | mitigate | Declarative arg-form schemas via ArgSpec DTO; Laravel `validate()` applies the rules array before spawn. Process receives args as an array — no shell interpolation. Whitelist of command names enforced via DevCommandRegistry::find() (raises on unknown names). NEVER-EXPOSED commands (D-14: `migrate`, `migrate:rollback`, `db:seed`) are absent from the registry → cannot be spawned via the runner. |
| T-16-12 | DoS | Process orphaned by browser disconnect | mitigate | The SSE controller's loop checks `connection_aborted()` and breaks; the cancel endpoint sends explicit SIGTERM. Cache TTL (24h per Open Q3) on the `pid` + `run_id` entries prevents indefinite buildup. Page-refresh during a live run loses the stream view but the audit-log row still gets written by the controller's done-handler (the loop runs to completion server-side even if the client disconnects). |
| T-16-13 | Information Disclosure | Activitylog excerpts contain sensitive content | mitigate (basic) | RedactionExcerptCap applies Bearer + JWT regex + 8KB cap before write (this plan). 16-05 swaps in the full RedactSecretsProcessor with OAuth scrub-set. Risk window: this plan ships → 16-05 ships. Mitigation in the gap: a stdout containing a JWT or Bearer header is already redacted; a stdout containing a raw OAuth secret string from `oauth_secrets` is NOT redacted. Document the gap in SUMMARY; ship 16-05 in the same wave (Wave 5) so the window is minimal. |
| T-16-14 | Elevation of Privilege | A Livewire `wire:click` from a non-developer that flips the Advanced toggle | mitigate | `AdvancedToggleController` requires the route to be inside the /dev group (EnsureDeveloperMode applies). Session write is per-user. A non-developer cannot reach the route (404 via middleware) so cannot flip their own toggle. |
| T-16-15 | Information Disclosure | SSE stream content leaks across users | mitigate | The SSE controller resolves the RunRecord by runId — the runId is a UUID (unguessable). The controller additionally verifies the requesting user matches the RunRecord's callerUserId (defense-in-depth — a developer cannot inspect another developer's run stream unless they have the UUID, AND the controller cross-checks ownership). |
| T-16-16 | Tampering | SIGTERM to arbitrary PID via forged cancel | mitigate | The cancel controller reads the PID FROM cache via the runId lookup, never from the request body. A forged runId resolves to 404; the PID never originates from user input. |
