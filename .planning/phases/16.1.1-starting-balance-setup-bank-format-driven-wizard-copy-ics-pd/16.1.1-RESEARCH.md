### Hook 2 — G1/D-03 — PayPal Activity CSV starting-balance column

**Answer: PayPal's `Saldo` column is NOT a usable starting balance. The G1 PayPal detector cannot read first-row Saldo and call it the starting balance. The honest baseline is `0` (treat PayPal as a zero-balance account because PayPal funds sweep through immediately) and surface the card to the user in an editable manual-entry state.**

Verified by reading `Modules/Ingestion/Internal/Adapters/Paypal/PaypalCsvAdapter.php` lines 48–52 and 198–214:

```
// The PayPal Activity Download does not ship explicit opening / closing
// balance rows — the per-event `Saldo` cell resets to zero after every
// funding sweep — so no opening-vs-closing reconciliation gate is
// computed for this adapter.
```

The adapter hard-codes `openingBalanceMinor: 0` and `closingBalanceMinor: $netSumMinor` (sum of net per row).

The column map (`PaypalCsvColumnMap.php` line 43) confirms `'balance' => 'Saldo'` — the column exists, but the adapter author already determined it's not usable as a running balance.

**Recommendation for the PayPal `StartingBalanceDetector` strategy:**

- Option A (preferred): The PayPal strategy returns `null` (no auto-detect possible). The G1 confirm card for the PayPal account renders in the **manual-entry state** (UI-SPEC line 397: "We couldn't auto-detect a starting balance for this account. Enter one manually or skip."). The user picks the value or skips (writes `NULL` to preserve user intent).
- Option B (rejected): Read first-row Saldo as the starting balance. Rejected because Saldo resets to 0 after every funding sweep, so the first row's Saldo is `0` for virtually every PayPal export (the export typically starts mid-month right after a sweep). Surfacing `€0.00 as starting balance` would be wrong silence.

**Implication for D-03:** The four "detector strategies" are not symmetric. Three (CAMT.053, MT940, ICS PDF) read from `statement_summaries`; one (PayPal) returns `null` and triggers the manual-entry card.

`[VERIFIED: PaypalCsvAdapter.php lines 48-52, 198-214]` and `[VERIFIED: PaypalCsvColumnMap.php line 43]`.

### Hook 6 — G1/D-05 — UX placement (new step vs. section)

**Answer: Section on FirstImportStep. UI-SPEC has already locked this** (line 34: "G1 confirm cards are a section appended to FirstImportStep").

The reasoning chain that confirms the UI-SPEC choice:

1. **WizardStepRegistry currently has 6 steps:** `welcome`, `connect-bank`, `connect-card`, `connect-email`, `first-import`, `done`. Adding a 7th step (`confirm-balances`) would require:
   - Migration to add the new row to `wizard_progress` for every existing user (idempotent backfill listener — exists for `SeedDefaultCategoryTree` pattern).
   - WizardStepRegistry update: new STEPS entry, non-skippable.
   - New step component + blade + Pest test.

### Pattern 1 — Tagged-strategy service container binding (D-03)

**What:** Mirrors the existing `PaymentTypeHinter` discovery pattern. Each `DetectsStartingBalance` implementation registers itself via a container tag; an aggregator service iterates the tag.

**When to use:** Whenever you have N pluggable per-source implementations of one contract and want them discovered without a hand-maintained registry array.

**Example (Provider register):**

```php
// Modules/Import/Providers/ImportServiceProvider.php
$this->app->tag([
    Camt053StartingBalanceDetector::class,
    Mt940StartingBalanceDetector::class,
    IcsPdfStartingBalanceDetector::class,
    PaypalCsvStartingBalanceDetector::class,
], 'starting-balance.detector');

$this->app->bind(
    \Modules\Import\Public\Services\DetectStartingBalancesQuery::class,
    fn (Application $app) => new DetectStartingBalancesQuery(
        detectors: iterator_to_array($app->tagged('starting-balance.detector')),
    ),
);
```

**Example (Strategy interface):**

```php
// Modules/Import/Public/Contracts/DetectsStartingBalance.php
interface DetectsStartingBalance
{
    /**
     * Returns null when no balance can be inferred for this source.
     * @param  list<int>  $importRunIds  Import runs of this source for the user
     */
    public function detect(array $importRunIds, User $user): ?StartingBalanceCandidate;

    public function supports(string $sourceFormat): bool;
}
```

### Pattern 2 — `DB::transaction()` wrapping multiple action invocations (D-08)

**What:** FirstImportStep's "Commit everything" wraps every `ConfirmImport($id, $user)` call in a single Laravel `DB::transaction`. If any call throws, the entire batch rolls back.

**Note:** `ConfirmImport::__invoke()` already wraps its OWN body in a `DB::transaction` (verified at `Modules/Import/Public/Actions/ConfirmImport.php` docstring line 32: "The transaction wrapping both writers means a recorder failure cannot land enrichments and an enrichment failure cannot land inserts — confirm is atomic across both halves.").

**Implication:** Nesting `DB::transaction()` in PHP/Laravel uses save-points by default — a nested transaction failure rolls back to the parent's save-point. The outer `DB::transaction` at FirstImportStep wraps all ConfirmImport calls; if commit #2 of #3 fails, commits #1 + #2 roll back; commit #3 was never attempted.

**Example:**

```php
// In FirstImportStep::commit(...)
$this->db->connection()->transaction(function () use ($importRunIds, $balanceConfirmations, $user): void {
    foreach ($importRunIds as $id) {
        ($this->confirmImport)($id, $user);  // throws on any failure → outer rolls back
    }
    foreach ($balanceConfirmations as $accountId => [$minor, $date]) {
        $this->db->connection()->table('accounts')
            ->where('id', $accountId)
            ->where('user_id', $user->id)
            ->update([
                'starting_balance_minor' => $minor,
                'starting_balance_date' => $date,
                'updated_at' => $this->clock->now()->toDateTimeString(),
            ]);
    }
});
```

Note the chain-resolver dispatch inside `ConfirmImport::__invoke` already deliberately runs OUTSIDE the inner transaction closure. Nesting under an outer transaction means the chain-resolver job may be queued before the outer transaction commits — same SQLite-write-pending race the inner closure avoids. **Mitigation:** dispatch chain resolution AFTER the outer transaction returns (the planner verifies this matches existing semantics; if needed, refactor ConfirmImport to take an optional `dispatchChain: bool` argument and have FirstImportStep dispatch once at the end).

### Anti-Patterns to Avoid

- **Inline `style="background: var(...)"` in dark-mode-relevant surfaces.** This is the root cause of batch-8 Issue A. Use explicit Tailwind utility classes with `dark:` variants. Applies to any new modal / card / overlay added by this phase.
- **Mounting OAuth modal only in `app.blade.php`.** Forgets that the wizard uses `app-wizard.blade.php`. Mount in BOTH.
- **Hand-rolled per-source `if/else` ladders for starting-balance detection.** Use the tagged-strategy pattern; mirrors PaymentTypeHinter.
- **Hardcoded "ASN" copy.** G3 explicitly forbids this outside the bank list. Use the per-format helper map in the connect-bank-step blade.
- **PHPDoc / comment references to G1–G9, UAT, or phase numbers.** Memory `feedback_codebase_gsd_agnostic`.
- **Per-step OAuth modal mount.** Per CR-01 (16.1-REVIEW.md), exactly the pattern this phase fixes.

## Common Pitfalls

### Pitfall 1: Mounting OAuth modal in only one layout
**What goes wrong:** ConnectEmailStep dispatches `oauth-client-wizard:open` but the modal is mounted in `app.blade.php` only. The wizard layout (`app-wizard.blade.php`) doesn't have the modal. Click is silent.
**Why it happens:** Easy to assume "one main layout" because the existing global mounts in `app.blade.php` are obvious.
**How to avoid:** Mount the modal in BOTH layouts. Pest test asserts the modal element renders inside each layout's slot.
**Warning signs:** Console quiet on click; DOM inspection in the wizard route shows no `oauth-client-wizard-modal` element.

### Pitfall 2: `DB::transaction` nesting around `ConfirmImport`
**What goes wrong:** `ConfirmImport` already wraps its body in `DB::transaction`. The outer `DB::transaction` at FirstImportStep nests as a save-point in Laravel. If commit #2 fails after commit #1, the OUTER transaction must roll back, but `ConfirmImport`'s post-transaction chain-resolver dispatch may have already enqueued a job for commit #1 — the worker would read stale state.
**Why it happens:** `ConfirmImport::__invoke` dispatches `ResolveChainLinksJob` AFTER `DB::transaction` closure returns but BEFORE the outer transaction commits.
**How to avoid:** Either (a) refactor `ConfirmImport` to accept an optional `dispatchChain: bool = true` arg and pass `false` from FirstImportStep, dispatching once at the end of the outer transaction; or (b) document that chain resolution may briefly see partial state for in-flight wizards (low-impact for a fresh-install scenario where there's nothing to chain against yet). **Prefer (a).**
**Warning signs:** Intermittent "chain resolution found N rows, expected M" log entries.

### Pitfall 3: PayPal detector returning `0` instead of `null`
**What goes wrong:** The detector returns a `StartingBalanceCandidate(0, $earliestBookedAt)` for PayPal because the adapter wrote `openingBalanceMinor: 0`. The user sees a `€0.00 starting balance` confirm card and clicks Confirm. Their actual PayPal opening balance (which they may have manually known) is lost as zero.
**Why it happens:** Confusion between "the adapter persisted 0" (true) and "0 is the actual starting balance" (often false).
**How to avoid:** The PayPal detector returns `null`, NOT `0`. The card renders in manual-entry state per UI-SPEC line 397. The user explicitly types their value or skips.
**Warning signs:** Pest test asserting `PaypalCsvStartingBalanceDetector::detect()` returns `null` for any input.

### Pitfall 4: Stale ImportRun stash after wizard re-run
**What goes wrong:** User runs the wizard, uploads a bank statement, gets to FirstImportStep, sees the consolidated preview, clicks Cancel (or closes the bundle). Two weeks later they re-run the wizard. The `bank_import_run_id` is still in `wizard_progress.data`. ConnectBankStep treats their fresh upload as a duplicate (same SHA-256 path), keeps the stash unchanged, but the user expects "the file I just uploaded." Meanwhile the stashed ImportRun's row may have been deleted by an unrelated cleanup.
**Why it happens:** `wizard_progress.data` survives any user action that doesn't explicitly clear it.
**How to avoid:** D-10 sets baseline 14-day staleness. FirstImportStep filters stashed IDs that point to deleted rows, confirmed-elsewhere rows, or rows older than 14 days. Filtered rows surface as the "we left it out" muted note (UI-SPEC line 396).
**Warning signs:** FirstImportStep blank when the user expected a preview.

### Pitfall 5: G3 CSV gate accepts a CSV before bank chip pick
**What goes wrong:** User clicks the CSV format chip but the drop-zone is somehow active (Livewire state desync); the user drops an ASN CSV; the parser dispatches without a `format_hint`; the content-sniff guesses ING and parses garbage.
**Why it happens:** Client-side state and server-side validation diverge.
**How to avoid:** Both server-side: rules() validates `format_hint` is present whenever `selectedFormat === 'asn-csv' || 'ing-csv'`; AND client-side: blade marks `aria-disabled="true"` + `tabindex="-1"` + opacity, AND uses `disabled` attribute on the file input.
**Warning signs:** Larastan-level rule complaining about unguarded enum branch; or Pest test "dispatches CSV without bank picked" returns 422.

```php
declare(strict_types=1);

namespace Modules\Import\Public\Contracts;

use Modules\Core\Models\User;
use Modules\Import\Public\Dto\StartingBalanceCandidate;

/**
 * Per-source starting-balance detector. Each implementation knows how to
 * extract a credible opening balance for its source format. Returns
 * `null` when the source has no usable opening balance signal.
 */
interface DetectsStartingBalance
{
    public function supports(string $sourceFormat): bool;

    /**
     * @param  list<int>  $importRunIds  ImportRuns of any source that belong to the user
     * @return list<StartingBalanceCandidate>  One per detected account; empty list when nothing detected.
     */
    public function detect(array $importRunIds, User $user): array;
```

```php
// Modules/Import/Internal/Detectors/IcsPdfStartingBalanceDetector.php
declare(strict_types=1);

namespace Modules\Import\Internal\Detectors;

use Illuminate\Database\DatabaseManager;
use Modules\Core\Models\User;
use Modules\Import\Public\Contracts\DetectsStartingBalance;
use Modules\Import\Public\Dto\StartingBalanceCandidate;

final class IcsPdfStartingBalanceDetector implements DetectsStartingBalance
{
    public function __construct(private readonly DatabaseManager $db) {}

    public function supports(string $sourceFormat): bool
    {
        return $sourceFormat === 'ics-pdf';
    }

    /**
     * @inheritDoc
     */
    public function detect(array $importRunIds, User $user): array
    {
        if ($importRunIds === []) {
            return [];
        }

        $rows = $this->db->connection()
            ->table('statement_summaries')
            ->join('import_runs', 'import_runs.id', '=', 'statement_summaries.import_run_id')
            ->where('statement_summaries.user_id', $user->id)
            ->where('import_runs.source_format', 'ics-pdf')
            ->whereIn('statement_summaries.import_run_id', $importRunIds)
            ->whereNotNull('statement_summaries.opening_balance_minor')
            ->whereNotNull('statement_summaries.opening_balance_date')
            ->select([
                'statement_summaries.account_id',
                'statement_summaries.opening_balance_minor',
                'statement_summaries.opening_balance_date',
                'import_runs.source_format',
            ])
            ->orderBy('statement_summaries.opening_balance_date', 'asc')
            ->get();

        $byAccount = [];
        foreach ($rows as $row) {
            $accountId = (int) $row->account_id;
            if (isset($byAccount[$accountId])) {
                continue;  // earliest per account wins
            }
            $byAccount[$accountId] = new StartingBalanceCandidate(
                accountId: $accountId,
                openingBalanceMinor: (int) $row->opening_balance_minor,
                openingBalanceDate: $row->opening_balance_date,
                sourceFormat: 'ics-pdf',
            );
        }

        return array_values($byAccount);
    }
}
```

### FirstImportStep `commit()` action skeleton

```php
public function commit(
    DatabaseManager $db,
    ConfirmsImports $confirmImport,
    CurrentUser $currentUser,
    Clock $clock,
    LoggerInterface $logger,
    Application $app,
): void {
    $this->commitError = null;
    $user = $currentUser->user();

    // 1. Read stashed import run ids.
    $importRunIds = $this->resolveImportRunIds($user);
    if ($importRunIds === []) {
        $this->commitError = 'Nothing to commit.';
        return;
    }

    // 2. Read confirmed starting-balance overrides from the
    //    StartingBalanceCard child components' Livewire props.
    //    (Aggregated via $this->balanceConfirmations during card events.)

    try {
        $db->connection()->transaction(function () use ($importRunIds, $user, $confirmImport, $clock, $db): void {
            foreach ($importRunIds as $id) {
                ($confirmImport)($id, $user);
            }
            foreach ($this->balanceConfirmations as $accountId => $confirmation) {
                $db->connection()->table('accounts')
                    ->where('id', $accountId)
                    ->where('user_id', $user->id)
                    ->update([
                        'starting_balance_minor' => $confirmation['minor'],
                        'starting_balance_date' => $confirmation['date'],
                        'updated_at' => $clock->now()->toDateTimeString(),
                    ]);
            }
        });
    } catch (Throwable $e) {
        $logger->error('FirstImportStep: commit failed.', [
            'exception_class' => $e::class,
            'exception_message' => $e->getMessage(),
            'exception_trace' => SafeTrace::cap($e, $app->basePath()),
        ]);
        $this->commitError = sprintf(
            "We couldn't commit your statements: %s. Nothing was changed.",
            $e->getMessage(),
        );
        return;
    }

    $this->dispatch('wizard.step.completed');
}
```

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-user data access via crafted `wizard_progress.data['bank_import_run_id']` | I (Information disclosure) | `BuildConsolidatedPreviewQuery` filters `import_runs.user_id = $user->id` explicitly. Pest test asserts a stashed import run id belonging to user B is invisible to user A. |
