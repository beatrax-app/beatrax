<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `BuildConsolidatedPreviewQuery::build()` → SQLite + PreviewCache | Per-user-scoped reads against `import_runs` + the in-memory cache. |
| Caller → `ConfirmImport::__invoke($id, $user, $dispatchChain)` | The new `$dispatchChain` flag controls whether `ResolveChainLinksJob` dispatches — misuse could double-dispatch or skip dispatch. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16.1.1-21 | Information disclosure | A tampered `wizard_progress.data['bank_import_run_id']` value (set by Plan 06) points at another user's ImportRun. Without an explicit user-scope check, `BuildConsolidatedPreviewQuery` could return foreign rows. | mitigate | `BuildConsolidatedPreviewQuery::build()` filters every input id against `->where('import_runs.user_id', $user->id)` — any non-owned id is dropped before reaching the section. The fourth Pest assertion (`respects user_id boundary`) locks this in. |
| T-16.1.1-26 | Race condition | Inner `ConfirmImport`'s `ResolveChainLinksJob` dispatch races a future outer transaction commit (Pitfall 2). A queue worker could read partial state. | mitigate | This plan extends `ConfirmImport` with `dispatchChain: bool = true` so Plan 07b's `FirstImportStep` can pass `false` on every inner call and dispatch chain resolution ONCE after the outer transaction returns. The new flag is the load-bearing fix; Plan 07b's `FirstImportStepCommitRollbackTest` second `it(...)` locks the once-per-commit invariant in place. |

No HIGH-severity threats. This plan is a back-end query + contract extension only — the user-facing UPDATE surface ships in Plan 07b.
