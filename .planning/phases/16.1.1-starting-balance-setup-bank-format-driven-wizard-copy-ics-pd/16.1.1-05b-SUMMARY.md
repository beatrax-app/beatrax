- **StartingBalanceCandidate readonly DTO** under `Modules/Import/Public/Dto/` — Spatie Data subclass with `accountId`, `openingBalanceMinor`, `openingBalanceDate` (ISO string), `sourceFormat`. Mirrors `PaymentTypeHint`'s file shape line-for-line.
- **Four detector implementations** under `Modules/Import/Internal/Detectors/`:
  - `Camt053StartingBalanceDetector` — joins `statement_summaries` to `import_runs`, filters to `asn-camt053`, returns earliest-date rows per account.
  - `Mt940StartingBalanceDetector` — same shape, `asn-mt940`.
  - `IcsPdfStartingBalanceDetector` — same shape, `ics-pdf`.

  1. Earliest `openingBalanceDate` wins.
  2. On a date tie, prefer `sourceFormat === 'asn-camt053'` over MT940.
  3. If still tied (two CAMT.053 imports disagreeing on the same date with different values), surface BOTH candidates so the wizard renders a conflict-resolution card.

## Decisions Made

- **DatabaseManager dropped from `DetectStartingBalancesQuery` constructor.** The plan's `<behavior>` block specified `__construct(private DatabaseManager $db, private iterable $detectors)`. PHPStan L10 strict (strict-rules + Larastan) reports `property.onlyWritten` on the unused readonly `$db` property; Larastan-strict's `Do not add type casts just to silence errors` and `Do not add @phpstan-ignore comments` guidance leaves no PHPStan-compliant escape. The aggregator does not actually need DB access — detectors own DB reads — so the cleanest fix was to drop the parameter and match the analog (`PaymentTypeClassifierStage` also injects only the iterable). Documented as a Rule 3 deviation (blocking-issue auto-fix) for completeness. The plan's external interface — `collect(array $importRunIds, User $user): list<StartingBalanceCandidate>` — is unchanged.
- **Detectors emit ALL distinct rows at the earliest per-account date.** The plan's `<behavior>` block could be read as "one candidate per account" (single emission). With single emission, the aggregator's fourth test ("surfaces both candidates when CAMT and MT940 disagree on the same date with different values") cannot pass because the detector already deduplicated to one row before the aggregator sees it. The detector now emits every distinct `(openingBalanceMinor, openingBalanceDate)` pair at the earliest date per account; the aggregator's `pickWinner()` then applies the cross-source tie-break across the full set. Test 4 passes.
- **PHPStan helper pattern** — `private static function toInt(mixed): int / toString(mixed): string / dateOnly(string): string` mirrors the `BackfillStartingBalanceFromStatementSummaries` (Plan 05) pattern for reading `stdClass` rows from `DB::table()` queries at Larastan L10 strict. Avoids `@phpstan-ignore` annotations and gratuitous casts.
- **Date normalisation at the boundary.** `statement_summaries.opening_balance_date` is a `dateTime` column; the candidate's `openingBalanceDate` is an ISO date string. The `dateOnly()` helper strips the time component so the candidate carries a stable `YYYY-MM-DD` value the wizard renders directly and that Plan 07's UPDATE path can write to the `accounts.starting_balance_date` `date` column without further normalisation.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking issue] Dropped `DatabaseManager` injection from `DetectStartingBalancesQuery`**
- **Found during:** Task 2 PHPStan verification
- **Issue:** Plan specified `__construct(private DatabaseManager $db, private iterable $detectors)`. PHPStan L10 strict flagged `$db` as `property.onlyWritten` (the aggregator never reads it). The aggregator doesn't need DB access — detectors own all DB reads — so retaining the parameter would have required a `@phpstan-ignore` annotation, which the Larastan strict ruleset rejects.
- **Fix:** Dropped the `DatabaseManager` parameter. Constructor is now `__construct(private iterable $detectors)`, matching the `PaymentTypeClassifierStage` analog the plan also cites as the reference implementation.
- **Files modified:** `Modules/Import/Public/Services/DetectStartingBalancesQuery.php`, `Modules/Import/Providers/ImportServiceProvider.php` (singleton closure simplified to drop the `$db` resolve).
- **Commit:** `3f24906`

**2. [Rule 1 - Bug] Detectors emit every distinct earliest-date row per account, not just one row per account**
- **Found during:** Task 2 conflict test (4th case)
- **Issue:** The fourth aggregator test (`surfaces both candidates when two CAMT.053 imports disagree on the same date`) failed initially because the CAMT.053 detector pre-deduplicated to one row per account before the aggregator could see the conflict. The aggregator's `pickWinner()` was correct — but the conflict was invisible because the detector had already collapsed it.
- **Fix:** Each of the three DB-backed detectors now emits every distinct `(openingBalanceMinor, openingBalanceDate)` pair at the earliest opening-balance-date per account. The aggregator's tie-break then applies across the full set. PayPal stays unaffected (it always returns `[]`).
- **Files modified:** `Modules/Import/Internal/Detectors/Camt053StartingBalanceDetector.php`, `Mt940StartingBalanceDetector.php`, `IcsPdfStartingBalanceDetector.php`.
- **Commit:** `3f24906`

**3. [Rule 3 - Blocking issue] `array_values()` redundancy at PHPStan L10 strict**
- **Found during:** Task 2 PHPStan verification
- **Issue:** PHPStan inferred the relevant arrays were already `list<>` so `array_values($list)` was flagged as `arrayValues.list` ("call has no effect"). Larastan strict rejects this.
- **Fix:** Removed the unnecessary `array_values()` calls inside `pickWinner()` — the source arrays are already lists by construction (PHP's `[]` collection + `[]` push).
- **Files modified:** `Modules/Import/Public/Services/DetectStartingBalancesQuery.php`.
- **Commit:** `3f24906`
