# Phase 16.1.1 Plan 05: Starting Balance Schema + Backfill Summary

**Two nullable accounts.starting_balance_* columns plus an idempotent backfill that seeds them from the earliest statement_summaries.opening_balance per account, with Account fillable extended so Plan 07's commit path can write them.**

## Accomplishments

- Schema migration adds `starting_balance_minor` (bigInteger, nullable) and `starting_balance_date` (date, nullable) to `accounts`, positioned after `default_currency`. Distinct from the existing Forecasting-owned `opening_balance_*` columns.
- Backfill service walks `statement_summaries` ordered by `(account_id, opening_balance_date, id)`, picks the earliest qualifying row per account, and UPDATEs `accounts` — guarded by `WHERE starting_balance_minor IS NULL AND starting_balance_date IS NULL` so re-runs are idempotent and never overwrite a user-set override.
- Backfill migration resolves the service from the container at the migration boundary (the documented exception to the DI-only rule for anonymous Laravel migrations).
- Account model `$fillable` extended; `casts()` added so `starting_balance_date` round-trips as `CarbonImmutable` and `starting_balance_minor` is typed `int`.
- Three Pest unit tests cover: schema column shape, backfill correctness across multiple summaries per account, and idempotency (pre-set values are preserved across re-runs).

## Decisions Made

- **Two-pass in-PHP earliest-pick.** Sorting on `(account_id, opening_balance_date, id)` and keeping the first row per `account_id` in a PHP array is portable across every SQLite build and avoids raw window-function SQL that PHPStan L10 strict cannot type-check. Trade-off: O(N) memory for N candidate statement_summaries rows — acceptable for a single-user, lifetime-history dataset.
- **Idempotency at the UPDATE clause, not the SELECT.** `whereNull('starting_balance_minor')->whereNull('starting_balance_date')` on the UPDATE means the source-side query stays a pure read; re-runs are safe even if a future caller invokes the service on a per-account loop.
- **Date-only normalization at the service boundary.** `statement_summaries.opening_balance_date` is a `dateTime` column; `accounts.starting_balance_date` is a `date` column. The service strips any time component before writing so SQLite stores a stable ISO date string.
