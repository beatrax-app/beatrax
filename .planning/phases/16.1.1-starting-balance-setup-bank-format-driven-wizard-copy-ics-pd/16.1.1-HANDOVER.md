#### A-2. Preview pagination — "see everything, load more"

**User report:** "people should be able to see everything on the import preview, and load more rows"

**Scope:** Today the consolidated preview shows `SAMPLE_ROW_LIMIT = 5` rows per section + "5 rows shown · 132 more" footer. Add a "Show all" or "Load more" affordance.

**Two implementation options:**
1. **Cursor pagination** — A "Load 25 more" button that fetches the next page via `BuildConsolidatedPreviewQuery->paginate($cursor)`. Lighter on memory for huge statements.
2. **Expand-in-place** — A "Show all 137 rows" link that bumps `SAMPLE_ROW_LIMIT` for that section to `PHP_INT_MAX` and re-renders. Simpler; can be slow for 1000+ rows.

**Recommendation:** Start with option 2 (expand-in-place) since most ICS statements are under 200 rows. Move to cursor pagination if user reports lag.

**Files to touch:**
- Modify: `Modules/Import/Public/Services/BuildConsolidatedPreviewQuery.php` — accept a per-section `?int $limit` override (or remove cap)
- Modify: `Modules/Onboarding/Resources/views/components/consolidated-preview-section.blade.php` — add the "Show all" button with `wire:click`
- Modify: `Modules/Onboarding/Internal/Http/Livewire/Steps/FirstImportStep.php` — add `$expandedSections: list<string>` public property + `expandSection(string $sourceFormat)` action

**Acceptance:**
- Click "Show all" on a section → all rows render
- Existing "5 rows shown · 132 more" footer becomes "137 rows shown" (or disappears)
- Performance acceptable for 500-row statements (target: < 200ms render)

**Estimated effort:** 2–3 hours.

### B. Coverage / quality gaps

#### B-1. Three missing FirstImportStep regression tests

**Already documented in:** Plan 07b SUMMARY.

The plan called for 7 Pest tests; the executor wrote 5 before the harness killed it. Missing:
- `FirstImportStepCommitEverythingTest` — asserts `commit()` runs all `ConfirmImport` calls + `setStartingBalance` writes inside a single `DB::transaction`

The underlying logic IS implemented at `FirstImportStep::commit()` lines 229–238. These are pure regression-coverage gap-fill, not behavior gaps.

**Estimated effort:** Probably a Composer `autoload-dev` boundary tweak or a NativePHP build-script hook.

#### C-3. "INSECURE BUILD" warning + DMG packaging failure

The very first `php artisan native:build` we ran failed at the DMG step (`No space left on device` on the temporary sparse image — separate from the host disk). Plus the build shows `INSECURE BUILD` because the bundle isn't code-signed.

**Recommendation:** This is the explicit scope of **phase 17 (ci/cd-pipeline-+-code-signing)**, which `STATE.md` already advanced to. Don't duplicate the work here.

#### C-4. DevTools disabled in `native:build` bundles

The user could not open DevTools (right-click / keyboard shortcut both unresponsive) in the production-bundled `.app`. This made diagnosing the modal bugs very expensive — we had to read code statically rather than inspect runtime state.

**Workaround already in use:** `php artisan native:run` (dev mode) gives DevTools + hot reload + no bundle step. Use for all UI iteration.

**Long-term fix candidates:**
- Enable DevTools in the production build via NativePHP config (likely a `webPreferences: { devTools: true }` somewhere in `nativephp/electron/src/main/index.js` or NativePHP's PHP config)
- OR add an in-app "Open DevTools" command in the dev-mode command palette (only when authenticated user has `is_developer` flag)

**Estimated effort:** 1 hour if NativePHP exposes a config knob; 2–3 hours if it requires patching the main process.
