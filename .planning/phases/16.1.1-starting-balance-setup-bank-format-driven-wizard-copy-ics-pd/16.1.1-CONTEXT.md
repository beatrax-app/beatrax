# Phase 16.1.1: UAT close-out from Phase 16.1 — starting balance, wizard upload→persist fix, bank-format-driven copy, multi-PDF, ICS PDF preview fix, OAuth modal mount, Dev Mode artisan popover fix, app-chrome brand logo — Context

<domain>
## Phase Boundary

Phase 16.1.1 is the **UAT close-out** of the nine findings (G1–G9) that
surfaced during the Phase 16.1 wizard build review against the freshly-
built Mac amd64 bundle. The phase makes the first-run setup wizard
actually work end-to-end on a fresh install so a new user can sign up
→ run the wizard → see their real transactions and their real starting
balance on the dashboard — not just transaction deltas, not "we did
nothing" silence, not "upload twice", not "ASN-only" copy.

All nine findings are in scope. The ROADMAP title (which lists only
G1+G2+G3+G4+G5) is out of date — the planner updates the title to
reflect the full close-out cluster. The reasoning is:

1. **G9 is core-value-blocking** — without it, the wizard appears to
   accept files but leaves the user with an empty `transactions`
   table. Cannot ship 16.1.1 without G9.
2. **G1 is moot without G9** — a starting-balance dashboard surface
   that has no transactions to anchor against ships an empty
   visualization.
3. **G7 + G8 + G9 share one architectural fix** (Option B below) —
   splitting them across two phases doubles the wiring work and
   forces the user to re-test the wizard twice.
4. **G6 likely shares the SuggestMappingModal mount-once root cause**
   already chosen by the CR-01 fix in 16.1 — folding it in here
   completes that pattern across the codebase.
5. G2 (artisan popover) and G4 (ICS PDF preview) are independent
   bugs that the planner can break into their own plans, but they
   close out in this phase to leave the 16.1.1 UAT walkthrough
   green.

The nine findings, mapped to the closing-out work below:

- **G1** — Starting balance setup (new schema + auto-detect from 4
  parser sources + one-click confirm UX in the wizard).
- **G2** — Dev Mode artisan-runner popover at `/dev/commands` renders
  a white page. Independent debug-and-fix; Phase 16 DEVUI-02
  regression. Distinct from the command-palette ⌘K modal which was
  fixed in batch-8 (commit `189d901`).
- **G3** — ConnectBankStep copy is locked to "ASN" but the parsers
  handle every Dutch bank. Restructure to format-first chip
  selection (CAMT.053 + MT940 auto-detect; CSV requires a bank-
  format chip).
- **G4** — ICS card PDF upload throws an error on import preview.
  Reproduce in the bundled .app first, capture the exact failure,
  then fix at the right layer (Phase 12 ICS PDF parser regression,
  `payment_type` DB CHECK trigger, or Livewire 4 file upload).
- **G5** — Brand SVG (`resources/brand/logo.svg`) missing from the
  authenticated app chrome's top-left. One-line addition to the
  main layout's header partial.
- **G6** — ConnectEmailStep "Connect Gmail" / "Connect Outlook" /
  Skip / Back buttons are inert in the built bundle. Fix by moving
  the `OAuthClientWizardModal` to a single global mount in the
  authenticated layout (mirrors the CR-01 SuggestMappingModal fix).
- **G7** — FirstImportStep currently re-opens the importer from
  scratch, asking the user to upload twice. Convert it into a
  consolidated "here's everything we found, commit everything"
  surface that reads `ImportRun` ids stashed by ConnectBankStep +
  ConnectCardStep.
- **G8** — ConnectCardStep currently single-file. Change to plural
  `array<UploadedFile> $statements` with multi-file drop + per-file
  validation. Existing FingerprintStage handles cross-file dedup.
- **G9** — CRITICAL: wizard uploads never persist to the
  `transactions` table. Root cause is each connector step calls
  the **preview** path only and never invokes `ConfirmImport`. Fix
  by making FirstImportStep the consolidated commit surface
  (Option B below) — one "Commit everything (N transactions)"
  button calls `ConfirmImport` against every stashed `ImportRun` in
  one DB transaction.

**Out of scope:**

- Refactoring the standalone `/imports/upload` flow (it works; we
  only wire its commit action into the wizard flow).
- Changing the `payment_type` enum, `merchant_aliases`, community
  corpus, OAuth re-consent banner, or pattern editor — all locked
  by 16.1-CONTEXT.md and shipped.
- Multi-account "second user" sharing.
- Any new wizard step beyond a possible starting-balance confirm
  section appended to FirstImportStep (researcher decides whether
  it's its own step or a section).

## Implementation Decisions

### G1 — Starting balance: schema, auto-detect, confirm UX

- **D-01:** New columns on `accounts`:
  `starting_balance_minor` (`bigInteger`, nullable),
  `starting_balance_date` (`date`, nullable). Currency is implied by
  the existing `accounts.default_currency` column — the per-account
  posture is the future-proof choice for the multi-account /
  multi-currency cases already required by PROJECT.md (Google Play
  USD via ICS settling to EUR). Per-account survives re-imports;
  per-user would break the moment the user has both an ASN account
  and an ICS card.
- **D-02:** Migration backfills `starting_balance_minor` +
  `_date` from `statement_summaries.opening_balance_minor` +
  `opening_balance_date` per account, taking the **earliest**
  statement-period opening for each account. Backfill is
  idempotent — re-running picks up newly imported earlier
  statements.
- **D-03:** Auto-detect fires from **all four** parser sources, each
  via a `StartingBalanceDetector` strategy collected by service-
  container tag (mirrors the `PaymentTypeHinter` discovery pattern
  in D-07 of 16.1-CONTEXT.md):
  - CAMT.053 `<OpngBal>` via genkgo/camt (already captured in
    `statement_summaries.opening_balance_minor`).
  - MT940 `:60F:` via kingsquare/php-mt940 (already captured).
  - ICS PDF closing balance — researcher confirms whether Phase
    12's ICS PDF parser already writes a `statement_summary` row
    with `opening_balance_minor`; if not, the parser is extended
    here.
  - PayPal Activity CSV — first row's pre-transaction balance =
    starting balance for the export window. New detector reads it
    directly from the CSV (not via statement_summaries, since the
    PayPal path may not write one).
- **D-04:** Conflict resolution between detectors — if multiple
  detectors fire for the same account (CAMT.053 + MT940 imports
  overlap), the **earliest opening_balance_date** wins. If two
  detectors disagree on the same date, surface both to the user in
  the confirm UI with a "We saw two values for this date — which is
  right?" inline picker (researcher decides exact UX; baseline is
  "prefer the canonical CAMT.053 opening, fall back to MT940").
- **D-05:** Confirm UX — one-click confirm + Edit link per account.
  Appended either as a new section on FirstImportStep (preferred)
  or as a sixth wizard step (researcher decides; section keeps the
  step count and matches the consolidated-preview shape from
  Option B below). Card per account: "We detected your ASN account
  (NL18ASNB…) started at €1,234.56 on 2026-01-01.
  [Confirm] [Edit]". Edit reveals inline number + date inputs.
  Detected zero-balance accounts still appear (so the user can
  override). Manual override always writable.
- **D-06:** Validation — `starting_balance_date` must be ≤ earliest
  `transactions.booking_date` for that account. If the user edits
  the date past the earliest transaction, the wizard warns inline
  ("This is later than your first imported transaction — your
  dashboard may show transactions before this date.") but accepts
  the save. We do not silently mutate.

### G7 + G8 + G9 — Wizard upload→persist architecture

- **D-07:** **Option B locked.** ConnectBankStep + ConnectCardStep
  preview only — never commit. Each step writes its resulting
  `ImportRun` id(s) into `wizard_progress.data` on success:
  `wizard_progress.data['bank_import_run_id']` (single int) and
  `wizard_progress.data['card_import_run_ids']` (array of ints,
  one per uploaded PDF). FirstImportStep loads all stashed
  `ImportRun`s, renders a unified preview (section per source,
  row count + first 5 rows each, total-rows-to-commit footer),
  and one **"Commit everything (N transactions)" button** calls
  the existing `ConfirmImport` action (or its equivalent — the
  same action the standalone `/imports/upload` flow uses) against
  every stashed `ImportRun` in a single DB transaction.
- **D-08:** Commit semantics — wrapped in `DB::transaction()` so a
  failure on any source rolls back the whole batch; the user sees
  "We couldn't commit your statements: {first error}. Nothing was
  changed." and the wizard stays on FirstImportStep. On success,
  every `ImportRun` row's status flips to `committed` (or its
  equivalent in the existing ConfirmImport contract), the
  `wizard_progress` row for `first-import` is marked `done`, and
  the user advances to G1's starting-balance confirm card +
  DoneStep.
- **D-09:** ConnectCardStep becomes plural: property changes from
  `FileUpload $statement` (single) to `array<UploadedFile> $statements`
  (multi-file). Blade file input gets the `multiple` attribute.
  Per-file validation via Livewire's `statements.*` rule syntax —
  same `extensions:pdf + max:10240` per file. Each file produces
  its own `ImportRun` (one preview per PDF; FingerprintStage
  deduplicates across files at preview time). Helper copy:
  "Drop all your monthly ICS PDF statements — we'll combine them
  into one preview." Drop zone shows a per-file chip list as
  files queue (file name + size + remove ×).
- **D-10:** Resume safety — if the user closes the wizard between
  ConnectBankStep (preview written) and FirstImportStep (commit),
  the stashed `ImportRun` ids stay in `wizard_progress.data`. On
  resume, FirstImportStep loads them and shows the same
  consolidated preview. If a stashed `ImportRun` is older than
  N days (researcher picks; baseline 14 days) or has been
  manually committed via `/imports/{id}/preview` outside the
  wizard, it is filtered out with a quiet "This statement was
  already imported elsewhere" note.
- **D-11:** FirstImportStep is no longer a thin wrapper around
  `<livewire:import.upload-wizard />`. It becomes its own
  Livewire component (`Modules/Onboarding/Internal/Http/Livewire/
  Steps/FirstImportStep.php` already exists — rewire it) that
  reads stashed `ImportRun` ids, calls a new `BuildConsolidatedPreview`
  query in `Modules/Import/Public/Queries/`, and renders the
  per-source preview sections. The standalone `UploadWizard`
  component continues to work for the existing `/imports/upload`
  surface.
- **D-12:** Multi-source FingerprintStage already deduplicates
  cross-file (and cross-source via canonical fingerprint). The
  consolidated preview surfaces the dedup result transparently —
  if 3 ICS PDFs overlap a settlement that's also in the ASN CSV,
  the user sees the final deduplicated count, not the sum.
  Aligns with the canonical-fingerprint match work tracked under
  batch-7 Issue 1 (CSV→XML re-import dedup); the planner verifies
  that fix is in main before relying on it here, or folds it in
  if not yet shipped.

### G6 — OAuth modal mount-once fix

- **D-13:** `OAuthClientWizardModal` moves to a single global mount
  in the main authenticated layout (the same blade file that hosts
  `SystemAlertsBanner`). ConnectEmailStep + InboxesPage + any
  future surface dispatches `oauth-client-wizard:open` with a
  `{provider: 'gmail'|'outlook', inboxId?: int}` payload via
  Livewire 4's event bus. Mirrors the CR-01 SuggestMappingModal
  fix already chosen in 16.1.
- **D-14:** ConnectEmailStep's blade stops mounting the modal
  inline. Its Connect Gmail / Connect Outlook buttons dispatch
  the event with the corresponding provider; Skip + Back continue
  to emit `wizard:skip` / `wizard:back` for the parent SetupWizard
  to handle. Verify in the running build with DOM inspection that
  the modal element is present in the layout (not the step) and
  that the dispatched event names match what the modal listens
  for. Add a Pest feature test asserting the dispatch contract
  (`ConnectEmailStepDispatchesGlobalOAuthOpenTest`).

### G3 — Bank-format wizard copy

- **D-15:** **Restructured to format-first.** ConnectBankStep
  renders three format chips (CAMT.053, MT940, CSV) above the
  drop zone with per-chip helper copy + bank list:
  - **CAMT.053** (`.xml`) — ASN, ING.
  - **MT940** (`.sta` / `.940`) — ASN, ING, Rabobank, Triodos,
    SNS, Bunq.
  - **CSV** (`.csv`) — Bank-specific column shapes; user selects
    one of {ASN, ING} from a follow-on chip row.
- **D-16:** Gate behavior — **CSV is gated, CAMT.053 + MT940 are
  not.** For CAMT.053 and MT940, the drop zone is always active;
  clicking a chip just re-skins the helper copy + extension hint.
  For CSV, the drop zone is **disabled** until a bank-format chip
  is picked (because ASN-CSV ≠ ING-CSV at the column level — the
  parser dispatch needs the hint). Helper copy when CSV is
  selected but no bank picked: "Pick which bank exported your
  CSV — we need to know to read it correctly."
- **D-17:** The wizard tells the parser the user-chosen format via
  a new `format_hint` field on the upload submit (CSV-only;
  CAMT.053 + MT940 auto-detect from extension + content sniff
  as today). New `BankCsvFormatHint` enum in
  `Modules/Import/Public/Enums/`. Parser dispatch in
  `Modules/Import/Internal/Pipeline/ImportPipeline` reads the
  hint when present and bypasses the content sniff for the
  CSV branch only.
- **D-18:** No copy mentions "ASN" outside its position in the
  bank list. The "files have nothing to do with our cloud /
  privacy" pill copy stays as locked in UI-SPEC.
