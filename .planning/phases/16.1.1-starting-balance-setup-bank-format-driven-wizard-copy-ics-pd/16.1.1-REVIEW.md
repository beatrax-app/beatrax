# Phase 16.1.1: Code Review Report

**Reviewed:** 2026-05-26
**Depth:** deep
**Files Reviewed:** 27
**Status:** issues_found

## Summary

The phase delivers the starting-balance detection and confirmation surface for the first-run wizard, including four per-source detectors, the aggregator with D-04 conflict-resolution logic, the consolidated preview query, and the `StartingBalanceCard` child component. The DB transaction design in `FirstImportStep::commit()` is mostly sound, but two structural defects exist: a post-commit code path that runs outside the transaction can leave the system half-committed without correctly reporting so, and the user-facing error message in that path makes a false claim. Several PHPDoc comments contain planning-artifact identifiers (Plan-IDs, T-IDs, UI-SPEC line references) that the project's codebase-agnostic-from-GSD rule forbids. Starting balance validation is also missing a future-date guard the class-level PHPDoc explicitly promises.

## Critical Issues

### CR-01: `FirstImportStep::commit()` — wizard_progress update and Livewire dispatch are outside the DB transaction; post-transaction exception produces a false "Nothing was changed" error

**File:** `Modules/Onboarding/Internal/Http/Livewire/Steps/FirstImportStep.php:259-285`

**Issue:** The `$db->connection()->transaction(...)` closure at line 229 ends at line 251. The chain dispatcher call, recurring dispatcher call, `wizard_progress` UPDATE, and `$this->dispatch('wizard.step.completed')` all run OUTSIDE that transaction (lines 259–277). If `$chainDispatcher->dispatchForUser()` or `$recurringDispatcher->dispatchForUser()` throws, execution jumps to the `catch (Throwable $e)` handler at line 278. At that point the DB transaction has already committed — transactions are landed in the ledger and `accounts.starting_balance_*` is written — but the wizard stays stuck on the first-import step and the user sees:

> "We couldn't commit your statements: [dispatcher message]. Nothing was changed."

That message is factually false. The data WAS committed. The user has no indication that re-clicking the commit button is now dangerous (it will double-dispatch chain resolution and attempt to re-confirm already-confirmed runs).

Additionally, the `wizard_progress` row is never marked `done`, so a future visit to `/setup-wizard` resumes on the first-import step, which will find no uncommitted runs (all confirmed) and display "Nothing to commit" — a confusing dead end.

**Fix:**

Move the `wizard_progress` UPDATE inside the transaction. Wrap chain and recurring dispatchers in their own try/catch with a distinct error message that accurately reflects "data committed, background processing failed":

```php
$db->connection()->transaction(function () use (
    $runIdsToCommit,
    $balanceConfirmations,
    $confirmImport,
    $user,
    $db,
    $now,
): void {
    foreach ($runIdsToCommit as $runId) {
        ($confirmImport)($runId, $user, dispatchChain: false);
    }
    foreach ($balanceConfirmations as $accountId => $confirmation) {
        $db->connection()
            ->table('accounts')
            ->where('id', $accountId)
            ->where('user_id', $user->id)
            ->update([
                'starting_balance_minor' => $confirmation['minor'],
                'starting_balance_date' => $confirmation['date'],
                'updated_at' => $now,
            ]);
    }
    // Move wizard_progress update inside the transaction so the
    // commit is truly atomic: either everything lands or nothing does.
    $db->connection()
        ->table('wizard_progress')
        ->where('user_id', $user->id)
        ->where('step_key', 'first-import')
        ->update([
            'status' => 'done',
            'completed_at' => $now,
            'updated_at' => $now,
        ]);
});

// Post-commit dispatches: failures here do NOT undo committed data.
// Use a separate try/catch with an honest error message.
try {
    $chainDispatcher->dispatchForUser($user->id);
    $recurringDispatcher->dispatchForUser($user->id);
} catch (Throwable $dispatchException) {
    $logger->error('FirstImportStep: post-commit dispatch failed (data already committed).', [
        'exception_class' => $dispatchException::class,
        'exception_message' => $dispatchException->getMessage(),
    ]);
    // Data is committed; wizard still advances. Chain/recurring will
    // catch up on next scheduled sweep.
}

$this->dispatch('wizard.step.completed');
```

### CR-02: `StartingBalanceCard` — `confirm()`, `save()`, and `pickConflictCandidate()` dispatch `starting-balance.confirmed` with `accountId: 0` when component is mounted without setting `$accountId`

**File:** `Modules/Onboarding/Internal/Http/Livewire/StartingBalanceCard.php:68,191-208,301-309,317-335`

**Issue:** `$accountId` defaults to `0` (line 68). Livewire permits client-side property mutation — a tampered request can reset `accountId` to `0` after mount. When any of the three action methods fires with `accountId = 0`, the parent `FirstImportStep::onStartingBalanceConfirmed()` stores `$this->balanceConfirmations[0] = [...]`. The subsequent `commit()` executes:

```php
$db->connection()->table('accounts')
    ->where('id', 0)          // matches no real row
    ->where('user_id', $user->id)
    ->update([...]);
```

This is a silent no-op at the DB level: the UPDATE fires but affects zero rows. The UI shows the account as "confirmed" (green checkmark) and the commit button becomes active, but the starting balance is silently discarded. A user who carefully entered a starting balance value then loses it with no feedback.

The `save()` transaction-query path at line 290 (`->where('account_id', $this->accountId)`) also executes with `account_id = 0`, returning whatever the earliest transaction is for a zero-id account (nothing), producing no D-06 warning that would otherwise flag a suspicious date.

**Fix:**

Add an early guard in each of the three public action methods:

```php
public function confirm(): void
{
    if ($this->accountId <= 0 || $this->detectedMinor === null || $this->detectedDate === null) {
        return;
    }
    // ...
}

public function save(DatabaseManager $db, CurrentUser $currentUser): void
{
    if ($this->accountId <= 0) {
        $this->validationError = 'Account not set. Reload the wizard.';
        return;
    }
    // ...
}

public function pickConflictCandidate(int $candidateIndex): void
{
    if ($this->accountId <= 0 || ! array_key_exists($candidateIndex, $this->alternativeCandidates)) {
        return;
    }
    // ...
}
```

### WR-01: `StartingBalanceCard::save()` — no future-date validation despite class-level PHPDoc promise

**File:** `Modules/Onboarding/Internal/Http/Livewire/StartingBalanceCard.php:138-139,278-283`

**Issue:** The `$validationError` property's PHPDoc at line 138–139 explicitly lists "future date" as a validation case: `"out-of-range amount, unparseable date, future date"`. The `save()` method at lines 278–283 validates that `strtotime($date) !== false` (parseable), but there is no check that the date is not in the future. A user — or a tampered request — can set a starting balance date of `2099-01-01`, which passes all current checks. The D-06 warning only fires when the date is later than the earliest imported transaction; before any transactions exist there is nothing to compare against, so a far-future date silently confirms.

**Fix:**

After the `strtotime` check, add:

```php
if ($timestamp > time()) {
    $this->validationError = 'Starting balance date cannot be in the future.';
    return;
}
```

### WR-03: `BuildConsolidatedPreviewQuery` — `PreviewCache::getPreview()` called twice per run

**File:** `Modules/Import/Public/Services/BuildConsolidatedPreviewQuery.php:186-218,249-264`

**Issue:** `buildSection()` calls `$this->cache->getPreview($runId)` for every run ID (line 193). `countDuplicateRowsAcrossRuns()` iterates the same list of IDs and calls `$this->cache->getPreview($runId)` again (line 253). The two loops are invoked back-to-back for every section (lines 120–123). If the preview cache backend is backed by a serialisation/deserialization cycle (JSON round-trip as the `PreviewCache` class comment suggests), this doubles the deserialization cost for every section's contributing runs with no architectural reason.

Beyond the performance concern this is a code correctness risk: if the cache TTL expires between the two calls, `buildSection()` returns `ready` status but `countDuplicateRowsAcrossRuns()` returns 0 for that run, silently under-counting `alreadyImportedCount`.

**Fix:**

Pass the already-built `$allRows` list to the caller or fold the duplicate count into `buildSection()`:

```php
private function buildSection(string $sourceFormat, array $importRunIds): ConsolidatedPreviewSection
{
    $allRows = [];
    $newRowCount = 0;
    $duplicateRowCount = 0;
    $hasCacheMiss = false;

    foreach ($importRunIds as $runId) {
        $preview = $this->cache->getPreview($runId);
        if ($preview === null) {
            $hasCacheMiss = true;
            continue;
        }
        foreach ($preview->rows as $row) {
            $allRows[] = $row;
            if ($row->status === 'new') {
                $newRowCount++;
            } elseif ($row->status === 'duplicate') {
                $duplicateRowCount++;
            }
        }
    }
    // Return $duplicateRowCount alongside the section, or adjust
    // the caller to not call countDuplicateRowsAcrossRuns separately.
    ...
}
```

Then remove `countDuplicateRowsAcrossRuns()` or reduce it to a pass-through of the already-computed value.

### WR-04: `BackfillStartingBalanceFromStatementSummaries` migration uses `app()` global helper

**File:** `Modules/Ledger/Database/Migrations/2026_05_27_000002_backfill_starting_balance_from_statement_summaries.php:17`

**Issue:** The migration file calls `app(BackfillStartingBalanceFromStatementSummaries::class)` — the `app()` global helper — which the project memory forbids: "Constructor DI only; no facade calls / global helpers". The migration file's inline comment acknowledges this ("standing exception to the DI-only rule for schema migrations"), but the memory rule has no carve-out for migrations. The first migration in this phase (`2026_05_27_000001_...`) correctly resolves `DatabaseManager` by calling `Container::getInstance()->make(DatabaseManager::class)` instead of the `app()` helper.

**Fix:**

Use `Container::getInstance()->make()` to match the pattern used in the sibling migration:

```php
use Illuminate\Container\Container;

public function up(): void
{
    /** @var BackfillStartingBalanceFromStatementSummaries $service */
    $service = Container::getInstance()->make(BackfillStartingBalanceFromStatementSummaries::class);
    $service->run();
}
```

### IN-02: `DetectStartingBalancesQuery::pickWinner()` — redundant guard in final branch adds dead-code smell

**File:** `Modules/Import/Public/Services/DetectStartingBalancesQuery.php:163-165`

**Issue:** Lines 163–165 read:

```php
// No CAMT in the tie but multiple non-CAMT candidates — surface both.
if (count($other) >= 2 && $camt053 === []) {
    return $other;
}
```

At this code point, `$camt053 === []` is always true because:
- Line 150 already returned if `count($camt053) === 1 && $other !== []`
- Line 159 already returned if `count($camt053) >= 2`

So any execution reaching line 163 necessarily has `count($camt053) === 0`, making the `&& $camt053 === []` guard permanently true. The guard is dead code and creates a false impression that a non-empty `$camt053` is possible at that branch point.

**Fix:**

```php
// No CAMT in the tie and multiple non-CAMT candidates — surface all.
if (count($other) >= 2) {
    return $other;
}
```

### IN-03: `StartingBalanceCard` `$state` property accepts arbitrary strings with no closed-set validation

**File:** `Modules/Onboarding/Internal/Http/Livewire/StartingBalanceCard.php:120,168`

**Issue:** `$state` is a `public string` with default `'detected'`. It is mounted from the parent blade at line 168. Because it is a public Livewire property, client-side tampering can set it to an arbitrary string. The blade `@switch($state)` has no `@default` branch — an unrecognised state silently renders an empty card body with no error or fallback, leaving just the eyebrow row visible. While not a security issue (the state machine's side effects are gated on named action methods), it degrades the UX silently.

**Fix:**

Add a `@default` branch to the Blade switch (in `starting-balance-card.blade.php`) that renders a fallback message:

```blade
@default
    <p class="wiz-error" role="alert">Unknown card state. Reload the wizard.</p>
```

Or add a guard in `mount()`:

```php
if (! in_array($state, ['detected', 'conflict', 'editing', 'confirmed', 'manual-entry'], strict: true)) {
    $state = $detectedMinor !== null ? 'detected' : 'manual-entry';
}
```
