<objective>
Rewrite `FirstImportStep` from a thin wrapper around `<livewire:import.upload-wizard />` (G7 anti-pattern) into the consolidated commit surface for the wizard, and ship the supporting child component + partials + CSS + 7 Pest tests. The step:
1. Loads stashed `ImportRun` ids from `wizard_progress.data['bank_import_run_id']` + `wizard_progress.data['card_import_run_ids']` (Plan 06's outputs).
2. Calls Plan 07's `BuildConsolidatedPreviewQuery` to produce per-source sections (stale/already-committed filters applied in the query).
3. Calls Plan 05b's `DetectStartingBalancesQuery` to surface per-account `StartingBalanceCandidate`s.
4. Renders one `StartingBalanceCard` per detected (or undetected — manual-entry) account, supporting Detected / Conflict / Editing / Confirmed states per UI-SPEC G1.
5. Renders the single "Commit everything (N transactions) →" primary button.
6. On commit click — wraps every stashed `ImportRun`'s `ConfirmImport(..., dispatchChain: false)` invocation AND every confirmed `accounts.starting_balance_*` UPDATE in a single `DB::transaction()`. On success, dispatches chain resolution ONCE for all confirmed runs (Pitfall 2 mitigation) and advances to DoneStep. On failure, surfaces the inline rose error and stays on the step (rollback automatic).

Purpose: Close UAT findings G1 (confirm UX) + G7 (single primary action; no re-upload) + G9 (uploads actually persist to `transactions`). Closes the wizard's core-value loop.

The split makes each plan focus on one concern and keeps both well under the 15-file blast-radius threshold.)

Output: One new Livewire child component + blade, one rewritten Livewire step + blade, one new Blade partial, CSS rule appends, and SEVEN Pest feature tests covering preview load, commit happy path, commit rollback, stale-run filtering, confirm card idempotency, confirm card validation warning, and consolidated preview shape.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → FirstImportStep `commit()` | The action that materializes every stashed ImportRun's preview into committed `transactions` rows + writes user-confirmed `accounts.starting_balance_*` values. |
| `wizard_progress.data['bank_import_run_id']` + `card_import_run_ids[]` | Untrusted JSON values from the per-user wizard_progress row — could be tampered with via direct SQLite write. |
| Child StartingBalanceCard → FirstImportStep dispatch | Cross-component event payload carries an `accountId` that controls which row is UPDATEd. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16.1.1-21 | Information disclosure | A tampered `wizard_progress.data['bank_import_run_id']` value points at another user's ImportRun. Without an explicit user-scope check, FirstImportStep could commit foreign data into the current user's `transactions` table. | mitigate | Plan 07's `BuildConsolidatedPreviewQuery::build()` filters every input id against `->where('import_runs.user_id', $user->id)` — any non-owned id is dropped before reaching the section. Plan 07's fourth Pest assertion (`respects user_id boundary`) locks this in upstream. |
| T-16.1.1-22 | Tampering | `starting-balance.confirmed` event dispatched from a malicious frontend with `accountId` of another user's account. The UPDATE in `commit()` would write to that account. | mitigate | The `commit()` UPDATE includes `->where('user_id', $user->id)` on the accounts table — an `accountId` belonging to another user matches zero rows and silently no-ops. |
| T-16.1.1-23 | Tampering | `editedMinor` value submitted as `-1_000_000_000_000_000_000` (negative quintillion). | mitigate | StartingBalanceCard::save() validates `-1_000_000_000_00 ≤ editedMinor ≤ 1_000_000_000_00` (±€10M minor units per RESEARCH.md Security Domain). Out-of-range values fail validation inline with a rose error message. |
| T-16.1.1-24 | Denial of service | An attacker stashes 10,000 ImportRun ids and triggers `commit()`. The DB::transaction loops them all. | accept | Single-user app; the wizard's UI emits at most 1 bank ImportRun + ≤ ~24 monthly card ImportRuns (2 years of statements). The 14-day stale filter (Plan 07) further bounds the set. Volumetric DoS is not a realistic threat in this surface. |
| T-16.1.1-25 | Repudiation | Commit-everything writes to `transactions` + `accounts.starting_balance_*` with no audit trail. | accept | `ImportRun.status = 'confirmed'` + `ImportRun.confirmed_at = now()` provide the audit timestamp; `accounts.updated_at = $clock->now()` records the balance write. For Phase 16.1.1 this is sufficient. A dedicated audit trail belongs in a future polish phase. |
| T-16.1.1-26 | Race condition | Inner `ConfirmImport`'s `ResolveChainLinksJob` dispatch races the outer transaction commit (Pitfall 2). A queue worker could read partial state. | mitigate | Plan 07 extended `ConfirmImport` with `dispatchChain: bool = true`. This plan's `FirstImportStep` passes `false` on every inner call and dispatches chain resolution ONCE after the outer transaction returns. Locked in by Task 2's FirstImportStepCommitRollbackTest second `it(...)`. |

No HIGH-severity threats unmitigated. The user-scope + bounded-input + audit-by-existing-columns posture matches the rest of the codebase.
