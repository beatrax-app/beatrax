# Phase 16.1.1 Plan 04: ICS PDF preview no-repro + PayPal CSV upload error fix Summary

Lock ICS PDF preview happy-path with a regression test (the original failure is no-repro on current main per user verification), root-cause and fix the PayPal CSV upload error reported during built-`.app` UAT, and add a Pest regression test pinning both halves of the PayPal CSV upload contract so future plan-06-style refactors cannot regress it.

## What was built

### 1. ICS PDF preview regression test (no source change)

The user confirmed in the built `.app` bundle that dropping an ICS PDF on `ConnectCardStep` now produces a non-empty preview with no toast error and no ERROR-status rows. Plan-04's original Task 1 reproduce step returned `no-repro`. Per the orchestrator handoff, the executor skipped the source change and wrote only the regression-guard test.

`Modules/Ingestion/tests/Feature/IcsPdfPreviewRegressionTest.php` exercises the tiny ICS PDF fixture (`Modules/Ingestion/tests/fixtures/ics/ics-sample-tiny.pdf`) end-to-end through `RunsImports::runFromUpload`. Two assertions lock the working contract:

- `count($result->rows) >= 1` AND at least one row carries `status === 'new'`.
- No row carries `status === 'error'`.

Note on the DTO: the plan's `<behavior>` block referenced `$result->totalRows` and `$row->disposition`, but the actual DTO is `Modules/Import/Public/Dto/ImportPreviewResult.php` exposing `array $rows` and `Modules/Import/Public/Dto/PreviewRowDto.php` exposing a lowercase string `$status` — the test uses the correct fields.

### 2. PayPal CSV upload error — root cause and fix

The user reported that dropping a PayPal CSV on the wizard's bank upload throws an error in the built `.app`. Reading `~/Library/Application Support/beatrax/storage/logs/laravel-2026-05-26.log` (line 3 onward) located the exception:

- **Exception class:** `Modules\Ingestion\Public\Exceptions\UnsupportedPaypalCsvLanguageException`
- **Message:** "PayPal CSV header tokens did not match any registered language profile. Supported locales: nl. If your account exports in a different language, file an issue with the redacted CSV."
- **First trace frame:** `HeaderSniffer::sniffPaypalCsv()` → called from `PaypalCsvAdapter::parse()` → from `ParseStage::run()` → from `ImportPipeline::preview()` → from `RunImport::runFromUpload()` → invoked by `PreviewWizard::savePaypalAccountName()` (NOT `ConnectBankStep` — the user uploaded via the standalone `/imports` wizard which is the only entry that currently accepts PayPal CSV; `ConnectBankStep` only supports ASN/ING bank CSV + CAMT.053 + MT940).
- **First header tokens captured in trace:** `"RH","Naam rapportage",...`

Inspecting the cached upload at `~/Library/Application Support/beatrax/storage/app/private/imports/1/b80090d92f85f1b4d7f7178c845c05349f54e8d8601cc0631226a51ae32496d2.csv` confirmed the file shape:

```
"RH","Naam rapport",...                       (Report Header columns)
"RH","BALANCE_RECONCILIATION_REPORT","Success",...   (Report Header values)
"RD","Referentie zakelijke rekening",...      (Report Data column names)
"RF","Bestandsnummer",...                     (Report Footer columns)
"RF","1","0","1"                              (Report Footer values — 0 data rows in this sample)
```

This is the PayPal **Balance Reconciliation Report (BRR)** export, not the **Activity Download** export. The two share the `.csv` extension, the comma delimiter, and the UTF-8 BOM, but their column shapes are completely different — the BRR uses `RH` / `RD` / `RF` row-type prefixes the Activity Download never carries.

**Failure layer classification (per the plan's matrix adapted for PayPal):**
- Layer a (parser): borderline — `HeaderSniffer` is technically the parser's gate, but the parser logic itself is fine for the format it was written for.
- Layer b (PaymentType CHECK): no — this is preview-time, not commit-time, and the exception is `UnsupportedPaypalCsvLanguageException` not `QueryException`.
- Layer c (Livewire upload): no — the file uploaded successfully and was readable.
- Layer d (UX-misleading error): **yes**. The sniffer raised the wrong typed exception for the actual cause. The "language not supported" message is misleading because the file IS in Dutch — the export type is wrong.

**The fix** (in `HeaderSniffer::sniffPaypalCsv()`):

```php
$firstCell = trim($columns[0] ?? '');
if (in_array($firstCell, ['RH', 'RD', 'RF'], strict: true)) {
    throw new UnsupportedPaypalCsvShapeException(
        'This looks like a PayPal Balance Reconciliation Report CSV, not the Activity Download. '
        .'In the PayPal portal, open Activity → Statements → Activity Download (CSV) and re-export.'
    );
}
```

The new typed exception `UnsupportedPaypalCsvShapeException` lives in `Modules/Ingestion/Public/Exceptions/`. The existing `ImportPipeline::preview()` `Throwable` catch turns it into a single ERROR-status preview row carrying the new message verbatim — no further plumbing required.

### 3. PayPal CSV pipeline regression test

`Modules/Ingestion/tests/Feature/PaypalCsvPreviewRegressionTest.php` pins both halves of the PayPal CSV upload contract through the full `RunsImports::runFromUpload` pipeline:

- Activity Download (existing fixture) still produces ≥1 row, none with `status === 'error'`.
- BRR shape produces exactly one row, `status === 'error'`, message contains "Activity Download".

`Modules/Ingestion/tests/Feature/HeaderSnifferPaypalShapeTest.php` covers the same two cases at the sniffer level (faster, more targeted failure messages on regression).
