# Phase 7 — UI Design Contract

> Visual and interaction contract for Phase 7: Email Template Matchers + Categorization Learning. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope (UI surfaces produced):**

1. **`/rules` top-nav page** (D-713, D-720) — new page that owns rule CRUD. Sections in render order: page heading + subheading + "New rule" primary action top-right; (when zero rules) the empty-state hero; (when ≥1 rule) the rules table with field / match / value / category / hits / created / actions columns; a calm helper note at the bottom about memory + rule coexistence (D-711 documentation).
2. **Rule form modal** (D-709, D-720) — Flux modal (NOT a flyout — modal posture matches the "create/edit a single record" semantic, mirroring Phase 6's OAuth-client wizard modal posture). Triggered by the "New rule" button OR per-row "Edit" action on the `/rules` table. Three dropdowns + one text input + one category picker + Save/Cancel. Re-used for create AND edit (modal title swaps; Save button label swaps).
3. **Confirm-delete inline confirmation** — per-row "Delete" action collapses into a two-step inline confirmation chip pair ("Delete?" → `[Yes, delete]` `[Cancel]`) rendered inside the same row. No separate modal — destructive but reversible (rule deletion is a v2 power-user "undo" candidate; v1 keeps it inline-cheap because rules are inexpensive to recreate).
4. **`/imports` wizard — "Email file (.eml/.mbox)" arm** (D-704, EML-07) — new issuer option `email-file` in the existing wizard `<select>`. When chosen, the format `<select>` shows `Email (.eml)` and `Mailbox archive (.mbox)`. File `<input>` accepts `.eml`, `.mbox`, `.eml.zip`. Otherwise reuses the existing preview-then-confirm flow verbatim — no new wizard chrome.
5. **`/settings` watched-folder toggle** (D-704 secondary path) — new section appended to the existing settings page. Single toggle row "Auto-import from drop folder" + help text explaining cadence (every 5 min), the on-disk path, and the `/processed/{YYYY-MM}/` move semantics. Default OFF.
6. **Transaction detail drawer — categorization provenance panels** (D-712) — two variants rendered on `/transactions/{id}` inside the existing detail page, below the Reclassify section, above the "View chain" section:
   - **Rule-driven panel** (rendered when `provenance='rule'`): always-visible "Rule that fired" card with field/match/value summary, category, and two inline actions `[Update rule]` `[Remove rule]`.
   - **Memory-driven panel** (rendered when `provenance='memory'`): lighter "Auto-categorized from merchant history" card with a single `[Override]` action.
   - **Manual panel** (rendered when `provenance='manual'` or `null`): no panel at all (clean default — no chrome for the routine case).
7. **Correction-divergence toast** (D-712) — one-shot Filament-notifications-style toast surfaced after the user reclassifies a transaction whose initial suggestion came from a rule. Inherits Phase 5's failed-job toast chrome. Two actions inline (`[Update rule]` `[Keep current rule]`); auto-dismiss after 8s if no action; dismissable manually; never re-fires for the same rule unless the user reclassifies again.
8. **First-conflict receipt toast** (D-707) — one-shot toast surfaced the FIRST time the user has a fingerprint conflict between a receipt and a CSV/CAMT/MT940 row, AND `users.receipt_conflict_resolution = 'unset'`. Two actions (`[Use receipt]` `[Keep CSV]`); sets `users.receipt_conflict_resolution`; from then on, the setting drives all conflicts silently. If dismissed without action, the setting stays `unset` and the toast re-fires on the next conflict (NOT one-time-only — explicit choice required per CONTEXT.md risk note).
9. **`/inboxes` extensions** (Phase 6 page) — extend the existing connected-inboxes table with: a new `matcher` column showing the matcher key per row OR `unmatched` / `skipped` chip; status filters above the table (`fetched | parsed | skipped | unmatched`); for `unmatched` rows, an inline "View raw .eml" text-link affordance for debugging.
10. **Top-nav "Rules" item** (D-721) — new top-nav entry inserted between "Uncategorized" and "Review chains". No badge in v1 (rules don't have a "needs attention" count). See § Navigation Decision for the placement rationale.

**Out of scope this phase:**

- Re-parse trigger UI for `status='unmatched'` rows after matcher updates (deferred per CONTEXT.md).
- Bulk rule import/export (JSON) UI (deferred).
- Per-field conflict precedence map UI (deferred — v1 ships the binary toast).
- Inline "+ Rule from this merchant" affordance on `/transactions/{id}` (deferred unless Wave 4 budget allows; UI-SPEC reserves the slot but does not promise it).
- Confidence indicator (green/dim dot) on transaction rows (deferred — the inline provenance panel on the detail drawer carries the same information at lower cost).
- Per-merchant `normalized_merchant` editor UI (deferred).
- Filament-style data-table for `/rules` (rejected — admin-panel aesthetic is explicitly NOT desired; Phase 7 uses a calm Tailwind table matching `/inboxes` and `/chains/review`).
- Top-nav "Categorize" / "Triage" submenu (declined — see § Navigation Decision; nav stays flat).
- Dark mode.

## Navigation Decision (D-721)

**Decision:** Keep the nav flat. Insert "Rules" as a standalone top-nav item between **Uncategorized** and **Review chains**. No submenu.

**Final top-nav order (left to right):**

```
diederik   Dashboard   Transactions   Imports   Inboxes [N]   Uncategorized [N]   Rules   Review chains [N]   Settings
```

**Rationale (why flat, not grouped):**

1. **Item count is still manageable.** Adding "Rules" brings the bar to 8 items (excluding the brand) — comparable to Linear's main nav (Dashboard / Inbox / My Issues / Views / Members / Settings ≈ 6) and Notion's sidebar (which is hierarchical for a different reason: it lists user-created pages, not navigation). A flat 8-item bar reads in <1 second on `max-w-5xl` and fits without wrapping at the project's only target viewport (desktop, ≥1024px).
2. **Submenus add a click + a hover-vs-tap ambiguity** that costs more than the bar real estate it saves. The user opens these pages directly from muscle memory; a "Categorize" hover-submenu inserts a state machine into a routing operation that today is a single anchor click.
3. **Semantic grouping is weak.** `/rules` and `/uncategorized` are both "categorization-adjacent" but serve different jobs: `/rules` is configuration (rare visits, deliberate), `/uncategorized` is triage (frequent visits, reactive). `/chains/review` is something else again. Forcing them under one label muddies all three.
4. **Linear/Notion aesthetic anchor.** Linear's primary nav is flat and dense; Notion's primary nav is sidebar-based and flat per section. Neither uses dropdown submenus in the top bar. Mirroring this gives Phase 7 the calm aesthetic without inventing a new chrome.
5. **Submenu deferred to v2** if Phase 8 (`/fixed-payments`) + Phase 9 (`/drift-alerts`) + Phase 10 (`/forecast`) all land top-nav items — at 11+ items the bar genuinely starts to crowd. That is the trigger to re-evaluate grouping.

**Visual posture:** "Rules" follows the exact pattern of "Uncategorized" minus the badge — no count, no dot, just the label. Active route uses the same `text-slate-900 font-semibold bg-slate-100` treatment as every other top-nav item.

## Spacing Scale

Inherited verbatim from `06-UI-SPEC.md`. No new tokens. No exceptions for this phase.

| Token | Value | Usage in Phase 7 |
|-------|-------|-------------------|
| xs | 4px | Gap between rule-row hit-count number and label; 4px optical offset between the rule's value and its category line; gap between the "Rule that fired" panel title and its meta line; gap between toast icon and message text |
| sm | 8px | Inner padding on the per-row Edit/Delete chip buttons; gap between the three rule dropdowns in the form modal (vertical); gap between toast actions; padding inside the watched-folder toggle row |
| md | 16px | Default padding inside a rule table row; `gap-md` between the provenance panel and the surrounding drawer sections; gap between the form-modal header and the form body; gap between the form fields stack and the Save/Cancel button row; toast vertical inner padding |
| lg | 24px | Top/bottom padding of the rule form modal body; gap between the page heading and the rules table on `/rules`; gap between the rules table and the helper note at the bottom; padding inside the empty-state hero on `/rules` |
| xl | 32px | Vertical breathing between the empty-state hero copy and the "Create your first rule" button; horizontal padding inside the wide form modal (matches Flux modal default) |
| 2xl | 48px | Vertical gap between the rules table and any future secondary section (Phase 7 ships only one section so this rarely fires) |
| 3xl | 64px | Page-level vertical breathing on `/rules` between the page heading and the first content section (mirrors `/inboxes` and `/chains/review`) |

**Page width:** `max-w-5xl` (~1024px) centered for `/rules` (same as `/chains/review`, `/inboxes`, `/transactions`).

**Rule form modal width:** Flux's default `md:max-w-lg` (~512px) — the form is short (3 dropdowns + 1 text input + 1 category picker + buttons) and a wider canvas would feel hollow. Same width as Phase 6's backfill-window modal.

**Rule table row min-height:** `min-h-12` (48px) per row — tall enough to host field + match + value + category + hits + actions without crowding. 48px = `3 × 16px` and respects the 4px-multiple invariant.

**Provenance panel chrome:** `rounded-md border border-slate-200 bg-slate-50 p-md` — same chrome as Phase 5's `chain-drawer` "No funding chain found" panel and Phase 6's backfill progress strip. The user reads all three as conceptually identical "context strip about this row".

**Toast chrome:** inherits Phase 5's failed-job toast verbatim — fixed bottom-right, `bottom-md right-md`, `max-w-sm`, `rounded-lg border border-slate-200 bg-white shadow-lg p-md`, two-action footer with `gap-sm`.

## Typography

Inherited verbatim from `06-UI-SPEC.md`. Phase 7 introduces no new sizes or weights. Uses the same 4-role scale.

| Role | Size | Weight | Line Height | Usage in Phase 7 |
|------|------|--------|-------------|-------------------|
| Micro / Caption | 12px | 400 (regular) | 1.4 | Rule table column headers (uppercase tracking-wide text-slate-500); rule row meta line (created date, hits count label); empty-state hero caption; toast helper text; provenance panel meta line ("Rule: contains 'SPOTIFY' → Streaming"); watched-folder toggle help text |
| Body | 14px | 400 (regular) | 1.5 | Rule row primary text (field, match, value, category name); form-modal field labels and option text; toast message body; empty-state hero body copy; provenance panel headline; transaction detail Reclassify body copy (existing) |
| Section heading | 20px | 600 (semibold) | 1.3 | (Reserved) — `/rules` page heading uses `text-2xl` like every other top-nav page heading (Phase 6 + Phase 5 precedent) which renders as 24px. Form-modal heading uses `<flux:heading size="lg">` (20px). |
| Page heading | 24px (text-2xl) | 600 (semibold) tracking-tight | 1.2 | `/rules` page heading "Rules". Matches `/inboxes` + `/chains/review` precedent (`text-2xl font-semibold tracking-tight text-slate-900`). |

**Empty-state hero typography (top-down stack):**

```
No rules yet                                       ← text-xl semibold tracking-tight text-slate-900
Rules pre-categorize transactions on import.       ← Body 14px regular text-slate-500, max 60ch
Each rule matches a field of a transaction and
assigns a category automatically.
[Create your first rule]                           ← solid-emerald-600 button, mt-xl (32px)
```

**Rule table row typography:**

- **Field cell** (`merchant` / `description` / `counterparty`): Body 14px weight 400 in `text-slate-900`, lowercase as enum-stored.
- **Match cell** (`contains` / `equals` / `starts_with`): Body 14px weight 400 in `text-slate-500`, lowercase. Visually subordinate to the value column.
- **Value cell** (the matched string): Body 14px weight 500 in `text-slate-900`. Slightly heavier so the user's eye lands on the actual match text. Renders with `<code>`-style mono font (`font-mono`) to reinforce "this is a literal string" — same posture as Phase 6's redirect-URI clipboard surface.
- **Category cell**: Body 14px weight 400 in `text-slate-900`. Renders the full breadcrumb path (`Subscriptions / Streaming`) using the existing `$cat->path` accessor from `InlineCategoryPicker`.
- **Hits cell**: Body 14px weight 400 in `text-slate-900`, `font-variant-numeric: tabular-nums`. `0` renders dim (`text-slate-400`) so the user can scan for never-fired rules.
- **Created cell**: Micro 12px weight 400 in `text-slate-500`, `font-variant-numeric: tabular-nums`. Format: `d M Y` (matches `transactions-list`).
- **Actions cell**: two text-style buttons (`Edit` / `Delete`) at Body 14px weight 500, `text-slate-900` / `text-rose-600` respectively. Same chip-style chrome as `/chains/review` (Phase 5).

**Provenance panel typography (rule variant):**

```
Rule that fired                                ← Body 14px semibold text-slate-900
merchant contains "SPOTIFY" → Streaming        ← Micro 12px regular text-slate-500, font-mono on the
                                                  quoted value
[Update rule]  [Remove rule]                   ← Body 14px medium text-slate-900 / text-rose-600
```

**Provenance panel typography (memory variant):**

```
Auto-categorized from merchant history          ← Body 14px regular text-slate-500
[Override]                                      ← Body 14px medium text-slate-900
```

**Form modal typography:**

- Modal heading: `<flux:heading size="lg">` (20px semibold).
- Field labels: Body 14px weight 400 `text-slate-900`, `mb-1` from the input.
- Help text below an input: Micro 12px `text-slate-500`.
- Validation error: Body 14px `text-rose-600` (matches existing Settings page pattern).

**Toast typography:**

- Heading: Body 14px weight 600 `text-slate-900` ("Rule suggested Streaming." / "Receipt has cleaner merchant name.").
- Body: Body 14px weight 400 `text-slate-700` (one sentence describing the action offered).
- Action buttons: Body 14px weight 500. Primary action (`Update rule` / `Use receipt`): `text-emerald-700 hover:bg-emerald-50 px-2 py-1 rounded-md`. Secondary action (`Keep current rule` / `Keep CSV`): `text-slate-700 hover:bg-slate-50 px-2 py-1 rounded-md`.

## Interaction Contracts

### `/rules` page lifecycle

1. **Mount** — `RulesPage::mount()` calls `CategorizationRuleQuery::forUser($this->currentUser->id)` and stores the rows on `public array $rules`. Sort: `created_at DESC` so newest rules sit on top.
2. **"New rule" click** — `wire:click="openCreateModal"` sets `$editingRuleId = null` and dispatches `rule-form:open` (Livewire event). The `RuleFormModal` SFC listens via `#[On('rule-form:open')]` and opens the Flux modal via Alpine `$dispatch('modal-show', { name: 'rule-form' })`.
3. **"Edit" click on a row** — `wire:click="openEditModal({{ $rule->id }})"` sets `$editingRuleId = $id`, hydrates the form fields from the matching row, dispatches `rule-form:open`.
4. **Form submit** — Form modal calls `CreateCategorizationRule::execute(...)` OR `UpdateCategorizationRule::execute(...)` from `Modules/Categorization/Public/Actions/`. On success, dispatches `rule-form:saved` event. The `RulesPage` listens, re-runs the query, closes the modal, and flashes a `Rule saved.` confirmation inline above the table (3s `wire:transition.duration.3000ms`).
5. **"Delete" click on a row** — Toggles `$confirmingDeleteId = $rule->id` on the row. The Blade conditionally renders the two-step `[Delete?] [Yes, delete] [Cancel]` chip row in place of `[Edit] [Delete]`. Esc key clears `$confirmingDeleteId`.
6. **"Yes, delete" click** — `wire:click="deleteRule({{ $rule->id }})"` calls `DeleteCategorizationRule::execute($currentUser, $ruleId)`. On success, removes the row from `$rules` and flashes `Rule deleted.` (3s).
7. **Validation failures** — Render under the relevant field via `@error('field')` (matches existing Settings page pattern). Duplicate-rule check fires server-side via the `UNIQUE (user_id, field, match, value)` constraint catching → the action translates to a `ValidationException` with the duplicate error message.

**Dispatched events (Livewire):**

| Event | Source | Listener | Payload |
|-------|--------|----------|---------|
| `rule-form:open` | `RulesPage` | `RuleFormModal` | `{ ruleId?: int }` |
| `rule-form:saved` | `RuleFormModal` | `RulesPage` | `{ ruleId: int, action: 'created'\|'updated' }` |
| `modal-show` (Alpine) | `RulesPage` (via Alpine) | Flux modal | `{ name: 'rule-form' }` |
| `modal-hide` (Alpine) | `RuleFormModal` after save | Flux modal | `{ name: 'rule-form' }` |

### Rule form modal lifecycle

1. **Initial state** — All fields empty, Save button disabled (`@disabled($field === '' || $value === '' || $categoryId === null)`).
2. **wire:model.live** on `field`, `match`, `value`, `categoryId` re-evaluates the disabled state. No server roundtrip on each keystroke for `value` — use `wire:model.lazy` for the `value` text input to avoid Livewire requests on every character (matches `transactions-list` search input precedent).
3. **Save click** — Submits the form via `wire:submit="save"`. Calls the appropriate Public action. On success, fires `rule-form:saved`. On validation failure, error renders under the offending field; modal stays open; focus moves to the first errored field via `x-init="$nextTick(() => $refs.firstError?.focus())"` (Alpine).
4. **Cancel click** — Fires `modal-hide` directly; no save; form state is reset on next `openCreateModal()` call (so re-opening for create always starts clean; opening for edit always re-hydrates from the queried row).
5. **Esc key** — Flux modal's default Esc-close fires `modal-hide`. Same as Cancel.

**Form field flow (rendered as a single readable sentence):**

```
When the [merchant ▼] [contains ▼] the value [_______________]
                                              e.g. SPOTIFY (help text)

Assign category [Subscriptions / Streaming ▼]

                                              [Save rule]  [Cancel]
```

The "sentence" layout (instead of a stacked form) is deliberate — it reads as a natural-language rule statement, mirroring the Notion-style "describe what you want" aesthetic. Three dropdowns inline left-to-right, value input continues the sentence, category dropdown below on its own line, actions right-aligned.

### Provenance panel lifecycle

1. **Mount** — `CategorizationProvenancePanel::mount(int $transactionId)` queries the most-recent `AutoCategorizationOutcome` for that transaction via `AutoCategorizationOutcomeQuery::latestForTransaction($txId)`. Result is one of three shapes: rule outcome / memory outcome / null.
2. **Render** — Conditional Blade renders the corresponding variant. Manual-categorized (null result) renders NOTHING (no chrome — calm aesthetic).
3. **"Update rule" click (rule variant)** — Dispatches `rule-form:open` with `{ ruleId: $outcome->ruleId }`. RulesPage doesn't have to be mounted — the RuleFormModal SFC is always mounted globally inside the layout (planner confirms — see § Mounting Strategy below).
4. **"Remove rule" click (rule variant)** — Two-step inline confirmation identical to the rule row pattern. On `[Yes, remove]`, calls `DeleteCategorizationRule::execute()`. The transaction's category is NOT changed (the rule deletion does not retroactively un-categorize) — same posture as the helper note. After delete, the panel re-renders as the memory variant if memory exists for this merchant, otherwise as the manual variant (no panel).
5. **"Override" click (memory variant)** — Dispatches `inline-category-picker:open` with `{ transactionId: $txId }` so the existing override flow runs. The new choice updates memory via the existing `AssignCategory` action.

### Correction-divergence toast lifecycle (D-712)

1. **Trigger** — When `AssignCategory::execute()` runs and detects that the prior categorization had `provenance='rule'` AND the new `category_id !== $rule->category_id`, it dispatches a `CategorizationDiverged` domain event with payload `{ rule_id, old_category_id, new_category_id, transaction_id }`.
2. **Listener** — `CorrectionDivergenceToast` Livewire SFC (mounted in the layout, always present, no visible chrome until activated) listens via `#[On('echo:CategorizationDiverged')]` OR via Livewire's session-flash → Alpine bridge (planner picks the cleaner shape; recommendation: session-flash via redirect path since Reclassify already does a save → wire navigate).
3. **Render** — Alpine `x-show` reveals the toast at bottom-right; `x-init` starts an 8s timer.
4. **Primary action "Update rule"** — Calls `UpdateCategorizationRule::execute($user, $ruleId, ['category_id' => $newCategoryId])`. On success, toast disappears with `wire:transition.opacity` and flashes a tiny `Rule updated.` inline (3s).
5. **Secondary action "Keep current rule"** — Dismisses the toast. No further action. Records the user's "skip" decision (planner picks — likely a no-op for v1; v2 can record a "don't show me this divergence again" pref).
6. **Auto-dismiss** — After 8s without interaction, toast hides itself; no record kept (the user simply didn't engage).
7. **Re-fire policy** — Each `CategorizationDiverged` event renders the toast fresh, but the SFC short-circuits if the same `rule_id + transaction_id` pair fires twice in the same session (debouncing identical bursts).

### First-conflict receipt toast lifecycle (D-707)

1. **Trigger** — During `ApplyEnrichments`, when a true field-value conflict is detected AND `users.receipt_conflict_resolution = 'unset'`, the stage holds the conflicting value in `pending_enrichment_conflicts` (per D-715) and dispatches `ReceiptConflictDetected` event with payload `{ transaction_id, field, receipt_value, csv_value }`.
2. **Listener** — `ReceiptConflictToast` SFC (mounted globally in layout) listens and renders the toast on the user's next page load (after the import job completes). The toast may also fire DURING a synchronous wizard upload — in that case it renders on the `/imports/{id}/results` page.
3. **Primary action "Use receipt"** — Calls a new `ApplyReceiptConflictResolution::execute($user, 'prefer_receipt')` Public action which: (a) writes `users.receipt_conflict_resolution = 'prefer_receipt'`, (b) resolves the held pending conflict by writing the receipt value to the transaction, (c) clears the held row from `pending_enrichment_conflicts`. Toast disappears.
4. **Secondary action "Keep statement"** — Same flow, but writes `'prefer_first_write'` and resolves the held conflict by KEEPING the CSV value (clearing the pending row without modifying the transaction).
5. **Dismiss without action** — Toast hides via the standard `[x]` close button. The setting stays `'unset'`. The pending row stays in `pending_enrichment_conflicts`. The next conflict re-fires the toast. This is intentional per CONTEXT.md risk note: "the user must explicitly choose to lock the setting."
6. **No auto-dismiss** — Unlike the correction-divergence toast (8s), this toast is permanent until the user acts because it represents an unresolved data conflict.

### Watched-folder toggle lifecycle

1. **Initial state** — Reads from `$user->auto_import_drop_folder` (new boolean column, default `false`).
2. **Toggle click** — `wire:click="toggleAutoImport"` flips the value, persists immediately (no Save button — instant-apply pattern matches Phase 3 Settings's currency-view select), and re-renders the help-text section.
3. **Help-text variant** — When OFF, shows full explanation (where files go, cadence, processed-move). When ON, shows the supplemental text including the last-scan timestamp (queried from a new `last_drop_folder_scan_at` field on the user OR a system_settings table — planner picks).

### `/imports` wizard email-file arm

The wizard already implements a two-step issuer→format pattern (Phase 3 D-33 introduced it for ICS). Phase 7 extends `availableFormats()`:

```
issuer 'email-file' → [
    { value: 'eml',  label: 'Email message (.eml)' },
    { value: 'mbox', label: 'Mailbox archive (.mbox)' },
]
```

Submit flow is unchanged — the `HeaderSniffer` validates the file shape against the declared format, then the standard preview-then-confirm path runs.

### `/inboxes` matcher column + status filter

1. **Filter dropdown** above the table — `wire:model.live="statusFilter"`. Options match the inbox_messages status enum + 'all'. Default 'all'.
2. **Matcher column cell rules** (rendered per row, conditional on `$inbox->lastFetchedMessageStatus`):
   - `parsed` + matcher_key present → text label of the matcher key (`paypal`, `ics-cards`, `google-play`).
   - `unmatched` → slate Flux badge with label `Unmatched` + inline link `View raw .eml`.
   - `skipped` → slate Flux badge with label `Skipped` and a `title="..."` attr carrying the skip reason (e.g., "PayPal login notification — not a transaction").
   - `fetched` → dim text `—` (pending parsing).
3. **"View raw .eml" inline link** click — Toggles `$expandedRawEmlInboxMessageId = $inbox->id`. Below the row, a collapsible `<pre>` block renders the first 4KB of the raw .eml (truncated with `[...]` marker if longer). Click again to collapse. The `<pre>` uses `bg-slate-50 border border-slate-200 rounded-md p-md text-xs font-mono whitespace-pre-wrap overflow-x-auto`.

### Mounting strategy

`RuleFormModal`, `CorrectionDivergenceToast`, and `ReceiptConflictToast` are mounted **globally** inside the `app.blade.php` layout (analogous to Phase 5's chain-drawer mounting pattern, which is page-local but the dispatch event is global). Recommendation: mount them after `@livewire('core.top-nav')` in the auth block:

```blade
@auth
    @livewire('core.top-nav')
    @livewire('categorization.rule-form-modal')
    @livewire('categorization.correction-divergence-toast')
    @livewire('receipts.receipt-conflict-toast')
@endauth
```

This means any page can dispatch `rule-form:open` to open the modal, and any page can receive the conflict / divergence events.

## Accessibility Notes

Phase 7 inherits the project's accessibility baseline from prior phases. Specific Phase 7 additions:

### Rule form modal (`<flux:modal>`)

- **Focus trap**: Flux modal handles focus trapping by default (verified in Phase 6 OAuth modal). The modal opens with focus on the first field (`Field` dropdown).
- **Esc closes**: Flux default; no override needed.
- **ARIA**: Modal carries `role="dialog"` + `aria-modal="true"` (Flux defaults). Add `aria-labelledby="rule-form-heading"` matching the `<flux:heading>` id.
- **Validation errors**: Each `@error('field')` rose-text paragraph gets `id="error-{field}"` and the input gets `aria-describedby="error-{field}"` + `aria-invalid="true"` when error present.
- **Submit during loading**: `wire:loading.attr="disabled"` prevents double-submit and screen readers announce the disabled state.

### Rules table

- `<table>` element with `<thead>` and `<th scope="col">` per column (matches `/uncategorized` precedent).
- Row hover state via `hover:bg-slate-50`, NOT relied on for action discoverability — Edit/Delete chips are always visible.
- Edit/Delete buttons carry `aria-label="Edit rule for {field} {match} '{value}'"` and `aria-label="Delete rule for {field} {match} '{value}'"` so screen-reader users hear meaningful action names.
- Confirm-delete chip pair: focus moves to `[Yes, delete]` button on activation (`x-init="$nextTick(() => $refs.confirmDelete.focus())"`). Esc reverts to the two-chip default state.

### Provenance panel

- Rendered as a `<section aria-labelledby="provenance-heading-{txId}">` so screen readers can navigate by landmark.
- The mono-formatted rule value `font-mono` carries `lang="en"` (matching project default — no specialty pronunciation needed since values are merchant strings).
- "Remove rule" action carries a stronger `aria-label="Remove rule (also deletes it from the Rules page)"` so the side-effect is announced.

### Correction-divergence toast

- `role="status" aria-live="polite"` on the toast container so AT users hear the new toast announcement without interrupting current speech.
- The two action buttons carry full `aria-label` including the rule context (`aria-label="Update rule to assign {new_category} instead of {old_category}"`).
- Auto-dismiss after 8s does NOT remove the toast for AT users until they tab past it — the visual timer is informational; the DOM node persists for `aria-live` announcement integrity. After AT engagement (focus enters then leaves), the node may be removed via `wire:transition`.

### First-conflict receipt toast

- `role="alert" aria-live="assertive"` — this represents an unresolved data conflict and should interrupt screen reader flow.
- NO auto-dismiss — accessibility-positive (matches the design intent that the user must explicitly choose).

### Watched-folder toggle

- Native `<input type="checkbox">` styled to look like a toggle via Tailwind (no custom widget — preserves screen reader semantics).
- `<label for="auto-import-toggle">` wraps the visible label + help text within a single `<label>` so clicking either toggles the checkbox.
- Help text below: `<p id="auto-import-help" class="text-xs text-slate-500">` referenced via `aria-describedby="auto-import-help"` on the checkbox.

### `/inboxes` status filter + matcher column

- Status filter is a native `<select>` (same as currency-view filter on Settings).
- "View raw .eml" inline link is a `<button>` (semantic — it expands content in place, doesn't navigate) with `aria-expanded` reflecting collapsed/expanded state and `aria-controls="raw-eml-{id}"` pointing to the `<pre>` container.
- The raw `<pre>` block has `tabindex="0"` so keyboard users can scroll through long content with arrow keys.

### Keyboard navigation summary (`/rules` page)

| Key | Effect |
|-----|--------|
| Tab | Forward through: New rule button → table rows (Edit, then Delete on each) → helper note |
| Shift+Tab | Reverse |
| Enter on focused row action | Activates Edit or Delete |
| Esc in modal | Closes modal (Flux default) |
| Esc on row in delete-confirm state | Reverts to two-chip default |

| Enter in Value input | Submits the form (matches OAuth wizard precedent — single-action form) |
