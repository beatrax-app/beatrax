# Phase 6 — UI Design Contract

> Visual and interaction contract for Phase 6: Email Receipt Ingestion Infrastructure. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope (UI surfaces produced):**

1. **`/inboxes` top-nav page** (D-124, D-127) — new page that owns the full email-ingestion lifecycle for the user. Page envelope inherits the Phase 3 `Route::view + Livewire SFC + view-extends('layouts.app')` convention. Sections in render order: page heading + subheading; (when zero inboxes) the empty-state hero; (when >= 1 inbox) the connected-inboxes table; (when an active backfill exists for any inbox) a backfill-progress strip rendered above the table; the "Add inbox" card pair (always rendered below the table after first connect); the "Discovered senders" panel (rendered last; hidden when zero candidates).
2. **OAuth-client-registration wizard modal** (D-114) — Flux modal (NOT a flyout — modal posture matches the wizard semantic). Triggered by clicking "Connect Gmail" or "Connect Microsoft 365" on `/inboxes` when no OAuth client is configured for that provider. Numbered steps + screenshot thumbnails + deep-link buttons to Google Cloud Console / Azure Portal + paste-back fields for `client_id` + `client_secret` + copy-to-clipboard for the exact loopback redirect URI. Google variant carries one additional step ("Push consent screen to In production") because Testing-mode refresh tokens expire after 7 days for `gmail.readonly` (RESEARCH.md correction to D-111). Submit closes the modal and auto-redirects the user into the provider's OAuth consent flow (no extra click).
3. **Backfill window picker modal** (D-128) — Flux modal that opens automatically after the OAuth callback returns with a freshly inserted inbox row. Hosts a 1–12 month range input (default 3) plus a single Confirm button that queues `BackfillInboxJob`. Re-opens via the inline `Window: 3 months [Edit]` link on each inbox row in the connected-inboxes table.
4. **Dashboard "Email scan health" tile** (D-125) — sibling to Phase 5's "Next ICS settlement" tile on the dashboard tile row. Compact tile body lists one line per connected inbox ("Gmail: last scanned 3 h ago"), max 3 lines then `+N more`. Tile-level status dot: red when ANY inbox is `needs_reauth`, gray when stale (>24 h since last successful scan), green when all healthy. Tile click navigates to `/inboxes`. Tile is hidden entirely when zero inboxes are connected.
5. **Top-nav "Inboxes" item with badge** (D-126) — new top-nav entry between "Imports" and "Uncategorized". Numeric badge sums (open `discovered_senders` with `state='candidate'`) + (inboxes with `inbox_scan_state.status='needs_reauth'`). Fed via View Factory composer (the same pattern Phase 5 issue #12 fix established for the chain-review badge — uses `$this->app->make(ViewFactoryContract::class)->composer(...)`, never the `view()` global helper).
6. **Reauth-detected toast** (D-115) — one-shot notification on the dashboard the first time any inbox transitions to `needs_reauth`. Reuses Phase 5's failed-job toast chrome (Filament-notifications-style, fixed bottom-right, `wire:poll.5s`-driven). Distinct from Phase 5's failed-job toast — this is a separate toast variant with its own copy. Persistent until the user dismisses it OR every needs_reauth inbox returns to a non-reauth state.
7. **Inbox row health badge variants** — six variants matching `inbox_scan_state.status` enum: `idle` / `backfilling` / `scanning` / `rate_limited` / `needs_reauth` / `error`. Each renders as a Flux Badge with a color + label + optional inline detail (e.g. `rate_limited` shows `retrying in 4m`).
8. **Inline row actions** — Scan-Now button + Reconnect button (visible only when `needs_reauth`) + Window-edit link, all on each inbox row in the connected-inboxes table. Reconnect re-runs the per-inbox OAuth consent flow without re-opening the OAuth-client wizard; existing `inbox_messages` rows + `.eml` blobs + `last_history_id` cursor are preserved.
9. **Discovered-senders panel** — list of `discovered_senders` rows with `state='candidate'` sorted by `occurrence_count DESC`, each with Add / Dismiss chip pair. Add promotes the row into `known_senders` and transitions the discovered row to `state='added'`; Dismiss transitions to `state='dismissed'` so the discovery query excludes the sender on future runs.

**Out of scope this phase:**

- Per-sender template matchers (Phase 7 — EML-05). The connected inbox UI never shows "this message was parsed into a transaction" because Phase 6's `inbox_messages.status` stays at `fetched`.
- `.eml`/`.mbox` drop-in upload UI (Phase 7 — EML-07).
- Per-inbox detail drawer / inbox-row drill-in (a follow-up may add it; Phase 6 keeps the row inline-only).
- Multi-folder selection UI (Phase 6 ships `INBOX`-only; schema is multi-folder-ready).
- Manual "Scan now with custom date range" — Phase 6 ships re-run-now only.
- OAuth-client wizard "edit existing client_id" mode (D-134 — likely policy is reset-and-mark-children-needs-reauth; deferred to plan-phase).
- Encryption-at-rest UI signal for `email-oauth.json` (D-138 — chmod-600 alone satisfies PLT-03).
- Dedicated `/horizon` page link in the nav (kept as the Phase 5 toast-only path).
- `/settings` page extension for OAuth-client reset (planner may add it later as a tiny artisan command path).
- Dark mode.

## Spacing Scale

Inherited verbatim from `05-UI-SPEC.md`. No new tokens. No exceptions for this phase.

| Token | Value | Usage in Phase 6 |
|-------|-------|-------------------|
| xs | 4px | Gap between status-badge dot and label; 4px optical offset between the inbox row's primary line and its secondary line; gap between count badge and the "Inboxes" nav label |
| sm | 8px | Inner padding on Flux badges; gap between Scan-Now / Reconnect / Window-edit actions in an inbox row; gap between Add and Dismiss chips in a discovered-senders row; horizontal padding inside the discovered-senders panel rows |
| md | 16px | Default padding inside an inbox row card; `gap-md` between connected inbox rows in the table; horizontal padding inside the modal body; gap between numbered wizard steps in the OAuth-client modal |
| lg | 24px | Top/bottom padding of the wizard modal body; gap between the page heading and the connected-inboxes table; gap between sections on `/inboxes` (table, add-inbox cards, discovered-senders panel); padding inside each Add-inbox card |
| xl | 32px | Modal's left/right outer padding (Flux default); vertical gap between the empty-state hero copy block and the two big Connect buttons; vertical gap between the connected-inboxes table and the Add-inbox card pair |
| 2xl | 48px | Vertical gap between dashboard tiles (matches Phase 5); same `2xl` separates the Email-scan-health tile from the Next-ICS-settlement tile in the dashboard tile row |
| 3xl | 64px | Page-level vertical breathing on `/inboxes` between the page heading and the first content section (mirrors `/chains/review`) |

**Page width:** `max-w-5xl` (~1024px) centered for `/inboxes` (same as `/chains/review` and `/transactions`). The OAuth-client wizard modal and the backfill-window modal both use Flux's default modal width — `md:max-w-lg` (~512px) for the backfill window picker (compact), `md:max-w-2xl` (~672px) for the OAuth-client wizard (numbered steps with screenshots need the wider canvas).

**Empty-state hero width:** `max-w-md` (~448px) centered, with `mt-3xl` (64px) top margin from the page heading. The two Connect buttons sit in a horizontal `flex gap-md` row beneath the hero copy.

**Connected-inboxes table row min-height:** `min-h-16` (64px) per row — tall enough to host the email-address primary line, the secondary line (provider + last-scan), the status badge, AND the three inline actions without crowding. 64px is `4 × 16px` and respects the 4px-multiple invariant.

**Status badge dimensions:** Flux badge default. Phase 5 declared a `px-2 py-0.5` exception for confidence chips (2px vertical); Phase 6 uses Flux's native `<flux:badge>` component which carries the same `py-0.5` internal default. This is the same single inherited exception, not a new one. Document and accept.

**Backfill progress strip:** `rounded-md border border-slate-200 bg-slate-50 p-md` — same chrome as the wizard's "Resolving chains…" status surface (Phase 5) so the user reads the two surfaces as conceptually identical "something is happening in the background".

## Typography

Inherited verbatim from `05-UI-SPEC.md`. Phase 6 introduces no new sizes or weights. Uses the same 4-role scale.

| Role | Size | Weight | Line Height | Usage in Phase 6 |
|------|------|--------|-------------|-------------------|
| Micro / Caption | 12px | 400 (regular) | 1.4 | Inbox row secondary line (provider + "last scanned X ago"); status-badge label text; backfill progress strip count ("1,234 / ~5,200"); discovered-senders panel "Seen N times" caption; OAuth wizard step caption; Email-scan-health tile per-line text ("Gmail: last scanned 3 h ago"); +N-more truncation label; toast helper text |
| Body | 14px | 400 (regular) | 1.5 | Inbox row primary line (email address); Add-inbox card body copy; empty-state hero body copy; discovered-senders row primary line (sender email + occurrence count); OAuth wizard step body copy; backfill modal body copy; Scan-Now / Reconnect / Window-edit / Add / Dismiss chip text |
| Section heading | 20px | 600 (semibold) | 1.3 | `/inboxes` page heading ("Inboxes"); OAuth-client wizard modal heading (`<flux:heading size="lg">`); backfill-window modal heading; empty-state hero heading; discovered-senders panel heading ("Discovered senders") |
| Display (Tile amount / hero) | 32px | 600 (semibold) | 1.2 | (Reserved for KPI tiles per Phase 1; Phase 6's Email-scan-health tile does NOT use Display because it has no single amount to anchor — its content is a stacked list of inbox lines. Tile uses Section heading 20px for the title row instead and Micro 12px for the per-inbox lines.) |

**Empty-state hero typography (top-down stack):**

```
Connect your email                            ← Section heading 20px semibold text-slate-900
Import receipts from PayPal, ICS Cards,        ← Body 14px regular text-slate-500, max 60ch
Google Play, and other merchants.
[Connect Gmail]  [Connect Microsoft 365]       ← two solid-emerald-600 buttons, gap-md (16px)
```

**Inbox row typography (within a row):**

- **Primary line** (email address): Body 14px weight 400 in `text-slate-900`. Left-aligned. Truncates with `truncate` at the row's available width (rare for personal emails; defensive).
- **Secondary line** (`{provider} · last scanned {duration} · Window: {N} months [Edit]`): Micro 12px weight 400 in `text-slate-500`. Below the primary line with `mt-1` (4px optical gap using `xs` token). `[Edit]` is rendered as a hand-rolled `<button>` inside the secondary line (same `underline-offset-2 hover:underline` posture as Phase 5's "View chain" text link — visual link, semantic button).
- **Status badge** (right-edge of the row, opposite the primary line): Micro 12px weight 500 (Flux badge's internal default; same medium-weight allowance Phase 5 declared for confidence chips — no new project weight introduced).
- **Inline actions** (Scan-Now, Reconnect when `needs_reauth`, Window-edit absorbed into secondary line): Body 14px weight 500 in `text-slate-900`. Same chip-style chrome as Phase 5's `/chains/review` action chips but in neutral slate (these are not destructive/positive actions).

**Email-scan-health tile typography (top-down stack):**

```
Email scan health                             ← Section heading 20px semibold text-slate-900 (caption)
● Gmail: last scanned 3 h ago                  ← Micro 12px regular text-slate-700, leading dot 8px
● Microsoft 365: last scanned 8 h ago          ← Micro 12px regular text-slate-700
● work@example.com: last scanned 1 d ago       ← Micro 12px regular text-slate-700, truncates email
+2 more                                        ← Micro 12px regular text-slate-500 (when >3 inboxes)
```

The leading dot is **per-inbox** color-coded (emerald-600 healthy, amber-700 stale >24h, rose-600 `needs_reauth`). The tile's overall status is the worst per-inbox status. The "Inboxes" label / 20px heading itself stays `text-slate-900` regardless of status — the calm aesthetic forbids painting the tile title red.

**OAuth-client wizard step typography:**

- Step number (e.g. `1`): Micro 12px weight 600 in white on `bg-slate-900` circle (Tailwind `flex h-6 w-6 items-center justify-center rounded-full`). Same chrome as numbered list bullets.
- Step heading (e.g. `Open Google Cloud Console`): Body 14px weight 600 in `text-slate-900`.
- Step body: Body 14px weight 400 in `text-slate-500`.
- Inline code snippets (the loopback redirect URI): `font-mono text-xs bg-slate-100 px-1.5 py-0.5 rounded text-slate-900`.

**Backfill window modal typography:**

- Heading: Section heading 20px semibold (`How far back should we look?`).
- Body: Body 14px regular `text-slate-500` (`Importing further back fetches more receipts but uses more provider quota. Default is 3 months.`).
- Slider value readout (live): Body 14px weight 600 in `text-slate-900` with tabular-nums (`{N} months`).
- Confirm button text: Body 14px weight 500 in white on `bg-emerald-600`.

2. **"Add" chip** on discovered-senders rows. Mirrors Phase 5's Confirm-chip chrome verbatim (D-86 dual-surface posture extended to D-120 discovery panel).
3. **Backfill window modal Confirm button** — solid emerald-600 with white text. Same chrome as Phase 1's upload-confirm CTA.
4. **OAuth-client wizard final-step Submit button** — solid emerald-600 with white text. Earlier wizard steps' "Open Google Cloud Console" / "Open Azure Portal" deep-link buttons are NOT emerald — they are slate-900 outline buttons (`border border-slate-300 bg-white text-slate-900 hover:bg-slate-50`) because the user is being directed OFF the application; consuming emerald there would equate "leave the app" with "complete the goal", which is wrong.
5. **Email-scan-health tile's leading dot** for healthy inboxes. Single 8px-diameter emerald-600 circle per inbox line.

**Destructive (`rose-600`) is reserved for — and ONLY for — these Phase-6-new elements:**

1. **`needs_reauth` status badge** (ghost variant: `bg-rose-50 text-rose-600`). Never solid rose. The badge sits in a row that the user must take action on; the calm aesthetic forbids painting the whole row red but the badge color is necessary to differentiate it from `rate_limited` (amber, recoverable without user action) and `error` (neutral, transient).
2. **Reauth toast left accent stripe** — 2px rose-600 vertical bar on the toast body's left edge. Toast text stays `text-slate-900`. Same chrome as Phase 5's failed-job toast — calm chrome with a single peripheral indicator.
3. **Email-scan-health tile leading dot** for inboxes in `needs_reauth` state.

**60 / 30 / 10 audit (Phase 6):**

- 60% dominant white surface — `/inboxes` page background, modal body, inbox row body, tile body, Add-inbox card body unchanged.
- 30% secondary slate-50 / slate-200 — status-badge ghost backgrounds, discovered-senders panel container, backfill progress strip, modal step bullet column, page borders.
- 10% accent — the two Connect buttons (hero + Add-inbox card pair), the Add chip, the backfill Confirm button, the wizard Submit button, the health-tile healthy dots. The Phase 1 + Phase 3 + Phase 5 accent budget (upload CTA, login button, Settings save button, NEW badge, net-positive KPI, segmented-control selected pill, /chains/review Confirm chip, auto-promotion check icon) is unchanged; Phase 6 additions land within the 10% budget by virtue of being interaction-locked (the two Connect buttons render once each, the Add chip renders per-discovered-row but the panel itself is contextual, the modal Submit/Confirm buttons render only when the modal is open).

**Audit safety:** the rose-600 destructive surfaces (needs_reauth badge + tile dot + toast stripe) live in the destructive role budget. The amber-700 and sky-700 status-badge variants live in the warning + info subdued roles, which carry no 10% budget caps.

**No new colors.** No hue ramp on the "last scanned X ago" duration (the duration string itself stays slate-500). No solid red anywhere. Currency is not surfaced in Phase 6.

  ```php
          $this->app->make(InboxesBadgeCount::class)->forCurrentUser()
      )
  );
  ```
- The `InboxesBadgeCount` Public service sums `count(discovered_senders WHERE state='candidate')` + `count(inbox_scan_state WHERE status='needs_reauth')`. Updates on every page navigation (no polling).
- **Never use the `view()` global helper.** This pattern was locked by Phase 5 issue #12 fix and applies verbatim.

### OAuth-client-registration wizard modal (D-114)

**Trigger:**

- Click on `Connect Gmail` (empty-state hero OR Add-inbox card) → server-side check `OAuthSecretsRepository::hasProviderClient('gmail')`. If false → `$this->dispatch('modal-show', name: 'oauth-client-wizard-gmail')`. If true → `$this->redirect(route('oauth.connect', ['provider' => 'gmail']))`.
- Same shape for `Connect Microsoft 365` with `provider='microsoft'`.

**Open behaviour:**

- Flux modal opens with Flux default animation (ease-out, ~200ms).
- `dismissible="false"` — clicking outside the modal does NOT close it (the user can lose 5 minutes of wizard work otherwise). Escape does NOT close.
- Initial focus lands on the modal heading. Tab cycles through deep-link button → input fields → Submit/Cancel buttons.
- Focus trap active (Flux default).

**Step progression:**

- All steps render simultaneously stacked vertically. There is NO "Next" / "Back" step-by-step navigation — the user reads the whole flow at once. The numbered circles are visual markers, not state machines.
- The Submit button at the modal footer is the only completion affordance. It is disabled (`disabled="true"` + `opacity-50 cursor-not-allowed`) until both `client_id` and `client_secret` fields pass client-side validation (regex + non-empty).

**Submit behaviour:**

- Click Submit → Livewire `save()` method:
  1. Validate inputs.
  2. Pass `client_id` + `client_secret` + `redirect_uri` to `OAuthSecretsRepository::saveProviderClient($provider, $payload)` (atomic write-tmp + fsync + rename per D-112).
  3. Dispatch `modal-hide` event on the wizard modal.
  4. Redirect to `route('oauth.connect', ['provider' => $provider])` to immediately enter the per-inbox consent flow (no extra click — D-114 invariant).
- On any exception (file system write fail, validation regression): inline error copy in the modal footer (`text-rose-600`). Modal stays open.

**Cancel behaviour:**

- Click Cancel → `$this->dispatch('modal-hide', name: 'oauth-client-wizard-{provider}')`. No data persisted. User returns to `/inboxes` with no inbox-state mutation.

**Multi-provider modal isolation:**

- Each provider has its own modal name (`oauth-client-wizard-gmail` vs `oauth-client-wizard-microsoft`). Only one is ever open at a time because clicking Connect for the other provider runs the same trigger logic and Flux's modal manager handles the swap.

**Redirect URI display:**

- The exact loopback URI is computed server-side from `config('app.url')` (or the request's `getSchemeAndHttpHost()` fallback). It must be of the form `http://127.0.0.1:{port}/oauth/callback/{provider}`. The wizard's copy-to-clipboard button surfaces this string verbatim. If `config('app.url')` resolves to a non-loopback scheme (e.g. `https://diederik.test`), the wizard renders an inline warning above step 1: `Your app URL is set to https://diederik.test, which Google and Microsoft reject as a redirect URI. The URI below uses the loopback IP scheme they require.` (locked verbatim — this addresses the RESEARCH.md correction to D-114.)

### Backfill window picker modal (D-128)

**Trigger:**

- (a) Auto-trigger after OAuth callback completes — `OAuthCallbackController` redirects to `/inboxes?backfill={newInboxId}` and the `InboxesPage` SFC `mount()` reads the query parameter and dispatches `modal-show` for that inbox's modal.
- (b) Manual trigger via the inline `[Edit]` link on any inbox row in the table.

**Open behaviour:**

- Flux modal opens with default animation.
- `dismissible="true"` — clicking outside closes; Escape closes. (Canceling is safe; no inbox state mutates on cancel.)
- Initial focus lands on the slider (Flux range input).

**Slider behaviour:**

- Range 1–12 with step 1. Default value: 3 (D-128 / EML-04).
- Tick labels at 1, 3, 6, 9, 12 below the slider (rendered as plain text spans, not slider notches — keeps the slider visually calm).
- Live binding: `wire:model.live="months"`. Slider value readout (`{N} months`) updates synchronously without a roundtrip.

**Confirm behaviour:**

- Click `Start backfill` → Livewire `save()` method:
  1. Defensive validation: `$months >= 1 && $months <= 12`. Server-side enforcement; the slider's range already prevents out-of-bounds but the controller never trusts the client.
  2. Update `inboxes.backfill_window_months` for the target inbox (where `user_id === currentUser->id`).
  3. Dispatch `BackfillInboxJob` via `$bus->dispatch(new BackfillInboxJob($inboxId, $months))`.
  4. Dispatch `modal-hide` on the modal.
  5. The backfill progress strip on `/inboxes` begins rendering on the next `wire:poll.2s` cycle as the job picks up.

**Window-shrink case:**

- If the new window is SMALLER than the current window (e.g. user had 6, sets to 3), the job is still dispatched but is a no-op for the months already fetched. Already-fetched `inbox_messages` are NOT deleted (D-128 invariant — "history retained forever"). The window value is the *intent for future fetches*, not a retention policy.

**Window-extend case:**

- If the new window is LARGER (e.g. user had 3, sets to 6), the job dispatches with `since = current_oldest_internal_date` walking backwards. Already-fetched rows in the prior 3-month window are not re-fetched (D-122 idempotency contract).

**Cancel behaviour:**

- Click Cancel → modal closes; no mutation. If the modal was auto-triggered after the OAuth callback, the user can re-trigger it later via the row's `[Edit]` link.

### Inbox row inline actions

**Scan-Now button:**

- Click fires `wire:click="scanNow({{ $inbox->id }})"`. The Livewire action dispatches `IncrementalScanJob` via injected `Dispatcher`. Returns immediately (no spinner — the badge flips to `Scanning` within ~2s via the page-level `wire:poll.2s` refresh).
- Disabled state: when `status === 'backfilling'` OR `status === 'scanning'`, the button renders disabled (`disabled="true"` + `opacity-60 cursor-not-allowed`) with `title="Scan already in progress"`.
- No optimistic flip on the badge — the page-level poll surfaces the real state within 2s.

**Reconnect button:**

- Visible ONLY when `status === 'needs_reauth'`.
- Click navigates the user via `<a href="{{ route('oauth.connect', ['provider' => $inbox->provider]) }}?inbox_id={{ $inbox->id }}">`. Same per-inbox OAuth consent endpoint as the initial Connect; the controller detects the `inbox_id` query parameter and updates the existing inbox row's `refresh_token` instead of inserting a new one.
- No optimistic flip. The user is redirected to the provider's consent screen, completes it, returns to `/inboxes`. The inbox row's badge transitions to `Idle` automatically once the new refresh token is saved.

**Window-edit inline link:**

- Click fires `wire:click="$dispatch('modal-show', name: 'backfill-window-{{ $inbox->id }}')"`. Backfill window modal opens scoped to this inbox.

### Backfill progress strip (D-122)

**Poll cadence:** `wire:poll.2s="refreshBackfillProgress"` on the page-level Livewire SFC. Each cycle queries `inboxes WHERE user_id = ? AND backfill_progress IS NOT NULL` (with the JSON column carrying `fetched_count`, `total_estimated`, `last_message_date`).

**Visibility:** Renders when at least one inbox has a non-null `backfill_progress`. Disappears (smoothly via Tailwind transition) when all backfills complete.

**Per-line content:** `Backfilling {provider} ({email}): {fetched_count} / ~{total_estimated} messages` with `font-variant-numeric: tabular-nums` on the numerator. Multiple parallel backfills (different inboxes) stack vertically inside the strip, one line each.

**No progress bar.** The numerator + estimated total is the motion signal; an animated progress bar would feel like a fake estimate (the `~total_estimated` may itself shift mid-backfill as Gmail's `resultSizeEstimate` refines). Calm aesthetic.

**Completion behaviour:** When a backfill completes, the line for that inbox disappears from the strip on the next poll cycle. When the strip's line count reaches zero, the whole strip's `<section>` is omitted from the render output (no empty box).

### Inbox status badge transitions

The page-level `wire:poll.2s="refreshBackfillProgress"` doubles as the status-badge refresh — every cycle re-queries `InboxQuery::forCurrentUser()` and re-renders each row's badge from the latest `inbox_scan_state.status`. No per-row poll; one poll for the whole page.

**Transition signaling:** A status transition (e.g. `backfilling` → `idle`) is communicated by the badge's color + label changing on the next poll cycle. No animation; no flash; calm aesthetic. The badge ARIA attributes update so screen readers re-announce the new status.

### Discovered-senders panel (D-120 / D-121)

**Sort:** `discovered_senders.occurrence_count DESC, discovered_senders.last_seen_at DESC`. Default page size: 25 rows. Standard Livewire `WithPagination` if more exist (matches `/chains/review` pagination posture).

**Empty state:** Panel is NOT rendered when `count(candidates) === 0`. There is no "no candidates yet" copy — discovery is a background feature; advertising its emptiness adds noise.

**Add click:**

- Click `Add` → `wire:click="addSender({{ $row->id }})"`. Livewire action:
  1. Insert into `known_senders` with `(user_id, email_pattern=$row->sender_email, label=$row->sender_name ?? local_part, source='user')`.
  2. Update `discovered_senders` row to `state='added'`.
  3. Optimistic flip: row fades out with `opacity-0 transition` and disappears from the panel on next render.
- The top-nav badge count decrements on the next page navigation (View Factory composer refresh).

**Dismiss click:**

- Click `Dismiss` → `wire:click="dismissSender({{ $row->id }})"`. Livewire action: update `discovered_senders` row to `state='dismissed'`. Same fade-out pattern as Add.
- The `DiscoveryScanJob` queries `WHERE state NOT IN ('dismissed', 'added')` so dismissed senders never resurface.

**Keyboard:**

- `Tab` cycles row by row; within each row, `Tab` goes Add → Dismiss.
- `Enter` activates the focused chip.
- Once a row is acted on, focus moves to the next row's Add button (Livewire `$dispatch('discovered-sender:resolved')` event handles focus advancement via Alpine).

### Dashboard "Email scan health" tile (D-125)

**Placement:** New `<section>` in the dashboard tile row, alongside Phase 5's "Next ICS settlement" tile. Order: when both tiles render, "Next ICS settlement" first then "Email scan health" (left-to-right on desktop; stacked vertically on mobile via `grid grid-cols-1 md:grid-cols-2 gap-md`).

**Visibility logic:**

- `emailScanHealth($user)` returns `null` → tile section is NOT rendered. No "—" placeholder, no "Connect your email" CTA.
- Returns an `EmailScanHealthTile` DTO with `inboxes: array<InboxHealthLine>` → tile renders.

**Interaction:** The entire tile is wrapped in `<a href="{{ route('inboxes') }}">`; click navigates to `/inboxes`. Hover affordance: `hover:ring-2 hover:ring-slate-200 transition` (subtle slate ring, not emerald — calm aesthetic; the tile is informational, not a primary CTA).

**Refresh:** The tile renders on every dashboard load. It does NOT poll independently — the dashboard component's existing poll cycle (if any) covers it. The user sees the latest scan state when they visit the dashboard, which is the right granularity for a health surface.

### Reauth-detected toast (D-115)

**Trigger:** Dashboard component runs `wire:poll.5s="refreshNotifications"` (the same poll cycle Phase 5's failed-job toast uses; this is an additional check inside the same cycle). When `count(inbox_scan_state WHERE status='needs_reauth' AND user_id=?) > 0` AND the user has not dismissed the toast in this session, the toast renders.

**Persistence:**

- The toast does NOT auto-dismiss on a timer (matches Phase 5 failed-job toast).
- Stays visible until: (a) user clicks the `×` Dismiss → Livewire sets session-scoped `$reauthToastDismissedAt = now()` and the toast hides for the rest of the session; OR (b) all `needs_reauth` inboxes return to a non-reauth state (user completed Reconnect for every affected inbox) → the toast hides on the next poll.

**Stacking with Phase 5's failed-job toast:** If both toasts are visible simultaneously, they stack vertically with the reauth toast above the failed-job toast (`bottom-4 right-4` + the failed-job toast offset to `bottom-24 right-4` when both are present). Phase 6 SFC publishes its toast first on render order; CSS positioning controls visual placement. Z-index for both: `z-50`.

**Link behaviour:** `Go to Inboxes` is `<a href="{{ route('inboxes') }}">` — same-tab navigation.

**One-shot semantics:** "One-shot" means "only fires the first time a needs_reauth state is detected after the user last cleared all such states OR last dismissed". The toast is not literally fired once per inbox ever; it is a session-scoped notification that re-surfaces when the user has a new (or re-newed) needs_reauth situation. This matches Phase 5's failed-job toast semantic verbatim.

### Top-nav "Inboxes" link

**Active state:** When the user is on `/inboxes`, the link gets the existing nav-active treatment (`text-slate-900 font-semibold bg-slate-100`). Same pattern as "Transactions" / "Settings" / "Review chains".

- Renders when `inboxesBadgeCount > 0`. Hidden when 0.

**Network / privacy invariant:**

- The OAuth-client wizard's deep-link buttons (`Open Google Cloud Console`, `Open Azure Portal`) open external URLs in a new tab — the user navigates to the provider's domain manually. The modal itself does not pre-fetch anything from Google or Microsoft.
- The copy-to-clipboard button uses the browser's native `navigator.clipboard.writeText()` — no network, no script.
- The wizard NEVER auto-populates `client_id` / `client_secret` fields from any remote source. The user types or pastes them by hand.
- The reauth toast, the backfill progress strip, the Email-scan-health tile, and the inbox row status badges are all driven by local DB reads on Livewire's `/livewire/update` endpoint bound to 127.0.0.1 (FND-01 / PLT-01).
- The OAuth-callback endpoint (`/oauth/callback/{provider}`) is served by Laravel on the same loopback origin; the OAuth `code` parameter from the provider arrives via a same-origin redirect back to 127.0.0.1.
- The Inter font stays self-hosted with the system-ui fallback chain.

**OAuth consent flow privacy posture:**

- During the per-inbox consent dance, the user's browser navigates AWAY from diederik to `https://accounts.google.com/...` or `https://login.microsoftonline.com/...`. This is expected and unavoidable (it is the OAuth 2.0 authorization code flow). The provider redirects back to `http://127.0.0.1:{port}/oauth/callback/{provider}` with an authorization code. The token exchange (code → access_token + refresh_token) happens server-side via `league/oauth2-google` / `thenetworg/oauth2-azure` — the refresh_token never reaches the browser. This is the correct OAuth posture for a confidential client.
- The Gmail / Graph API calls themselves run server-side from the queue worker (Horizon) — the user's browser never sees an `Authorization: Bearer ...` header for the provider APIs.

**Horizon dashboard auth (D-101 inherited):** Phase 5's pattern unchanged. The Phase 6 jobs (`BackfillInboxJob`, `IncrementalScanJob`, `DiscoveryScanJob`) appear in `/horizon` under the existing session auth.
