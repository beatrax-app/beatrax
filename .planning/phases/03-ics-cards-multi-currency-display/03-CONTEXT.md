<domain>
## Phase Boundary

Phase 3 broadens ingestion to ICS Cards (**PDF statements only — Mijn ICS consumer portal does not offer CSV or Excel export**) and lights up the multi-currency machinery that Phase 1 front-loaded but never exercised. The user can: upload an ICS Cards PDF statement and see foreign-currency charges (e.g. a USD purchase) imported with both the native pair (`$X` / `USD`) and the settled pair (`€Y` / `EUR`) preserved on the same canonical row; toggle the `/transactions` list and the dashboard "this month at a glance" tiles between EUR-only and original-currency presentation, with the per-page choice overriding a global default stored in a new minimal `/settings` page; and rely on the schema to never lose FX information that the source provided (effective `fx_rate_used` derived from settled / original when both legs are present).

The wizard's upload UI is refactored from Phase 2's flat dropdown into a two-step grouped picker (issuer → format) so PayPal and Google Play groups in later phases land cleanly. The `SourceTransactionDto` contract gains nullable `settledAmountMinor`/`settledCurrency`/`fxRateUsed` fields so adapters can yield foreign-currency rows; Phase 1/2 ASN adapters keep returning `null` and the NormalizeStage substitutes settled=native, rate=null for them.

The ICS adapter introduces this codebase's first **text-extraction-driven** ingestion path: `pdftotext -layout` (via `spatie/pdf-to-text` around the poppler-utils binary) extracts a spatially-preserved *.txt dump; the adapter parses that text against an `IcsPdfExtractionMap` whose precise tokens are resolved by Wave 0 against a real anonymised fixture. The `PdfTextExtractor` service isolates the `exec()` boundary so the parser is unit-testable against a committed *.txt fixture and Larastan-strict typing stays clean.

This phase does NOT add per-card visibility (single ICS Account in Phase 3 — the user only has one card), does NOT add PayPal / Google Play / email-receipt ingestion, does NOT touch chain resolution, recurring detection, or forecasting. Those are Phases 4 through 11 per ROADMAP.md.

## Implementation Decisions

### ICS Export Format Coverage

- **D-31 (REVERSED 2026-05-15):** ~~CSV only.~~ The Mijn ICS consumer portal does not ship a CSV or Excel export — the only download channel is a monthly PDF statement. CSV adapter pattern is no longer applicable to Phase 3. See D-31a for the replacement decision. (ICS CSV ingestion is moved to "Deferred Ideas" in case ICS ever introduces a CSV export.)
- **D-31a (NEW 2026-05-15):** **PDF parsing via `spatie/pdf-to-text` (poppler `pdftotext` binary, `-layout` flag).** The `-layout` flag preserves the statement's tabular column structure as whitespace in the extracted text — exactly what a multi-column statement parser needs. `spatie/pdf-to-text` is a thin Composer wrapper that does the `exec()` call. macOS Herd prerequisite: `brew install poppler` (one-time, documented in README). The Phase 3 `PdfTextExtractor` service (lives at `Modules/Ingestion/Internal/Adapters/Ics/PdfTextExtractor.php`) wraps the `spatie/pdf-to-text` call so the `exec()` boundary is injectable for tests (mocked in unit tests; the real binary runs only in the integration smoke test against a tiny synthetic PDF). Pure-PHP `smalot/pdfparser` was considered and rejected for Phase 3: tabular layout recovery from per-glyph coordinates is materially more fragile than poppler's spatially-aware mode, and a one-time `brew install` cost is acceptable on a single-user macOS-only stack.
- **D-32 (UPDATED 2026-05-15):** **Real-fixture-first Wave 0 with extract-then-redact-text protocol.** The user provides a raw ICS PDF statement; **anonymisation is OUR job, not the user's**. Wave 0 runs `pdftotext -layout` on the raw PDF, anonymises the resulting *.txt dump (card numbers → `****-****-****-XXXX`, cardholder name → `KAARTHOUDER`, any cross-referenceable identifiers randomised), preserves dates / amounts / currencies / merchants verbatim, and commits the redacted *.txt as the fixture under `Modules/Ingestion/tests/fixtures/ics/ics-sample-1.txt`. **The raw PDF stays out of the repo** (gitignored under `local/ics/`). Wave 0 reports back on (a) extraction map — anchor tokens for the transactions table region + per-page noise patterns to strip (D-53), (b) source_ref availability (reframed D-34), (c) FX-row visual rendering (reframed D-35), (d) markup separability (reframed D-40), (e) statement-summary tokens (D-51), (f) Dutch date/amount formats present (D-52). Mirrors Phase 2 Plan 1's enablement-wave philosophy but sidesteps PDF binary redaction entirely — the committable fixture is plain UTF-8 text, trivially diffable.
- **D-33 (UPDATED leaf key):** **Two-step grouped wizard picker.** Refactor `UploadWizard`'s flat `['asn-csv', 'asn-camt053', 'asn-mt940']` dropdown into a two-step picker: first "Which issuer?" (ASN / ICS), then "Which format?" (ASN → CSV / CAMT.053 / MT940; ICS → **PDF**). The `sourceFormat` field stores the leaf key (`ics-pdf` — was `ics-csv` in the pre-revision plan; 1-token rename in plan 03-03). `HeaderSniffer` still validates the declared format (D-54 covers the PDF magic-byte sniff). PayPal and Google Play groups in later phases extend the issuer list without touching the format dropdown logic again.
- **D-34 (REFRAMED 2026-05-15):** **`source_ref` strategy is deferred to Wave 0 PDF-extraction inspection.** The question shifts from "does the CSV expose a stable per-transaction reference column" to "does the extracted statement text expose a stable per-transaction identifier token (authorisation code, slip number, transaction reference) that the parser can reliably capture from each transaction's text block". If yes, the parser populates `source_ref` from that token. If no, `source_ref` stays `NULL` and the v3 fingerprint tuple is the only dedup anchor. Either way, this matches the contract Phase 2 D-23/D-23a established (sources may legitimately have NULL source_refs; chain resolution adapts).
- **D-35 (REFRAMED 2026-05-15):** **FX-row visual shape is deferred to Wave 0 PDF-extraction inspection.** The question shifts from "one CSV row vs two CSV rows per FX charge" to "how does the extracted text render a foreign-currency charge". Three shapes the parser must distinguish (Wave 0 reports which one is present): (a) **single text line** with both native and settled amounts on the same row; (b) **two-line block** — merchant + native amount on line 1, conversion rate + settled amount on line 2; (c) **footnote-style** with reference markers (¹ ² ³ or similar) on the transaction line that lead to a per-statement conversion-rate footer block. Whichever shape is present, the parser rolls it up into ONE canonical `SourceTransactionDto` per logical transaction. The wizard preview MUST continue to show one preview row per canonical transaction regardless of source-line count.

### ICS Account Modeling

- **D-36:** **Single ICS Account in Phase 3.** The user has only one ICS card today. The `accounts` table records one row with `type = 'ics_card'` (new value alongside existing `bank` / `paypal` etc.), nameable by the user during first upload, currency `EUR` (the settlement currency). No `card_last4` column, no per-card subtable.
- **D-37 (UPDATED 2026-05-15):** **No card_number on transactions in Phase 3.** The card-number text rendered in the PDF (statement header watermark + transaction-table cells if present) is dropped at the adapter boundary and NOT preserved in `transactions.rawPayload`. Per-transaction card visibility is a v2 problem. **However:** masked card metadata (`issuer`, `cardLast4`, `cardholderName=STRIPPED`) IS captured in `statement_summaries.extras` JSON per D-56 — archive-only, never read by Phase 3 queries, gives the eventual multi-card phase a populated history without requiring re-import.
- **D-38 (Claude's discretion):** **Wizard prompts to name the ICS Account on first upload.** Mirrors Phase 1's "unknown IBAN → name the account" step (D-14), but the trigger is "no Account of type `ics_card` exists yet" rather than IBAN-not-found. Subsequent ICS uploads skip the prompt. Implementation lives in `UploadWizard` alongside the IBAN-account-naming step.

### FX Rate + ICS Markup Handling

- **D-39:** **`fx_rate_used` is derived: `settled_amount_minor / amount_minor`** with `decimal(18,8)` precision (the column's existing shape). Populated whenever both legs are present on the source row. This is the **effective** rate the user actually paid — markup-inclusive — which is the rate Phase 9 drift detection will care about. The column stays `NULL` when no FX took place (EUR-native rows).
- **D-40 (REFRAMED 2026-05-15):** **ICS markup is invisible at the canonical layer in Phase 3.** The question shifts from "does the CSV expose a separate markup row" to "is markup itemised as a separate text line or footnote in the extracted PDF text, or rolled implicitly into the displayed rate". Whichever it is, the adapter rolls the entire FX charge into one canonical row whose `settled_amount_minor` already includes any markup. The markup figure (if Wave 0 confirms it's structurally separable) remains recoverable from the per-transaction extracted-text block stored in `rawPayload` (D-49) for any later phase that wants to split it out. Revisit if Wave 0 shows that ICS markup is structurally separable in a way that materially changes Phase 9 drift detection.
- **D-41:** **EUR-native rows mirror native → settled.** The Phase 1 migration declared `settled_amount_minor` + `settled_currency` `NOT NULL`. For a EUR-native ICS row (or any future EUR-native source), the canonical row sets `settled_amount_minor = amount_minor`, `settled_currency = currency`, `fx_rate_used = NULL`. No schema change required.
- **D-42:** **`SourceTransactionDto` gains nullable `settledAmountMinor`, `settledCurrency`, `fxRateUsed` fields.** Phase 1/2 ASN adapters keep yielding `null` (every Phase 1/2 row was EUR-native). The Import pipeline's NormalizeStage substitutes `settled = native`, `fx_rate_used = null` when the source DTO leaves them `null`, then constructs the `CanonicalTransaction` (whose `settledAmountMinor` + `settledCurrency` remain `NOT NULL` per Phase 1's contract). This keeps the canonical layer's non-null guarantees intact while letting source-format adapters be honest about whether the source provided settled info or not. Cleanest typing path for Larastan level 10 strict.
- **D-43 (implicit / no change):** **The v3 fingerprint tuple uses native `amount_minor` + `currency`.** Two USD charges of the same merchant on the same day differ in seconds (the booked_at column) or in amount — same as Phase 2's EUR analogue. Fingerprint composer needs no change for multi-currency.

### PDF Extraction & Statement Handling (NEW 2026-05-15)

- **D-49:** **`rawPayload` for an ICS PDF transaction stores the per-transaction extracted-text block.** Specifically: the contiguous text lines from the `pdftotext -layout` output that correspond to ONE logical transaction (merchant line + any FX-conversion line + any markup footnote line clearly attached). This honors D-40's "markup remains recoverable from rawPayload" promise without bloating storage (~200 bytes per row vs ~20 KB if the full extracted statement were duplicated per row). Maintains the "this rawPayload describes THIS row" semantics other adapters already honor. Storage shape on `transactions.raw_payload` (existing `JSON` cast): `{ "format": "ics-pdf", "extractedText": "<contiguous text block>" }` — the discriminator field is consistent with how Phase 1/2 adapters tag their payloads.
- **D-50:** **One PDF = one statement = one import_run.** The Mijn ICS portal exports one monthly statement per download; multi-statement-per-PDF is not a thing the source produces. The adapter assumes a single statement per file (no multi-`:20:` MT940-style enumeration needed). Wave 0 confirms by inspecting the real fixture. If a future portal behavior change yields multi-statement PDFs, the adapter would be extended at that time — captured as a deferred consideration.
- **D-51:** **Populate `statement_summaries` from the PDF header block.** Mirrors Phase 2's CAMT/MT940 pattern (plan 02-03 D-29). The ICS PDF header carries: `Periode` (start/end dates), `Beginsaldo` (opening balance), `Eindsaldo` (closing balance), `Totaal nieuw saldo` / `Totaal betaald` (period totals). The adapter follows the stateful-adapter pattern (plan 02-03's Option B): after iteration, `IcsPdfAdapter::lastStatementSummary()` returns a `StatementSummaryData` that the `ImportPipeline` polls and writes via the existing `StatementSummary` Eloquent model. **Wave 0 reports the exact Dutch tokens and their text positions.** Schema: no migration — `statement_summaries` is already in place from plan 02-03; the `(user_id, import_run_id)` UNIQUE contract holds (one statement summary per import run).
- **D-52:** **Dutch-locale parsing helpers, no global locale state.** New classes `IcsAmountParser` and `IcsDateParser` under `Modules/Ingestion/Internal/Adapters/Ics/`, parallel to Phase 2's `AsnAmountParser` and `AsnDateParser` (plan 02-04). Both use explicit nl_NL formats — comma decimal (`€ 22,75` → `2275` minor units), space or period thousands separator, Dutch date format (`12-04-2026` and/or `12 apr 2026` with month abbreviations `jan feb mrt apr mei jun jul aug sep okt nov dec`). **No `setLocale()` global state mutation** — Larastan-strict + DI-only safe. Wave 0 reports the precise date and amount formats present; the helpers handle just those, new variants added when a new statement shape appears.
- **D-53:** **Page header/footer noise stripped by a first-pass regex before transaction iteration.** Multi-page statements repeat the cardholder name, masked card number, page-number footer (`Pagina X van Y`), and possibly a per-page issuer banner. The parser pipeline is: (1) read extracted *.txt; (2) strip known per-page noise via regex; (3) locate the transactions-table region by anchor token; (4) iterate transaction blocks per D-35's resolved shape; (5) extract statement-level fields per D-51. **Wave 0 reports the precise per-page noise patterns and the transactions-table anchor token.** Stored as constants on a new `IcsPdfExtractionMap` class (parallels Phase 2's `IcsCsvColumnMap` planned shape — except the constants are anchor strings and regex patterns instead of column indices).
- **D-54:** **Wizard validator and `HeaderSniffer` extended for PDF.** Three minimal changes: (1) `UploadWizard` validation rule `'file' => ['required', 'file', 'max:10240', 'mimes:csv,txt,xml,sta,mt940,940,pdf']` (adds `pdf`); (2) `HeaderSniffer` gains a `sniffIcsPdf()` arm that reads the first ~5 bytes of the upload and verifies the `%PDF-` magic; (3) wizard error copy updated to mention PDF when the declared format is `ics-pdf`. Existing 10 MB size cap stays (monthly statements are ~100 KB; 100× headroom). Single-file upload contract stays — multi-PDF backfill is deferred.
- **D-55:** **Idempotency uses the existing two-tier dedup — no PDF-hashing layer.** Tier 1 (file-level): the existing `import_runs.sha256` UNIQUE index already catches byte-identical re-uploads — the wizard's `RunImport` action hashes the uploaded file before kicking off ingestion (verified at `Modules/Import/Public/Actions/RunImport.php`). Re-uploading the same PDF skips before `pdftotext` even runs. Tier 2 (row-level): fingerprint v3 (`account_id, booked_at, amount_minor, currency, merchant_cleaned`) catches content-equivalent re-uploads (e.g., a re-exported PDF of the same period whose binary metadata differs but whose transactions are identical). `pdftotext -layout` is deterministic on identical input + same poppler version; even across poppler upgrades, fingerprint v3 normalises the merchant string before hashing so the canonical fingerprint stays stable. No extra hashing layer, no extracted-text caching layer.
- **D-56:** **`statement_summaries.extras` JSON captures masked card metadata for the future multi-card phase.** Per-statement, the adapter writes `extras: { "issuer": "Mastercard", "cardLast4": "1234", "cardholderName": "STRIPPED" }` (the real cardholder name is dropped at the anonymisation/redaction stage in Wave 0; in production it's also stripped at the adapter boundary so the DB never carries it). Phase 3 does NOT read this field — it's archive-only metadata, identical in spirit to Phase 2's `extras.multiStatement` flag (plan 02-04). When the multi-card phase arrives (deferred), it inherits a fully-populated card history without requiring re-import of every historical statement.

### Dual-Currency Display UX

- **D-44:** **Toggle scope = both global default + per-page override.** A new `default_currency_view` user-preference field (`'eur_only'` | `'original'`) is read from Settings as the default. The `/transactions` page surfaces a Flux segmented control that, when toggled, overrides the default via a `?currency=` URL query parameter (`?currency=eur` or no query for default). URL is the source of truth for the request; refresh-stable.
- **D-45:** **Ship a minimal `/settings` page in Phase 3.** Discharges Phase 1's deferred Settings UI question (D-19's "planner picks"). Surfaces: (a) `default_currency_view` toggle, (b) the existing `period_start_day` integer (migrated from install-only config to user-editable). Lives under `Modules/Core/Internal/Http/Livewire/SettingsPage.php`. Calm aesthetic per UI-05; one accent color.
- **D-46:** **Dashboard tiles respond to the toggle.** In EUR-only mode, `ThisPeriodAtAGlanceQuery` returns one set of in/out/net totals computed from `settled_amount_minor WHERE settled_currency = 'EUR'`. In original-currency mode, the query GROUPs BY currency and returns one tile-row per currency present in the period. EUR-only months collapse to a single row in original-currency view (visually identical to EUR-only view). The Blade view stacks tile-rows vertically.
- **D-47:** **Transaction rows render two-line stack when native ≠ settled in original-currency view.** Primary line: native (e.g. `$12.99 USD`). Secondary line in muted/`text-muted-foreground`: settled (`€12.07 EUR`). In EUR-only view, rows show only the settled amount on one line. The existing `TransactionListQuery`'s `?string $currency` projection (which already swaps `display_minor`/`display_currency` between native and settled) is consumed by the Blade view to drive both lines. For EUR-native rows in either view, only one line renders.
- **D-48 (Claude's discretion):** **FX-rate placement = transaction detail page only.** Success Criterion 2 requires the per-transaction FX rate to "surface when available". Inline on the list row adds visual density that conflicts with UI-05; tooltip-only hides information until hover. The transaction-detail drill-in page (post-Phase 1) is the natural home: it renders "Charged $12.99 USD · effective rate €0.929/USD · settled €12.07 EUR" alongside the existing detail fields. Planner may revisit if the user wants the rate more prominent.

### Established Patterns
- **DI-only** — no `auth()` / `Auth::user()` / global helpers / facades. The Larastan boundary rule + custom DI-enforcement rule (Phase 1) catch violations. The new `SettingsPage` Livewire component must inject `CurrentUser` and `DatabaseManager`, never `auth()`. The new `PdfTextExtractor` is injected into `IcsPdfAdapter` — never instantiated inside the adapter.
- **`Public/` vs `Internal/`** — `IcsPdfAdapter` and all its collaborators live under `Modules/Ingestion/Internal/Adapters/Ics/`. New DTOs / contracts that the Import module touches stay under `Public/`.
- **Lazy generators in adapters** — Even though the PDF extraction is eager (a single `pdftotext` call returns the full text), the parser-side iteration through transaction blocks remains a `Generator<int, SourceTransactionDto>`. Memory footprint is dominated by the extracted-text string (≤200 KB for a typical statement), not by the DTO stream.
- **Integer-cent arithmetic** — every amount stays on integer minor units. `brick/money` for any cross-currency or display arithmetic (Phase 3 finally exercises non-EUR `brick/money` calls). The `NoFloatMoneyArchTest` allow-list stays untouched.
- **Pest test layout** — adapter tests live next to the adapter (`Modules/Ingestion/tests/Unit/Adapters/Ics/IcsPdfAdapterTest.php`). Snapshot tests via `spatie/pest-plugin-snapshots` for the canonical-DTO stream from the redacted *.txt fixture. The integration test that actually exec's `pdftotext` against a synthetic PDF is tagged `@group integration` so CI hosts without poppler can `--exclude-group=integration`.
- **Idempotency in the UI** — preview wizard surfaces NEW / DUPLICATE / ERROR per row. ENRICHED (Phase 2's fourth state) is unreachable in Phase 3 (ICS ships one format), but the code path stays in place for later phases.

### Risks Phase 3 Specifically Owns
- **No real ICS PDF fixture yet.** Wave 0 must land the redacted *.txt fixture before adapter code is written. If the user's PDF reveals an extraction shape that contradicts D-34 / D-35 / D-40, the adapter plan revises accordingly (and CONTEXT.md gets a follow-up entry).

Wave 0's empirical examination is the mitigation; the alternative `-fixed N` flag (force a fixed character width per column) is the fallback if `-layout` fails.
- **`exec()` boundary requires careful Larastan typing.** `spatie/pdf-to-text` returns `string` but throws on binary-not-found / non-zero exit. The `PdfTextExtractor` wraps the call in a typed exception (`PdfExtractionFailed`) and surfaces it through the existing ingestion error path. No `mixed`-typed return values escape.
- **Two-step wizard picker is a UI refactor** — the Phase 1/2 single-dropdown surface is reshaped. Snapshot tests of the wizard need re-baselining. The planner explicitly carves a task for "regenerate wizard snapshots".
- **`ThisPeriodAtAGlanceQuery` group-by-currency mode is new work** — the current query has only one summation path. Adding a GROUP BY without breaking the existing EUR-only path needs an unit test for both modes.
- **`default_currency_view` user preference must round-trip through Settings page → DB → query → URL override** — four boundaries; planner adds a Pest feature test that exercises the full path.
- **`brew install poppler` is a real friction point on a fresh dev machine.** README needs a prominent setup note; the wizard surfaces a graceful error (rather than a Larastan exception trace) when `pdftotext` is missing.

<specifics>
## Specific Ideas

- **Fixture anonymisation is OUR responsibility, not the user's, AND happens on the extracted text rather than the PDF binary.** The user hands over a raw ICS PDF (which may include card numbers, cardholder name, real merchants/amounts). Wave 0 runs `pdftotext -layout` on it, then anonymises the resulting *.txt — card numbers → `****-****-****-XXXX`, cardholder name → `KAARTHOUDER`, any cross-referenceable identifiers randomised, but dates / amounts / currencies / merchant strings preserved verbatim so the parser is exercised against truth. This sidesteps PDF binary redaction entirely (CID fonts, watermarks, multi-page headers) and yields a trivially-diffable text fixture. The raw PDF stays under `local/ics/` (gitignored) on the user's machine only. This is the spiritual sibling of Phase 2's CAMT IBAN check-digit re-anonymisation (02-03's "Major Deviation") — same posture, different medium.
- **`fx_rate_used` is the effective post-markup rate.** Honest representation of what the user paid. The "market rate vs markup" split is rejected for v1 — the project is a personal finance tool, not an FX-cost auditor. Phase 9 drift detection can still spot a rising effective rate over time and flag it.
- **Dashboard tiles in original-currency mode collapse cleanly for EUR-only months.** A month with no foreign-currency transactions in original mode renders identically to EUR-only mode (single row). This is a feature: the toggle never adds visual clutter when there's nothing to disclose.
- **The Settings page is the long-deferred Phase 1 D-19 question now answered.** `period_start_day` moves from install-only into the page. Future phases can grow the page (e.g., Phase 6 OAuth credential management surface) without re-debating its existence.
- **Single ICS Account is a deliberate v1 choice.** The user has one card today. Multi-card support is a real future requirement but it depends on a fingerprint-tuple change (D-43's note → see deferred ideas). Don't ship that until card 2 actually arrives. D-56's `extras.cardLast4` archiving means whenever multi-card lands, the history is already there.
- **The two-tier idempotency dedup (file SHA + row fingerprint) is what makes the PDF extraction step safe to re-run.** No extra caching layer, no extracted-text persistence. `pdftotext` runs every time a NEW SHA hits the wizard; the row-level fingerprint catches duplicates regardless of whether the source was the same PDF or a re-export of the same period. This is the same shape Phase 2's cross-format CSV/CAMT dedup uses (different sources, same logical transactions) — Phase 3 just doesn't have the cross-format axis yet.
- **`spatie/pdf-to-text` is a tactical choice, not an architectural commitment.** If poppler ever becomes problematic, `PdfTextExtractor` is the only file that needs to change (swap to `smalot/pdfparser` or an inline shell-exec). The adapter operates on extracted text — completely decoupled from how the text was produced.

</specifics>

## Deferred Ideas

- **ICS CSV / Excel (.xlsx) ingestion** — the Mijn ICS consumer portal does not currently expose either; if a future portal change ships one, revisit. CSV would mirror `AsnCsvAdapter` (lazy `league/csv` Generator, ~half a day's work given the Phase 1/2 plumbing); Excel would add `phpoffice/phpspreadsheet`. Both would coexist alongside (not replace) the `IcsPdfAdapter` and engage the cross-format ENRICHED dedup path Phase 2 built — at which point ICS becomes the project's third format-pluralised source (alongside ASN's three).
- **Multi-PDF backfill via the wizard** — Phase 3 keeps single-file upload (one PDF per import_run). If the user accumulates a multi-year backlog and the per-PDF upload friction becomes a chore, add multi-select / zip-upload support in a later phase. The underlying ingestion pipeline already handles N independent imports cleanly via fingerprint v3 dedup; the deferral is purely a wizard UX call. Captured here so the multi-card phase or a "history-import" phase can pick it up.
- **`smalot/pdfparser` as a pure-PHP fallback** — D-31a chose `spatie/pdf-to-text` (poppler) for spatial-layout fidelity. If the `brew install poppler` prerequisite ever becomes a portability blocker (e.g., this project gets dockerised, or a non-macOS host enters the picture), `smalot/pdfparser` is the obvious swap — same `PdfTextExtractor` interface, different implementation. No architectural lock-in.
- **OCR / scanned-PDF support** — the Mijn ICS portal exports born-digital PDFs with a text layer; OCR is unnecessary. If a future source ships image-only PDFs (e.g., a paper-statement scan), add tesseract via an alternate `PdfTextExtractor` implementation. Heavy dependency; defer until proven needed.
- **Per-card visibility within one ICS contract** — Phase 3 ships single Account, no `card_last4` column on transactions. A future phase must (a) add `card_last4` (or `card_id`) to the transaction or to a `cards` subtable, (b) extend the v3 fingerprint tuple to include card identity (= v4 bump with re-derivation, like Phase 2 did v2→v3), (c) update the dashboard to optionally group totals by card. D-56 already archives `cardLast4` in `statement_summaries.extras` so the history is populated when this lands. **Landmine:** importing a second card under the current single-Account model BEFORE this work would cause two cards posting the same merchant+date+amount to falsely de-duplicate via the v3 fingerprint. Plan this before card 2 is added to ICS.
- **Splitting ICS FX markup as a separate fee row** — Phase 3 rolls markup into the same canonical row (D-40). If Phase 9 drift detection or a future "where is my money going" view wants to surface FX cost explicitly, revisit. The per-transaction extracted-text block in `rawPayload` (D-49) preserves the markup detail so retro-extraction is possible without re-import.
- **Market-rate-vs-effective-rate split (`fx_market_rate` + `fx_markup_basis_points` columns)** — explicitly rejected for v1. Adds two columns we'd populate from external rate APIs (privacy hit) for marginal user value.
- **PayPal Reporting API + USD-funded PayPal** — Phase 4, not Phase 3.
- **Chain-resolution use of ICS source_ref** — if Wave 0 confirms a stable per-transaction identifier in the extracted text (reframed D-34), Phase 5 can lean on it for PayPal → ICS chain joins. Captured here so the Phase 5 researcher knows to check.
- **Password-protected ICS PDFs** — Mijn ICS doesn't currently ship password-protected statements. If that changes, `pdftotext` accepts `-upw <password>` and the `PdfTextExtractor` interface would gain an optional password parameter (probably stored in `storage/app/secrets/ics.json` chmod-600 like the IMAP creds in PLT-05's pattern). Out of scope right now.
- **OFX / QIF export of multi-currency rows** — out of v1 scope entirely (REQUIREMENTS.md → v2 Deferred).
- **Per-currency budgets / spending limits** — out of scope; this is a visibility tool, not envelope budgeting.
- **Settings UI for `period_start_day`** — landing in Phase 3 (D-45) as a co-discharge of Phase 1 D-19's deferred decision. Future Settings extensions (notifications, OAuth credentials, etc.) build on the same page.
