16.1.1 with one coherent pass. It adds the missing PayPal connector step so
the wizard's funding-source coverage is complete (bank → PayPal → card →
email → first-import), lets the user expand any consolidated-preview section

## Implementation Decisions

### PayPal connector step (A-1)

- **D-01:** Wizard step order becomes
  `welcome → connect-bank → connect-paypal → connect-card → connect-email
  → first-import → done`. PayPal sits between bank and card — mirrors the
  chain-resolution mental model from Phase 5 (bank funds PayPal funds card).
  Update `Modules/Onboarding/Internal/Services/WizardStepRegistry::STEPS`
  + add `connect-paypal` to `SKIPPABLE`.
- **D-02:** Step accepts a **single PayPal Activity CSV** (not multi-file).
  Property is `?TemporaryUploadedFile $activityCsv` bound via
  `wire:model="activityCsv"` on a single-file `<input type="file">`. PayPal
  Activity Downloads cover a user-chosen date range so one export typically
  spans the wanted window; the standalone `/imports/upload` flow remains
  the path for additional CSVs later.
- **D-03:** The step previews the upload via `RunsImports::runFromUpload`
  with leaf format key `paypal-csv`, then stashes the resulting ImportRun id
  into `wizard_progress.data['paypal_import_run_id']` (single int, not an
  array). Mirrors the bank-step pattern (single int) rather than the
  card-step pattern (array).
- **D-04:** Auto-create the user's PayPal Account row on first successful
  preview, then re-preview from the stable stored path so the preview
  cache reflects the now-resolvable account. Same fix pattern 16.1.1 commit
  `0d7502f` applied to ICS — applied preemptively to PayPal to avoid the
  same "rows resolve against unknown account" regression. Synthetic IBAN
  literal is `PAYPAL` (already locked by `PreviewWizard::PAYPAL_OWN_IBAN`).
- **D-05:** The synthetic-account creation is extracted into a shared
  action `EnsurePaypalAccountAction` (or similar) under
  `Modules/Import/Public/Actions/`. Both `ConnectPaypalStep` and the
  existing `PreviewWizard` standalone flow call this action; the duplicated
  `Account::query()->create([...kind: 'paypal', iban: 'PAYPAL'...])` block
  in `PreviewWizard.php:347` is replaced with the action call. Constructor-
  DI'd, no facades, no global helpers — per memory `feedback_laravel_di_only`.
- **D-06:** `FirstImportStep::resolveStashedImportRunIds` (line 347) is
  extended to also read `paypal_import_run_id` from `wizard_progress.data`
  on the `connect-paypal` step row, alongside the existing bank + card
  reads. The `step_key` whereIn list adds `'connect-paypal'` and the
  ORDER BY case statement assigns it precedence 1.5 (between bank=1 and
  card=2) so preview sections render in the wizard's flow order.
- **D-07:** Step is skippable (matches the other three connector steps).
  If skipped, `wizard_progress.data['paypal_import_run_id']` is null and
  the FirstImportStep's PayPal section simply doesn't render. No empty-
  state UI required — the consolidated preview already only emits sections
  for sources with ImportRuns.
- **D-08:** Acceptance — drop a PayPal Activity Download CSV → preview
  section shows rows + Type-chip column; drop a PayPal Balance Reconciliation
  Report → friendly `UnsupportedPaypalCsvShapeException` toast (already
  shipped in 16.1.1-04; confirm the exception bubbles into the step's
  inline error band the same way ConnectCardStep handles per-file failures).

### Preview pagination (A-2)

- **D-09:** Per-section cursor pagination via "Load more (N remaining)"
  button at the bottom of each consolidated-preview section. The button
  text changes count each click; when N reaches 0 the button disappears
  and the footer reads `{totalRows} rows shown`. Single affordance — no
  "show all" shortcut, no global expand toggle.
- **D-10:** Chunk size is **25 rows per click**. Initial render still
  shows the SAMPLE_ROW_LIMIT = 5 sample (no change to the first paint);
  subsequent clicks add 25 rows each (5 → 30 → 55 → … → totalRows).
- **D-11:** FirstImportStep tracks expansion state in a public property
  `array<string,int> $expandedRowCount` keyed by `source_format` value
  ('asn-camt053', 'ics-pdf', 'paypal-csv', etc.). The Livewire action
  `loadMoreRows(string $sourceFormat): void` increments the per-section
  count by 25 (clamped to that section's totalRows) and re-runs
  `BuildConsolidatedPreviewQuery::build()`.
- **D-12:** `BuildConsolidatedPreviewQuery` accepts a per-section limit
  override via a new constructor parameter or build-method argument
  (e.g. `array<string,int> $sectionLimitOverrides`). When present,
  `array_slice($allRows, 0, $override)` replaces the
  `SAMPLE_ROW_LIMIT` slice for that section only. Sections without an
  override keep the default 5-row cap. The existing
  `SAMPLE_ROW_LIMIT = 5` constant stays as the default for first paint.
- **D-13:** Performance — re-running the full query on each "Load more"
  click is acceptable for typical statement sizes (≤500 rows total).
  The PreviewCache is already in-memory, so a re-run is sub-100ms.
  The query reads cached preview rows, not the database. If the user
  reports lag on huge statements later, the optimization is to memoize
  the resolved `$allRows` per ImportRun on the Livewire component for
  the lifetime of the page render.

### FirstImportStep visual polish (A-3 + A-4) — sketch-gated

- **D-14:** A-3 (starting-balance section tidy) and A-4 (preview body-
  block layout) are sketch-gated. The phase opens with one
  `/gsd:sketch first-import-step-layout` session that explores card
  geometry, eyebrow weight, sub-card-per-source vs single-frame,
  stacked vs two-column composition, and starting-balance card
  placement together — so the user judges composition, not just
  isolated cards.
- **D-15:** ConnectPaypalStep visuals are **not** in the sketch scope.
  The new connector step follows the existing visual contract from
  sketch 003 (winner: four-tile mini-step row + format chips +
  persistent drop zone in the same wizard card) — same atoms used by
  ConnectBankStep + ConnectCardStep. The PayPal step gets a
  `vd-glyph` glyph variant and a single `format-chip` "PayPal CSV"
  (no choice — PayPal exports only one format).
- **D-16:** The sketch's winning variant becomes the CSS contract for
  plans 03 (starting-balance polish) and 04 (preview body-block
  layout). The two CSS plans may merge into one if the sketch winner
  uses one composition (e.g. a single sub-card frame containing both
  the preview tables and the starting-balance cards) — planner's
  call once the sketch lands.
- **D-17:** No new theme tokens. The sketch must reuse the existing
  slate-50/100/200/700/900/950 token set from
  `sources/themes/default.css`; calm-slate Linear/Notion aesthetic
  established by sketch-findings-diederik is the design contract.

### Regression test gap-fill (B-1)

- **D-18:** Three Pest tests land in
  `Modules/Onboarding/tests/Feature/`:
  - `FirstImportStepCommitEverythingTest` — asserts `commit()` runs all
    `ConfirmImport` calls + `setStartingBalance` writes inside a single
    `DB::transaction`. Verify via a spy / transactional outbox check
    that the transaction depth never decrements between calls.
  - `FirstImportStepCommitRollbackTest` — asserts that if any single
    `ConfirmImport` throws inside `commit()`, the transaction rolls
    back all earlier writes (no half-committed transactions in DB,
    no half-applied starting balances, wizard stays on FirstImportStep
    with the inline error band populated).
  - `FirstImportStepStaleFilterTest` — asserts stale
    `card_import_run_ids` (orphaned by a re-upload, or older than
    `STALE_WINDOW_DAYS`) are filtered out of the commit list before
    `ConfirmImport` is called. Mirrors the boundary rule documented
    in `BuildConsolidatedPreviewQuery` lines 26–37.
- **D-19:** Tests use real DB transactions (no `Mockery`-style
  transaction spies). Per memory `feedback_no_mocking_db` (16.1
  D-?): integration tests hit a real database. Same Pest scaffold
  pattern as the existing
  `Modules/Onboarding/tests/Feature/FirstImportStepWidthTest.php`.
- **D-20:** The underlying `commit()` logic already exists at
  `FirstImportStep.php:229–238` — these tests are pure regression
  coverage, not behavior gaps. No production code change in this
  plan beyond what may surface as a refactor-for-testability concession
  (e.g. extracting a thin commit helper if the current Livewire
  internals don't admit clean assertions).

### Phase shape

- **D-21:** Phase 16.1.2 is one merge boundary containing one sketch
  session + five plans. The sketch runs first (blocking the visual-
  polish plans 03 + 04); PayPal step (01), pagination (02), and
  regression tests (05) can begin in parallel waves while the sketch
  is being processed. Final wave ordering is planner's call based on
  file-overlap on `FirstImportStep.php` + the shared
  `resources/css/app.css`.

### Claude's Discretion

- Exact namespace for `EnsurePaypalAccountAction` — `Modules/Import/
  Public/Actions/` is the natural home (import-time concern, single-
  responsibility action class), but `Modules/Ledger/Public/Actions/`
  is defensible (the action creates a Ledger `Account` row).
  Planner picks based on module-boundary rules already in arch
  tests; either passes the constructor-DI rule.
- Whether `BuildConsolidatedPreviewQuery::build()` grows a new
  parameter or a fluent
  `->withSectionLimits(array $overrides)->build()` shape — planner's
  call. The DTO contract (`ConsolidatedPreviewBatch` /
  `ConsolidatedPreviewSection`) does not change.
- Whether the "Load more" button copy reads
  "Load more (132 remaining)" exactly, or includes "rows"
  ("Load 25 more rows (132 remaining)"). Sketch may tighten or
  loosen this; the locked behavior is the 25-row chunk + N-remaining
  affordance, not the literal copy.
- Whether the regression tests sit in
  `Modules/Onboarding/tests/Feature/` or `Modules/Onboarding/
  tests/Integration/` (the repo currently uses Feature for
  Livewire-against-real-DB tests; planner confirms).
- Whether the sketch session also produces an ASCII / Mermaid
  composition diagram that lives next to the sketch HTML — useful
  for planner's CSS plan, not required.

<specifics>
## Specific Ideas

- **"Load more (N remaining)" copy is minimal.** No "rows", no "show all" shortcut, no global toggle. Per UAT principle: a finance app should not bury the user under affordances.
- **PayPal step is single-file by design.** PayPal Activity Downloads cover an arbitrary user-chosen date range, so one export almost always spans the wanted window. The standalone `/imports/upload` flow remains the path for "I forgot a year" follow-ups. Multi-file is a deferred enhancement, not a missing requirement.
- **Sketch session covers FirstImportStep page composition, not isolated cards.** The whole reason the handover flagged A-3 and A-4 separately is that the user can't articulate the issue without seeing variants. The sketch produces 3-4 variants of the whole page (eyebrow weight + sub-card vs single-frame + starting-balance card placement) — user picks one.
- **ConnectPaypalStep glyph + format chip.** The new step gets a `paypal` variant in `vd-glyph` (a PayPal "P" or wallet glyph) and one disabled-by-default chip in the format-chip atom labeled "PayPal CSV" — the user doesn't pick a format, they just drop the CSV. Mirrors the ICS single-format step.
- **No new theme tokens.** The sketch must produce a winning variant that lives entirely within the existing slate-50/100/200/700/900/950 token set. Calm-slate Linear/Notion aesthetic stays the design contract.
