# Phase 16.1.2 Plan 02: PayPal connector wizard step + FirstImportStep stash read Summary

**Shipped the missing PayPal connector wizard step (step 3): a Livewire component that accepts a single PayPal Activity Download CSV, previews it via the shared `RunsImports` pipeline, idempotently auto-creates the synthetic PAYPAL account via the cross-module `EnsurePaypalAccountAction` (Plan 01), and stashes the resulting ImportRun id into `wizard_progress.data['paypal_import_run_id']` (single int) — extended `FirstImportStep::resolveStashedImportRunIds` to read that key alongside the existing bank + card ids and ranked the ORDER BY so preview sections render bank → PayPal → card → email in the wizard's flow order.**

WizardProgressInitializer auto-seeds a `connect-paypal` row per new user from the next signup.

Submit calls `RunsImports::runFromUpload('paypal-csv', ...)`, then `EnsurePaypalAccountAction` (returns true on real INSERT), re-previews from the stored path when the action created a row, and finally upserts `paypal_import_run_id` into `wizard_progress.data` as a single int. ## Decisions Made

- **Method-DI on every collaborator inside `submit()` (no constructor DI on the Component subclass).** Livewire forbids constructor DI on `Component` subclasses; ConnectBankStep + ConnectCardStep already document this in their class-level PHPDoc and the same rule applies here. Per project memory `feedback_laravel_di_only`.
- **Single-file `?TemporaryUploadedFile` (not `array<TemporaryUploadedFile>`) — mirrors the bank-step, not the card-step.** PayPal exports one Activity CSV per user-chosen date range, so the single-file shape matches reality; the standalone `/imports/upload` flow remains the path for "I forgot a year" follow-ups.
- **Stash as a single int (`paypal_import_run_id`), not an array (`paypal_import_run_ids`) — mirrors the bank-step single-int pattern.** Same rationale as above: one CSV per user-chosen range means one ImportRun per step submission.
- **Re-preview after auto-create only when `EnsurePaypalAccountAction` returns true.** The action returns false when the PayPal account already exists; in that branch the re-preview pass would be wasted work because the original preview already resolved every row against the existing account. Mirrors ConnectBankStep's `if ($created > 0)` guard.
- **No new atomic primitives.** The connector-step contract from sketch 003 (winner: four-tile mini-step row + format chips + persistent drop zone) already covers PayPal's needs — `mini-step` + `format-chip` + `drop-zone` + `wiz-actions` ship as-is. Per CONTEXT.md D-15.

## Issues Encountered

- **Worktree vendor symlink + Pest path resolution (recurrence of the issue Plan 01 documented).** The worktree initially had no `vendor/`. Built a hybrid vendor: most package dirs symlinked to the main repo's `vendor/` for read-only collaborators (laravel/livewire/spatie/etc), but `vendor/composer/` and `vendor/pestphp/` are real local copies, `vendor/bin/{pest,pint,phpstan}` are real local files (so `__DIR__` resolves inside the worktree), and `vendor/autoload.php` is a worktree-local file that uses a renamed `ComposerAutoloaderInit${SUFFIX}` class (to avoid the redeclaration error from the main repo's autoload also being loaded by phpstan's parallel workers). Resolved the Plan-01 mode of "Call to a member function connection() on null" — pest now boots with the worktree's `tests/Pest.php` `pest()->extend(TestCase::class)->use(RefreshDatabase::class)->in('Feature')` binding. No production code lives in the worktree's `vendor/`; the artifact is local-execution-only.
- **PHPStan parallel-worker memory exhaustion.** Even with `--memory-limit=4G` passed, PHPStan's parallel workers spawn `php` without `-d memory_limit=4G` set, so the workers OOM at 128 MB (the default `php.ini` limit). Worked around by invoking with `php -d memory_limit=4G vendor/bin/phpstan analyse --no-progress --memory-limit=4G --debug ...` — `--debug` forces single-process and bypasses the parallel worker.
- **Pre-existing Vite-manifest failures in the wider Import Feature suite.** Five tests in `Modules/Import/tests/Feature/` fail with `ViteManifestNotFoundException` (AliasesSettingsPageTest, PreviewWizardTest, UploadWizardPaypalTest, UploadWizardTest, plus one more). These all do a full HTTP GET that renders the app layout's `@vite(...)` directive; the worktree has no built JS assets. Verified the failures predate this plan (Plan 01's deferred-items.md already documented them). Out of scope per the SCOPE BOUNDARY rule.
