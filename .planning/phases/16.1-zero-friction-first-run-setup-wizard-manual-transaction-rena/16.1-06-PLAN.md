<objective>
Surface OAuth re-consent failures (token expiry / revocation / consent withdrawal) in the existing `SystemAlertsBanner` so the non-technical user sees a calm "Reconnect your Gmail" prompt instead of silent inbox-scan stalls. No new banner component, no inline re-consent flow — detection wiring + a new alert kind + a query-param hand-off to the existing `OAuthClientWizardModal`. This plan inherits the SystemAlertsBanner pattern established for the system_alerts table; no new UI primitive is introduced.

Moved to Wave 3 (depends on Plan 03a) so Plan 03b's wizard email step — which mounts OAuthClientWizardModal and dispatches `oauth-client-wizard:open` with only the provider arg — lands BEFORE this plan extends the modal's open() signature with `?int $inboxId = null`. The new argument has a default so the wizard call-site continues to work after this plan ships.

Purpose: D-18 / D-19 / D-20 + OAUTH-RC-01 / OAUTH-RC-02 / OAUTH-RC-03. The background inbox scanner hits token failures periodically (tokens expire after 1h, refresh tokens can be revoked by the user in Google/Microsoft account settings). Without surfacing the failure the user is silently stuck — receipt ingestion stops and they don't know why. This plan adds the smallest possible detection-to-recovery wiring: typed exception → listener → existing banner → existing modal.

Output: ReconsentRequiredException sentinel; InboxTokenFailed event payload; RaiseReconsentAlertOnTokenFailure listener with dedup; GmailApiClient + GraphApiClient extended with provider-specific exception catches; system-alert-message blade extended with the new kind branch; InboxesPage extended with the `?reconnect` query param hand-off; OAuthClientWizardModal accepts optional inboxId; OAUTH-RC-01/02/03 tests green.
</objective>
