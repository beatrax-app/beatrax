# Phase 16.1: Zero-friction first-run setup wizard, manual transaction renaming, payment-type classification (PIN vs online vs transfer vs direct-debit), and crowd-sourced merchant identification corpus — Context

**Gathered:** 2026-05-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 16.1 ships four user-facing capabilities as one vertical MVP, all
gated to first-launch + everyday use of the bundled NativePHP app:

1. **First-run setup wizard** at `/setup` — guided onboarding through
   signup → welcome → connect bank (ASN) → connect credit card (ICS PDF)
   → optional email (Gmail / MS Graph OAuth) → first import preview
   → done. Skippable per step. Resumable across app restarts. Designed
   for non-technical users (no IBAN/SEPA/Laravel jargon without
   explanation).
2. **Manual rename of fallback-description rows** on the import
   preview — italic-fallback names are themselves the click target;
   popover with "Remember for future imports" learning-rule seeding.
3. **Payment-type classification** — new `transactions.payment_type`
   enum field (7 values: `pin`, `online`, `transfer`, `direct_debit`,
   `cash`, `fee`, `refund`, plus implicit `unknown` fallback).
   Classifier runs as a shared post-parse pipeline stage so every
   ingestion path produces the same field. Surfaces as a leading Type
   column chip on the import preview + `/transactions` list.
4. **Crowd-sourced merchant identification corpus** — in-repo YAML
   file (`resources/corpus/merchant-mappings.yaml`) bundled at app
   build time. Three-layer surface: Triage row CTA (primary entry) +
   `/community/mystery-merchants` browse destination + `Settings →
   Shared merchant list` toggles. Single suggest-mapping modal whose
   "Submit" opens a pre-filled GitHub Compare URL in the system
   browser (no GitHub-App backend in this phase).

Out of scope for this phase: real diederik-bot / GitHub-App
infrastructure, live corpus fetching from GitHub (relies on Phase 18
Auto-Update Plumbing for snapshot refresh), receipt-image OCR,
multi-language wizard copy.

</domain>

<decisions>
## Implementation Decisions

### Wizard state & resume
- **D-01:** New dedicated `wizard_progress` table (per-user) — schema
  shape: `(id, user_id, step_key, status [pending|done|skipped|in_progress],
  data jsonb, completed_at)`. One row per (user_id, step_key). Survives
  app restarts. Cleaner than a JSON column on `users` (single-
  responsibility); not session-only (non-technical user closes laptop).
- **D-02:** Resume behavior on relaunch — drop the user back into the
  step they were on, with a small "Welcome back — let's pick up where
  you left off" banner. Banner has a quiet "Skip the rest" dismiss
  option that marks remaining steps as `skipped` and routes to
  dashboard.
- **D-03:** First-launch detection — the existing
  `EnsureDatabaseReady` middleware (Phase 16) already redirects fresh
  installs to `desktop.welcome`. After signup completes (User #1
  created + `UserInstalled` fires via the fix in commit `529fd7a`),
  the wizard initializes `wizard_progress` rows for every step and
  routes to `/setup` instead of `/`.
- **D-04:** Skip routes — every skippable step has an in-app surface
  to come back to later (Connect bank → `/imports/upload`; Connect
  card → `/imports/upload`; Email → existing `/inboxes`). The wizard
  itself is also re-runnable from `Settings → First-run tour`.

### Payment-type field & classifier
- **D-05:** New `transactions.payment_type` enum column. Values:
  `pin`, `online`, `transfer`, `direct_debit`, `cash`, `fee`,
  `refund`, with `unknown` as the safe fallback when classification
  is indeterminate. Migration backfills `unknown` for all existing
  rows (a follow-up reclassification pass can run idempotently).
- **D-06:** Classifier lives in `Modules/Import/Internal/Pipeline/
  Stages/PaymentTypeClassifierStage.php` — runs after parsing,
  before fingerprint. Single shared stage; per-source parsers feed
  it normalized **hints** (CAMT.053 `BkTxCd` codes, ASN-CSV
  description keywords like `Betaalautomaat` / `iDEAL` / `Incasso`,
  PayPal CSV event types, ICS PDF transaction-type codes). The
  shared stage decides the final value from the union of hints +
  fallback heuristics on the canonical description text. Keeps
  classification logic in one place — easy to fix for every source
  at once.
- **D-07:** Source-specific hint contributors live next to their
  parsers (e.g. `Modules/Import/Internal/Parsers/Asn/
  AsnCsvPaymentTypeHinter.php`), implement a `PaymentTypeHinter`
  contract exposed from `Modules/Import/Public/Contracts/`. The
  classifier collects all hinters via service-container tagging
  (no global registry).

### Manual rename + alias learning
- **D-08:** New `merchant_aliases` table — per-user `(id, user_id,
  pattern, generalized_pattern, friendly_name, created_at)`. The
  `pattern` is the exact raw description first seen; the
  `generalized_pattern` is the auto-generalized variant (see D-10).
  Consulted at preview/render time only; does NOT mutate the stored
  `Transaction.description`.
- **D-09:** Name and category are stored separately. The rename
  popover's optional category hint, if set, additionally seeds a
  Categorization rule (existing `Modules/Categorization/Public/
  Services/RuleRecorder` or its equivalent). Aliases live in
  `Modules/Import/` (or a new `Modules/MerchantAliases/` if the
  module count makes sense — researcher decides); rules continue to
  live in `Modules/Categorization/`.
- **D-10:** Smart auto-generalize on save — when the user accepts
  the rename, run a `PatternGeneralizer` heuristic that strips
  trailing terminal IDs (`7438`), trailing digit runs in PIN-row
  shapes (`BCK*SHELL PIETER NIEUW *0123` → `BCK*SHELL PIETER NIEUW`),
  and known noise tokens. The popover renders the resulting
  generalized pattern as a preview line beneath the "Remember for
  future imports" checkbox: *"This will also rename future merchants
  matching `BCK*SHELL PIETER NIEUW*`."* User can override the
  generalized pattern inline before saving.
- **D-11:** Alias precedence at render time — if both `pattern`
  (exact) and `generalized_pattern` (fuzzy) match for a row, the
  exact-pattern alias wins. Prevents accidental over-matching when
  the user has both a specific and a generalized rename for the same
  merchant.

### Crowd corpus
- **D-12:** Corpus file location — `resources/corpus/merchant-
  mappings.yaml`. Bundled with the app at build time; snapshot
  refresh happens via the app-update mechanism (Phase 18 Auto-Update
  Plumbing). No live network fetch on launch — preserves the
  local-only privacy posture.
- **D-13:** Corpus schema — every entry is `{ pattern: string,
  name: string, category?: string, region?: string, contributor:
  "diederik-bot" }`. `category` and `region` are optional. Pattern
  matching uses the same `PatternGeneralizer` shape as D-10 so
  user-contributed mappings behave identically to local aliases.
- **D-14:** Corpus auto-seed on install — a
  `SeedCommunityCorpus` listener fires on `UserInstalled` (alongside
  the existing `SeedDefaultCategoryTree` listener). It loads the
  bundled YAML and writes corpus rows into a new
  `community_merchant_mappings` table (global rows, `user_id IS
  NULL`). Idempotent — re-running on an existing install upserts
  by pattern, never duplicates.
- **D-15:** Render-time precedence (extends D-11) — for a row, the
  resolution order is: (a) user's exact `merchant_alias`, (b) user's
  generalized `merchant_alias`, (c) community-corpus exact pattern,
  (d) community-corpus generalized pattern, (e) raw description
  fallback (italic muted, click-to-rename). Aliases the user
  contributes back to the corpus override their own local-only
  versions silently on next snapshot refresh.
- **D-16:** Submission flow — the "Submit as draft PR" button in the
  suggest-mapping modal does NOT submit to a GitHub App in this
  phase. Instead it opens the system browser to a pre-filled GitHub
  Compare URL of the form `https://github.com/nightworksio/beatrax/
  compare/main...{branch}?expand=1&body={url-encoded-yaml-entry}`.
  The user manually completes the PR creation in GitHub. The modal
  copy is updated to set this expectation honestly ("Opens GitHub
  in your browser so you can submit the suggestion").
- **D-17:** Settings toggles (sketch 005 variant C) — only D-15's
  "Use the shared merchant list" toggle is meaningful in this phase
  (turns corpus matching on/off). The "Offer to contribute"
  toggle ships and controls whether the Triage row CTA appears.
  The "Update the shared list on app updates" toggle is a no-op
  control surface in 16.1 (no live update mechanism); ship it
  disabled with a small inline note "Activates with the next app
  update — diederik 1.2+". (Researcher: confirm with Phase 18
  timing.)

### Claude's Discretion
- Default category-tree changes (the existing `DefaultCategoryTreeSeeder`)
  are not modified in this phase. Adding categories suggested by the
  community corpus (e.g. if a corpus entry references a new top-level
  category) — researcher decides whether to auto-create or skip with
  a warning.
- The pre-discovered-category auto-suggest on the first import
  (sketch 004D's "Auto-suggested" chip state) comes from the union
  of: (a) existing Categorization rules (none on fresh install), (b)
  the bundled community corpus's `category` hints, (c) a small set of
  built-in heuristics for very common Dutch merchants ("Albert Heijn"
  → Groceries, "Spotify" → Subscriptions, "Vattenfall" → Utilities).
  Heuristic source list is researcher discretion.
- Wizard step copy tone and exact phrasing — locked to UI-SPEC
  §Copywriting; planner does not re-deliberate.

</decisions>

## Existing Code Insights

### Reusable Assets
- **`SignupAction` → `UserInstalled` dispatch** (Phase 16 commit `529fd7a`): wizard initialization hooks into the same lifecycle event the category seeder already uses. No need for a new "first-launch detected" signal.
- **`OAuthClientWizardModal` (EmailScan)**: the email step in the new setup wizard hosts this modal directly. Researcher confirms whether to embed the existing modal as-is or wrap with a thin wizard-aware adapter that handles the "next step" hand-off on success.
- **`FingerprintStage` (Import pipeline)**: precedent for a post-parse shared stage. `PaymentTypeClassifierStage` (D-06) mirrors its structure.
- **`PreviewRowDto.description` fallback** (Phase 16 commit `442f139`): already in place; this phase adds the click-italic rename behavior on top, plus the resolved `aliasFriendlyName` field for both user aliases and corpus matches.
- **`SeedDefaultCategoryTree` listener pattern**: `SeedCommunityCorpus` (D-14) mirrors structure — idempotent `updateOrCreate` against a `community_merchant_mappings` table with `user_id IS NULL`.
- **`DefaultCategoryTreeSeeder`**: existing global default categories; the corpus's `category` hints map to these names. If a hint doesn't match an existing category, researcher decides skip-with-warning vs auto-create (D-12 / Claude's discretion).
- **Tailwind v4 `@source` directive** (Phase 16.1 batch commit `ea9f885`): Flux vendor stubs are already scanned. New chip classes for `fee` and `refund` will pick up dark-mode utilities automatically.
- **Existing `audit-log-page.blade.php` truncate + copy pattern**: layout precedent for `/community/mystery-merchants` page (per-card actions, footer counter).

### Established Patterns
- **Constructor DI only** — every new service (`PatternGeneralizer`, `PaymentTypeClassifierStage`, `PaymentTypeHinter`s, `SeedCommunityCorpus`, wizard step controllers, alias resolver) wires through constructor. No facades, no `event()` helper, no `auth()` — `CurrentUser` contract for authenticated context.
- **Module Public/Internal split (nwidart-laravel-modules)** — services exposed via `Public/Services/` or `Public/Actions/`; routes / Livewire / parsers stay `Internal/`. New stage contributions follow `Public/Contracts/PaymentTypeHinter.php` exposed surface.
- **Service-container tagging for plugin discovery** — used by Categorization to collect rule evaluators; mirror for `PaymentTypeHinter` collection so per-source hinters register themselves without a global registry.
- **Idempotent seeding** — `updateOrCreate(['slug' => …, 'user_id' => null])` pattern from `DefaultCategoryTreeSeeder`. Reuse for community corpus seeder.
- **Pipeline stage composition (`ImportPipeline`)** — explicit ordered chain; new stage inserted between parsing and fingerprinting.
- **Pest feature tests against Livewire components** — precedent in Phase 16 (`AuditLogPage`, `InboxesPage`, `UploadWizard`); the wizard pages and the new preview affordances follow the same test shape.
- **Larastan L10 strict + Pint + Pest as hard CI gates** — non-negotiable on every commit.

### Integration Points

<specifics>
## Specific Ideas

- The wizard's three "what's coming" rows on the welcome step are
  literal emoji glyphs (🏦 / 💳 / ✉️) per sketch 002D. Treat as the
  spec, not as placeholders. If a real icon set is sourced before
  execution, that's a Phase 19 brand-asset concern.
- The "remember for future imports" copy on the rename popover should
  render the generalized pattern preview line (D-10) so the user sees
  *what they're agreeing to* before saving. The popover gets one
  extra line below the checkbox.
- "diederik" → "beatrax" rename (Phase 16 commit cohort) is canonical;
  all new code, copy, route names, command names, table names use
  `beatrax` even though the project repo and the user-facing brand
  retain `diederik` in some places per the migration plan.
- The GitHub Compare URL in D-16 targets `nightworksio/beatrax`
  (the private repo we just configured). If the repo flips to a
  public release repo (Phase 19 boundary), the URL's base needs to
  update; planner notes this as a config-resolved value, not a
  hardcoded string.

</specifics>

<deferred>
## Deferred Ideas

- **Real `diederik-bot` GitHub App with draft-PR submission and
  anonymous-by-default contributor flow.** Captured as a follow-up
  to Phase 16.1; revisit after Phase 19 (Public Release Boundary) so
  the GitHub App can be set up on the public repo. Architecture note:
  the bot needs server-side OAuth + webhook handling + a write token
  in a managed account. Out of scope for a local-only single-user
  desktop release.
- **Live corpus fetch on app launch / scheduled refresh.** Naturally
  folds into Phase 18 Auto-Update Plumbing — when the auto-updater
  pulls a new diederik release, the bundled corpus snapshot updates
  with it. No separate "fetch corpus" infrastructure.
- **Generalized merchant pattern editor as a power-user surface.**
  Right now the user gets a preview of the generalized pattern but
  can only edit it inline at rename time. A future "Aliases" settings
  page lets the user audit and edit their accumulated aliases.
- **Per-step OAuth re-consent prompts.** If the user revokes Gmail
  access after the wizard, the email step ideally re-runs from
  Settings, not from the wizard. Out of scope for 16.1.
- **Receipt-image OCR / Apple Wallet receipt scanning.** Out-of-scope
  from PROJECT.md, not introduced here.
- **Multi-language wizard copy (NL / DE / etc.).** All copy is English
  in 16.1; localization is its own future phase.
- **Receipt-amount-aware payment-type heuristics.** The classifier in
  D-06 uses description + source-provided hints; using amount
  patterns ("this looks like a typical PIN amount") is a refinement
  for a future tuning phase, not 16.1.

</deferred>
