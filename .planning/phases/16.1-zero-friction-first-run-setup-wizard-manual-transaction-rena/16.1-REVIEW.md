# Phase 16.1 — Code Review

**Reviewed:** 2026-05-25T16:20:29Z

## Summary

The phase ships six bounded surfaces — the onboarding wizard, manual rename popover, payment-type classifier, crowd corpus, OAuth re-consent banner, and Settings → Aliases editor — with strong cross-user isolation discipline, mostly clean constructor-DI compliance, and a defensible SSRF posture for the GitHub Compare browser launch and the Graph client. Security primitives that matter (URL allow-list, host check, BelongsToUser global scope, YAML parsing with `PARSE_EXCEPTION_ON_INVALID_TYPE`, paired SQLite triggers for the new enum) are in place and tested.

The headline regression is one functional break: the `SuggestMappingModal` is documented as a globally-mounted component but is only mounted inside the dedicated mystery-merchants page view. The Triage row's `Help others identify this` CTA (CORPUS-05) and the Settings → Shared list "Browse mystery merchants" entry will dispatch `suggest-mapping:open` into a layout with no listener present — the modal never opens. The unit test covers that the event is dispatched, but no integration test covers that a listener exists on the relevant page chrome.

The remaining findings are GSD-leakage in production source, temporal language in PHPDocs, brand drift in three onboarding views (Plan 03a/03b — already documented in deferred-items.md and excluded), a couple of robustness gaps in the OAuth banner-and-callback flow, one DI-rule grey area (`Illuminate\Support\Facades\Route` in Onboarding/Community routes — acceptable Laravel convention but inconsistent with rule C-1's letter), and a handful of testing gaps and code-quality observations.

## Critical Issues

### CR-01: SuggestMappingModal is not mounted in the global app layout — Triage CTA cannot open the modal

**File:** `resources/views/layouts/app.blade.php:127-148` (missing mount); `Modules/Community/Internal/Http/Livewire/SuggestMappingModal.php:19-25` (docblock contradicts reality); `Modules/Categorization/Resources/views/livewire/triage-inbox.blade.php:88` (button); `Modules/Community/Resources/views/mystery-merchants.blade.php:7` (only mount site)
**Category:** bug
**Issue:** `HelpOthersTriageButton::clicked()` dispatches `suggest-mapping:open`, and `SuggestMappingModal` listens for that event via `#[On('suggest-mapping:open')]`. The modal's docblock states "Mounted once at the layout level so the `suggest-mapping:open` Livewire event can open the modal from anywhere — the Triage row CTA, the `/community/mystery-merchants` card, and the Settings → Shared list 'Browse mystery merchants' button all dispatch the same event." In reality the modal is mounted only inside `Modules/Community/Resources/views/mystery-merchants.blade.php` (line 7). The global `resources/views/layouts/app.blade.php` does not include `@livewire('community.suggest-mapping-modal')`. As a result, when a user on `/uncategorized` (the triage page) clicks the Help-others CTA, the dispatched event has no listener in the DOM and the modal silently fails to open. `TriageHelpOthersCtaTest` only proves the button dispatches the event — it never verifies the modal can consume it on the triage page. CORPUS-05 is functionally broken in production while green in tests.
**Fix:** Mount the modal once in the authenticated section of `resources/views/layouts/app.blade.php` alongside the other globally-mounted modals (`rule-form-modal`, `correction-divergence-toast`, `receipt-conflict-toast`), e.g. add `@livewire('community.suggest-mapping-modal')` inside the `@auth` block. Add a feature test that mounts the triage page, clicks the CTA, and asserts the modal becomes visible — not just that the event was dispatched.
**Fixable:** yes

### WR-02: `oauth_canceled` session flash is consumed via `session->pull()` but `open_backfill_modal` is read via `has()`/`get()` — repeated wire:poll renders re-fire the modal

**File:** `Modules/EmailScan/Internal/Http/Livewire/InboxesPage.php:98-110`
**Category:** bug
**Issue:** The `mount()` method handles the post-OAuth-callback flash inconsistently: `oauth_canceled` and `oauth_failed` are pulled with `session()->pull()` (single-use), but `open_backfill_modal` is read with `$session->has(...)` + `$session->get(...)` and never cleared. On a Livewire `wire:poll` re-mount or a back-button revisit during the same session, the modal-open dispatch fires repeatedly. **Fix:** Switch `$session->has('open_backfill_modal')` + `$session->get('open_backfill_modal')` to `$session->pull('open_backfill_modal')` so the value clears after the first read, matching the pull-pattern already used for the two error flashes.
**Fixable:** yes

### WR-03: `MergeMerchantAliases` JSON-encode failure aborts the transaction with `JsonException` — surface is a 500, not a calm flash

**File:** `Modules/Import/Public/Actions/MergeMerchantAliases.php:125`
**Category:** bug
**Issue:** The action calls `json_encode($mergedFrom, JSON_THROW_ON_ERROR)` inside the transaction closure. If any absorbed-row pattern contains an invalid UTF-8 byte sequence (possible since `pattern` is raw bank-statement text), the encode throws `JsonException`, aborts the transaction, and propagates to `AliasesSettingsPage::confirmMerge` where the generic `catch (Throwable)` swallows it. The user sees `Merge failed (JsonException).` but the wrapping `try/catch` does NOT clear `$showMergeModal`. The error happens before the dialog state can be reset because `confirmMerge`'s state reset runs AFTER the `($merge)(...)` call.
**Fix:** Either pre-validate the patterns with `json_encode($mergedFrom)` (returning false on bad UTF-8) and surface a clear error before opening the transaction, OR strip non-UTF-8 bytes before storing into `merged_from`. Also, in `AliasesSettingsPage::confirmMerge`'s `catch (Throwable)` branch, set `$this->showMergeModal = false;` before returning so the dialog doesn't linger after a failure.
**Fixable:** yes

### WR-08: `SeedCommunityCorpus::handle()` re-stamps `created_at` on every re-dispatch — provenance is lost

**File:** `Modules/Community/Internal/Listeners/SeedCommunityCorpus.php:66`
**Category:** bug
**Issue:** The `updateOrInsert` payload includes `'created_at' => $now` on the UPDATE branch, so every re-dispatch of `UserInstalled` (which the install command can re-emit) overwrites the original row creation timestamp with the current time. ### WR-09: `MerchantAlias` Eloquent model carries `BelongsToUser` global scope BUT every query in production explicitly `where('user_id', ...)` — confirms the scope is not load-bearing and may not bind correctly under all paths

**File:** `Modules/Import/Models/MerchantAlias.php:38`; `Modules/Import/Public/Services/MerchantNameResolver.php:81-96`; `Modules/Import/Internal/Http/Livewire/AliasesSettingsPage.php:212-219, 303-310, 374-383, 635-642`
**Category:** security
**Issue:** `MerchantAlias` uses `BelongsToUser` so reads through the Eloquent surface auto-scope by current user. Every production query in scope, however, uses the raw `DatabaseManager` query builder via `$this->db->connection()->table('merchant_aliases')` — which bypasses Eloquent and the global scope entirely. The author defended this elsewhere as "rule against `staticMethod.dynamicCall` from phpstan-strict-rules" but the net effect is that the BelongsToUser scope is unreachable on every preview / list / save / delete / merge / YAML path. The current code is safe because each call also carries an explicit `->where('user_id', $userId)`, but: (1) the apparent defence-in-depth ("scope + explicit filter") is only one layer, not two; (2) a future contributor adding a new merchant_aliases query who forgets the explicit `where('user_id')` will silently leak cross-user data. The defensive narrative is misleading.
**Fix:** Either (a) remove the `BelongsToUser` trait from `MerchantAlias` and document that every query must carry an explicit `user_id` filter (consistent with current practice), or (b) keep the trait AND route every read through the Eloquent surface to actually exercise it. Add an arch invariant scanning `Modules/Import` and any other consumer for raw `->table('merchant_aliases')` calls that lack a `->where('user_id'` clause within the same statement chain.

### WR-10: `AliasYamlImporter::diff()` returns `unchanged` based on `existing_name` (friendly_name) equality only — ignores `generalized_pattern` drift

**File:** `Modules/Import/Internal/Services/AliasYamlImporter.php:151-170`
**Category:** bug
**Issue:** The diff classifies each parsed entry against the user's `existing_name` only. If the user's existing alias has the same `friendly_name` but a DIFFERENT `generalized_pattern` than the uploaded YAML, `diff()` returns it as `unchanged` and `apply()` never writes the YAML's generalized pattern back. **Issue:** The LIKE-fallback shape is `'%"inbox_id":'.$inboxId.'%'`. The needle is anchored on the literal `"inbox_id":` prefix but NOT on a trailing boundary character (closing `}` or `,`). For `inbox_id=1`, the needle `%"inbox_id":1%` matches the JSON serialization of `inbox_id=1`, `inbox_id=10`, `inbox_id=11`, `inbox_id=123`. The same comment block notes this risk in `PreviewWizard.php:81-89` ("user_id=1 would falsely match user_id=11"), but the EmailScan LIKE-fallback re-introduces the same shape. The JSON1 path is correct (uses `json_extract`); the fallback is the failure mode. The fallback only fires on older SQLite builds without JSON1 — Herd ships SQLite 3.45 which has JSON1, so in practice this is theoretical, but the code is the wrong defensive form.
**Fix:** Append a trailing character bound to the LIKE pattern. JSON serialisation of `{"inbox_id":N,…}` or `{"inbox_id":N}` always follows the integer with `,` or `}`; the needle should be `'%"inbox_id":'.$inboxId.'[,}]%'` (but SQLite LIKE doesn't support character classes — use two LIKE clauses OR'd, or two-needle approach). Cleaner: drop the LIKE fallback entirely (SQLite 3.38+ has JSON1 built-in unconditionally) and let the JSON1-extract path be the only path.
**Fixable:** yes
