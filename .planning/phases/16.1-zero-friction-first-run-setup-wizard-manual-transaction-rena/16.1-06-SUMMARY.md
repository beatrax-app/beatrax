  - "Dispatch InboxTokenFailed from the API clients (not from the OAuth providers themselves) because the providers do not know the inbox id — they only know the refresh token. The API client owns the inbox id context, so it is the right layer to map a refresh failure into an inbox-scoped event."

# Phase 16.1 Plan 06: OAuth Re-Consent Detection + Banner Summary

**Surfaces OAuth token-refresh failures as a calm "Reconnect your Gmail/Outlook" banner with a Reconnect link that hands the user back into the existing inbox row via `/inboxes?reconnect={id}`; server-side dedup + acknowledge keep the banner clean.**

## Accomplishments

- **Detection:** GmailApiClient + GraphApiClient now catch the typed `InvalidGrantException` at their `ensureFreshAccessToken()` boundary; on catch they dispatch `InboxTokenFailed` (carrying inbox_id + user_id + provider) and throw the new `ReconsentRequiredException` for the caller's existing error-recovery path.
- **Alert raising:** `RaiseReconsentAlertOnTokenFailure` listener writes a single un-acknowledged `oauth_reconsent_required` row per (user_id, inbox_id). Dedup runs via `json_extract(metadata, '$.inbox_id')` with a `LIKE` fallback; the row's message is the locked provider-specific literal ("Reconnect your Gmail" / "Reconnect your Outlook"). No OAuth token text ever lands in the row (ASVS V7 — metadata carries only inbox_id + provider string).
- **Banner rendering:** `system-alert-message.blade.php` gained an `@case('oauth_reconsent_required')` branch that defensively reads metadata.inbox_id and conditionally appends a `Reconnect →` link targeting `/inboxes?reconnect={inbox_id}`. The link is omitted when inbox_id is missing — defensive guard against a future regression of the writer.
- **Reconnect hand-off:** `InboxesPage` gained a `#[Url(as: 'reconnect')]` query-param binding. On mount, the page looks the inbox up via the existing `InboxQuery::findForUser` (per-user scoped, 404-not-403) and dispatches `oauth-client-wizard:open` with the provider + inbox id. Cross-user and missing-row ids are silently no-op'd.
- **Modal extension:** `OAuthClientWizardModal::open()` accepts an optional `?int $inboxId = null`. On submit, when inboxId is set, the modal dispatches `oauth-client-wizard:saved` + `oauth-client-wizard:reconsented` and redirects to `oauth.connect?inbox_id={N}` so `OAuthConnectController`'s existing reconnect path binds the consent dance to the existing inbox row.
- **Alert acknowledge:** `InboxesPage` gained an `#[On('oauth-client-wizard:reconsented')]` listener that acknowledges the active `oauth_reconsent_required` row for the supplied inbox via `AcknowledgeSystemAlert`. `OAuthCallbackController` also acknowledges server-side after a successful re-consent rotation — defence in depth so either path self-heals the banner.

## Decisions Made

See key-decisions in the frontmatter. The most load-bearing one is decision #1 — catching the existing `InvalidGrantException` typed sentinel rather than introducing a new provider-specific catch ladder in the API clients. The plan's W-10 fix demands a "PROVIDER-SPECIFIC exception, not generic `\Throwable`" — `InvalidGrantException` IS the project's own typed sentinel for `invalid_grant`/`consent_required`, mapped one layer down inside `GoogleOAuthProvider::mapIdentityProviderException` and `MicrosoftOAuthProvider::mapIdentityProviderException`. The catch is provider-specific in the strongest sense — it can never accidentally swallow a network error or a JSON-decode failure, because those classes do not extend `InvalidGrantException`.
