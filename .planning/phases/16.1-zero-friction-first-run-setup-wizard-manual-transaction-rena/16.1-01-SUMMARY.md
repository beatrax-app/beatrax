## Decisions Made

- **Re-install transactions.type trigger pair inside add_payment_type_to_transactions** — SQLite's blueprint compiler rebuilds the transactions table on `Schema::table()->string()->after()`, dropping attached triggers; the recreate_transactions_type_triggers migration exists for exactly this hazard. Co-locating the reinstall in the same migration that risks dropping it keeps the invariant local.
- **Partial UNIQUE INDEX on community_merchant_mappings(pattern) WHERE user_id IS NULL** — SQLite treats NULL values in composite UNIQUE indexes as distinct, so the documented `(user_id, pattern)` UNIQUE allows multiple global rows with the same pattern. The partial index closes that gap without disturbing per-user override behavior.
- **PaymentType-literal arch invariant scans only the three unambiguous values** (`pin`, `online`, `direct_debit`) — the other enum values (`transfer`, `cash`, `fee`, `refund`, `unknown`) overlap with `transactions.type`, with the categorization seeder slugs, and with PayPal CSV event-type literals. A broader scan flagged 9 legitimate uses in production code; the narrower scan locks containment for the values that have no other home.
- **Cast Transaction.payment_type to the PaymentType backed enum** — reads return enum instances so consumers reach `->chipLabel()` directly; writes accept enum or string values. Trigger-rejection tests bypass the enum cast by using raw `DB::table()` insert/update paths so the SQL reaches the SQLite trigger rather than failing with a PHP ValueError at the cast boundary.

**2. [Rule 1 — Bug] Re-install transactions.type trigger pair after the payment_type ALTER**

- **Committed in:** `c498268` (Task 2b commit)

**3. [Rule 1 — Bug] Partial UNIQUE INDEX on community_merchant_mappings(pattern) WHERE user_id IS NULL**
