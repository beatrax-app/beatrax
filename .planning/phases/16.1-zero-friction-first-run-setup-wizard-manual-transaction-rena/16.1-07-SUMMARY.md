**Full /settings/aliases page over the per-user merchant_aliases table — inline edit with 400ms-debounced live transaction-preview, bulk-merge with LCP prefill and merged_from JSON provenance, and YAML export/import in the community-corpus schema with PARSE_EXCEPTION_ON_INVALID_TYPE safety.**

## Accomplishments

- Route `GET /settings/aliases` (auth-gated) renders the AliasesSettingsPage Livewire component inside the existing app shell.
- Paginated list (25/page) of the user's `merchant_aliases` rows with read-only `pattern`, inline-editable `generalized_pattern`, and a right-rail "Test against my transactions" preview pane that fires after a 400ms debounce, scans 500 rows max, returns total + first 5 matches, and never mutates the transactions table.
- Bulk-merge: checkbox-select two or more rows → confirm dialog prefills the longest-common-prefix of the patterns (or empty when no shared 4+ char prefix exists) and the first selected row's friendly name → MergeMerchantAliases consolidates into a single surviving row whose `merged_from` JSON carries the absorbed rows' provenance + ISO-8601 merge timestamps.
- YAML export streams `aliases.yaml` in the community-corpus schema. Round-trip (export → re-import → diff) classifies every entry as `unchanged`. Snapshot test locks the serialized shape.
- YAML import: file upload validated (`extensions:yaml,yml`, max 1024 KB) → parse with `Yaml::PARSE_EXCEPTION_ON_INVALID_TYPE` → diff classification (`new` / `unchanged` / `conflicts`) → conflict-resolution selects (`keep` / `replace`) → `confirmImport` applies the chosen resolutions in a transaction.
- Settings → Aliases + First-run tour links wired into the Core SettingsPage. The `route('setup', ['force' => 1])` link re-launches the onboarding wizard at any time (deferred from Plan 03a).
- Strict-rules posture: zero global helper usage (no `abort` / `response` / `now` / `redirect` / `auth` / `request` / `event` in new code); every collaborator either constructor-DI'd (services / actions) or method-DI'd (Livewire); every `merchant_aliases` read / write carries an explicit `where('user_id', $currentUser->user()->id)` clause; cross-user attempts surface a calm flash instead of crashing.

## Decisions Made

- **Cross-user surface is calm-flash, not exception** — every cross-user action (save, delete, merge) clears the relevant Livewire state and surfaces a calm "not found" flash instead of bubbling NotFoundHttpException through the Livewire test framework. The structural ownership guard remains the `where('user_id', $currentUser->user()->id)` clause; the flash is purely the UI affordance. Matches RulesPage WR-02 catch-pattern documented in `Modules/Categorization/Internal/Http/Livewire/RulesPage.php`.
- **Livewire properties are primitive-only** — `previewResult` (the live-test pane) and `importDiff` (the YAML-import preview) both shape as nested arrays of scalars; the action methods rehydrate `CorpusEntryDto` instances before piping into `AliasYamlImporter::apply()`. Livewire's wire-payload synthesizer rejects unsupported custom types with "Property type not supported in Livewire for property: [..]".
- **Raw query builder for chained orderBy / whereIn** — Larastan strict rules' `staticMethod.dynamicCall` flags Eloquent's magic-method chain at the static `Model::query()->orderBy(...)` shape. Every read / write of `merchant_aliases` in the new code uses `$db->connection()->table('merchant_aliases')->where(...)->...` instead, matching MerchantNameResolver + PreviewWizard's convention.
- **Snapshot tests live under the module** — `tests/Pest.php` now binds `Modules/<Name>/tests/Snapshot` per-module so the round-trip test sits next to the code it exercises rather than in the root `tests/Snapshot/` directory. `phpunit.xml`'s `Snapshot` testsuite covers both locations.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] Livewire property type incompatibility**
- **Found during:** Task 2 verification
- **Issue:** Plan specified `public ?AliasMatchPreviewResultDto $previewResult = null`. Livewire 4 cannot synthesize the spatie/laravel-data DTO over its wire payload — every interaction with the property crashed with "Property type not supported in Livewire for property: [..]".
- **Fix:** Switched to a primitive-only array shape `{total: int, first5: list<array{description, counterparty_name, booked_at}>, emptyMessage: ?string}`. The `updatedEditingPattern` hook flattens the AliasMatchPreviewQuery DTO into this shape before assignment. Same pattern applied to `importDiff` (flatten CorpusEntryDto → primitive array; rehydrate at `confirmImport`).
- **Files modified:** `Modules/Import/Internal/Http/Livewire/AliasesSettingsPage.php`, `Modules/Import/Resources/views/livewire/aliases-settings-page.blade.php`
- **Verification:** AliasesSettingsPageTest + ImportAliasesYamlTest exercise the wire round-trip; both pass.
- **Committed in:** `64c8480` (Task 2) + `1f65518` (Task 3)

**2. [Rule 2 — Missing Critical] Cross-user surface needed to be a calm flash, not a thrown 404**
- **Found during:** Task 2 verification
- **Issue:** Plan specified "find via `MerchantAlias::query()->...->first()`; if null throw a `NotFoundHttpException`". Livewire's `->test()` helper does not propagate the exception in a way `->throws(NotFoundHttpException::class)` recognises (the framework wraps it). The plan's intent — 404-not-403 surface — was satisfied, but the cross-user assertion shape needed to change.
- **Fix:** Adopted the existing RulesPage WR-02 catch pattern: the user-scoped `update()` / `delete()` returns 0 affected rows for a cross-user id; the page sets a calm "Alias not found (it may have been deleted in another tab)" flash and clears the editing state. The structural ownership guard remains the `where('user_id', ...)` clause — the flash is the UI surface. Foreign rows MUST stay in the DB (assertion).
- **Files modified:** `Modules/Import/Internal/Http/Livewire/AliasesSettingsPage.php`, `Modules/Import/tests/Feature/AliasesSettingsPageTest.php`, `Modules/Import/tests/Feature/BulkMergeAliasesTest.php`
- **Verification:** Tests assert calm flash + foreign row presence (database state check via `DB::table('merchant_aliases')->where('id', $foreign->id)->exists()->toBeTrue()`).
- **Committed in:** `64c8480` (Task 2) + `1f65518` (Task 3)

**3. [Rule 3 — Blocking] Larastan strict `staticMethod.dynamicCall` rule on Eloquent chains**
- **Found during:** Task 1 close-out (Larastan run)
- **Issue:** Initial implementation used `MerchantAlias::query()->whereIn(...)->orderBy(...)`. The project's phpstan-strict-rules `staticMethod.dynamicCall` rule flags this pattern.
- **Fix:** Switched every `MerchantAlias` query (in AliasYamlExporter, AliasYamlImporter, MergeMerchantAliases, AliasesSettingsPage) to the raw query builder via `$db->connection()->table('merchant_aliases')`. Matches MerchantNameResolver + PreviewWizard's convention. Eloquent `create()` / `Model::query()->first()` calls (single static + single accessor) stay where appropriate.
- **Files modified:** `Modules/Import/Internal/Services/AliasYamlExporter.php`, `Modules/Import/Internal/Services/AliasYamlImporter.php`, `Modules/Import/Public/Actions/MergeMerchantAliases.php`, `Modules/Import/Internal/Http/Livewire/AliasesSettingsPage.php`
- **Verification:** `php -d memory_limit=2G vendor/bin/phpstan analyse` runs clean against the full project.
- **Committed in:** `b823ffd` (Task 1) + `64c8480` (Task 2)

**4. [Rule 3 — Blocking] Vendor + Vite manifest missing in the parallel-execution worktree**
- **Found during:** Task 2 first test run (`GET /settings/aliases` returned 500 with `ViteManifestNotFoundException`)
- **Issue:** The Claude Code worktree is provisioned without `vendor/` or `public/build/` symlinks; `vendor/autoload.php` resolved to the main repo (causing Pest's `dirname($autoloadPath, 2)` rootPath calculation to point at the main repo, which broke per-module TestCase binding); `public/build/manifest.json` was absent.
- **Fix:** Ran `composer install` in the worktree (full vendor install, ~18s) so binaries resolve to local paths. Symlinked `public/build` → main repo's pre-built Vite output so `@vite('resources/css/app.css')` resolves at render time. These changes touch worktree filesystem state only — they are not committed.
- **Files modified:** none (worktree infrastructure only)
- **Verification:** Full Modules/Import/tests/ suite (271 cases) passes; the GET /settings/aliases render test passes.
