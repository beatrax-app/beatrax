# Phase 16.1: Zero-friction first-run setup wizard, manual rename, payment-type classification, crowd corpus, OAuth re-consent banner, and Settings → Aliases — Research

**Researched:** 2026-05-25
**Domain:** Laravel 13 + Livewire 4 + Volt + Flux UI 2 + Tailwind v4 (CSS-first) + nwidart/laravel-modules + SQLite (WAL) + NativePHP `^2.2` desktop bundle
**Confidence:** HIGH (every recommendation is grounded in code inspection of the existing repo; novel design choices are explicitly flagged)

## Summary

This phase ships six tightly-coupled user-facing surfaces as one vertical MVP. None of the work introduces new third-party libraries — every package required is already in `composer.json` (verified: `spatie/laravel-data ^4`, `symfony/yaml v8.0.10`, `nativephp/desktop ^2.2`, `livewire/livewire ^4`, `livewire/flux ^2`). The work is shape, schema, and wiring — not dependency growth.

The architecture has three structural decisions to make and one classifier shape to pin down. The structural decisions (new `Modules/Onboarding/`, new `Modules/Community/`, location of `merchant_aliases`) are recommended below with rationale grounded in the existing module-layout precedents (Modules already follow Public/Internal split via `nwidart/laravel-modules`; new bounded modules cost a service provider + an arch invariant, but quarantine ownership cleanly). The classifier shape leans heavily on the existing `RuleEvaluator` precedent (per-user reads via `DatabaseManager`, no facades, mb_-safe string ops) and the `MatcherRegistry` container-tagging precedent in `Modules/Receipts/Providers/ReceiptsServiceProvider.php` line 86–119 — both are exact templates to mirror.

Two privacy-sensitive lookups (the live "Test against my transactions" preview in D-22 and the corpus seed-time YAML loader) need read-only posture and partial-failure tolerance respectively. Both are addressable with existing patterns; concrete shapes are below.

**Primary recommendation:** Create two new modules (`Modules/Onboarding/` for the wizard + `Modules/Community/` for the corpus + mystery-merchants page + suggest-mapping modal). Co-locate `merchant_aliases` schema, model, services, and the `Settings → Aliases` Livewire page inside `Modules/Import/` because Import already owns Preview rendering and the alias resolver only runs at preview/list-render time. Implement `PaymentType` as a PHP 8.4 backed string enum stored in a SQLite `string` column protected by paired BEFORE-INSERT/BEFORE-UPDATE triggers (mirrors the existing `system_alerts.severity` and `categorization_rules.field` precedents). Tag per-source `PaymentTypeHinter` implementations with `'import.payment_type_hinter'` and resolve them via the container in `PaymentTypeClassifierStage`, exactly like Receipts collects `SenderMatcher` instances.

### Locked Decisions

(Verbatim from `16.1-CONTEXT.md` `<decisions>` — D-01 through D-25, all 25 decisions are LOCKED. Researcher choices are confined to the explicit "researcher decides" carve-outs at D-09, D-12, D-17, D-21.)

**Wizard state & resume**
- **D-01:** New dedicated `wizard_progress` table (per-user) — `(id, user_id, step_key, status [pending|done|skipped|in_progress], data jsonb, completed_at)`. One row per `(user_id, step_key)`. Survives app restarts.
- **D-02:** Resume behavior on relaunch — drop the user back into the step they were on, with a "Welcome back — let's pick up where you left off" banner. Quiet "Skip the rest" dismiss marks remaining steps `skipped` and routes to dashboard.
- **D-03:** First-launch detection — `EnsureDatabaseReady` middleware already redirects fresh installs to `desktop.welcome`. After signup completes (`UserInstalled` fires per Phase 16 commit `529fd7a`), the wizard initializes `wizard_progress` rows for every step and routes to `/setup` instead of `/`.
- **D-04:** Skip routes — every skippable step has an in-app return surface (bank → `/imports/upload`, card → `/imports/upload`, email → `/inboxes`). Wizard is re-runnable from `Settings → First-run tour`.

**Payment-type field & classifier**
- **D-05:** New `transactions.payment_type` enum column. Values: `pin`, `online`, `transfer`, `direct_debit`, `cash`, `fee`, `refund`, with `unknown` as the safe fallback. Migration backfills `unknown` for all existing rows.
- **D-06:** Classifier lives in `Modules/Import/Internal/Pipeline/Stages/PaymentTypeClassifierStage.php` — runs after parsing, before fingerprint. Single shared stage; per-source parsers feed it normalized hints.
- **D-07:** Source-specific hint contributors next to their parsers (e.g. `Modules/Import/Internal/Parsers/Asn/AsnCsvPaymentTypeHinter.php`), implement `PaymentTypeHinter` exposed from `Modules/Import/Public/Contracts/`. Classifier collects all hinters via service-container tagging.

**Manual rename + alias learning**
- **D-08:** New `merchant_aliases` table — per-user `(id, user_id, pattern, generalized_pattern, friendly_name, created_at)`. Consulted at preview/render time only; does NOT mutate stored `Transaction.description`.
- **D-09:** Name and category stored separately. The rename popover's optional category hint, if set, additionally seeds a Categorization rule. Aliases live in `Modules/Import/` or new `Modules/MerchantAliases/` — researcher decides.
- **D-10:** Smart auto-generalize on save — `PatternGeneralizer` heuristic strips trailing terminal IDs (`7438`), trailing digit runs in PIN-row shapes, known noise tokens. Popover renders the generalized pattern as a preview line.
- **D-11:** Alias precedence at render time — if both exact and generalized match, exact wins.

**Crowd corpus**
- **D-12:** Corpus file location — `resources/corpus/merchant-mappings.yaml`. Bundled at build time; snapshot refresh via Phase 18 auto-update plumbing. No live network fetch on launch.
- **D-13:** Corpus schema — every entry is `{ pattern, name, category?, region?, contributor: "diederik-bot" }`. Pattern matching uses the same `PatternGeneralizer` shape as D-10.
- **D-14:** Corpus auto-seed on install — `SeedCommunityCorpus` listener fires on `UserInstalled` alongside `SeedDefaultCategoryTree`. Writes corpus rows to `community_merchant_mappings` (global rows, `user_id IS NULL`). Idempotent upsert by pattern.
- **D-15:** Render-time precedence — (a) user's exact alias, (b) user's generalized alias, (c) community exact, (d) community generalized, (e) raw description fallback.
- **D-16:** Submission flow — "Submit as draft PR" opens system browser to a pre-filled `https://github.com/nightworksio/beatrax/compare/main...{branch}?expand=1&body={url-encoded-yaml-entry}`. No GitHub-App backend.
- **D-17:** Settings toggles — Toggle 1 ("Use the shared merchant list") is meaningful; Toggle 2 ("Offer to contribute") controls Triage CTA visibility; Toggle 3 ("Update on app updates") ships as a disabled no-op with inline note "Activates with next app update — diederik 1.2+". (Researcher: confirm with Phase 18 timing.)

**OAuth re-consent**
- **D-18:** Detection in `Modules/EmailScan/` — on 401 / `invalid_grant` / `consent_required` / token-refresh failure, write `system_alert` of kind `oauth_reconsent_required` with `inbox_id` in payload.
- **D-19:** Surface — existing `SystemAlertsBanner` renders the row with a Reconnect button routing to `/inboxes?reconnect={inbox_id}`. `InboxesPage` reads query param on mount, auto-opens the existing `OAuthClientWizardModal`.
- **D-20:** Recovery — on successful re-consent, alert resolved via existing `SystemAlert` lifecycle, scanner unparked.

**Pattern editor (Settings → Aliases)**
- **D-21:** New route `/settings/aliases`. New Livewire component `AliasesSettingsPage` in `Modules/Import/Internal/Http/Livewire/` or new module — researcher decides.
- **D-22:** Per-row inline edit of `generalized_pattern` (exact `pattern` is immutable — provenance). Save triggers a live "Test against my transactions" preview showing match count + first 5 rows BEFORE committing.
- **D-23:** Bulk-merge — checkbox-select, "Merge selected" prompts for a single canonical `friendly_name` + `generalized_pattern` (pre-filled with longest-common-prefix). Provenance preserved in new `merged_from` JSON column on the surviving row.
- **D-24:** YAML import/export — export produces `aliases.yaml` matching the corpus schema. Import diffs against existing aliases, shows preview ("3 new, 2 existing unchanged, 1 conflicts — keep yours or replace"), then commits.
- **D-25:** Test runner safety — "Test against my transactions" query MUST use the same `withoutGlobalScopes(false)` posture (i.e. keep user-scoping); pattern matching runs read-only.

### Pattern 1: Container-tagged collaborators (the `PaymentTypeHinter` registry)

**What:** Per-source hinters self-register in their parent service provider via `$app->tag([$fqn], 'import.payment_type_hinter')`. `PaymentTypeClassifierStage` resolves the iterable via the container at construction time.

**When to use:** Whenever a stable contract has N implementations that the rest of the module just iterates over without caring about identity.

**Example (mirror exactly from `Modules/Receipts/Providers/ReceiptsServiceProvider.php` lines 86–119):**

```php
// Source: Modules/Receipts/Providers/ReceiptsServiceProvider.php (verified shape)
foreach (self::HINTER_FQNS as $fqn) {
    if (class_exists($fqn)) {
        $this->app->singleton($fqn);
        $this->app->tag([$fqn], 'import.payment_type_hinter');
    }
}

$this->app->singleton(
    PaymentTypeClassifierStage::class,
    static function (Container $app): PaymentTypeClassifierStage {
        /** @var iterable<PaymentTypeHinter> $tagged */
        $tagged = $app->tagged('import.payment_type_hinter');
        $hinters = [];
        foreach ($tagged as $hinter) {
            $hinters[] = $hinter;
        }

        return new PaymentTypeClassifierStage($hinters);
    },
);
```

### Pattern 2: Idempotent install-time seeders (the corpus loader)

**What:** A listener on `UserInstalled` that reads a bundled YAML, upserts global rows by `pattern`, and tolerates partial-file failure (one malformed entry logged + skipped, the rest proceed).

**When to use:** All install-time seeders. Mirror exactly from `Modules/Categorization/Internal/Listeners/SeedDefaultCategoryTree.php` (verified shape).

**Example (concrete shape for `SeedCommunityCorpus`):**

```php
// New: Modules/Community/Internal/Listeners/SeedCommunityCorpus.php
final class SeedCommunityCorpus
{
    public function __construct(
        private readonly CorpusLoader $loader,
        private readonly DatabaseManager $db,
        private readonly LoggerInterface $logger,
    ) {}

    public function handle(UserInstalled $event): void
    {
        $entries = $this->loader->loadBundled(); // returns list<CorpusEntryDto>

        $now = $this->clock->now();
        foreach ($entries as $entry) {
            // Upsert by pattern; user_id IS NULL for global rows.
            // updateOrInsert on the query builder yields one statement per row;
            // the SQLite WAL writer handles ~1000 rows/sec comfortably.
            try {
                $this->db->connection()->table('community_merchant_mappings')->updateOrInsert(
                    ['pattern' => $entry->pattern, 'user_id' => null],
                    [
                        'name' => $entry->name,
                        'category' => $entry->category,
                        'region' => $entry->region,
                        'contributor' => $entry->contributor,
                        'updated_at' => $now,
                    ],
                );
            } catch (Throwable $e) {
                $this->logger->warning('SeedCommunityCorpus: skipped malformed entry.', [
                    'pattern' => $entry->pattern,
                    'exception_class' => $e::class,
                    'exception_message' => $e->getMessage(),
                ]);
            }
        }
    }
}
```

### Pattern 3: SQLite enum-via-trigger pair (the `payment_type` column)

**What:** `transactions.payment_type` is a `string(16)` column; allowed values enforced by a paired BEFORE-INSERT / BEFORE-UPDATE-OF-payment_type trigger. The Eloquent layer casts the column to the `PaymentType` enum.

**When to use:** Every new enum-shaped column where the value space is finite + stable.

**Example (mirror exactly from `Modules/Core/Database/Migrations/2026_05_20_010001_create_system_alerts_table.php` lines 70–82):**

```php
// New migration: add_payment_type_to_transactions
$connection = $this->db()->connection($this->getConnection());

// Add column with default 'unknown' (backfills automatically — single transaction).
$this->schema()->table('transactions', static function (Blueprint $table): void {
    $table->string('payment_type', 16)->default('unknown')->after('description');
    $table->index(['user_id', 'payment_type']);  // chip-filter hot path on /transactions
});

$connection->statement(<<<'SQL'
    CREATE TRIGGER transactions_payment_type_check_insert BEFORE INSERT ON transactions FOR EACH ROW
    WHEN NEW.payment_type NOT IN ('pin','online','transfer','direct_debit','cash','fee','refund','unknown')
    BEGIN SELECT RAISE(ABORT, 'Invalid transactions.payment_type value'); END
SQL);
$connection->statement(<<<'SQL'
    CREATE TRIGGER transactions_payment_type_check_update BEFORE UPDATE OF payment_type ON transactions FOR EACH ROW
    WHEN NEW.payment_type NOT IN ('pin','online','transfer','direct_debit','cash','fee','refund','unknown')
    BEGIN SELECT RAISE(ABORT, 'Invalid transactions.payment_type value'); END
SQL);
```

### Pattern 4: Per-user query with explicit `where('user_id', …)` (the alias lookup)

**What:** Every alias / corpus / wizard read filters by `user_id` explicitly rather than relying on the `BelongsToUser` global scope.

**When to use:** Any service consumed in unauthenticated CLI / queue / test contexts. Mirror exactly from `FingerprintStage::classify` (verified shape, line 83–95).

**Example:**

```php
// New: Modules/Import/Public/Services/MerchantNameResolver.php
public function resolve(string $rawDescription, int $userId): ?string
{
    // Step (a): user exact alias
    $exact = $this->db->connection()->table('merchant_aliases')
        ->where('user_id', $userId)
        ->where('pattern', $rawDescription)
        ->value('friendly_name');
    if ($exact !== null) {
        return $exact;
    }

    // Step (b): user generalized alias (uppercased contains)
    // Pattern is stored as the generalized template; we compare via mb_strpos
    // in PHP rather than SQL LIKE — same SQL-injection-defence rationale as RuleEvaluator.
    foreach ($this->fetchUserGeneralized($userId) as $alias) {
        if (self::matchesGeneralized($rawDescription, $alias->generalized_pattern)) {
            return $alias->friendly_name;
        }
    }

    // Step (c): community exact
    $exact = $this->db->connection()->table('community_merchant_mappings')
        ->whereNull('user_id')
        ->where('pattern', $rawDescription)
        ->value('name');
    if ($exact !== null) {
        return $exact;
    }

    // Step (d): community generalized
    foreach ($this->fetchCommunityGeneralized() as $row) {
        if (self::matchesGeneralized($rawDescription, $row->pattern)) {
            return $row->name;
        }
    }

    // Step (e): null → caller renders italic-muted fallback (.desc-fallback)
    return null;
}
```

### Anti-Patterns to Avoid

- **Storing the resolved alias on the `transactions` row.** Aliases are render-time only (D-08). Mutating the stored `description` would lose provenance and break re-resolution after the user edits their alias. The resolver runs on every preview/list render.
- **Building a custom YAML parser** because the corpus shape is "simple." `symfony/yaml` is already in lock; hand-rolled YAML breaks the first time a value contains a colon or a multi-line description.
- **Putting the GitHub Compare URL in code as a literal string.** D-16 specifies the repo could move at the Phase 19 boundary. Resolve it via `config('community.github_compare_base')` set from `config/community.php` so a single env var rebrand suffices.
- **Auto-creating a category when a corpus entry references one that doesn't exist.** D-12 Claude's-discretion area; recommend skip + log a `system_alerts` row of severity `info` so the user sees the corpus mismatch without silent data drift.
- **Using `LIKE` in SQL for the generalized-pattern match.** Mirror `RuleEvaluator` (verified, line 38–46): pull active rules into PHP, do `mb_strpos`/`mb_strtolower` in PHP. The pattern.value never reaches the SQL string — the SQL-injection mitigation.
- **Making the wizard a single Livewire component with step branching.** UI-SPEC implies one component per step (`Steps/WelcomeStep.php`, etc.). Branching one mega-component defeats `wire:transition` and inflates render cost.
- **Holding `auth()` / facade / helper in any new class.** Will fail `BoundaryArchTest::noLaravelFacadeUsageInModuleCode` (lines 57–114). Inject `CurrentUser` contract for the user; inject `Dispatcher` for events; inject `UrlGenerator` for URLs; inject `LoggerInterface` for logs.

## Common Pitfalls

### Pitfall 1: `EnsureDatabaseReady` middleware redirect-loop on `/setup`

**What goes wrong:** `EnsureDatabaseReady` middleware redirects fresh-install requests to `desktop.welcome`. If `/setup` isn't on its `EXEMPT_ROUTE_PREFIXES` list (currently lines 57–61), the wizard will loop right back to `welcome` for every request.

**Why it happens:** `isFreshInstall()` only checks if the `users` table is empty. After signup, the user exists, but the wizard is the *next* gate. The redirect logic doesn't know about wizard state.

**How to avoid:** Add `'setup'` to `EnsureDatabaseReady::EXEMPT_ROUTE_PREFIXES`. The new `/setup` route's `Modules/Onboarding/Routes/web.php` must register the route with the canonical name `setup` so the prefix match works. Verified shape against `EnsureDatabaseReady.php` lines 57–76.

**Warning signs:** Infinite-redirect-detected error in browser; Livewire heartbeat fails; Pest feature test for WIZ-01 returns 500 after 3 redirects.

### Pitfall 2: PaymentTypeClassifierStage trigger violation on backfill

**What goes wrong:** Adding the `payment_type` column with `->default('unknown')` works on row create, but if the migration is run twice in a row, the second run's "column already exists" check might silently skip — leaving rows with NULL on a column the trigger requires.

**Why it happens:** SQLite ALTER TABLE doesn't have IF NOT EXISTS semantics for columns; the schema builder swallows the "duplicate column" SQLITE_ERROR depending on Laravel version.

**How to avoid:** The migration must (a) check column existence via `Schema::hasColumn` before adding, (b) explicitly run a `UPDATE transactions SET payment_type = 'unknown' WHERE payment_type IS NULL` statement after column add, and (c) only create the trigger AFTER the backfill statement (otherwise the trigger fires on the backfill UPDATE and may reject if the schema builder used a different default).

**Warning signs:** `SQLSTATE[HY000]: General error: 1 Invalid transactions.payment_type value` in CI after a re-run; phpunit `RefreshDatabase` test that re-creates the schema dies on second-test-run boot.

### Pitfall 3: Alias precedence — exact match must short-circuit before generalized scan

**What goes wrong:** If `MerchantNameResolver` iterates aliases naively (`foreach all → match`), an over-broad generalized pattern (e.g. `BCK*SHELL*`) wins over a more specific exact pattern (`BCK*SHELL PIETER NIEUW`) because both match.

**Why it happens:** Two-tier matching where the broader pattern is checked before the narrower one inverts the user's intent (D-11 explicitly: "exact wins").

**How to avoid:** Two separate queries — first a single-row exact lookup on `(user_id, pattern)`, return immediately if found; only then fetch the user's generalized aliases and walk them. Same pattern repeats for community corpus.

**Warning signs:** A renamed-with-Remember row reverts to a different friendly name on next preview render; a "Test against my transactions" preview returns matches the user didn't expect.

### Pitfall 4: SystemAlert dedup miss on OAuth re-consent spam

**What goes wrong:** The background scanner catches a token failure every 60 seconds while polling. Without dedup, a single revoked token spawns 60 `system_alerts` rows per hour, swamping the banner.

**Why it happens:** `SystemAlertsBanner` renders every un-acknowledged row; there's no "one active alert per (user, kind, metadata.inbox_id) at a time" constraint at the DB layer.

**How to avoid:** In `RaiseReconsentAlertOnTokenFailure` (the new listener), before inserting, run an existence check: `SELECT 1 FROM system_alerts WHERE user_id = ? AND kind = 'oauth_reconsent_required' AND json_extract(metadata, '$.inbox_id') = ? AND acknowledged_at IS NULL LIMIT 1`. If the row exists, no-op. SQLite's `json_extract` is available in 3.38+ (Herd ships 3.45+ per CLAUDE.md). The 1-hour debounce in REQ OAUTH-RC-01 is satisfied by the user-acknowledgment / lifecycle pattern, not by a time window.

**Warning signs:** 50+ banner rows after the user closes the laptop for a weekend with an expired token; the banner's severity-first ordering becomes useless because the OAuth alerts dominate.

### Pitfall 5: Livewire 4 SFC + Volt — `wire:model.live` on a pattern editor without debounce

**What goes wrong:** The Settings → Aliases page's inline edit field uses `wire:model.live` for the "Test against my transactions" preview. Without debouncing, every keystroke fires a roundtrip — at 100ms typing cadence, you're firing 10 queries per second over the user's full transaction history.

**Why it happens:** Livewire 4 defaults `wire:model.live` to fire on every keystroke. The pattern field is small; the *consumer* (the matching query) is heavy because it scans the user's transactions.

**How to avoid:** Use `wire:model.live.debounce.400ms` on the pattern input. 400ms is the standard editor-debounce per Phase 16 precedent (`AuditLogPage` filter input — verified earlier in code-skim). Cap the preview to LIMIT 5 + COUNT(*) — never return all matches.

**Warning signs:** SQLite WAL writer contention warnings in `/dev/logs` while the user is typing in the alias editor; n+1 queries reported by Telescope.

### Pitfall 6: Bulk-merge LCP — edge case explosion

**What goes wrong:** Longest-common-prefix on a single selected row returns the entire pattern. On two patterns with no shared prefix, returns the empty string — which then matches everything (all transactions) and silently catastrophically over-merges.

**Why it happens:** Naive LCP doesn't guard against degenerate inputs.

**How to avoid:** The LCP service rejects: (a) input of size 1 (caller bug — selection should require ≥2), (b) result LCP of length < 4 characters (refuse the merge, show "These patterns are too dissimilar to merge automatically — edit the merged pattern manually"). The "merge selected" UI confirms by showing the LCP + a count of how many transactions would now match the merged pattern.

**Warning signs:** A bulk-merge action renames thousands of transactions instead of dozens; user files a bug after the next import preview.

### Pitfall 7: NativePHP Shell facade vs DI contract

**What goes wrong:** CONTEXT.md `<code_context>` says "NativePHP exposes `Native\Laravel\Facades\Shell::openExternal($url)`" — this is the v1 namespace. The project uses `nativephp/desktop ^2.2`, which exposes `Native\Desktop\Contracts\Shell` (verified at `vendor/nativephp/desktop/src/Contracts/Shell.php` line 5). A misconfigured `OpenExternalUrlAction` against the wrong namespace will fail at composer-autoload time or runtime.

**Why it happens:** NativePHP renamed namespaces between v1 and v2; documentation lag.

**How to avoid:** Inject `Native\Desktop\Contracts\Shell` (the interface), bound by NativePHP's own ServiceProvider (Desktop module already includes the package, so the binding exists in any environment that boots `App\Providers\NativeAppServiceProvider`). For tests, bind `ShellFake` (verified at `vendor/nativephp/desktop/src/Fakes/ShellFake.php`). For non-NativePHP runtime (Herd dev), bind a `NoOpShell` that no-ops and logs.

**Warning signs:** `Target [Native\Laravel\Contracts\Shell] is not instantiable` exception; tests fail with `ContainerException` after they pass on the developer's bundled-app build.

### New: `PatternGeneralizer` heuristic shape

```php
// New: Modules/Import/Public/Services/PatternGeneralizer.php
namespace Modules\Import\Public\Services;

/**
 * Generalizes a raw bank-statement description into a fuzzy-match pattern
 * by stripping volatile tokens. The output stays a literal-substring
 * comparison target — never a regex — so it can be matched safely from
 * PHP without entering SQL.
 *
 * Algorithm (token-classifier + regex stack hybrid):
 *
 *   1. Split on whitespace into tokens.
 *   2. For each token, classify:
 *      - 'terminal-id'   — 4-7 digit run, sometimes prefixed by 'T' or '#'
 *      - 'pin-tail'      — '*' followed by exactly 4 digits at end of string
 *      - 'sepa-noise'    — token starts with 'EREF:' / 'KENMERK:' / 'BkTxCd:'
 *      - 'amount'        — token matches /^\d+[.,]\d{2}$/
 *      - 'date-fragment' — matches /^\d{2,4}[-./]\d{1,2}([-./]\d{1,4})?$/
 *      - 'token'         — anything else (kept verbatim)
 *   3. Drop all non-'token' classifications.
 *   4. Re-join with spaces, lower-case.
 *
 * Examples (verbatim from sketch session 004 fixtures):
 *   "BCK*SHELL PIETER NIEUW *0123"  → "bck*shell pieter nieuw"
 *   "ALBERT HEIJN 1245 T07438"      → "albert heijn"
 *   "iDEAL Bestelling KENMERK:..."  → "ideal bestelling"
 */
final class PatternGeneralizer
{
    public function generalize(string $rawDescription): string
    {
        $tokens = preg_split('/\s+/', trim($rawDescription)) ?: [];
        $kept = [];
        $lastTokenIndex = count($tokens) - 1;

        foreach ($tokens as $i => $token) {
            // PIN-tail (always at the end): *0123
            if ($i === $lastTokenIndex && preg_match('/^\*\d{4}$/', $token)) {
                continue;
            }
            // Terminal IDs: 4-7 digit run, optionally prefixed by T/#
            if (preg_match('/^[T#]?\d{4,7}$/', $token)) {
                continue;
            }
            // SEPA / CAMT noise: token starts with known noise prefix
            if (preg_match('/^(EREF|KENMERK|BKTXCD|MARF|REF):/i', $token)) {
                continue;
            }
            // Amounts: 12.50 / 12,50
            if (preg_match('/^-?\d+[.,]\d{2}$/', $token)) {
                continue;
            }
            // Date fragments: 12-05 / 12-05-2026 / 2026-05-12
            if (preg_match('/^\d{2,4}[-.\/]\d{1,2}([-.\/]\d{1,4})?$/', $token)) {
                continue;
            }
            $kept[] = $token;
        }

        return mb_strtolower(implode(' ', $kept));
    }
}
```

// New: Modules/Import/Public/Services/AliasMatchPreviewQuery.php
public function preview(string $generalizedPattern, int $userId): AliasMatchPreviewResultDto
{
    if (mb_strlen(trim($generalizedPattern)) < 3) {
        return AliasMatchPreviewResultDto::empty('Pattern is too short to test.');
    }

    // Read-only; LIMIT 5; explicit user_id (per D-25 — never trust global scope
    // in a service called from Livewire wire:model.live where the auth state
    // might not be established at first render). Mirror RuleEvaluator's
    // PHP-side matching: SQL `LIKE` would inject the pattern; this scans in PHP.
    $rows = $this->db->connection()->table('transactions')
        ->where('user_id', $userId)
        ->select(['id', 'description', 'counterparty_name', 'booked_at', 'amount_minor'])
        ->orderByDesc('booked_at')
        ->limit(500)  // bounded scan window — sufficient for preview
        ->get();

    $needle = mb_strtolower($generalizedPattern);
    $matched = [];
    $total = 0;
    foreach ($rows as $row) {
        $haystack = mb_strtolower((string) ($row->description ?? $row->counterparty_name ?? ''));
        if (mb_strpos($haystack, $needle) !== false) {
            $total++;
            if (count($matched) < 5) {
                $matched[] = $row;
            }
        }
    }

    return AliasMatchPreviewResultDto::withMatches($total, $matched);
}

## Open Questions

1. **Fee / Refund chip color tokens**
   - What we know: UI-SPEC §Color locks PIN-violet, online-blue, transfer-muted, dd-amber, cash-dark-amber, but the 7-value enum (D-05) adds `fee` and `refund` chips that the UI-SPEC explicitly defers ("planner adds `fee` + `refund` chips using established token vocabulary").
   - What's unclear: which `--color-*` tokens map to fee + refund. Fee feels like it should reuse `--color-text-faint` on `--color-bg-subtle` (quiet, indistinct — a fee is not a meaningful action); refund could reuse `--color-emerald` on `--color-emerald-bg` (positive money flowing back). Both stay within "no new tokens" rule.
   - Recommendation: The planner runs a quick `/gsd-ui-phase 16.1 --delta` to formalize the fee/refund chip palette and the OAuth re-consent banner copy + the Settings → Aliases layout. All three are minor extensions of locked patterns; the delta should be <30 minutes of design work.

2. **Wizard "Skip the rest" → marks remaining steps `skipped` but resume detector**
   - What we know: D-02 says "Skip the rest" marks remaining as `skipped`. Resume detector picks the first `in_progress` then first `pending`.
   - What's unclear: After "Skip the rest", every row is `done | skipped`. On re-launch, the resume detector finds neither `in_progress` nor `pending` and should route to dashboard. The planner should make this explicit in the `ResumeStepResolver` test cases.
   - Recommendation: Encode the three branches as separate Pest tests: (a) one row `in_progress` → that step renders; (b) no `in_progress`, some `pending` → first pending renders; (c) all `done | skipped` → redirect to `/`.

3. **Suggest-mapping modal — duplicate detection (UI-SPEC §"Post-submit state — duplicate detected")**
   - What we know: UI-SPEC §"Suggest-mapping modal" mentions a "duplicate detected" inline notice with "See the existing draft →" link. Without a real diederik-bot backend, where does the dedup signal come from?
   - What's unclear: Is the "duplicate detected" path live in 16.1 or deferred with the bot? Per D-16 the modal opens an *external* browser to GitHub — diederik itself never knows whether the PR is a dup.
   - Recommendation: Treat the duplicate-detected and network-failure post-submit states as deferred-with-bot. The 16.1 modal only ships the success path: "Submitted. The GitHub page is now open in your browser." The two error states are documented in the modal copy as not-yet-wired (per UI-SPEC §"Post-submit state" — they describe the future bot's behavior). The planner should flag this for confirmation.

4. **PayPal CSV payment type — when the row is a PayPal-internal transfer (which never showed on a card)**
   - What we know: PayPal CSV "event_type" enum is rich (~30 values). Some map cleanly (`ExpressCheckoutPayment` → online); some are ambiguous (`UserInitiatedWithdrawal` could be transfer or refund).
   - What's unclear: Which PayPal event types map to which enum value. Recommend: planner consults `Modules/Ingestion/Internal/Adapters/Paypal/` event-type handling for the existing canonical list, then expands the mapping into `PaypalCsvPaymentTypeHinter`.

5. **`merchant_aliases.merged_from` JSON column on bulk-merge — schema versioning**
   - What we know: D-23 specifies "Provenance preserved in a new `merged_from` JSON column on the surviving row." Shape unspecified.
   - What's unclear: Recommend the shape `[{ pattern, generalized_pattern, friendly_name, merged_at }]` — a list of absorbed rows. Survives multiple merges by appending. Planner should pin this in the migration.

### Known Threat Patterns for {Laravel 13 + Livewire 4 + SQLite + NativePHP}

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| YAML deserialization → arbitrary PHP object | Tampering, Elevation | Use `Yaml::PARSE_EXCEPTION_ON_INVALID_TYPE` flag (default in symfony/yaml v8+); never `Yaml::PARSE_OBJECT` |
| Livewire wire snapshot leak of `oauth_secrets`-shaped data | Information Disclosure | New wizard / popover / settings Livewire components MUST NOT have public properties referencing OAuth secrets. Phase 19 REL-07 will enforce via arch test; we ride that contract. |
| SQLite WAL writer starvation under concurrent alias edits | Denial of Service | Single-user app; not a real risk. Debounce the "Test against my transactions" query (400ms) so typing doesn't fire 10 SELECTs/sec |
| Cross-user data leak via 403 (vs 404) on `/settings/aliases?user_id=` probe | Information Disclosure | 404-not-403 contract from Phase 12 MULTI-03 + the `BelongsToUser` global scope + explicit `where('user_id', $current)` in `AliasMatchPreviewQuery` |
| Pattern editor SQL injection via `LIKE '%{pattern}%'` | Tampering, Elevation | Mirror RuleEvaluator: pull rows, match in PHP via `mb_strpos`. Never interpolate user-controlled strings into SQL. |
| External URL open spoofing (e.g. `javascript:` URL) | Tampering | `OpenExternalUrlAction` whitelists `https://` only via `str_starts_with` |
| Wizard state tampering via direct URL access | Tampering | Wizard step routes check the user's `wizard_progress` row for the step is reachable (not later than the next pending step) — prevent skipping ahead via URL fiddling |
| File-upload abuse (alias YAML import) | Tampering, DoS | Extension allow-list + 1MB size cap + ephemeral temp path (Livewire default) |
| GitHub Compare URL XSS via malformed merchant pattern in URL params | Tampering | The pattern is URL-encoded via PHP's `urlencode` before insertion into the Compare URL body; GitHub's own server rejects malformed URL fragments |
