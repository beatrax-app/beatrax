## Current Test

UAT walkthrough of phase 16.1's "zero-friction first-run setup" against the locked CONTEXT.md, UI-SPEC.md, and the freshly-built Mac amd64 bundle. The user surfaced five gaps/bugs before formally clicking through the .dmg.

## Tests

### 1. Setup wizard captures the user's starting balance
expected: After the user completes the first import (FirstImportStep), the wizard captures or auto-derives a starting balance + starting date so the dashboard can report an actual current balance, not just transaction deltas. "Frictionless" means the wizard should auto-detect from the imported files when possible (CAMT.053 `<OpngBal>`/`<ClsgBal>`, MT940 `:60F:`/`:62F:`, ICS PDF closing balance, PayPal running balance column) and present a one-click confirm.
result: missing
notes: Neither CONTEXT.md `<decisions>` nor UI-SPEC.md mention starting balance. The wizard ends at FirstImportStep with a preview but no balance capture. The whole "this is your balance today" loop is broken without it.

### 2. Artisan commands popover (Dev Mode) renders without a white page
expected: From `/dev/commands` (Dev Mode → Artisan), opening the run-artisan-command popover for any whitelisted command (db:backup, diederik:doctor, cache:clear, route:list, etc.) renders the command form with arg inputs, a Run button, and live stdout/stderr stream.
result: failed
notes: Popover renders a white page. Confirmed regression. Pre-existing Phase 16 work (DEVUI-02 SAFE-tier artisan runner). Not introduced by 16.1.

### 3. Wizard copy is bank-format-driven, not ASN-only
expected: ConnectBankStep copy + format chips + helper text refers to the supported export formats (CAMT.053, MT940, CSV) and lists the Dutch banks that support each (CAMT.053: ASN, ING; MT940: ASN, ING, Rabobank, Triodos, SNS, Bunq). Users with non-ASN banks should not be told this is an "ASN-only" wizard.
result: failed
notes: The wizard copy in `Modules/Onboarding/Resources/views/livewire/steps/connect-bank-step.blade.php` is locked to ASN. The supporting parsers (genkgo/camt + kingsquare/php-mt940) handle every Dutch bank's exports. Pure copy fix, no architecture change.

### 4. Importing a PDF (ICS card statement) renders without an error on the preview
expected: User drops an ICS card monthly PDF on the ConnectCardStep upload zone (or `/imports/upload`). The import pipeline parses the PDF, produces preview rows, and the preview wizard renders them. No error toast, no crash, no infinite spinner.
result: failed
notes: User reports "PDF upload still gives an error on import preview". Need to reproduce and capture the exact error (toast text, log line, exception class). Could be (a) pre-existing Phase 12 ICS PDF parser bug, (b) the new ConnectCardStep sending the PDF to a code path that hasn't been wired correctly, or (c) the new PaymentTypeClassifierStage rejecting the parsed row. Needs debug session before fix.

### 5. App top-left shows the brand logo
expected: The top-left corner of the in-app chrome (every authenticated page) shows the brand SVG that is rendered on the start/welcome page. Brand consistency, no placeholder, no missing element.
result: failed
notes: The brand SVG lives at `resources/brand/logo.svg` (Phase 16 / REL-04). The start/welcome page renders it; the in-app layout's top-left does not. Likely a one-line addition to the main layout's header partial.

### 6. Email step (ConnectEmailStep) buttons actually work
expected: On the wizard's email step, clicking "Connect Gmail" / "Connect Outlook" opens the OAuthClientWizardModal (Phase 13's existing email-scan modal) so the user can authenticate. Clicking "Skip" advances the wizard to the next step (first import). The footer "Back" navigates to the previous step.
result: failed
notes: User reports buttons on the Email step do nothing — no modal opens, no navigation happens. Likely candidates: (a) the modal-open dispatch event name mismatch between ConnectEmailStep (Plan 03b) and OAuthClientWizardModal (Phase 13 existing) — Plan 03b's ConnectEmailStep was supposed to mount the modal AND dispatch `oauth-client-wizard:open` with the provider, but the modal listens for that event only if it's globally mounted (same shape as the CR-01 critical finding for SuggestMappingModal); (b) the step's skip/next/back wire:click handlers route through SetupWizard which may not be receiving the events because the parent component isn't listening for the same names; (c) the embedded OAuthClientWizardModal slot in the step's blade isn't actually rendered (placeholder lost during the 03a→03b split). Needs reproduction + DOM/console inspection in the running app to pin down which.

### 7. FirstImportStep shows preview of statements already uploaded in earlier steps
expected: By the time the user reaches step 5 (FirstImportStep), the bank statements from step 3 (ConnectBankStep) and the credit-card PDFs from step 4 (ConnectCardStep) have already been uploaded. Step 5 should render the resulting preview of those imports (combined transaction list across both sources, ready to confirm and commit) — NOT re-open a blank importer asking the user to upload again. The user must not be asked to upload the same files twice.
result: failed
notes: ConnectBankStep + ConnectCardStep collect the files but the FirstImportStep blade mounts `<livewire:import.upload-wizard />` (or equivalent) which starts from scratch. The collected files from earlier steps are never handed off to the preview surface, so the user perceives the wizard as broken / repetitive. Two reasonable fixes: (a) earlier steps stash uploaded file paths into wizard_progress.data; FirstImportStep reads them and runs the preview pipeline against the stashed paths automatically; or (b) consolidate uploads so the earlier connector steps ARE the upload UX and FirstImportStep is a read-only preview of the resulting transactions across both sources. Option (b) is closer to the locked UI-SPEC intent and avoids the upload-twice anti-pattern entirely.

### 8. ConnectCardStep supports multiple monthly PDFs in one upload
expected: ICS card statements are PDF-only (per project memory `project_ics_portal_pdf_only.md`) and ICS issues one PDF per calendar month. To bootstrap any meaningful history, a new user needs to upload 12+ monthly PDFs. ConnectCardStep must accept a multi-file selection (drag-multiple or pick-multiple). The import pipeline processes each PDF and the fingerprint stage deduplicates any transactions that overlap statement-period boundaries.
result: failed
notes: Plan 03b's ConnectCardStep enforces `extensions:pdf + max:10240` on a single-file Livewire `WithFileUploads` shape (the `FileUpload $statement` property). Needs to be `array<UploadedFile> $statements` with the same per-file validation, plus the file-input element gets the `multiple` attribute + the helper copy clarifies multi-file support. The drop-zone Blade component (Plan 03b's `drop-zone.blade.php`) already supports multiple drag-and-drop visually; the property needs to be plural. Downstream: each file becomes its own ImportPipeline run; the existing FingerprintStage already handles cross-file deduplication, so no new dedup logic needed. Coupled with G7 — if the wizard consolidates uploads into a stashed-paths model, this trivially extends to N files per source.

### 9. After completing the wizard, transactions actually land in the database
expected: After the user goes through ConnectBankStep + ConnectCardStep (uploading real statements), the parsed transactions persist to the canonical `transactions` table. When the user opens the dashboard / `/transactions` after finishing the wizard, they see their actual data. The core value of the app ("show me my finances in one place") depends on this.
result: failed
notes: **Most severe finding to date.** User reports the wizard steps appeared to accept uploads but no transactions are visible afterwards — neither in dashboard nor in the transaction list. This means either: (a) The connector steps run upload + parse → preview cache but NEVER call the confirm/commit stage that promotes preview rows into `transactions`. The standalone Import flow (`/imports/upload` → preview → confirm) has an explicit user-confirm step that's missing from the wizard. (b) The PaymentTypeClassifierStage (Plan 02) is silently rejecting rows because the CHECK trigger on `transactions.payment_type` rejects nulls and the per-source hinters return null for too many rows. (c) The wizard step's `submit()` succeeds but the result is held in component state that vanishes when the wizard advances to the next step. Compounds G7 — even if FirstImportStep re-opens the importer, the user's earlier uploads were already discarded. Compounds G1 — starting balance derivation is moot if no transactions are imported. This single finding probably explains why the user feels the wizard "did nothing." Needs urgent reproduction with logging at every pipeline stage.

### G9 — Wizard uploads never persist to transactions table (CRITICAL bug)
status: open
severity: critical
type: bug
test_ids: [9]
note: Top-priority finding. User reports the wizard steps accept files but no transactions appear after the wizard finishes. This is the core-value-defeating bug — the whole wizard accomplishes nothing if data doesn't land. Debug path: (1) Add `Log::info` at the end of each connector step's submit handler showing rows-parsed-count. (2) Check `transactions` table row count before/after a wizard run. (3) Compare against the standalone `/imports/upload` flow which DOES work — diff the call chain. Likely the wizard steps stop at preview (PreviewCache) and never invoke the ConfirmImport action that the standalone flow calls. If that's the cause, the fix is either: (a) auto-confirm at the end of each connector step (no user confirm needed — they explicitly uploaded); or (b) defer all confirms to FirstImportStep's "Commit everything" button, requires G7's stashed-paths model. Option (a) is the simplest; option (b) is the better-aligned with the locked UI-SPEC intent of FirstImportStep being the "here's everything we found, confirm" surface. **This finding likely subsumes part of G7 — if uploads don't persist, the FirstImportStep re-opening the importer is the user's only chance to actually commit data, which is why it exists at all.**
