## Current Test

UAT walkthrough of phase 16.1's "zero-friction first-run setup" against the locked CONTEXT.md, UI-SPEC.md, and the freshly-built Mac amd64 bundle. The user surfaced five gaps/bugs before formally clicking through the .dmg.

## Tests

### 1. Setup wizard captures the user's starting balance
expected: After the user completes the first import (FirstImportStep), the wizard captures or auto-derives a starting balance + starting date so the dashboard can report an actual current balance, not just transaction deltas. "Frictionless" means the wizard should auto-detect from the imported files when possible (CAMT.053 `<OpngBal>`/`<ClsgBal>`, MT940 `:60F:`/`:62F:`, ICS PDF closing balance, PayPal running balance column) and present a one-click confirm.
result: missing
notes: Neither CONTEXT.md `<decisions>` nor UI-SPEC.md mention starting balance. The wizard ends at FirstImportStep with a preview but no balance capture. The whole "this is your balance today" loop is broken without it.

### 2. Artisan commands popover (Dev Mode) renders without a white page
expected: From `/dev/commands` (Dev Mode → Artisan), opening the run-artisan-command popover for any whitelisted command (db:backup, diederik:doctor, cache:clear, route:list, etc.) renders the command form with arg inputs, a Run button, and live stdout/stderr stream.
result: failed
notes: Popover renders a white page. Confirmed regression. Pre-existing Phase 16 work (DEVUI-02 SAFE-tier artisan runner). Not introduced by 16.1.

### 3. Wizard copy is bank-format-driven, not ASN-only
expected: ConnectBankStep copy + format chips + helper text refers to the supported export formats (CAMT.053, MT940, CSV) and lists the Dutch banks that support each (CAMT.053: ASN, ING; MT940: ASN, ING, Rabobank, Triodos, SNS, Bunq). Users with non-ASN banks should not be told this is an "ASN-only" wizard.
result: failed
notes: The wizard copy in `Modules/Onboarding/Resources/views/livewire/steps/connect-bank-step.blade.php` is locked to ASN. The supporting parsers (genkgo/camt + kingsquare/php-mt940) handle every Dutch bank's exports. Pure copy fix, no architecture change.

### 4. Importing a PDF (ICS card statement) renders without an error on the preview
expected: User drops an ICS card monthly PDF on the ConnectCardStep upload zone (or `/imports/upload`). The import pipeline parses the PDF, produces preview rows, and the preview wizard renders them. No error toast, no crash, no infinite spinner.
result: failed
notes: User reports "PDF upload still gives an error on import preview". Need to reproduce and capture the exact error (toast text, log line, exception class). Could be (a) pre-existing Phase 12 ICS PDF parser bug, (b) the new ConnectCardStep sending the PDF to a code path that hasn't been wired correctly, or (c) the new PaymentTypeClassifierStage rejecting the parsed row. Needs debug session before fix.

### 5. App top-left shows the brand logo
expected: The top-left corner of the in-app chrome (every authenticated page) shows the brand SVG that is rendered on the start/welcome page. Brand consistency, no placeholder, no missing element.
result: failed
notes: The brand SVG lives at `resources/brand/logo.svg` (Phase 16 / REL-04). The start/welcome page renders it; the in-app layout's top-left does not. Likely a one-line addition to the main layout's header partial.

### 6. Email step (ConnectEmailStep) buttons actually work
expected: On the wizard's email step, clicking "Connect Gmail" / "Connect Outlook" opens the OAuthClientWizardModal (Phase 13's existing email-scan modal) so the user can authenticate. Clicking "Skip" advances the wizard to the next step (first import). The footer "Back" navigates to the previous step.
result: failed
notes: User reports buttons on the Email step do nothing — no modal opens, no navigation happens. Likely candidates: (a) the modal-open dispatch event name mismatch between ConnectEmailStep (Plan 03b) and OAuthClientWizardModal (Phase 13 existing) — Plan 03b's ConnectEmailStep was supposed to mount the modal AND dispatch `oauth-client-wizard:open` with the provider, but the modal listens for that event only if it's globally mounted (same shape as the CR-01 critical finding for SuggestMappingModal); (b) the step's skip/next/back wire:click handlers route through SetupWizard which may not be receiving the events because the parent component isn't listening for the same names; (c) the embedded OAuthClientWizardModal slot in the step's blade isn't actually rendered (placeholder lost during the 03a→03b split). Needs reproduction + DOM/console inspection in the running app to pin down which.

### G6 — Email step buttons do nothing (bug)
status: open
severity: high
type: bug
test_ids: [6]
note: ConnectEmailStep buttons are inert in the running build. Both connector buttons (Connect Gmail / Connect Outlook) and the Skip / Back navigation buttons. Most likely cause is the OAuthClientWizardModal embed: Plan 03b's `EmailStepEmbedsOAuthModalTest` asserts that the step's blade mounts `<livewire:email-scan.o-auth-client-wizard-modal />` AND that clicking the connector buttons dispatches `oauth-client-wizard:open` with a provider arg. If the test passed in isolation but the modal isn't being found in the rendered DOM in production (or the dispatched event name doesn't match what the modal listens for), the click handler succeeds silently and nothing visible happens. Mirror the CR-01 critical finding (SuggestMappingModal) from the 16.1 code review: mount the OAuthClientWizardModal once in the main authenticated layout, NOT per-step, and have ConnectEmailStep dispatch into the globally-mounted modal. Skip/Back stagnation suggests a separate wire:click → SetupWizard parent event mismatch — verify the step actually emits `wizard:next` / `wizard:skip` and the parent's `#[On]` listeners catch those exact names. Needs DOM inspection of the running build (right-click → inspect the step card → check what Livewire components are mounted at that node, then check the browser console for any wire:click errors).
