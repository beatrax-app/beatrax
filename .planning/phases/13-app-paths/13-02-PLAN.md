<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → EmlBlobStore::appRelative() | Per-message `.eml` blob paths are built from `provider_message_id`; an untrusted id segment could escape the inbox dir |
| migration → filesystem | The Auth migration moves a secrets file; a wrong path could write the secrets file outside the protected directory |
| app → user (error copy) | `OAuthClientWizardModal` surfaces a filesystem path to the user — path disclosure in UI copy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-04 | Tampering / EoP | `EmlBlobStore` blob-path construction | mitigate | `MESSAGE_ID_PATTERN` validation preserved unchanged; `appRelative()` rejects `..` segments (Plan 01 control); only validated slugs are joined |
| T-13-05 | Information Disclosure | `OAuthClientWizardModal` error string naming `storage/app/secrets/` | mitigate | Reword the user-facing copy so it does not name a hard-coded filesystem path — reduces path disclosure and removes the literal the gate forbids |
| T-13-06 | Information Disclosure | OAuth secrets file path after re-rooting (`secretsPath()`) | accept | The Auth migration + `OAuthSecretsRepository` keep their existing chmod-0600/0700 hardening; this plan changes the *path*, not the *mode* — file-permission posture is unchanged (RESEARCH Security Domain V12) |
| T-13-SC | Tampering | npm/pip/cargo installs | mitigate | Phase 13 installs no packages; no install task exists, so no slopcheck checkpoint is required (RESEARCH § Package Legitimacy Audit — not applicable) |
