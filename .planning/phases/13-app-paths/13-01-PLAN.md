<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS env → app | `NATIVEPHP_STORAGE_PATH` is read from the process environment and becomes a filesystem-path base — an attacker-controlled value would redirect every read/write |
| caller → UserDataPathService::appPath() | A `$relative` argument crosses into path construction; untrusted segments could escape the storage sandbox |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Tampering / EoP | `appPath(string $relative)` | mitigate | `appPath()` throws `\InvalidArgumentException` on any `..` segment (Task 1); callers keep their own id-validation; service only joins trusted sub-paths onto `storageRoot().'/app'` |
| T-13-02 | Tampering | `NATIVEPHP_STORAGE_PATH` env value | accept | In Herd dev the var is absent (project-root fallback); in a shipped build Phase 15 sets it from NativePHP's own appdata path. The value originates from the trusted bundle config, not user input — local-only single-user app, low-value target. Documented as a Phase 15 hand-off (RESEARCH Pitfall 6). |
| T-13-03 | Information Disclosure | resolved path strings in env-unset vs env-set branches | accept | Path strings contain no secrets; the secrets *files* keep their existing chmod-0600/0700 hardening (owned by callers, not this service — preserved in Plan 02). |
| T-13-SC | Tampering | npm/pip/cargo installs | mitigate | Phase 13 installs no packages (RESEARCH § Package Legitimacy Audit — not applicable); no install task exists, so no slopcheck checkpoint is required. |
</threat_model>
