<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| env file → config layer | `DIEDERIK_DEV_MODE` / `CACHE_LOCK_STORE` values cross from the local `.env` into runtime config; a wrong value silently changes which infrastructure the app uses |
| shipped build → database | The `database` queue + cache lock store reads/writes new tables on the local SQLite file |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01-01 | Elevation of Privilege | `config('app.dev_mode')` | mitigate | `(bool)` cast at the config layer + default `false` (fail-closed): a shipped build with `DIEDERIK_DEV_MODE` unset gets dev-mode OFF; Plan 03's Horizon gate uses strict `!== true` |
| T-14-01-02 | Tampering | `cache_locks` table absence | mitigate | `make:cache-table` generates the exact framework schema for `DatabaseLock`; hand-authoring is forbidden to avoid column-name drift that would make atomic lock acquire silently fail-open |
| T-14-01-03 | Information Disclosure | `config/cache.php` `redis` store entry | accept | The `redis` store entry stays defined for the dev box (D-07); it is inert in a shipped build because `CACHE_LOCK_STORE` defaults to `database` and no Redis daemon runs — no transaction data is exposed |
| T-14-01-SC | Tampering | npm/composer installs | mitigate | No package installs in this plan — only framework-stub migration generation. RESEARCH Package Legitimacy Audit confirms zero new packages; no slopcheck checkpoint required |
</threat_model>
