# Phase 11 — UI Design Contract

> Visual and interaction contract for the **`SystemAlertsBanner`** Livewire SFC — the single new frontend surface this phase ships. Phase 11 is a backend-heavy phase (artisan commands, migrations, probes, arch tests); the banner is the only user-visible deliverable. Generated by gsd-ui-researcher (auto-mode; every decision pre-populated from CONTEXT.md D-1108..D-1111 + RESEARCH.md Pattern 4 + existing Phase 9 drift-alert / Phase 5 chain-drawer chrome), verified by gsd-ui-checker.

---

## Scope

ONE component + ONE slot. Nothing else.

| Surface | Path | Purpose |
|---------|------|---------|
| Livewire SFC (component class) | `Modules/Core/Internal/Http/Livewire/SystemAlertsBanner.php` | Reads `SystemAlertQuery::active($user)` on every render; calls `AcknowledgeSystemAlert` on click |
| Livewire SFC (Blade view) | `Modules/Core/Resources/views/livewire/system-alerts-banner.blade.php` | Renders one banner row per active alert, severity-tiered |
| Layout slot | `resources/views/layouts/app.blade.php` | One new `@livewire('core.system-alerts-banner')` line, inserted between `@livewire('core.top-nav')` and the `@livewire('categorization.rule-form-modal')` line, INSIDE the existing `@auth` block |

Out of scope: new pages, forms, modals, charts, Flux components, layout containers, mobile-specific styling. The banner inherits the existing responsive `app.blade.php` shell.

## Spacing Scale

Declared values (Tailwind 4 default scale, used multiples only):

| Token | Value | Banner Usage |
|-------|-------|--------------|
| xs | 4px (`gap-1`, `mt-1`) | Icon-to-text gap inside a banner row; secondary-line top margin |
| sm | 8px (`gap-2`, `mt-2`, `space-y-2`) | Action-cluster gap; stack gap BETWEEN warning rows under the critical stack |
| md | 16px (`p-4`, `gap-4`) | Banner row inner padding; gap between message column and action column |
| lg | 24px (`px-6`) | Horizontal page-edge padding matches existing `app.blade.php` content gutter |
| xl | 32px | Not used in banner; reserved for parent layout |

**Stack gap between consecutive banners:** 8px (`space-y-2`) — visually grouped, never collapsed to zero, never widened beyond 8px (the banner is a single conceptual surface even when multiple rows render).

**Exceptions:** none. The banner uses only the 4px multiples already on the substrate.

## Typography

Banner uses **three** sizes (compact surface; no display type). All weights drawn from the existing two-weight system locked by `dashboard-drift-badge.blade.php`.

| Role | Size | Weight | Line Height | Banner Usage |
|------|------|--------|-------------|--------------|
| Banner message (primary) | 14px (`text-sm`) | 500 (`font-medium`) | 1.5 (`leading-normal`) | The headline sentence of every banner row, including the leading `⚠` for critical |
| Banner metadata (secondary) | 12px (`text-xs`) | 400 (regular) | 1.5 (`leading-normal`) | Timestamp / suspect file path / "Mark as resolved" button label |
| Action button | 12px (`text-xs`) | 500 (`font-medium`) | 1.0 (`leading-none`) — button padding handles vertical rhythm | "Mark as resolved" dismiss button label |

Two weights total: regular (400) for metadata; medium (500) for message + action label. NO semibold, NO bold. Mirrors `drift-alert-row.blade.php` exactly.

Numerics: every timestamp, file path, and elapsed-time string MUST render under `font-variant-numeric: tabular-nums` via the inline style attribute (project convention from `app.css`).

## Color

The substrate uses an explicit **60 / 30 / 10** split with `slate` as dominant + secondary and `rose` / `amber` / `emerald` reserved for semantic states. The banner adopts the same palette verbatim — NO new colors are introduced.

| Role | Tailwind tokens | Banner Usage |
|------|-----------------|--------------|
| Dominant (60%) — page surface | `bg-white text-slate-900` | Inherited from `app.blade.php`; the banner does NOT recolor the page |
| Secondary (30%) — neutral chrome | `border-slate-200`, `text-slate-500` (metadata), `bg-slate-100 hover:bg-slate-200 text-slate-700` (default button rest), `focus-visible:ring-slate-900` | Warning + info banner chrome; default-state action button |
| Accent (10%) — semantic critical | `border-rose-500 bg-rose-50 text-rose-900` (banner row) + `bg-rose-600 text-white hover:bg-rose-700 focus-visible:ring-rose-600` (critical-only dismiss button) | EXCLUSIVELY for `critical` severity rows. **No other surface on the page uses rose.** |
| Semantic warning | `border-amber-300 bg-amber-50 text-amber-900` | EXCLUSIVELY for `warning` severity rows |
| Semantic info | `border-slate-200 bg-slate-50 text-slate-700` | EXCLUSIVELY for `info` severity rows |

**Accent (rose) reserved for:** the **critical** banner row and its dismiss button. Nothing else. The banner is the only place rose appears in v1; Phase 10's "shortfall pill" already uses `rose-50` and is the only adjacent token consumer — the banner does not collide because they never co-render in the same row.

**Destructive:** there are NO destructive actions in this phase. "Mark as resolved" is an **archive** action (sets `acknowledged_at`; row never deleted); it is NOT styled destructive. The critical-severity dismiss button uses `rose-600` because the banner row already announces a critical state — the button color matches the row tone, it does not signal a destructive action.

**Severity tier rationale (locked by D-1110):**
- `critical` (rose-50/500/900) — only `backup_corrupt` raises this in v1. Demands visual attention because data integrity is at risk.
- `warning` (amber-50/300/900) — `backup_overdue`, `wal_mode_missing`, `synchronous_misconfigured`. Inconvenient, not data-losing.
- `info` (slate-50/200/700) — none in v1 (the schema allows it; no kind is wired to it yet). Reserved for future modules.

## Anatomy

```
┌──────────────────────────────────────────────────────────────────────┐
│ <livewire:core.system-alerts-banner>                                 │
│                                                                      │
│  Critical stack — rendered first, in chronological order (oldest top)│
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │ [⚠]  message (text-sm / font-medium / rose-900)  │ [button] ←┐│  │
│  │      metadata (text-xs / rose-900 @ 70% opacity) │           ││  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                              ↑ 8px stack gap          │
│  Warning stack — rendered below critical, in chronological order     │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │ message (text-sm / font-medium / amber-900)      │ [button]    │  │
│  │ metadata (text-xs / amber-900 @ 70% opacity)     │             │  │
│  └────────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  Info stack — none in v1                                             │
└──────────────────────────────────────────────────────────────────────┘
```

**Per-row layout:**
- Flex row: `flex items-start justify-between gap-4`
- Left column (`min-w-0 flex-1`): message line (with optional leading `⚠` glyph for critical) + metadata line beneath
- Right column (`shrink-0`): single dismiss button
- Row container: `rounded-lg border p-4` + severity background tokens above
- Wrapper around all rows: `space-y-2 px-6` (matches existing content gutter)
- Banner placement is NOT sticky-on-scroll in v1 — it sits at the top of the document flow between top nav and `@yield('content')`, scrolling out of view normally. **The "sticky until acknowledged" semantics from CONTEXT (D-1109) refer to DATA persistence across page navigations**, not CSS `position: sticky`. The banner re-renders on every page load until the row's `acknowledged_at` is non-null.

## Severity × Kind Copywriting Contract

Every row's headline is fully template-locked. No free-form server messages render in the banner — the row's `kind` selects the template, and `metadata` JSON fills the placeholders.

| Kind | Severity | Template (verbatim) | Required metadata placeholders |
|------|----------|---------------------|--------------------------------|
| `backup_corrupt` | critical | `⚠ The backup written at {timestamp} failed integrity check. Inspect {suspect_path}. Resolve before relying on backups.` | `timestamp` (ISO 8601 local, formatted `d M Y · HH:mm`), `suspect_path` (path under `storage/app/backups/`, basename only in the rendered string; full path lives in `metadata.suspect_path` for debug) |
| `backup_overdue` | warning | `The most recent verified backup is {hours_old}h old. Run `php artisan db:backup` or wait for the 03:00 scheduled run.` | `hours_old` (integer; rendered without leading zero) |
| `wal_mode_missing` | warning | `SQLite is not in WAL mode (currently {current_mode}). Concurrent writes may stall. Run `php artisan diederik:doctor` for guidance.` | `current_mode` (string from `PRAGMA journal_mode`, e.g. `delete`, `truncate`) |
| `synchronous_misconfigured` | warning | `SQLite synchronous level is {current_level} (expected NORMAL/1). Durability semantics may differ from config. Run `php artisan diederik:doctor` for guidance.` | `current_level` (integer 0–3 from `PRAGMA synchronous`) |

**Punctuation + capitalisation rules:**
- Sentence case. NO trailing emoji. The leading `⚠` glyph is **only** permitted on `backup_corrupt` (D-1109: "calm tool — severity gradient is honest"). It is part of the template, not a CSS pseudo-element.
- Backtick-wrapped artisan commands render as inline `<code class="rounded bg-rose-100 px-1 text-rose-900">` (or amber-100/amber-900 for warning rows) inside the message text — tightens the visual cue without inventing new tokens.
- Every interpolation goes through Blade `{{ }}` escaping; raw `{!! !!}` is forbidden in this view (mirrors `DashboardDriftBadge` security note from RESEARCH §S4).

**Metadata line (secondary, beneath message):** renders the alert's `created_at` formatted `d M Y · HH:mm` plus the alert id badge (`#{id}`). One line, two-pieces separated by middle dot.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (per banner row) | **Mark as resolved** |
| Primary CTA `aria-label` | `Mark system alert #{id} as resolved` |
| Primary CTA disabled-while-saving label | `Resolving…` (only visible if Livewire `wire:loading` fires longer than 200ms — `wire:dirty.class.add="opacity-60"` permitted; no spinner glyph) |
| Empty state | **(no render)** — when `$alerts->isEmpty()`, the component returns an empty `<div></div>` wrapper. No "no active alerts" placeholder, no celebratory empty-state. The banner is INVISIBLE when calm. Locked by D-1109 + "calm tool" ethos. |
| Error state (action throws) | The banner is replaced for this request by a single warning row: `Could not resolve alert #{id}. Refresh and try again.` Backed by a try/catch in `acknowledge()` that flashes via session and falls through to render. NO native browser alert, NO Flux toast — visual feedback stays inside the existing banner surface. |
| Destructive confirmation | **none** — "Mark as resolved" is non-destructive (archive-in-place). No confirmation dialog is added in v1. |

**Why no empty-state copy:** the banner is a failure surface. A calm app has no banner. Adding a "no alerts" placeholder would visually anchor the surface even during calm operation, which conflicts with the user's explicit "calm tool" decision and reproduces the loud admin-panel aesthetic the project's UI-05 requirement rejects.

## Interaction Contract

**Mount + render lifecycle (mirrors `DashboardDriftBadge` exactly):**

```
mount: (no state — component is stateless; render does the work)
render(CurrentUser $u, SystemAlertQuery $q, ViewFactory $v): View
  → $user = $u->user()
  → $alerts = $q->active($user)
  → returns view 'core::livewire.system-alerts-banner' with [alerts => $alerts]
```

**Click handler:**

```
public function acknowledge(int $alertId, AcknowledgeSystemAlert $action, CurrentUser $u): void
  → $action($alertId, $u->user())
  → (no explicit re-render — Livewire 4 re-runs render() automatically after the action returns)
```

**Trigger element (per row):**

```blade
<button
  type="button"
  wire:click="acknowledge({{ $alert->id }})"
  wire:loading.attr="disabled"
  wire:target="acknowledge({{ $alert->id }})"
  aria-label="Mark system alert #{{ $alert->id }} as resolved"
  class="{severity-tier classes}"
>Mark as resolved</button>
```

**Refresh semantics:**
- After `acknowledge()` returns, Livewire's automatic re-render re-queries `SystemAlertQuery::active($user)`. The acknowledged row no longer satisfies the scope and disappears.
- No `wire:poll` in v1. Background jobs (`db:backup` corrupt detection, `BackupFreshnessProbe`, app-boot health check) write to `system_alerts` between page loads; the banner surfaces them on the **next** page navigation. Multi-tab live refresh is deferred.
- Optional `wire:poll.30s` is NOT implemented in v1 (explicit RESEARCH §Pattern 4 recommendation).

**Cross-user safety:** `SystemAlertQuery::active(?User $user)` scopes per-user AND includes system-wide (`user_id IS NULL`) rows. `AcknowledgeSystemAlert($alertId, $user)` MUST refuse to acknowledge an alert belonging to a different non-null `user_id`. UI does not need a separate cross-user guard — the action throws `NotFoundHttpException` which Livewire surfaces as a 404 on the next render (mirrors Phase 5 chain-confirm + Phase 9 acknowledge contract).

## Accessibility

| Aspect | Contract |
|--------|----------|
| Landmark role | The banner wrapper has `role="region"` and `aria-label="System alerts"` so screen readers can navigate to it. |
| Per-row role | **Critical rows** use `role="alert"` (assertive — interrupts AT). **Warning + info rows** use `role="status"` (polite — announced on idle). This is the WAI-ARIA-spec-aligned mapping; no aria-live attribute is added because the role already implies the live region. |
| Focus order | Banner sits between top-nav and main content in the DOM, so default tab order is: skip-link → top-nav links → banner dismiss buttons (top-to-bottom) → main content. No `tabindex` manipulation. |
| Dismiss button keyboard | Standard `<button>` — Space + Enter activate, focus ring visible via `focus-visible:ring-2 focus-visible:ring-offset-2` (token per severity: `focus-visible:ring-rose-600` for critical, `focus-visible:ring-slate-900` for warning + info). |
| Focus after dismiss | After `acknowledge()` re-renders the banner with one fewer row, focus MAY be lost (the dismissed button DOM is gone). Acceptable for v1 because the user is dismissing — they do not need to keep interacting. NO programmatic focus shift implemented (would require Alpine on the wrapper; v1 keeps zero Alpine in this SFC). |
| Color-contrast | Every text-on-background pair meets WCAG AA 4.5:1 — verified via the Tailwind palette: rose-900 on rose-50 = 12.6:1; amber-900 on amber-50 = 11.2:1; slate-700 on slate-50 = 10.4:1; white on rose-600 = 5.1:1; slate-700 on slate-100 = 9.1:1. |
| Icons | Inline `aria-hidden="true"` on the `⚠` glyph (it's redundant with the `role="alert"` + message text). |
| Reduced-motion | No animations are introduced; banner appears/disappears on render without transition. Honors `prefers-reduced-motion` by default. |

## State Matrix

| State | Trigger | UI |
|-------|---------|-----|
| Idle (calm) | `$alerts->isEmpty()` | Banner renders an empty wrapper `<div role="region" aria-label="System alerts" class="space-y-2"></div>` (no visible chrome, no copy). The slot reserves zero vertical space. |
| One critical alert | `backup_corrupt` row from `db:backup` | One rose-tinted row at top of page with `⚠` glyph + locked template copy + rose-600 dismiss button. |
| One or more warnings | Any of `backup_overdue` / `wal_mode_missing` / `synchronous_misconfigured` | Amber-tinted row(s) stacked beneath the critical area (which may be empty). Each row has its own slate-100 dismiss button. |
| Mixed | Critical AND warnings active | Critical stack renders first (top), warnings beneath, 8px gap between every row. Order within a severity is chronological (oldest first → newest last), matching `created_at ASC`. |
| Acknowledging (transient) | Between `wire:click` and Livewire's re-render | The clicked button is `disabled` via `wire:loading.attr="disabled"` and dims to 60% opacity via `wire:loading.class="opacity-60"`. No spinner glyph. |
| Action error | `acknowledge()` catches exception | The clicked row is replaced (during this request cycle) by a single warning-style row with copy `Could not resolve alert #{id}. Refresh and try again.` Original row will reappear on the next page load (alert was never archived). |

## Banner Insertion Point (verbatim diff)

**Before** (current `resources/views/layouts/app.blade.php` lines 12–17):

```blade
<body class="antialiased bg-white text-slate-900" style="font-family: 'Inter', system-ui, -apple-system, sans-serif;">
```

**After** (one new line, immediately after `core.top-nav`):

```blade
<body class="antialiased bg-white text-slate-900" style="font-family: 'Inter', system-ui, -apple-system, sans-serif;">
    @auth
        @livewire('core.top-nav')
        @livewire('core.system-alerts-banner')   {{-- new --}}
        @livewire('categorization.rule-form-modal')
        @livewire('categorization.correction-divergence-toast')
        @livewire('receipts.receipt-conflict-toast')
    @endauth
    @yield('content')
```

Rationale for placement:
- INSIDE `@auth` — unauthenticated visitors (loopback login screen) never see system alerts; the banner reads `$currentUser->user()` which requires auth.
- BEFORE the other Livewire modal/toast components — those are interaction surfaces that overlay content; the banner is part of document flow and must precede them so the toast surface can overlay it if both render in the same request.
- Single line addition, surgical change; existing layout structure untouched.

## Flags (genuinely unanswered — surface for verifier, not interactive)

These are intentionally noted rather than asked, per auto-mode protocol:

| # | Flag | Default Recommendation | Author of Final Call |
|---|------|------------------------|----------------------|
| F1 | Should the banner re-render on a `wire:poll.30s` interval to catch background-job-written alerts in long-lived tabs? | **No for v1** — RESEARCH Pattern 4 explicitly recommends deferring. Next page load surfaces them. | Planner / executor; locked here as "no". |
| F2 | Should focus shift programmatically to the next dismiss button (or to top-nav) after a row is acknowledged? | **No for v1** — would require Alpine on the wrapper; the banner is intentionally zero-Alpine. Acceptable accessibility trade-off because focus is being lost on the user's own dismiss action. | Planner; locked here as "no". |
| F3 | What does the rendered backtick-wrapped artisan command look like inside the message? | Inline `<code class="rounded bg-{tier}-100 px-1 text-{tier}-900">php artisan db:backup</code>` — keeps the visual cue tight, no new tokens. | F4 | When the banner re-renders mid-request after an action error, does the original row remain visible OR is it replaced by the error-state row? | **Original disappears for this request; error row takes its place.** Original returns on next page load (the underlying `system_alerts` row was never archived). | Locked here per "Interaction Contract → Action error" row. |

None of these flags are blockers; the defaults are the contract.
