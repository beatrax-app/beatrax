<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| settings user → enable flow | Enabling generates the LOCK-04 data key; the account password crosses here once to build the recovery wrap |
| security downgrade → confirmation | Disabling / changing PIN / removing biometric must re-prove the PIN (D-23) |
| forgot-PIN → recovery wrap | The only path that survives a forgotten PIN without losing the data key |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-15 | Elevation of privilege | Security downgrade without re-auth | mitigate | disable() and changePin() require the correct current PIN; the settings modals gate on it (D-23) — asserted in tests |
| T-05-16 | Denial of service | Forgotten PIN → permanent key loss | mitigate | Password-derived recovery wrap (D-21); rewrapForNewPin recovers the identical data key — asserted by ForgotPinFlowTest |
| T-05-17 | Information disclosure | Account password captured at enable time | mitigate | Password used only transiently to derive the wrap key, verified via Hasher->check, then dropped; sodium_memzero on the derived wrap key; never persisted in plaintext |
| T-05-18 | Spoofing | Idle-preset change treated as a downgrade | accept | Idle preset is not security-sensitive (D-23 explicitly exempts it); no PIN confirmation required |
</threat_model>
