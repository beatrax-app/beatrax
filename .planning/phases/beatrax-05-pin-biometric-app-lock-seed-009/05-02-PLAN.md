<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → AppLockMiddleware | Every authenticated HTTP and Livewire-update request crosses here; a locked session must not serve data |
| PIN attempt → PinVerificationService | Untrusted repeated PIN guesses; online brute force must be throttled |
| session → data key custody | The unwrapped key sits in the encrypted session only while unlocked |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-06 | Tampering | Livewire /livewire/update bypass | mitigate | `Livewire::addPersistentMiddleware(AppLockMiddleware::class)` re-runs the gate on every update request (RESEARCH pitfall 1) — asserted by AppLockLivewireTest |
| T-05-07 | Spoofing | Online PIN brute force | mitigate | Escalating backoff at 5 failures (locked_until short-circuits before hashing) then hard sign-out at 10 (D-10) — asserted by PinVerificationServiceTest |
| T-05-08 | Elevation of privilege | Guest reaching the lock screen / locked user reaching data routes | mitigate | Middleware exempts only auth.lock + logout, and only fires for authenticated users; Authenticate is prepended to the auth group |
| T-05-09 | Information disclosure | Wrap key resident in memory | mitigate | `sodium_memzero` on every derived wrap key in PinVerificationService and AppLockProvisioner |
| T-05-10 | Denial of service | Corrupted pin_wrapped_key | mitigate | unwrap()===false is handled as a non-counting failure with a SystemAlert, not an uncaught crash; password recovery wrap (05-04) is the escape hatch |
</threat_model>
