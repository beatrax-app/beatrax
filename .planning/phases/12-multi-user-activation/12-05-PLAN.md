<objective>
Close the two structural code-review blockers that the verifier left open and ship the owner-creates-partner foundation that Plan 12-06's partner-reset flow depends on.

This plan delivers four things:
1. **CR-01 fix** — make `SignupAction`'s concurrency guard deterministic under SQLite WAL by forcing the transaction into write mode before the `User::count()` check (a plain `SELECT COUNT` does not promote to a write lock; two concurrent signups can both pass).
2. **WR-05 fix** — add the unique index on `user_recovery_codes.code_hash` that the redemption path (Plan 12-06) needs to rely on for at-most-one match; de-duplicate generated codes in `SignupAction`.
3. **CR-02 fix** — implement `ForcePasswordChangeMiddleware` so the `force_password_change_at_next_login` flag is actually enforced, plus the `/change-password` page it redirects to. The User-model docblock currently documents enforcement that does not exist; the middleware makes it true.
4. **Partner foundation** — `AddUserAction` + the `/settings/users/new` developer-gated page so the owner can create the partner account (born with `force_password_change_at_next_login = true`). This is the second user the cross-user tests and the partner-reset flow require.

Purpose: Phase 12's goal requires TWO users; the four executed plans deliver infrastructure for ONE. Without a partner-creation surface there is no second user to isolate or to reset. Without enforcement, the forced-password-change flag is inert.

Output: A developer can sign up, open `/settings/users/new`, create a partner; the partner signs in, is force-redirected to `/change-password`, sets their own password, and lands on the dashboard.
</objective>

<!-- Existing SignupAction — current race-guard shape, see 12-04-SUMMARY.md -->

`Modules/Auth/Public/Actions/SignupAction.php` already exists. Its `__invoke()`
opens a transaction and re-checks `db->connection()->table('users')->count()`
inside it. CR-01: under SQLite WAL a plain SELECT does not acquire a write
lock, so two concurrent transactions can both read 0 and both insert. Fix:
issue a no-op write statement at the TOP of the transaction body to force the
connection into IMMEDIATE write mode:

```
$this->db->connection()->statement('UPDATE users SET id = id WHERE 0 = 1');
```

Place this BEFORE the `count()` re-check. The no-op UPDATE matches zero rows
but still promotes the transaction to a write lock; the second concurrent
signup then blocks on the lock and observes the committed first user.

<!-- ForcePasswordChangeMiddleware — analog: Modules/Core/Internal/Http/Middleware/LoopbackOnly.php; full draft in 12-RESEARCH.md Pattern 5 -->

```
final readonly class ForcePasswordChangeMiddleware
  constructor: CurrentUser $currentUser, UrlGenerator $urls
  private const ALLOWED_ROUTE_NAMES = ['auth.change-password', 'logout']
  handle(Request $request, Closure $next): Response
    $user = $this->currentUser->user();   // CurrentUser contract — NOT Auth facade
    if ($user !== null && $user->force_password_change_at_next_login
        && ! in_array($request->route()?->getName(), self::ALLOWED_ROUTE_NAMES, true)):
      return new RedirectResponse($this->urls->route('auth.change-password'));
    return $next($request);
```

NOT on the noAuthFacadeOrHelper allow-list — `CurrentUser` is the DI seam.
