# Phase 12 — UI Design Contract

> Visual and interaction contract for Phase 12 (Multi-User Activation). Inherits the v1.0 calm-Linear visual vocabulary already in production. Generated by gsd-ui-researcher from CONTEXT.md (D-01..D-27) + the existing v1.0 codebase; verified by gsd-ui-checker.

This phase ships eight new authenticated and unauthenticated views plus one persistent middleware banner:

1. `/signup` — first-user signup ceremony (gated to `User::count() === 0`)
2. `/signup` — recovery-codes inline display (post-signup, same flow)
3. `/login` — sign-in form (reskin of v1.0 `core::auth.login-form` from email→username)
4. `/reset-password` — recovery-code-driven password reset
5. `/change-password` — forced password change (after one-time-login OR `force_password_change_at_next_login = true`)
6. `/settings/recovery-codes` — self-regenerate (and download) own recovery codes from Settings
7. In-app "Add user" page — owner adds the partner; `is_developer`-gated (lives under Settings until Phase 16 promotes it to Dev Console)
8. In-app "Manage user `<username>`" page — owner views the partner profile with "Set new password" + "Regenerate recovery codes" actions
9. `ImpersonationBannerMiddleware` — persistent header banner painted on every authenticated route while `session('auth.impersonating.original_user_id')` is set (the Phase 16 button triggers this; Phase 12 ships the visual cue + the back-end so Phase 16 can wire the click)

Phase 12 does NOT ship a UI for switching users — Phase 16 (Dev Console) owns that button. Phase 12 only delivers the back-end action, the banner middleware, and the visual cue for it (D-20).

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Tailwind v4 + Livewire + Blade — no shadcn; React/Vue stack is not present) |
| Preset | not applicable |
| Component library | none (bespoke Livewire + Volt + Blade snippets; v1.0 pattern locked) |

| Font | `Inter`, `system-ui`, `-apple-system`, `sans-serif` (locally installed; no webfont fetched per local-only constraint) |

**Stack derivation:**

- Layout: `resources/views/layouts/app.blade.php` (loads `@vite(['resources/css/app.css'])`, `@livewireStyles`, `@livewireScripts`).
- Body classes: `antialiased bg-white text-slate-900` with inline `font-family: 'Inter', system-ui, -apple-system, sans-serif`.
- Tabular-nums utility: `style="font-variant-numeric: tabular-nums;"` is sprinkled inline (see `resources/css/app.css`); recovery-codes display MUST use it for the 5×4 grouped code blocks so monospace alignment holds across rows.

## Spacing Scale

Tailwind v4 default 4px-step scale, applied with discipline. Declared tokens used by Phase 12 views (drawn directly from v1.0 usage in `dashboard.blade.php`, `settings-page.blade.php`, `login-form.blade.php`, `system-alerts-banner.blade.php`):

| Token | Value | Tailwind utility | Usage |
|-------|-------|------------------|-------|
| xs | 4px | `p-1`, `gap-1`, `mt-1`, `space-y-1` | Label-to-input gap, inline icon gap |
| sm | 8px | `p-2`, `gap-2`, `space-y-2`, `py-2` | Compact tile padding, button vertical padding, banner section grouping |
| (12px) | 12px | `px-3`, `py-1.5` | Button horizontal padding (compact actions) — matches v1.0 nav buttons |
| md | 16px | `p-4`, `gap-4`, `space-y-4`, `mb-4` | Default card padding (banner, toast); form-section internal spacing |
| lg | 24px | `px-6`, `py-6`, `p-6`, `space-y-6` | Tile padding (KPI), form-card padding, header-block stack |
| xl | 32px | `px-8`, `py-8` | Page-shell horizontal margin (matches top-nav `px-8`) |
| 2xl | 48px | `space-y-12` | Major section breaks (dashboard, settings page sections); applied between the "Sign up" header and the form, and between the "Save these codes" header and the code grid |
| 3xl | 64px | `py-16` | Page-level vertical breathing room above auth viewport (used on `/login`, `/signup`, `/reset-password`, `/change-password` outer containers) |

**Per-element rules:**
- Login/signup/reset/change-password centered viewports: outer `min-h-screen flex items-center justify-center bg-white`; inner `w-full max-w-sm px-6` (v1.0 `login.blade.php` pattern preserved verbatim for the 4 unauthenticated single-action forms).
- Recovery-codes inline page: wider — `max-w-xl px-6` — to fit the 5×4 grouped code block + the "Download .txt" CTA + checkbox + Continue button without crowding.
- Owner-resets-partner "Manage user" page sits inside the authenticated layout (top-nav present): outer container `mx-auto max-w-md` (matches Settings page).
- Persistent impersonation banner: full-width strip, `px-6 py-3` internal, sits ABOVE `core.top-nav` (in the layout slot order: impersonation banner → top nav → system alerts → page content). Justifies the existing `space-y-2` rhythm in `system-alerts-banner.blade.php`.

**Exceptions:**
- The recovery-code group separators are visually a "hairline" — not a spacing token; rendered as `text-slate-400` hyphens between groups, no extra padding.
- The "Mark as used" checkbox tap target is the full-width label, not the 16×16 input — Tailwind `flex items-start gap-3 cursor-pointer` preserved from `settings-page.blade.php` auto-import toggle.

## Interaction Contracts

This section is non-template but load-bearing for the executor — every interaction below has prescriptive details that go beyond the visual contract.

### Sign-in flow (`/login`)

- One form, vertical: `Username` text input → `Password` password input → `Stay signed in on this device` checkbox (checked by default — 5-year remember-me per D-27) → `Sign in` primary button → secondary text-link `Lost your password? Use a recovery code.` → `/reset-password`.
- `autocomplete="username"` on the username input; `autocomplete="current-password"` on the password input. Lowercase the username server-side (D-02) — the input itself is sentence-case-permissive.
- On error: single error line below the form, `text-sm text-rose-600`, copy `Username or password is incorrect.` Never per-field; never differentiated.

### First-user signup (`/signup`)

- Same layout as `/login` but with `Username` → `Password` → `Confirm password`. No remember-me checkbox (no session yet to remember).
- `Create the first account` primary button.
- On submit, server flips `is_developer = true` (D-04), generates 10 recovery codes (D-07/D-08), creates the row, **redirects to the recovery-codes inline page (NOT to dashboard)** — the codes display flow gates the dashboard.

### Recovery-codes inline page (post-signup AND post-regenerate)

- `max-w-xl px-6` container, vertically centered until the content overflows.
- H1 + subhead (see Copy contract).
- 5×2 grid of code cells (so 10 codes lay out 5 down × 2 across on desktop, single column on mobile). Each cell: `text-lg font-semibold font-mono tabular-nums tracking-wider text-slate-900`. Background `bg-slate-50 border border-slate-200 rounded-md px-4 py-3`. Hyphens between groups are `text-slate-400`.
- Below the grid: `Download as .txt` secondary button (slate styling) → produces `diederik-recovery-codes-{username}.txt`, one code per line, no trailing whitespace, no header (D-Specifics).
- Below the download: `I have saved these codes somewhere safe.` plain checkbox — UNCHECKED by default. The `Continue to diederik` primary button is `disabled` (greyed out + `cursor-not-allowed` + `aria-disabled="true"`) until the checkbox is ticked.
- No modal. No `confirm()` prompt. Once the user clicks `Continue` they are redirected to `/` and the codes are NEVER shown again.
- No "back" link, no "I'll do this later" escape hatch — the navigate-away IS the dismissal; codes can only be re-seen via regenerate.

### Forced password change (`/change-password`)

- Middleware redirects every request EXCEPT `/change-password`, `/logout` to `/change-password` whenever `force_password_change_at_next_login = true` (D-Specifics).
- Form: `Current password` (only if NOT triggered by recovery-code login — recovery-code login skips this field because the code itself proved identity) → `New password` → `Confirm new password` → `Save new password` primary button.
- On success: flag clears, redirect to `/` (or to the original intended URL if one was captured before the redirect).

### Recovery-code reset (`/reset-password`)

- Form: `Username` → `Recovery code` (single-line text input, monospace placeholder `A2BJ-XK9M-PQ7N-RX4F-V8HD`) → `New password` → `Confirm new password` → `Save new password` primary button.
- The recovery code input MUST normalize whitespace and case server-side (uppercase, strip dashes for comparison against the bcrypt hash AFTER normalizing).
- On success: code stamped `used_at`, password updated, `force_password_change_at_next_login = false` (the user just set the password they wanted), redirect to `/login` with a single flash `Password updated. Sign in with your new password.` (info severity — uses `text-slate-700`, not emerald).

### Owner-adds-partner ("Add user" page)

- Lives at `/settings/users/new` (developer-only — middleware gate per D-03 + the existing `is_developer` flag).
- Settings-page chrome: `max-w-md mx-auto space-y-12` outer (matches v1.0 settings).
- Form: `Username` → `Initial password` → `Confirm initial password` → `Set initial password` primary button.
- On success: new user row created with `force_password_change_at_next_login = true`, owner sees a flash `User {username} created. They will set their own password the first time they sign in.` (slate info, not emerald). Owner is NOT shown the partner's recovery codes (the partner sees them on their first sign-in after the forced password change).

### Manage-partner page

- Lives at `/settings/users/{username}` (developer-only).
- Settings-page chrome.
- Page H1: `Manage {partner-username}`.
- Two stacked sections:
  1. `Set new password for this user` — secondary slate trigger → opens modal (see Copy contract).
  2. `Regenerate recovery codes for this user` — secondary slate trigger → opens type-to-confirm modal → on success: inline-displays the 10 new codes ON THE SAME PAGE, same `5×2 mono grid` chrome as the signup ceremony, with `Download as .txt` button. NO checkbox-gate this time — the owner can navigate away freely (the partner is the one with the responsibility to memorize).

### Impersonation banner (paint contract, banner middleware)

- Renders on EVERY authenticated route when `session('auth.impersonating.original_user_id')` is set (D-22, D-23). No per-route opt-in.
- Placement: ABOVE the `core.top-nav` slot in `resources/views/layouts/app.blade.php`. Stack order: `impersonation-banner → top-nav → system-alerts-banner → page content`.
- Markup outline:
  ```html
  <div role="alert"
       class="border-b border-amber-300 bg-amber-50 px-6 py-2 text-sm text-amber-900">
  ```

Phase 12 introduces zero new toasts. All ephemeral feedback goes through the existing `system_alerts` banner (via `Modules\Core\Public\Services\SystemAlertQuery`) or inline form flash messages. The v1.0 toast surface (reauth-detected, failed-chain-resolution) is unchanged.

## Accessibility Contracts

- Every form input has a paired `<label for="...">`. No placeholder-only labels.
- Every interactive element has visible focus state via `focus-visible:ring-2 focus-visible:ring-slate-900 focus-visible:ring-offset-2` (emerald variants for emerald buttons; amber-300 variant for the in-banner "Return to self" link).
- The impersonation banner uses `role="alert"` (it appears post-navigation in response to an explicit user action, so polite is acceptable too; alert is chosen so screen readers re-announce it after every page change while impersonating).
- The recovery-codes page sets `aria-live="polite"` on the code grid wrapper so the codes are announced once after the page loads; subsequent re-renders (none happen by design) would not re-announce.
- The forced-password-change interstitial sets `<title>Set a new password · diederik</title>` (`@extends('layouts.app', ['title' => 'Set a new password · diederik'])`); same pattern as `core::auth.login`.
- All buttons that submit destructive actions have `aria-describedby` pointing at their modal body so the screen-reader user hears the irreversibility statement before confirming.
