<!-- OAuthSecretsRepository — REWRITTEN; self-analog. Read the existing file in full first. -->

The existing `OAuthSecretsRepository` has TWO concerns in one JSON document:
1. **Provider client credentials** keyed by provider (`gmail` / `microsoft`):
   `hasProviderClient`, `saveProviderClient`, `loadProviderClient`.
2. **Per-inbox rotation tokens** keyed by `inbox_id`:
   `loadInbox`, `saveInboxRefreshToken`, `rotateRefreshToken`, `removeInbox`.

The `oauth_secrets` table (D-15) has one row per `(user_id, provider)` with
`client_id`, `client_secret` (encrypted), `redirect_uri`, and one
`tokens_blob` (encrypted, nullable) column. The repository must keep BOTH
concerns. Mapping:

- **Provider credentials** → the `client_id` / `client_secret` /
  `redirect_uri` columns of the `(current_user_id, provider)` row.
- **Per-inbox tokens** → encode the inbox-token list as a JSON object inside
  the encrypted `tokens_blob` column. The `tokens_blob` of a provider row
  holds the inbox entries for THAT provider (each inbox already carries a
  `provider` field). An inbox's tokens therefore live in the `tokens_blob` of
  its provider's row. `loadInbox(int $inboxId)` must locate the inbox across
  the current user's provider rows; `saveInboxRefreshToken` /
  `rotateRefreshToken` / `removeInbox` mutate the relevant provider row's
  `tokens_blob`.
- ALTERNATIVE the executor may choose: if cross-provider inbox lookup by id is
  awkward, decode-merge all of the current user's `tokens_blob` columns into
  one in-memory map keyed by inbox_id for reads, and on write target the row
  whose `provider` matches the inbox's stored provider. Pick the simpler
  correct option and document it in the summary. Either way the PUBLIC
  signatures are frozen.

Constructor rewrite — replace `public function __construct(private readonly
Filesystem $files) {}` with:

```
public function __construct(
    private readonly DatabaseManager $db,
    private readonly CurrentUser $currentUser,
) {}
```

`CurrentUser` is `Modules\Core\Public\Contracts\CurrentUser`. Use
`OAuthSecret` (the Eloquent model — `Modules\EmailScan\Models\OAuthSecret`,
already exists with `encrypted` casts + `BelongsToUser`) for reads and writes
so the encrypted casts apply. Every read: `OAuthSecret::query()->where(
'user_id', $this->currentUser->id())->where('provider', $provider)`. Every
write sets `user_id => $this->currentUser->id()`.

CLI may resolve the repository without an authenticated user. Read
`Modules/Core/Public/Contracts/CurrentUser.php` + `CurrentUserService.php` to
see what `id()` returns when unauthenticated. If it can return null, the
repository must handle that — either throw a clear typed exception or operate
on the null-user scope consistently. EmailScan jobs run under an authenticated
context in v2.0; confirm and document.

The `InboxCredentials` DTO and the `SecretsWriteFailed` exception are part of
the Public surface — keep them. `SecretsWriteFailed` may become rare (DB
writes throw `QueryException`); keep the type for signature compatibility but
it is acceptable for the new code path to never throw it. Document.

The class-level docblock currently narrates the chmod-600 atomic-write JSON
sequence. REPLACE it entirely (do not append) with a present-state description
of the per-user SQLite-backed store with encrypted casts. No history language,
no "previously this was..." — CLAUDE.md `feedback_docs_describe_current_state`.

Drop the now-dead members: `PATH_RELATIVE`, `DIR_MODE`, `FILE_MODE`,
`writeAtomic`, `readAll`, `absolutePath`, `performRename`, the umask/flock
machinery, and the `Filesystem` import. Keep `ALLOWED_PROVIDERS` + the
`assertProvider` guard.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OAuthSecretsRepository → oauth_secrets table | per-user OAuth client credentials + inbox refresh tokens cross into persistence |
| current user scope → repository read | a query unscoped by user_id would leak another user's inbox tokens |
| legacy JSON file → filesystem | the pre-swap secrets file remains on disk as a rollback artefact |
| oauth_secrets columns at rest | client_secret + tokens_blob ciphertext on disk in the SQLite file |

## STRIDE Threat Register (ASVS V6 Cryptography · V8 Data Protection · V4 Access Control · V14 Configuration)

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
