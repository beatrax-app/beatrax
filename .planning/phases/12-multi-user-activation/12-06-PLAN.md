<objective>
Close CR-03 — the recovery codes are write-only — by shipping the redemption
path: a `/reset-password` page, a CLI fallback, and the owner-resets-partner
surface. After Plan 12-04 the codes are issued, hashed, and displayed but can
never be redeemed; the login page renders a live `/reset-password` link that
404s. This plan makes that link resolve.

Delivers:
1. **RecoveryCodeNormalizer + RecoveryCodeAuthenticator** — the shared
   verification core: normalise a typed code (uppercase, strip hyphens/space),
   find the user by username, match against unused `code_hash` rows under a
   row lock, stamp `used_at` on the match, emit a `system_alerts` audit row.
2. **ResetPasswordAction + /reset-password page** — username + recovery code +
   new password → password updated, code consumed, `force_password_change_at_
   next_login` cleared, redirect to `/login`.
3. **ResetPasswordCommand** — `php artisan diederik:reset-password <username>`
   interactive CLI fallback (hidden password prompt, refuses non-interactive
   use), sets `force_password_change_at_next_login = true`.
4. **RegenerateRecoveryCodesAction + ManageUserPage** — the developer opens
   `/settings/users/{username}` and can set a new password for the partner or
   regenerate their recovery codes (10 new rows; old unused codes stamped
   used).

Purpose: A single-user local app has no SMTP and no other way back in — if the
owner forgets the password the database is unrecoverable despite saved codes.
This plan is the recovery path. It also gives the owner a way to reset the
partner without the partner present.

Output: A user who forgot their password can visit `/reset-password`, type
their username + a recovery code + a new password, and sign back in. The owner
can manage the partner's password and codes from `/settings/users/{username}`.
</objective>

<!-- RecoveryCodeNormalizer — first-of-kind; trivial stateless -->

```
final class RecoveryCodeNormalizer
  normalize(string $input): string
    // strtoupper, remove every char not in the D-11 alphabet [A-NP-Z2-9]
    // returns the bare 20-character code (no hyphens) for hashing comparison
```

The codes are bcrypt-hashed at issue time as the FORMATTED string
(`AAAA-BBBB-...`). DECISION for this plan: RecoveryCodeAuthenticator compares
the normalised typed input re-formatted into the 5-group hyphenated shape
against the stored hash — i.e. normalise to bare 20 chars, then re-insert
hyphens every 4 chars, then `Hasher::check` against `code_hash`. Read
`SignupAction.php` + `RecoveryCodeFormatter` to confirm exactly what string
was hashed (the displayed/`.txt` formatted string) and match that shape.

<!-- RecoveryCodeAuthenticator — analog: Modules/Core/Public/Actions/AcknowledgeSystemAlert.php; full draft 12-RESEARCH.md Pattern 4 -->

```
final class RecoveryCodeAuthenticator
  constructor: DatabaseManager $db, Hasher $hasher, Clock $clock, RecoveryCodeNormalizer $normalizer
  verify(string $usernameInput, string $codeInput): ?User
    return $this->db->connection()->transaction(function () ... {
      $username = strtolower(trim($usernameInput));
      $user = User::query()->where('username', $username)->first();
      if (! $user instanceof User) { $this->emitFailure($usernameInput); return null; }
      $candidate = re-formatted normalised code
      $unused = UserRecoveryCode::query()
        ->where('user_id', $user->id)->whereNull('used_at')->lockForUpdate()->get();
      foreach ($unused as $code):
        if ($this->hasher->check($candidate, $code->code_hash)):
          $code->forceFill(['used_at' => $this->clock->now()])->save();
          $this->emitSuccess($user->username);
          return $user;
      $this->emitFailure($usernameInput);
      return null;
    });
```

NOT on the noAuthFacadeOrHelper allow-list — `Hasher` + `DatabaseManager` are
contracts, no facade or guard call.

<!-- system_alerts severity — CRITICAL CONSTRAINT -->

`system_alerts.severity` is enum-locked by a trigger pair to exactly
`info` / `warning` / `critical` (verified in
Modules/Core/Database/Migrations/2026_05_20_010001_create_system_alerts_table.php).
UI-SPEC writes "severity = error" — there is NO `error` tier. Map every
UI-SPEC "error" to `critical`. Use `SystemAlert::create([...])` (the model is
fillable, `$timestamps = false`, `created_at` via useCurrent default) — do NOT
pass `created_at` unless you intend the DB default. `kind` is a short slug;
use `auth.recovery_code_consumed` (warning) and `auth.recovery_code_failed`
(critical). Message copy: `Recovery code used by {username}.` /
`Failed recovery code attempt for {username}.` (UI-SPEC Copy contract).

<!-- ResetPasswordAction — analog: CreateCategorizationRule.php -->

```
final class ResetPasswordAction
  constructor: DatabaseManager $db, Hasher $hasher, RecoveryCodeAuthenticator $authenticator
  __invoke(string $usernameInput, string $codeInput, string $newPassword): void
    if strlen($newPassword) < 12: ValidationException keyed 'password'
      'Use at least 12 characters.'
    $user = $this->authenticator->verify($usernameInput, $codeInput)
    if $user === null: ValidationException keyed 'code' with copy
      'That username and recovery code do not match. Check the code carefully
       — uppercase, no zero, no oh, no one, no L.'
    update the user row: password (hashed), force_password_change_at_next_login = false
```

ON the noAuthFacadeOrHelper allow-list (already pre-declared in 12-01) — but it
does NOT need to call the guard; it only mutates the password. Keep it free of
any guard call so it stays clean even though the allow-list permits it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /reset-password | unauthenticated user supplies a username + recovery code + new password |
| typed recovery code → bcrypt comparison | attacker-guessable secret crosses into the verification core |
| browser → /settings/users/{username} | a non-developer probing the partner-management route |
| CLI → diederik:reset-password | operator-supplied username at the terminal |
| RegenerateRecoveryCodesAction → user_recovery_codes | 10 plaintext codes briefly exist in memory before hashing + inline display |

## STRIDE Threat Register (ASVS V2 Authentication · V3 Session · V4 Access Control · V6 Cryptography · V11 Business Logic)

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-06-01 | Spoofing | recovery-code brute force | accept | local-only deployment + bcrypt cost factor is the defence per D-12; no app-level rate limiter; ~99-bit code entropy makes guessing infeasible; failed attempts audited to system_alerts |
| T-12-06-02 | Tampering | recovery-code replay (reuse a code) | mitigate | RecoveryCodeAuthenticator queries unused codes under `lockForUpdate()` and stamps `used_at` inside the same transaction — single-use is enforced; a concurrent reuse blocks on the row lock |
| T-12-06-03 | Information Disclosure | username enumeration via reset error | mitigate | the wrong-code error copy is identical whether the username exists or the code is wrong (`That username and recovery code do not match...`) — a prober cannot distinguish the two cases |
| T-12-06-04 | Elevation of Privilege | non-developer reaching /settings/users/{username} | mitigate | RequireDeveloperMiddleware + ManageUserPage defensive `is_developer` check both 404; an unknown username also 404s — no existence leak |
| T-12-06-05 | Repudiation | recovery-code use not logged | mitigate | every verify (success or failure) writes a system_alerts audit row (kind + severity + username) |
| T-12-06-06 | Tampering | weak password set via reset/CLI | mitigate | ResetPasswordAction + ResetPasswordCommand both enforce the 12-character minimum |
| T-12-06-07 | Spoofing | scripted CLI password reset on an unattended machine | mitigate | diederik:reset-password refuses non-interactive use (no `--password` flag, `isInteractive()` gate) per D-14 |
| T-12-06-08 | Information Disclosure | regenerated codes leaking via the Livewire snapshot | mitigate | the 10 plaintext regenerated codes are rendered inline once; follow the 12-04 pattern — never hold them on a serialised public property in a way that re-fetches; if stored on a public prop for the single render, accept the same ~30s window the signup ceremony accepts (T-12-04-02 precedent) and document it |
