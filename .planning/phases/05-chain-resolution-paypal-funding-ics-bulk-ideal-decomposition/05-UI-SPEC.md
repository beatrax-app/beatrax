# Phase 5 — UI Design Contract

> Visual and interaction contract for Phase 5: Chain Resolution (PayPal Funding + ICS Bulk-iDEAL Decomposition). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope (UI surfaces produced):**

1. **Chain drill-down drawer** (D-90 / D-91 / D-92 / D-93, UI-02) — project's first `flux:modal flyout` use. Triggered from `/transactions/{id}` "View chain" button. Vertical waterfall (top = merchant charge, downward = funders). Fully-expanded by default. Three-tier confidence chip per leg. Long ICS bulk-settle fan-outs paginate INSIDE the fan-out block ("Show 10 more · X of N") with no outer drawer scroll.
2. **`/chains/review` page** (D-86 / D-87) — dedicated batch surface for `state='candidate'` chain_links across all the user's transactions. Sort: highest confidence first, then most-recent first. Per-row Confirm / Reject chips. Surfaces an inline "Confirming will auto-promote future matches" hint on the 3rd same-signature confirm.
3. **Inline drawer Confirm/Reject chips** (D-86) — within the chain drawer, candidate legs render dimmed with the same `ConfirmChainLink` / `RejectChainLink` actions as the dedicated page. Optimistic flip on click.
4. **"Next ICS settlement" dashboard tile** (D-99 / D-100, CHN-06) — new tile on the `this month at a glance` dashboard row alongside the existing in/out/net + per-currency tiles. Renders amount + due-date; hides entirely when no open card_statement exists.
5. **Wizard "Resolving chains…" status surface** (D-103 / D-105) — the post-confirm import wizard step polls `chain_resolution_status` every 2s via `wire:poll.2s`. States: `pending` → `running` → `complete`. On `complete`, auto-navigates to the import summary surface ("Imported X transactions · linked Y chain candidates · Z pending review").
6. **Failed-job toast** (D-103) — Filament-notifications-style toast on the dashboard via `wire:poll` against a `failed_jobs` count query. Persistent (does not auto-dismiss); links to `/horizon` for retry/inspect.
7. **Top nav "Review chains" link with count badge** — gains a new nav entry to `/chains/review` between "Uncategorized" and "Settings"; renders a small slate-900 numeric badge with the open-candidate count when > 0.

**Out of scope this phase:**

- Recurring detection (Phase 8), drift alerts (Phase 9), forecasting / what-if (Phase 10).
- Email ingestion (Phase 6), receipt template matchers (Phase 7).
- Manual chain-link creation ("manually link these two rows" — deferred per CONTEXT.md Deferred Ideas).
- Numeric 0..1 confidence display (D-91 explicit; raw confidence stays in `chain_link.confidence` for future audit).
- Per-row "View chain" icon on the `/transactions` list (D-90 — calm aesthetic; entry point is detail-page-only).
- Dedicated `/jobs` failed-jobs page (toast only — full page is Phase 6).
- Dark mode.

## Spacing Scale

Inherited verbatim from `03-UI-SPEC.md`. No new tokens. No exceptions for this phase.

| Token | Value | Usage in Phase 5 |
|-------|-------|-------------------|
| xs | 4px | Gap between confidence-chip and leg label; 4px optical offset between the tile amount and its caption (mirrors Phase 3 dual-currency stack) |
| sm | 8px | Inner padding on confidence chips; gap between waterfall connector lines and the chain-node card body; gap between Confirm and Reject chips in the candidate inline pair |
| md | 16px | Default padding inside a chain-node card; `gap-md` between leg cards in the waterfall; horizontal padding inside the drawer body |
| lg | 24px | Top/bottom padding of the drawer's content region; gap between the chain header and the first waterfall leg; gap between sections on `/chains/review` |
| xl | 32px | Drawer's left/right outer padding; vertical gap between the candidate-rows region and the empty-state message on `/chains/review` |
| 2xl | 48px | Vertical gap between the dashboard's per-currency KPI tile rows (unchanged from Phase 3); same `2xl` separates the "Next ICS settlement" tile section from the per-currency rows when both render |
| 3xl | 64px | Page-level vertical breathing on `/chains/review` between the page heading and the first candidate row |

**Page width:** Unchanged from Phase 1/3 — `max-w-5xl` (~1024px) centered for `/chains/review`. The chain drawer is a Flux flyout, not a page — its width is **`md:w-2xl` (~672px)** at the right edge of the viewport; on mobile it occupies the full viewport width. This width is the locked default for every drawer instance in Phase 5.

**Drawer height:** Full viewport height (Flux flyout default). **No outer scroll** (D-93). Long fan-outs paginate INSIDE the fan-out block — the drawer body itself never overflows.

**Confidence chip dimensions:** `px-2 py-0.5` (8px horizontal, 2px vertical) — `py-0.5` = 2px is exempt from the 4px-multiple rule, locally justified because chips are intentionally smaller than buttons. This is the single Phase 5 exception to the 4px-multiple invariant; declared here so the checker pre-approves it.

## Typography

Inherited verbatim from `03-UI-SPEC.md`. Phase 5 introduces no new sizes or weights. Uses the same 4-role scale.

| Role | Size | Weight | Line Height | Usage in Phase 5 |
|------|------|--------|-------------|-------------------|
| Micro / Caption | 12px | 400 (regular) | 1.4 | Confidence-chip text ("Deterministic" / "Confirmed" / "Candidate"); "Next ICS settlement" tile secondary line ("due ~20 May"); fan-out pagination caption ("Show 10 more · 12 of 23"); review-queue auto-promotion hint; failed-job toast helper text; chain drawer empty-state body |
| Body | 14px | 400 (regular) | 1.5 | Chain-node leg label (counterparty + date), fan-out row label, review-queue row text, Confirm / Reject chip button text, drawer body copy, "Resolving chains…" wizard surface body text |
| Section heading | 20px | 600 (semibold) | 1.3 | Drawer header (`<flux:heading size="lg">` — Flux maps to ~20px semibold); `/chains/review` page heading ("Review chains"); "Next ICS settlement" tile amount caption (matches the existing "In / Out / Net" tile-caption pattern but with the larger heading role for prominence) |
| Display (Tile amount) | 32px | 600 (semibold) | 1.2 | "Next ICS settlement" tile amount (`€523.47`) — matches verbatim the existing Phase 1 KPI tile display role for visual consistency with the surrounding tile row |

**Chain-node leg label typography:**

- **Primary line** (counterparty + amount): Body 14px weight 400 in `text-slate-900` with `font-variant-numeric: tabular-nums` on the amount span. Right-aligned amount.
- **Secondary line** (booked_at date + account name): Micro 12px weight 400 in `text-slate-500`. Below the primary line with `mt-1` (4px optical gap using `xs` token). Same hierarchy contract as Phase 3 dual-currency rows — primary = what the user paid; secondary = where it landed.

**Confidence chip typography:**

- Micro 12px weight **500 (medium)** in chip text. Weight 500 is allowed because Flux's default chip variants ship at medium weight; this does NOT introduce a new project weight (regular 400 + semibold 600 stay declared) — the medium weight is the chip-component-internal default we accept verbatim from Flux. Document only.

**"Next ICS settlement" tile typography (top-down stack):**

```
Next ICS settlement          ← Section heading 20px semibold text-slate-900 (caption above amount)
€523.47                       ← Display 32px semibold text-slate-900 tabular-nums
due ~20 May                   ← Micro 12px regular text-slate-500
```

Note: the existing dashboard KPI tiles use a 12px UPPERCASE caption above the amount (e.g. `In`, `Out`, `Net`). The Next-ICS tile **departs from that pattern** because the label is longer and reads more naturally as a sentence-case Section heading. This is the only Phase 5 typographic deviation from existing tile chrome; locked here for the checker.

**Accent (`emerald-600`) is reserved for — and ONLY for — these Phase-5-new elements (in addition to the Phase 1 + Phase 3 lists):**

1. **`Confirm` chip** on candidate chain links (inline drawer + dedicated `/chains/review` rows). Solid emerald-600 background with white text. This is the only solid-emerald surface Phase 5 adds.
2. **Auto-promotion-success hint icon** — single `<svg>` check mark in emerald-600 next to the inline auto-promotion-hint copy when the user has 2 prior confirmations of the same signature and is about to fire the 3rd. Outlines D-87's "3rd confirm auto-promotes" contract visually.

**Destructive (`rose-600`) is reserved for — and ONLY for — these Phase-5-new elements:**

1. **`Reject` chip** on candidate chain links (ghost variant: `text-rose-600 bg-rose-50 hover:bg-rose-100`). Never solid rose. The `Reject` chip is the second-most-common click on `/chains/review`; making it solid red would dominate the page visually and violate UI-05 "calm".
2. **Failed-job toast accent stripe** — a 2px-wide rose-600 vertical bar on the left edge of the toast body. The toast text stays `text-slate-900`. This is the only Phase-5 use of rose adjacent to body text.

**Three-tier confidence chip color mapping (D-91):**

| Chip label | Resolver state | Background | Text | Border |
|------------|----------------|-----------|------|--------|
| `Deterministic` | `state='confirmed' AND resolver='auto' AND confidence=1.0` | `bg-white` | `text-slate-900` | `ring-1 ring-slate-200` |
| `Confirmed` | `state='confirmed' AND (resolver IN ('user','rule') OR confidence < 1.0)` | `bg-slate-50` | `text-slate-900` | `ring-1 ring-slate-200` |
| `Candidate` | `state='candidate'` | `bg-slate-50` | `text-slate-500` | `ring-1 ring-slate-200` |

**No tier uses a hue.** Confidence is communicated by chip text + dim treatment of the parent leg card (`Candidate` legs render with `opacity-60` on the leg card itself plus the slate-500 chip text). The decision to NOT color-code (e.g. green for Deterministic, amber for Candidate) is deliberate — the project's calm aesthetic forbids semantic-color-by-confidence; users distinguish via the label.

**60 / 30 / 10 audit (Phase 5):**

- 60% dominant white surface — drawer body, `/chains/review` page, "Next ICS settlement" tile, top-nav background unchanged.
- 30% secondary slate-50 / slate-200 — confidence-chip backgrounds, dimmed candidate rows, fan-out containers, review-queue separator lines.
- 10% accent — the `Confirm` chip + the auto-promotion-success icon. The Phase 1 + Phase 3 budget (upload CTA, login button, NEW badge, net-positive KPI, segmented-control selected pill, Settings save button) is unchanged; the new `Confirm` chip is the single Phase 5 addition to the accent budget.

**Audit safety:** the rose-600 destructive surfaces (Reject chip ghost + toast accent stripe) live in the destructive role budget, NOT the 10% accent budget. Total accent surfaces on a typical page remain bounded.

**No new colors.** No hue-based confidence ramp. No solid red anywhere. Currency is communicated by formatted string (carried forward from Phase 3) — never by tile color.

## Focal Points (per Phase 5 surface)

Each new Phase 5 surface declares exactly one primary visual anchor.

| Surface | Primary focal point |
|---------|---------------------|

### Destructive confirmations

**Phase 5 introduces no new destructive actions requiring a confirmation modal.**

- **`Reject` chip on candidate chain links is NOT a destructive action.** It writes `state='rejected'` on a single `chain_links` row; no transactions data is mutated (D-84 invariant); a rejected pair can still be re-linked later via a manual link action (deferred). Single-click with the optimistic flip pattern; no modal.
- **`Confirm` chip is NOT destructive.** It writes `state='confirmed'`; same posture.
- **Re-confirming or un-rejecting** is not a Phase 5 surface — deferred to a future manual-link action.

The wizard's "Discard import" from Phase 1 remains the sole destructive surface in the app.

## Interaction Contracts

### Chain drill-down drawer (D-90 / D-91 / D-92 / D-93, UI-02)

**Trigger:** A `View chain` button on `/transactions/{id}` mounts under the existing detail content. Button styling: hand-rolled `text-sm font-medium text-slate-900 underline-offset-2 hover:underline focus-visible:ring-2 focus-visible:ring-slate-900 focus-visible:ring-offset-2`. **Not** a solid button — visually a text link to avoid competing with the page's existing focal hierarchy (Phase 3 contract). The button is rendered only when the resolver has run at least once for the user (i.e. `ChainLinkQuery::forTransaction($txId)` returns a non-null `ChainTree`, even if the tree is empty).

**Open behaviour:** Click fires `wire:click="$dispatch('chain-drawer:open', { transactionId: {{ $tx->id }} })"`. The drawer Livewire component listens for this event and mounts/refreshes the chain tree. Flux flyout opens with its default animation (ease-out, ~200ms).

**Keyboard:**
- `Escape` closes the drawer (Flux default behaviour; `dismissible="true"`).
- Click anywhere outside the drawer closes it (Flux default).
- Focus trap: Flux applies a focus trap when the drawer is open (Flux default).
- Initial focus: lands on the drawer heading (`<flux:heading>`) — set via the Flux `autofocus` slot pattern.
- Tab cycles through every interactive element in document order: confidence chips are not tabbable (no `tabindex`); fan-out pagination buttons are tabbable; Confirm / Reject chips on candidate legs are tabbable; the close `×` (Flux-internal) is the last tab stop and loops back to the heading.

**Click-outside-to-close:** Yes. Flux default. No override.

**Sticky header:** The `<flux:heading>` block carries `sticky top-0 bg-white z-10 pb-3 -mx-6 px-6` so it remains visible as the drawer body scrolls. The header is the only sticky element; fan-outs do not have sticky sub-headers.

**Default expansion:** Every leg is rendered fully expanded (D-92). Each leg card has a `<button>` in its top-right corner with `aria-expanded="true"` and `aria-controls="leg-body-{id}"` that the user can click to collapse the leg body (the leg's secondary line + any nested fan-out). Click toggles the leg's expanded state, persisted in the drawer's Livewire `$collapsedLegs` array property. Refreshing the drawer resets to fully-expanded.

**Fan-out pagination (D-93):**
- Default page size: **10** rows per "show more" click.
- Pagination is forward-only. Initial state: 10 rows visible. Click `Show 10 more · 11 of 23` → 20 rows visible, button updates to `Show 3 more · 21 of 23`. Click again → all 23 visible, button hidden.
- The drawer body itself never scrolls. Long fan-outs grow the drawer's internal content but the drawer container stays fixed-height; the fan-out container has its own `overflow-y-auto max-h-96` so it scrolls in place. Each fan-out container can scroll independently.
- Tappable fan-out rows: clicking a row dispatches `chain-drawer:open` with that row's `transactionId`; the current drawer closes and a fresh drawer opens scoped to the new transaction (single drawer instance; no nested drawers).

**Empty / loading states:** See Copywriting Contract → "Chain drawer — empty / edge states".

**Snapshot baselines required (per RESEARCH.md Pattern 6):**
- 0-leg chain (just-imported, no resolver pass yet) → `Chain not yet resolved` empty state
- 0-leg chain (resolver completed, no links) → `No funding chain found` empty state
- 1-leg chain (PayPal funding only, deterministic) — root + 1 funder
- 3-leg chain (PayPal → ASN with a refund pair) — root + 2 funders
- N-leg chain with fan-out collapsed (10 of 23 visible)
- N-leg chain with fan-out fully expanded (23 of 23)
- N-leg chain with one candidate leg (dimmed, Confirm/Reject chips visible)

### Three-tier confidence chips (D-91)

- Chip text is the only differentiator across the three tiers. Background hue does not encode confidence.
- Chips are **non-interactive** for `Deterministic` and `Confirmed` legs (decorative `<span>`).
- `Candidate` chips remain `<span>`s, but their parent leg card carries the inline `Confirm` / `Reject` buttons (real `<button>`s with full keyboard semantics). The chip itself never has a click handler.
- Tooltips: none. The chip label is self-evident; adding a tooltip with the raw 0..1 confidence violates D-91.
- Screen-reader semantics: `Deterministic` chip carries `aria-label="Confidence: deterministic match"`; `Confirmed` carries `aria-label="Confidence: confirmed"`; `Candidate` carries `aria-label="Confidence: candidate; needs review"`.

### Confirm / Reject inline actions (D-86)

**Optimistic flip:**
- Click `Confirm` → button immediately re-renders as the `Confirmed` chip (`bg-slate-50 text-slate-900`, non-button). Livewire `wire:click` fires `ConfirmChainLink($id)` in the background.
- On server success: flip stays. No toast (the visual flip is the success signal).
- On server error: revert to `Confirm` button + inline 12px `text-rose-600` flash: `Could not save. Refresh and try again.` Flash auto-dismisses after 4 seconds.

**Same action class powers both surfaces (D-86):** `Modules\Chains\Public\Actions\ConfirmChainLink::__invoke($chainLinkId, $user)` is called identically from the drawer Livewire SFC and from the `/chains/review` page SFC. UI shape difference: drawer surfaces the chips inline below the candidate leg's secondary line; review page surfaces them right-aligned on the row.

**Reject scope is per-pair only (D-89):** The button copy is `Reject` not `Reject and ignore similar`. No checkbox for "and similar". The reject scope is one row, not a signature. The auto-promotion hint copy specifically does NOT mention rejects.

**Auto-promotion hint (D-87):**
- Trigger: `chain_link.evidence.confirms_remaining === 1` — meaning this Confirm click would be the 3rd same-signature confirm.
- Render position: directly below the candidate leg's secondary line (drawer) or below the row's secondary line (`/chains/review`).
- Copy: `One more confirm and similar links auto-confirm.` (See Copywriting Contract.)
- After the user clicks Confirm, the hint disappears with the row (drawer leg becomes a `Confirmed` chip; review row fades out). No persistent acknowledgement screen.
- This is the only proactive UX nudge about the learning loop. The dedicated `/chains/review` page does NOT show a global "how this works" banner — calm aesthetic forbids onboarding chatter.

### `/chains/review` page (D-86)

**Sort:** highest confidence first (`chain_links.confidence DESC`), tie-break by most-recent transaction `posted_at DESC`. No user-controllable sort or filter in Phase 5 (calm aesthetic; defer to v2 if the queue grows uncomfortably large).

**Pagination:** Standard Livewire `WithPagination` trait, 25 rows per page. Page navigation links live below the row list, slate-500 underlined "Previous" / "Next" (matches existing transactions-list pagination in Phase 1).

**Empty state:** See Copywriting. Fades in when `count(candidates) === 0`.

**No bulk actions in Phase 5.** Each row's Confirm / Reject is its own click. A future "Confirm all from {merchant}" action is explicitly out-of-scope.

**Keyboard:** `Tab` cycles row by row; within each row, `Tab` goes Confirm → Reject. `Enter` activates the focused chip. Once a row is acted on, focus moves to the next row's Confirm button (Livewire `$dispatch('chain-link:resolved')` event handles focus advancement via Alpine).

### "Next ICS settlement" dashboard tile (D-99 / D-100)

**Placement:** New `<section>` rendered ABOVE the existing in/out/net + per-currency tile rows on `/`. Section has no heading of its own (the tile itself carries the `Next ICS settlement` caption). `mb-2xl` (48px) gap between this tile and the next tile section below.

**Visibility logic:**
- `nextIcsSettlement($user)` returns `null` → tile section is NOT rendered. No "—" placeholder; no empty box. The dashboard simply skips to the in/out/net tile row.
- Returns a `CardStatementForecastTile` DTO with `amount` + `dueDate` → tile renders.
- Multi-statement edge case (rare): see Copywriting → Multi-statement edge case.

**Hover / interaction:** The tile is NOT clickable in Phase 5. A future `Phase 8` recurring-detection surface may make the tile drill into the underlying `card_statement`; for now, the tile is read-only.

**Visual consistency:** Border + radius + padding match the existing in/out/net tiles verbatim (`rounded-lg border border-slate-200 bg-white p-6`). The amount uses Display 32px semibold tabular-nums in `text-slate-900` (NEVER emerald — emerald is reserved for net-positive KPIs per Phase 3 D-46, and a settlement balance is fundamentally negative cash flow, never positive-good).

### Wizard "Resolving chains…" status surface (D-103 / D-105)

**Poll cadence:** `wire:poll.2s="refreshStatus"` (D-105 locked default). Polling stops when status transitions to `complete` OR when the user navigates away.

**State display:**
- `pending` → heading `Resolving chains…` + body `Queued. The chain resolver will start shortly.` + indeterminate Tailwind `animate-pulse` dot (`h-2 w-2 rounded-full bg-slate-400`).
- `running` → heading `Resolving chains…` + body `Linking funding chains and decomposing statement settlements.` + same animated dot.
- `complete` → heading `Done.` + auto-navigate via Livewire `$this->redirect(route('import.results', $importRunId))` fired in `refreshStatus()` when `$status === 'complete'`. Body never visibly renders.

**Failure handling:** If `refreshStatus()` reads `failed_jobs` count > 0 for a chain-resolution job with this user's payload, the surface flips to the `Chain resolution failed` failed-job toast variant inline (replaces the polling status). User can dismiss or click `Open Horizon`.

**No timeout:** Phase 5 does NOT cap the polling duration. A long resolver job (e.g. first scan after a year of imports) is acceptable behaviour; the user sees the status surface until completion. If the user navigates away, the resolver continues in the background and the failed-job toast surfaces any failure on the next dashboard visit.

### Failed-job toast (D-103)

**Trigger:** Dashboard component runs `wire:poll.5s="refreshFailedJobs"` (slower than the wizard poll because the dashboard is the long-lived surface). When `failed_jobs.count_for_user > 0` AND the user has not dismissed the toast in this session, the toast renders.

**Persistence:** The toast does NOT auto-dismiss on a timer. It stays visible until:
1. User clicks the `×` Dismiss button → Livewire sets `$dismissedAt = now()` on a session-scoped property; the toast hides for the rest of the session.
2. OR the `failed_jobs` count for the user drops to 0 (user retried in Horizon) → the toast hides on the next poll.

**Stacking:** Phase 5 ships exactly one toast variant; no stacking required. If a future phase adds another toast type, the layout assumption `fixed bottom-4 right-4` will need a stacking strategy.

**Z-index:** `z-50`. Drawer is `z-40` (Flux default). Toast wins over drawer when both are visible — which is correct: the failed-job is more urgent than a chain detail view.

**Link behaviour:** `Open Horizon` is a plain `<a href="/horizon/failed">` — same-tab navigation. Horizon is local-only (FND-01 / PLT-01) and runs at the same host.

### Top-nav "Review chains" link

**Active state:** When the user is on `/chains/review`, the link gets the existing nav-active treatment (`text-slate-900 font-medium`, slate-200 underline). Same pattern as "Transactions" / "Settings" / "Uncategorized".

**Count badge:**
- Renders when `openCandidateCount > 0`. Hidden when 0.
- The count is fetched via the existing `top-nav.blade.php` partial's `mount()` method (which already reads `$currentUser->user()`); add a single new `Modules\Chains\Public\Services\ChainLinkQuery::openCandidateCount($user): int` method to the existing Public surface.
- Updates on every page navigation. Phase 5 does NOT poll the badge on a timer (the user sees the updated count when they navigate, which is sufficient; polling every nav element is wasteful).
- Cap: `99+` when count > 99. Same cap rule as the existing Uncategorized badge (Phase 1).

All amounts in Phase 5 use the existing `Money::format($locale)` formatter — EUR amounts in `nl_NL` (`€ 523,47` with non-breaking space), non-EUR amounts in `en_US` (`$12.99`). ### Loading & latency

- `View chain` button → drawer open: Drawer Livewire mount + chain-tree query. SQLite + WAL handles this in <100ms for typical chains; no spinner needed.
- `Confirm` / `Reject` click: Optimistic flip is instant; server roundtrip <50ms on SQLite. No spinner.
- Wizard "Resolving chains…" surface: the polling pattern IS the loading indicator; no separate spinner.
- Failed-job toast: surfaces on the dashboard's `wire:poll.5s` cadence; no explicit loading state.

### Focus & a11y

- **Confidence chips** carry `aria-label` per the tier (see "Three-tier confidence chips" above).
- **Confirm / Reject buttons** carry visible focus rings via `focus-visible:ring-2 focus-visible:ring-{color}-600 focus-visible:ring-offset-2`.
- **Drawer:** Flux applies focus trap, `aria-modal="true"`, `role="dialog"` automatically. Initial focus lands on the heading.
- **Sticky drawer header:** Inserts a 1px slate-200 border-bottom when the drawer body has scrolled (rendered via Alpine `x-data="{ scrolled: false }"` + `x-on:scroll.window="scrolled = ($el.scrollTop > 0)"`). Provides a subtle hierarchy cue without violating the calm aesthetic.
- **`/chains/review` page:** Standard `<main>` landmark + page heading `<h1>`; each row is a `<li>` inside a `<ul>`. Confirm / Reject buttons are real `<button>`s with `aria-label="Confirm chain link {N}"` / `aria-label="Reject chain link {N}"` (the N is the chain_link ID).
- **Failed-job toast:** `role="status" aria-live="polite"`. Persistent visibility ensures screen-reader users hear the announcement on page load; the dismiss button is keyboard-reachable via Tab.
- **Color contrast (WCAG AA — verified):**
  - `text-slate-900` on `bg-white` = 16.1:1 (AAA pass).
  - `text-slate-500` on `bg-white` = 5.41:1 (AA pass).
  - `text-white` on `bg-emerald-600` = 4.83:1 (AA pass for normal text).
  - `text-rose-600` on `bg-rose-50` = 4.59:1 (AA pass for normal text).
  - `text-emerald-700` on `bg-white` = 5.07:1 (AA pass).
  - `text-slate-500` on `bg-slate-50` (Candidate chip text) = 4.92:1 (AA pass).
- **Touch targets:** Confirm / Reject buttons via `px-2.5 py-1` calculate to ~28px high — under the WCAG 2.5.5 44×44 recommendation. **Lock exception:** these chips are intentionally small to preserve the calm row density; they sit in a row of 24px-tall text and matching the surrounding rhythm reads as the right hierarchical choice for a desktop-first localhost app. The hit-target rule applies to mobile-primary surfaces; this app is desktop-localhost-only per FND-01. The chips remain keyboard-reachable and the row itself is large enough for a confident pointer click. Document and accept.
