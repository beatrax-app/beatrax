    **Modules/Forecasting/Internal/Pipeline/ScenarioApplier.php**

    `final readonly class` constructor DI: `\Modules\Forecasting\Public\Services\ScenarioQuery $scenarioQuery`, `\Modules\Recurring\Public\Services\RecurringSeriesQuery $seriesQuery`, `Clock $clock`.

    Public method:
    ```
    public function apply(
        array $baselineContributions,    // array<ForecastContribution> from RangeProjector (after ChainAwareForecastRouter)
        int $scenarioId,
        User $user,
        \Illuminate\Support\Carbon $asOf,
        int $horizonDays,
    ): array;                            // array<ForecastContribution> — the scenario's effective contributions
    ```

    Algorithm (the LOAD-BEARING FCT-03 logic — purely in-memory, NEVER touches transactions / recurring_series_occurrences / chain_links / card_statements / drift_alerts):
    1. Load the scenario's mutations: `$mutations = $this->scenarioQuery->mutationsFor($scenarioId, $user);` — this returns typed `ScenarioMutationDto[]` with hydrated payload subclasses.
    2. Start with `$contributions = $baselineContributions` (immutable copy).
    3. For each mutation, apply the transform:
       - **`cancel_series`** (`CancelSeriesPayload`): filter `$contributions` removing every entry whose `$contribution->seriesId === $payload->seriesId`.
       - **`add_one_off`** (`AddOneOffPayload`): if the payload date is within `[$asOf, $asOf + $horizonDays]`, append a NEW ForecastContribution. The mutation has no series_id → use seriesId=0 sentinel. The direction maps to sign: expense → negative point/low/high; income → positive. low_minor = high_minor = point_minor for one-off (no variance envelope per UI-SPEC mutation form — one-off has a fixed amount).
       - **`add_recurring`** (`AddRecurringPayload`): expand the start_date + cadence into per-occurrence dates within the horizon (mirror RangeProjector::envelope's date walking) AND apply a default ±5% envelope (the mutation form's "Amount" input has no variance field; ScenarioApplier defaults to ±5% as the calmest assumption). NULL fxRateUsed; the contribution carries the payload's currency. Wave 5 D-1022 picks horizon-bounded vs fixed-365-day window; this plan picks horizon-bounded for memory efficiency.
       - **`change_series_amount`** (`ChangeSeriesAmountPayload`): map over `$contributions`, for entries with `$contribution->seriesId === $payload->seriesId`, recompute low/point/high using the new amount + the series's original variance_tolerance_percent (look up via $seriesQuery::approvedForUser if needed — or extend RecurringSeriesQuery with a `findForUser` method if it doesn't exist yet).
       - **`shift_series_date`** (`ShiftSeriesDatePayload`): map over `$contributions`, for entries with matching seriesId, shift the date forward by `(newNextDate - origNextDate)` days. If `payload.scope === 'next'`, only shift the FIRST matching occurrence; if `'all_subsequent'`, shift all of them (cadence offset preserved). Entries that shift past the horizon are dropped.
    4. Return the transformed contributions array.

    **PHPDoc**: "ScenarioApplier reads forecast_scenario_mutations (Forecasting-owned) and the baseline projection arrays (in-memory). It NEVER joins forecast_scenario_mutations onto transactions / recurring_series_occurrences / chain_links / card_statements / drift_alerts — the noScenarioMutationsJoinedToTransactionQueries arch test (Plan 10-01) is the single most load-bearing structural enforcement of FCT-03.
