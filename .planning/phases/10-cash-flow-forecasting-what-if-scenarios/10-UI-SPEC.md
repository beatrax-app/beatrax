# Phase 10 — UI Design Contract

> Visual and interaction contract for Phase 10: Cash-Flow Forecasting + What-If Scenarios. Generated by gsd-ui-researcher under the auto-chain orchestrator. Inherits all tokens from Phase 9 ← Phase 7 ← Phase 6 ← Phase 5 ← Phase 3 ← Phase 1.

**Phase scope (UI surfaces produced):**

1. **`/forecast` top-level page** (new Livewire SFC `ForecastPage`) — the dedicated forecasting surface. Sections in render order: page heading + subheading + helper link top-right (`Adjust buffers →` to `/settings#forecast-buffers`); per-account switcher tab bar (one tab per real account + `All accounts` tab); 30 / 60 / 90-day horizon segmented control; scenario picker (Baseline + saved scenarios + `+ New scenario`); `View by funder` toggle; the side-by-side two-panel `rangeArea` comparison region (baseline left, scenario right) with the "Net diff at day 30 / 60 / 90" delta tile rendered between the panel headers; scenario mutation sidebar (right rail, collapses when no scenario is selected); confidence legend sidebar (under or beside the chart on wide viewports). All horizon, account, scenario, and "view by funder" state is `#[Url]`-bound for shareability and back-button correctness (Phase 3 D-44 + Phase 8 D-855 carry-forward).
2. **Dashboard `/` "Forecast highlights" tile** — REPLACES the existing Phase 5 "Next ICS settlement" tile in the dashboard status-tile grid. Strict superset: surfaces lowest projected balance + active shortfall windows in the next 30 days AND the next ICS settlement amount + date. Text-only chrome (no sparkline — calm aesthetic rules per D-1026). Entire tile is wrapped in `<a href="{{ route('forecast.index') }}">` → drills to `/forecast`. Hides entirely when the user has no projection data yet (e.g. no approved recurring series AND no upcoming ICS settlement).
3. **Top-nav "Forecast" slot** — new top-level entry inserted between the existing "Recurring" and "Settings" entries. No badge by default. When the user has one or more active shortfall windows in the next 30 days, a single rose-50 pill with the shortfall count and a small `↘` glyph renders to the right of the label (mirrors the Phase 9 D-927 drift-chip chrome verbatim, swapping the up-arrow for a down-arrow because shortfalls indicate balance dipping below the buffer).
4. **`/settings` Forecasting section** — new `<section id="forecast-buffers">` appended to the existing settings page. Contains a per-account list with three editable fields per account row: `Minimum buffer`, `Opening balance`, `Opening balance as of`. Anchor target `#forecast-buffers` so the `/forecast` "Adjust buffers →" link can scroll to it.
5. **Inline per-account buffer editor on `/forecast`** — small text-link `Buffer: €500` (slate-500, hover underline) under each per-account chart header that opens a numeric popover (currency input + Save / Cancel). Same posture as the Phase 9 D-915 per-series threshold-editor popover. Saves on Save click; closes popover; flashes `Buffer updated.` inline (3s).
6. **Scenario mutation editor sidebar** — right rail on `/forecast` when a non-baseline scenario is selected. Lists the scenario's existing mutations with `Edit` / `Remove` chips per mutation; bottom of the rail carries an `Add mutation` chip that opens a five-option chooser (`Cancel a series` / `Add a one-off` / `Add a recurring` / `Change a series amount` / `Shift a series date`). Each kind opens its own inline form (see § Mutation form copy). The sidebar's header carries the scenario name + a `Rename` text-link + a `Delete scenario` destructive text-link.
7. **Phase 9 drift-alert "Model cancel" launchpad** — the existing Phase 9 D-920 `I cancelled this` chip on `/drift` gains a sibling chip `Model cancel ↗` that creates a new forecast scenario pre-seeded with a `cancel_series` mutation targeting the alert's `recurring_series_id` and redirects to `/forecast?scenarioId={newId}`. This is a Phase 10 addition that extends the Phase 9 surface; Phase 9's existing chip behavior is preserved verbatim.
8. **`/recurring/series/{seriesId}` "Model what-if" link** — small text-link added under the existing detail page header next to the Phase 9 threshold-editor mount. Opens a tiny dropdown with two options: `Model cancellation` (creates a scenario with `cancel_series` mutation) and `Model amount change…` (creates a scenario with `change_series_amount` mutation pre-seeded with the series's current amount in an editable input). Both redirect to `/forecast?scenarioId={newId}`.
9. **Scenario CRUD + buffer-change + opening-balance-change toast surface** — every action dispatches a 10-second Undo toast via `$this->dispatch('toast', ...)` inheriting Phase 4 / Phase 5 / Phase 8 / Phase 9 chrome verbatim. Bottom-center, single line, single inline `[Undo]` action when applicable. `Delete scenario` is the single destructive action and uses a two-step inline confirm (Phase 7 / Phase 9 destructive-confirmation pattern).

## Charting Decision (D-1027)

**Decision:** The per-account switcher renders an ApexCharts `rangeArea` band per chart. The optional `All accounts` tab renders a SINGLE-LINE point-only aggregated chart (no rangeArea, no stacking).

**Rationale:**

1. **`rangeArea` stacking is not a first-class Apex concept.** Stacking N translucent rangeArea series produces visually muddy bands that defeat FCT-02's "honest uncertainty" goal — the eye cannot disentangle account A's band from account B's band.
2. **Quadrature combination already happens at the per-account level.** Each per-account chart is itself the daily fold of N series via the quadrature spread formula (D-1004). The math is correct AT the per-account level; aggregating bands further would require a second-order quadrature that has no obvious user mental model.
3. **"All accounts" answers a different question than per-account.** Per-account answers "is THIS account going to dip below its buffer?". "All accounts" answers "what is the household cash position over time?" — for that question, the point estimate is what the user wants. Showing the band on the aggregate adds visual noise without information gain.
4. **The aggregate's accuracy is the AND of the per-account accuracy.** If the user wants band detail, they switch to the relevant per-account tab. The aggregate is the "calm cockpit view"; the per-account is the diagnostic view.

**`All accounts` tab chrome:**

- ApexCharts `line` (not `rangeArea`) chart.
- Single bold center line per day = sum of per-account point estimates (in EUR — every per-account chart's point estimate is converted to the account's default currency, and the All-accounts roll-up converts each into EUR using each occurrence's stored `latest_fx_rate_used`).
- No band shading.
- Below-buffer overlay: the chart renders a single horizontal dashed line at `Σ(per-account buffer)` — the sum of every account's `forecast_min_buffer_minor` — with a small caption `Total buffer floor`. If the point line dips below this floor, the area between the line and the floor is shaded rose-50 with the same shortfall-badge chrome as per-account charts.
- The `All accounts` tab is the DEFAULT landing tab on `/forecast` when no `account` URL parameter is present.

## Navigation Decision (D-1025)

**Decision:** Keep the nav flat at 10 items. Insert a new "Forecast" slot between "Recurring" and "Settings". Do NOT consolidate Recurring + Drift + Forecast under a "Money" parent menu.

**Final top-nav order (left to right):**

```
diederik   Dashboard   Transactions   Imports   Inboxes [N]   Uncategorized [N]   Rules   Review chains [N]   Recurring [N | N↗]   Forecast [N↘]   Settings
```

**Compound-badge chrome (Forecast slot):**

The Forecast slot mirrors Phase 9 D-927's drift-pill chrome verbatim, swapping the `↗` (Phase 9 drift-up) for `↘` (Phase 10 shortfall-down) so the user reads the signal at a glance without parsing labels.

```blade
{{-- No badge (no active shortfall in next 30 days) — bare slot --}}
<a href="{{ route('forecast.index') }}" class="..."
   aria-label="Forecast">
    Forecast
</a>

{{-- Single-pill (active shortfall present) — rose-50 chip with ↘ glyph --}}
<a href="{{ route('forecast.index') }}" class="..."
   aria-label="Forecast; {{ $shortfallLabel }} active shortfall {{ $shortfallCount === 1 ? 'window' : 'windows' }} in the next 30 days">
    Forecast
    <span class="inline-flex items-center justify-center rounded-full bg-rose-50 px-2 py-0.5 text-xs font-medium text-rose-700"
          style="font-variant-numeric: tabular-nums;"
          aria-hidden="true">{{ $shortfallLabel }}<span class="ml-0.5">↘</span></span>
</a>
```

**Rationale (why a separate slot, not a "Money" parent):**

1. **The bar at 10 items is at the calm-aesthetic ceiling, not over it.** Phase 9 D-927 noted that 11+ items start to crowd; 10 items is the exact ceiling we accept for v1. No further item is planned beyond Phase 10.
2. **Forecast is a fundamentally different mental concept from Recurring.** Recurring = "approved series management" (calm administrative task); Forecast = "will I have enough money on the 22nd?" (anxious operational question). Co-locating them under a "Money" parent would force the user to two-step every operational forecast check.
3. **`/drift` already has no top-nav slot** (Phase 9 D-927 resolved this with a compound badge on Recurring). Adding a "Money" parent would force exposing `/drift` AND `/recurring` AND `/forecast` AS A FLYOUT MENU — heavier UX than the current pattern.
4. **A dropdown menu on the top nav is heavier than the calm aesthetic permits.** The current top nav uses flat link chrome; adding a parent menu would introduce hover/click flyout state, focus management, and visual emphasis the rest of the bar doesn't carry.
5. **A `↘` glyph in rose-50 is the calmest possible attention signal.** When no shortfall is active, the slot renders bare (no badge — zero attention cost). When a shortfall lands, the rose-50 pill is the same chrome the user already learned in Phase 9 — they recognize "something needs your attention".

**Active-state behavior:** `/forecast` activates the Forecast slot via the existing `$isActive('/forecast')` pattern; no other top-nav item is highlighted while the user is on `/forecast`.

## Interaction Contracts

### `/forecast` page lifecycle

1. **Mount** — `ForecastPage::mount(CurrentUser $currentUser, ForecastQuery $forecastQuery, ScenarioQuery $scenarioQuery)` reads:
   - URL params (Livewire `#[Url]`): `account` (default `all`), `horizon` (default `30`), `scenarioId` (default `null` = baseline), `viewByFunder` (default `false`).
   - Resolves the account list via `Account::query()->where('user_id', $user->id)->orderBy('name')->get()`.
   - Calls `$forecastQuery->forUser($accountId, $horizonDays, $scenarioId)` for the baseline panel (always) AND for the scenario panel (when `$scenarioId !== null`).
   - Calls `$scenarioQuery->forUser($user)` for the scenario-picker options.
   - Calls `$scenarioQuery->mutationsFor($scenarioId, $user)` for the sidebar's mutation list.
2. **Account switcher click** — `wire:click="setAccount('{{ $account->id }}')"` updates `$account` + re-runs `ForecastQuery` for both panels. URL updates via `#[Url(as: 'account', except: 'all')]`.
3. **Horizon segmented control click** — `wire:click="setHorizon(30 | 60 | 90)"` updates `$horizon`. URL updates via `#[Url(as: 'horizon', except: '30')]`.
4. **Scenario picker click** — `wire:click="setScenario({{ $scenario->id ?? 'null' }})"` updates `$scenarioId`. If `null`, side-by-side region collapses to a single (baseline) panel. URL updates via `#[Url(as: 'scenarioId', except: null)]`.
5. **`+ New scenario` click** — Opens an inline create-scenario form (replaces the scenario picker row). On `Create scenario` submit, calls `CreateScenario` Public Action → dispatches `ScenarioCreated` (which fires `ProjectForecastJob` per D-1017) → sets `$scenarioId = $new->id` → flashes toast `Scenario "{name}" created.` → URL updates.
6. **`View by funder` toggle click** — `wire:click="toggleViewByFunder"` flips `$viewByFunder`. The `ForecastQuery` re-runs with the toggle applied (the query passes the flag to `ChainAwareForecastRouter`). URL updates via `#[Url(as: 'viewByFunder', except: false)]`.
7. **Buffer text-link click (per-account chart header)** — Opens `AccountBufferEditor` popover (Alpine `x-data="{ open: false }"`). Click on Save invokes `SetAccountForecastBuffer` Public Action → dispatches a `BufferUpdated` Livewire event (no global event needed; scoped to `ForecastPage`) → flashes toast `Buffer for {account_name} set to {amount}.` → projection job re-runs in background (`ProjectForecastJob` triggered via the Action's domain event listener).
8. **Optimistic vs job-completes-then-poll for scenario mutations (D-1021)** — **Decision: job-completes-then-poll.** Rationale: the `ProjectForecastJob` writes to the `forecast_shortfall_windows` table + invalidates the per-scenario projection cache; a fully-correct optimistic render would have to re-implement the entire quadrature fold client-side. Instead, after every `AddScenarioMutation` / `RemoveScenarioMutation` / `EditScenarioMutation`:
   - Livewire UI flashes a `Forecast updating…` slate-tint toast immediately.
   - The Add-mutation form closes and the mutation card appears in the sidebar instantly (sidebar list is local state).
   - The chart panel applies a `opacity-60 pointer-events-none` overlay with a small inline `Updating…` caption (top-right of the scenario panel).
   - `wire:poll.2s` polls `forecast_runs.status` for the scenario × horizon. When `status === 'complete'`, the poll stops, the overlay clears, the chart re-renders with the fresh `ForecastDto`, and a `Updated.` toast flashes (3s, no Undo).
9. **`Delete scenario` click** — Sets `$confirmingDeleteForScenarioId = $scenarioId`. The sidebar header re-renders with the inline two-step confirm UI. Esc clears. On `Delete scenario` (yes) click, calls `DeleteScenario` Public Action → flashes toast `Scenario "{name}" deleted.` with `[Undo]` (10s) → `$scenarioId = null` (page collapses to baseline-only).
10. **`Rename` click** — Replaces the sidebar header with an inline rename form (input + Save / Cancel). On `Save name` click, calls `RenameScenario` Public Action → flashes toast `Scenario renamed to "{name}".` (5s, no Undo).
11. **Mutation card `Edit` click** — Expands the mutation card into its per-kind form pre-populated with the existing payload. Save replaces the mutation; Cancel reverts.
12. **Mutation card `Remove` click** — Calls `RemoveScenarioMutation` Public Action immediately (no inline confirm — removal is undoable via toast). Flashes toast `{mutation_summary} removed from "{scenario_name}".` with `[Undo]` (10s).
13. **`Model cancel ↗` chip (on Phase 9 `/drift`)** — Invokes `CreateCancellationScenarioForAlert` Public Action (creates a new scenario with one `cancel_series` mutation atomically) → `$this->redirect(route('forecast.index', ['scenarioId' => $new->id]))`.
14. **`Model what-if ↗` link (on `/recurring/series/{id}`)** — Opens the `ModelWhatIfDropdown` popover (Alpine). Two options:
    - `Model cancellation` → invokes `CreateCancellationScenarioForSeries` Public Action (parallel to the drift one but takes a series id) → redirects.
    - `Model amount change…` → opens an inline amount input → on Save, invokes `CreateAmountChangeScenarioForSeries` → redirects.
15. **wire:poll** — Two distinct polls on `/forecast`:
    - `wire:poll.30s="refreshShortfallSummary"` on the page footer — re-queries `ForecastHighlightsQuery` to detect newly-computed shortfall windows from background `ProjectForecastJob` runs (e.g. another tab approved a recurring series). If the summary diverged, a subtle inline cue `(forecast updated — refresh)` appears between the chart and the legend with a `[Refresh]` button.
    - `wire:poll.2s="refreshProjectionStatus"` ONLY active during the brief window between a scenario mutation save and the corresponding `forecast_runs.status='complete'`. Polls `forecast_runs` for the active `(user_id, scenario_id, horizon_days)` triple; auto-stops when status flips.
16. **Loading skeleton** — Server renders the chart container chrome on first paint (Livewire SSR). ApexCharts hydrates client-side after `wire:init`. While Apex is hydrating (typically <100ms), the container shows `Loading chart…` Micro 12px slate-500 centered.

### Account buffer editor lifecycle

1. **Mount** — `AccountBufferEditor::mount(int $accountId, ?int $currentBufferMinor, string $currency)` opens with the input pre-populated to the current buffer (formatted in the account's `default_currency` locale).
2. **Input change** — `wire:model.live` updates the displayed value. Server-side parses the value via the existing `Money` formatter routing (Phase 3 D-46).
3. **Save click** — `wire:click="save"` calls `SetAccountForecastBuffer::execute($currentUser, $accountId, $bufferMinor)`. On success, dispatches `buffer-editor:saved` event; popover closes via Alpine `modal-hide`-style dispatch; parent `ForecastPage` re-renders the affected per-account chart header (the buffer text-link label updates AND the chart re-renders with the new floor line + any new shortfall band).
4. **Clear-buffer text-link click** — Calls `SetAccountForecastBuffer::execute($currentUser, $accountId, null)` → toast `Buffer for {account_name} cleared.` (5s).
5. **Cancel click** — Closes popover without save; no state change.
6. **Validation** — Server-side validates `bufferMinor >= 0`; negative values reject with `Buffer must be zero or positive.`

### Opening-balance editor lifecycle (on `/settings`)

1. **Mount** — `SettingsPage::mount()` extension reads `accounts.opening_balance_minor` + `accounts.opening_balance_as_of_date` per account.
2. **Field change** — Bound via `wire:model="forecastSettings.{accountId}.opening"` and `.opening_as_of` (NOT instant-apply — joined with the existing `Save forecast settings` button).
3. **Soft-warning soft-trigger** — On blur of the opening-balance input, an inline `BalanceDivergenceCheck` query (Internal) computes the difference vs the sum-of-transactions-since-earliest. If `|diff| > €500` (D-1029 threshold locked here), the soft-warning banner renders below the row with `[Use diederik's number]` and `[Use my number]` chips. The banner is non-blocking — the user can save anyway.
4. **Save** — On `Save forecast settings` click, persists all per-account fields alongside other settings fields. Inherits existing settings-page Save UX.
5. **Scroll-to from `/forecast`** — `/forecast`'s `Adjust buffers →` link uses `#forecast-buffers` fragment.

## Multi-currency rules (D-1006)

Every per-series legend row renders with original-currency primary + EUR shadow when the original currency is not EUR (inherits Phase 3 D-46 + Phase 8 D-840 + Phase 9):

```
Netflix     $11.49/mo  (≈ €10.85/mo)    high
└─ Body 14px slate-900   └─ slate-400 shadow    └─ confidence chip
```

**Chart panel currency:** The per-account `rangeArea` chart's y-axis uses the account's `default_currency` (typically EUR for ASN / ICS, USD or EUR for PayPal depending on the user's account state). Every series projected onto that account is converted to the account's default currency using each occurrence's stored `latest_fx_rate_used` (Phase 8 D-840 carry-forward). The conversion happens ONCE at the per-occurrence level — no forward-curve FX provider in Phase 10.

**All-accounts aggregate currency:** ALWAYS rolls up to EUR. When per-account charts span multiple default currencies (rare — PayPal-only households), the aggregate uses each account's `default_currency → EUR` rate stored on the account (Ledger metadata).

**Chart tooltip currency:** Mirrors the chart panel currency. When the hovered point is on a non-EUR series's chart, the tooltip shows the original-currency primary `$1,180 – $1,260 (≈ $1,220) on May 31` with the EUR shadow `(≈ €1,113 – €1,189 / ≈ €1,151)` rendered on a second tooltip line in slate-400.

**Net diff tile currency:** ALWAYS rolls up to EUR. The three horizon deltas sum across scenarios in EUR using the per-occurrence rates. No multi-currency tile state.

**Dashboard "Forecast highlights" tile currency:** ALWAYS rolls up to EUR. The "lowest projected balance" and "Next ICS settlement" lines BOTH show EUR amounts. The originating account's currency does not appear on the tile (consistent with Phase 9's dashboard tile EUR-rollup rule).

**Edge case — currency switch mid-series:** Phase 8 D-839 creates two distinct series when currency flips. Phase 10 renders them as separate legend rows (each in its own currency) — no cross-series merging — and the chart converts both to the account's default currency independently.

## Out-of-Contract Items (deferred to v2 / future phases)

These items were considered and explicitly excluded from Phase 10's design contract:

- **Multi-scenario overlay on a single chart** — D-1009 picks two-panel side-by-side for v1; stacking 3+ scenarios is v2.
- **Goal-based forecasting** — "Reach €X savings by date Y; show required monthly reduction." v2.
- **Account-level sub-budgets** — v2 categorization-layer feature.
- **Outbound payment initiation** — Out of scope (PROJECT.md explicit).
- **Push / email digest notifications on shortfall** — Out of scope (PLT-01 localhost-only).
- **`/accounts/{id}` per-account page with forecast as a tab** — Phase 10 builds the forecast view standalone; embedding it as a tab on a future `/accounts` page is a v2 / Phase 11+ structural refactor.
- **Scenario sharing / export / import** — Power-user feature; v2.
- **Forecast accuracy auto-calibration** — v2.
- **Drift-correlation forecasting** — v2 (also flagged in Phase 9 deferred).
- **FX rate provider for forward-projection FX** — Phase 10 uses each occurrence's stored `latest_fx_rate_used`. A forward-curve provider is v2.
- **Optimistic-UI for scenario mutations** — Phase 10 picks job-completes-then-poll (D-1021 locked here); optimistic can land if perceived latency disappoints.
- **All-accounts STACKED `rangeArea` chart** — D-1027 picks single-line aggregate for the All-accounts tab. Stacked rangeArea is rejected for visual-muddiness reasons documented in § Charting Decision.
- **Inline mini-sparkline preview on the dashboard tile** — D-1026 picks text-only. A future sparkline is a v2 polish if user feedback asks for it.
- **Hourly `ProjectForecastJob` tick** — Daily sweep + event-driven re-runs is the v1 floor.
- **Soft + hard buffer tiers per account** — Single buffer per account in v1.
- **CSV/JSON export of forecast or scenarios** — Power-user / tax-prep; v2.
- **Dark mode** — Out of scope for v1 entirely.
- **A "Money" parent menu on the top nav** — Declined for v1 (Forecast is a flat top-level slot). Re-evaluation trigger: if Phase 11 / v2 adds an 11th top-level concept, revisit the consolidation question then.
