    **Modules/Forecasting/Internal/Pipeline/ChainAwareForecastRouter.php**

    `final readonly class` constructor DI: `\Modules\Chains\Public\Services\ChainLinkQuery $chainQuery`, `\Modules\Chains\Public\Services\CardStatementQuery $cardStatementQuery`, `Clock $clock`.

    Public method:
    ```
    public function route(
        array $contributions,    // array<ForecastContribution> from RangeProjector
        \Modules\Core\Models\User $user,
        bool $viewByFunder,      // future flag — Wave 5 surfaces this in UI; Wave 3 default false
    ): array;                    // array<ForecastContribution> (possibly with account_id rewritten)
    ```

    Algorithm (D-1002):
    1. For each `$contribution` (ForecastContribution), check whether the underlying series is chain-resolved. Call `$this->chainQuery->confirmedAndDeterministicForSeries($contribution->seriesId, $user)`. If empty → the series is not chain-resolved, contribution stays on its original account. If non-empty → take the funder account from the deepest link in the chain (the link's `funder_account_id` field).
    2. **PayPal-funded charges**: when the series's account is PayPal AND there's a confirmed chain link to ASN/ICS, the contribution's `account_id` is REWRITTEN to the funder's account_id. The `point_minor` stays the same (the funder is the one whose balance dips). This is the "deduct from the funder on the actual debit date" semantic from D-1002.
    3. **ICS bulk-iDEAL synthesis**: regardless of per-series chain links, fetch `$nextSettlement = $this->cardStatementQuery->nextSettlementForUser($user)`. If not null AND the settlement date falls within the horizon window, synthesize a NEW ForecastContribution: `new ForecastContribution(date: $nextSettlement->dueDate, pointMinor: -abs($nextSettlement->amount->getAmount()->toInt()), lowMinor: -abs(...), highMinor: -abs(...), currency: $nextSettlement->amount->getCurrency()->getCurrencyCode(), fxRateUsed: null, seriesId: 0, accountId: $nextSettlement->accountId)`. The lowMinor/highMinor = pointMinor (the settlement amount is deterministic — the cleared lines since last settlement are summed, no envelope). This synthesized contribution lands on the ASN funder account (`$nextSettlement->accountId` is already the ASN funder per Phase 5 D-95 semantics).
    4. **De-duplicate**: if the ICS bulk-iDEAL synthesized contribution overlaps with a Phase 8 recurring series that's already chain-resolved to the same funder on the same date, prefer the synthesized contribution (the Phase 5 next-settlement math is the authoritative source). Match by `accountId + date` tuple.
    5. **`$viewByFunder=true` collapse**: when the toggle is on, contributions whose `accountId` was REWRITTEN by step 2 are MERGED back to display under the funder's per-account chart panel as a single line. Wave 3 implementation: pass-through (return the contributions as-is). Wave 5 lands the actual collapse semantics.
    6. Return the modified contributions array.

    **PHPDoc constraints**: "FX conversion does NOT happen here (RESEARCH Pitfall 6). Each contribution is left in its original currency; ProjectionPipeline's DailyFold applies the per-contribution fx_rate to convert to the account's default currency. This avoids the side-by-side-comparison FX-noise pitfall."

    **Modules/Forecasting/Internal/Pipeline/ShortfallDetector.php**

    `final readonly class` constructor DI: `DatabaseManager $db`, `\Illuminate\Contracts\Events\Dispatcher $events`, `Clock $clock`.

    Public method:
    ```
    public function detect(
        array $dailyPoints,         // result of DailyFold (per-day low/point/high in account.default_currency)
        int $accountId,
        ?int $scenarioId,
        ?int $effectiveBufferMinor, // accounts.forecast_min_buffer_minor; NULL = effective 0 zero-crossing
        string $currency,
        \Modules\Core\Models\User $user,
    ): array;                       // array<ShortfallWindowDto> — the windows just written
    ```

    Algorithm:
    1. Determine the effective buffer: `$buffer = $effectiveBufferMinor ?? 0;` (NULL = zero-crossing default per D-1011).
    2. Iterate the sorted daily points. Track a state machine: `not_in_shortfall` → `in_shortfall(starts_at, lowest_balance_minor)` → back to `not_in_shortfall` (emits a window row).
    3. For each day:
       - If `point_minor < $buffer` AND state is `not_in_shortfall`: transition to `in_shortfall`; record `starts_at = day`, `lowest_balance_minor = point_minor`.
       - If `point_minor < $buffer` AND state is `in_shortfall`: update `lowest_balance_minor = min(lowest_balance_minor, point_minor)`.
       - If `point_minor >= $buffer` AND state is `in_shortfall`: transition to `not_in_shortfall`; emit a window row with `ends_at = day - 1 day` and `buffer_used_minor = $buffer`. Insert the row into `forecast_shortfall_windows` via `$this->db->connection()->table('forecast_shortfall_windows')->insertGetId([...])`. Fire `ForecastShortfallDetected` event.
    4. **Edge case** — `in_shortfall` state at end of horizon: emit the final window with `ends_at = last_day_of_horizon` and the accumulated `lowest_balance_minor`.
    5. **Pre-write cleanup**: BEFORE writing any new rows, delete any existing `forecast_shortfall_windows` for `(user_id, account_id, scenario_id)` from prior runs — the shortfall picture is fully replaced on each projection run. Wrap delete + inserts in a single DB transaction.
    6. Return `array<ShortfallWindowDto>` for downstream listener / UI consumption.
