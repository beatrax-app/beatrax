## Accomplishments

- New `UpsertsCardStatements` Public contract + `CardStatementUpserter` concrete service. The upserter is idempotent via `insertOrIgnore` against `card_statements`' UNIQUE `(user_id, account_id, period_start, period_end)`, preserves the `state` column on re-runs (firstOrCreate-style), filters strictly on `accounts.kind='ics_card'`, skips rows with null `period_start` or null `period_end`, and is scoped per-import-run so prior runs' summaries are not re-promoted.
- `ConfirmImport` gains a new constructor dependency on `UpsertsCardStatements`. The upsert call sits INSIDE the existing `if ($dispatchChain && ($result->inserted > 0 || $result->enriched > 0))` block as the FIRST statement, BEFORE the `chain_resolution_runs` insert and BEFORE the chain dispatcher fires. Order is load-bearing: the chain resolver's worker reads `card_statements` to match ASN→ICS bulk-iDEAL settlements, so the fresh ICS card_statement rows must exist before the dispatch.
- `IcsSettlementResolver` rewired (Option B): candidate iteration changes from ICS-side `transfer_in` on `accounts.kind='ics_card'` to ASN-side `transfer_out` on `accounts.kind='bank'` with `whereNotNull('transactions.counterparty_iban')`. Each candidate's `counterparty_iban` is consulted through `ResolvesKnownCounterpartyIban`; only rows resolving to a `ics_card`-kind Account proceed (bank-to-bank transfers and ASN→PayPal funding rows are skipped — they belong to other resolvers).
- `resolveOne()` signature gains an `Account` parameter (the alias-resolved ICS account); the `$accountId` for the card_statement lookup is `$icsAccount->id`, NOT the ASN transfer's `account_id`. The settled magnitude is taken at entry (`abs(...)`) so the rest of the algorithm runs unchanged in the positive ICS-side sign convention.

## Decisions Made

- **Option B over Option A — three reasons documented in the resolver's class-level PHPDoc:**
  1. **Ledger purity.** The Mijn ICS PDF DOES NOT carry a per-row settlement entry — the bulk settlement only exists on the ASN side. Forcing a synthetic ICS-side row would mean the ledger no longer faithfully reflects the source statements; the user could see a transaction on the ICS card account that never appeared on any printed statement.
  2. **Single source of truth.** Plan 03's `ResolvesKnownCounterpartyIban` is now the canonical "real IBAN → user's synthetic-IBAN account" mapping. Option B reuses it as a third consumer alongside Plan 04's `ClassifyTransactionType` and `PairTransferCandidates`. Option A would have either duplicated the mapping logic in the ICS adapter or pulled the resolver into the adapter — a much wider blast radius.
  3. **Adapter scope discipline.** `IcsPdfAdapter` is a pure parser (PDF text → DTOs). Cross-account synthesis in the adapter would couple it to the user's Account model, breaking single responsibility.
- **Upsert order INSIDE the existing `$dispatchChain` gate, BEFORE the chain_resolution_runs insert.** Order is load-bearing: the chain resolver's queue worker reads `card_statements` to find the matching open statement for an ASN `transfer_out`. If the upsert ran after the dispatch, the worker would see an empty `card_statements` table for the user's fresh ICS import and write no chain_links.
- **`insertOrIgnore` (firstOrCreate semantics), not `upsert`.** The state machine moves a `card_statement` from `open` → `partially_settled` → `settled` / `overpaid` as the resolver writes chain_links. `upsert` (`updateOrCreate`) would reset the state column on re-runs; `insertOrIgnore` preserves it. Test 3 (`does NOT mutate an existing card_statements row state column on re-run`) locks this invariant against a refactor regression.
- **Plan-spec divergence — Test 4 (kind filter) test design.** The original plan called for "Seed: same import_run with TWO statement_summaries: one ics_card, one bank". But `statement_summaries` has UNIQUE `(user_id, import_run_id)` — two summaries on the same import_run for the same user is structurally impossible. The test was redesigned to seed an ASN summary on a SEPARATE import_run for a SEPARATE user, then call `upsertForImportRun(asnRun, asnUser)` and assert zero card_statements rows land (the `accounts.kind='ics_card'` filter rejects the bank-kind summary). A PayPal summary is added on a third import_run to confirm the predicate is `kind='ics_card'`, not `kind!='bank'`.
- **Plan-spec divergence — Test 5 (null-period skip) test design.** Same UNIQUE-`(user_id, import_run_id)` constraint made the original "two summaries on same import_run" design impossible. Redesigned to seed two SEPARATE import_runs (period_start NULL + period_end NULL) and assert both are silently skipped. Both halves of the null-period predicate are exercised independently.
