### BL-01: Pair-detection silently fails when ASN-side leg imports before PayPal-side leg

**Files modified:** `Modules/Transfers/Internal/Listeners/PairTransferCandidates.php`, `Modules/Transfers/tests/Feature/PairTransferCandidatesAliasBridgeTest.php`
**Commit:** 62a5bd6
**Applied fix:** Added a reverse-direction lookup so when the firing leg's `counterparty_iban` is null/empty (the empirical PayPal `Bankstorting` parent shape), the listener computes the IBAN set that points AT the firing leg's own account (own `accounts.iban` + every `known_counterparty_ibans.real_iban` whose `target_account_kind` matches the firing account's kind) and searches for an unpaired equal-and-opposite transfer leg on a different account whose `counterparty_iban` sits in that set. The forward direction stays unchanged. Helper named `findPartnerByReverseLookup()`, typed `?stdClass` return. Pre-existing class docstring rewritten to describe both directions explicitly.

**Design call:** The review listed two options — (a) drop the short-circuit and drive a reverse search; (b) catch the inverse via alias-bridge in reverse. The implementation is (a) — the reverse search is per-firing-leg and bounded by the existing index `transactions_unpaired_transfer_idx`. The IBAN-set is computed once from `accounts` + `known_counterparty_ibans`, then funneled through a single `whereIn('counterparty_iban', ...)`. Regression test added for the ASN-first ordering; the existing "PayPal-first" test was tightened to assert the pair closes immediately when both rows are pre-persisted (matching the canonical in-batch shape `RecordTransactions` produces).

### BL-02: KnownCounterpartyIbanResolver returns a non-deterministic Account when the user owns multiple accounts of the alias's target kind

**Files modified:** `Modules/Import/Internal/Services/KnownCounterpartyIbanResolver.php`, `Modules/Import/Public/Contracts/ResolvesKnownCounterpartyIban.php`, `Modules/Import/tests/Unit/KnownCounterpartyIbanResolverTest.php`
**Commit:** 4e19774
**Applied fix:** Switched account lookup from `Account::query()->...->first()` (unordered) to a raw query builder against `accounts` with `orderBy('id')` returning the lowest-id row, followed by an `Account::find($id)` to hydrate the typed model. The contract docstring on `ResolvesKnownCounterpartyIban` now states the lowest-id-wins disambiguation rule explicitly. Regression test seeds two `bank`-kind accounts on one user and asserts the lowest-id account wins.

**Design call:** The review listed option (a) "pin to a specific Account.id at seed time via a migration extension" vs option (b) "`orderBy('id')` for deterministic-but-arbitrary tiebreak." Picked (b) per the task brief's prefer-oldest-account guidance and the project's preference for minimal-change fixes; the option-(a) migration is the right answer when a real multi-account-per-kind user scenario lands and can be added without breaking the v1 contract.

**PHPStan correctness:** The naive `Account::query()->orderBy('id')->first()` form trips Larastan's `staticMethod.dynamicCall` rule on `orderBy()`. Resolved by the raw-query-builder + Eloquent-find shape described above.

### CR-01: ClassifyTransactionType swallows MissingPaypalTransactionTypeMapException for `parent` rows lacking a TRANSACTION_TYPE entry

**Files modified:** `Modules/Import/Internal/Pipeline/Stages/ClassifyTransactionType.php`, `Modules/Import/tests/Feature/ClassifyTransactionTypeTest.php`, `Modules/Ingestion/Public/Paypal/PaypalCsvEventTypeMap.php`, `Modules/Ingestion/tests/Unit/Adapters/Paypal/PaypalCsvEventTypeMapTest.php`
**Commit:** 0641ab4
**Applied fix:** The naive review fix (catch narrower-first, re-throw) was insufficient on its own — `PaypalCsvEventTypeMap::transactionType()` was throwing the narrower `MissingPaypalTransactionTypeMapException` for BOTH miss conditions (event-type absent from MAP entirely AND event-type-in-MAP-but-missing-from-TRANSACTION_TYPE), so the catch-side change alone would have made every unmapped event type throw. The full fix updates `transactionType()` to distinguish the two miss conditions:

  - event type not in MAP → throw broader `UnknownPaypalEventTypeException` (user-data condition)
  - event type in MAP but not in TRANSACTION_TYPE → throw narrower `MissingPaypalTransactionTypeMapException` (code-internal inconsistency)

Then catch narrower-first in `ClassifyTransactionType` and re-throw the narrower (`throw $missing;`), while the broader catch still falls through to the subtractive default.

Regression test in `ClassifyTransactionTypeTest`: drives the narrower exception via the existing `'Bankstorting naar PP-rekening'` child-fee MAP entry that intentionally has no TRANSACTION_TYPE row; asserts the stage re-throws. A companion test drives an event type missing from MAP entirely and asserts the broader catch lets the row fall through to the amount-sign default.

The corresponding test in `PaypalCsvEventTypeMapTest` (which previously asserted event-type-missing-from-MAP raised the narrower exception) was updated to assert it now raises the broader exception, with an explicit hierarchy check that pins which subtype is the right one for which miss condition.
