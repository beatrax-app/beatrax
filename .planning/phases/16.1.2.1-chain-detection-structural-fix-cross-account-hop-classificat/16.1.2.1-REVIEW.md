# Phase 16.1.2.1: Code Review Report

**Reviewed:** 2026-05-27T12:00:00Z

## Summary

The phase delivers the alias-bridge plumbing (Public contract + resolver + per-user seeder + listener), wires it into `ClassifyTransactionType`, `PairTransferCandidates`, and `IcsSettlementResolver`, introduces a `CardStatementUpserter` Public service called from `ConfirmImport`, ships a 92-row universal-merchant categorisation seeder + UserInstalled listener, and extends `PaypalCsvEventTypeMap` with the three funding-leg parent event types.

DI-only and GSD-agnostic invariants hold: no facades, no global helpers in production code (one `app()` call sits in the production-side `Listener::handle()`? no — verified clean; the `app(...)` calls are all in test fixtures, which is acceptable). No `.planning/` or `PLAN.md`/`RESEARCH.md` references in production sources or PHPDocs. Module boundaries are respected: every cross-module touch goes through `Modules\X\Public\*`. Migration follows the project's `BIGINT` + `user_id` + per-user UNIQUE + RAISE-trigger idiom.

However, two BLOCKER-level correctness defects exist:

1. **Pair-detection has an unenforced import-order dependency.** When the ASN-side `transfer_out` lands before the PayPal-side `transfer_in`, the pair is never linked — the PayPal side short-circuits on empty `counterparty_iban`, and only the ASN side can drive a partner search. Real users can import ASN→PayPal in either order. The phase's only test exercises PayPal-first; ASN-first is the silent loss-of-feature path.
2. **`KnownCounterpartyIbanResolver` does not filter on `target_account_kind`.** When the user owns *two* accounts of the same kind (the realistic ICS+secondary bank scenario or a future joint account), the resolver returns an arbitrary one via `->first()` with no `orderBy` — non-deterministic across SQLite versions. The unit test only verifies one-account-per-kind shape, masking the defect.

Plus two CRITICAL classifier defects, six WARNINGs (Eloquent global-scope drift, dead-code "use" suppressor, ConfirmImport gating semantics, fixture-vs-rules drift risk, listener defensive throw shape, etc.), and five smaller INFO items.

## Blocker Issues

### BL-01: Pair-detection silently fails when ASN-side leg imports before PayPal-side leg

**Files:**
- `Modules/Transfers/Internal/Listeners/PairTransferCandidates.php:104-106`
- `Modules/Transfers/tests/Feature/PairTransferCandidatesAliasBridgeTest.php:154-186` (test gap)

**Issue:**
`PairTransferCandidates::handle()` early-returns when the incoming leg's `counterparty_iban` is null or empty:
```php
if ($tx->counterparty_iban === null || $tx->counterparty_iban === '') {
    return;
}
```
The empirical PayPal CSV does NOT carry a per-row counterparty IBAN on the `Bankstorting` parent (this is documented in the test file itself, lines 119–124). The PayPal `transfer_in` therefore always short-circuits, and only the ASN-side `transfer_out` (which carries `LU89751000135104200E`) can drive a partner search via the alias bridge.

Scenario: user imports the ASN CSV in January, the matching PayPal CSV in February.
1. ASN `transfer_out` persisted → handler fires → alias resolves to PayPal account → partner-search returns NULL (PayPal row not yet in ledger) → half-state.
2. PayPal `transfer_in` persisted → handler fires → `counterparty_iban=''` → early return → never searches for the now-persisted ASN partner.

**The pair is permanently unlinked.** The phase's only ordering test (`PairTransferCandidatesAliasBridgeTest` "PayPal side firing first is a no-op …") covers the *opposite* order and explicitly notes "PayPal first — its counterparty_iban is empty so the listener short-circuits and writes nothing. Then ASN fires; the alias bridge resolves the partner account and the listener pairs both legs symmetrically." The reverse order is never asserted.

`CrossAccountHopClassificationEndToEndTest` hides the defect identically — line 211 persists the PayPal side first via `$recorder([$paypalTyped], $world['user'])` before persisting the ASN side, never the other way around.

**Fix:**
Either (a) drop the empty-counterparty-IBAN short-circuit and let the partner search drive itself off `(user_id, account_id, amount_minor, currency, booked_at, type)` even when the firing leg lacks a counterparty IBAN, or (b) on the firing leg with no counterparty IBAN, look up the partner via the alias-bridge in reverse — search across the user's *other* accounts for an unpaired equal-and-opposite row whose `counterparty_iban` alias-resolves to the firing row's own account. Option (a) is simpler:
```php
// REPLACE the short-circuit with a branch that handles BOTH directions.
if ($tx->counterparty_iban === null || $tx->counterparty_iban === '') {
    // No counterparty IBAN on this leg — search for an already-persisted
    // partner whose counterparty_iban alias-resolves to *our* account.
    $partnerAccountId = null;
    // ...drive a reverse search by account_id + sign-flipped amount within
    // the same window, then close the pair if found.
} else {
    // existing two-arm partner lookup
}
```
Either way, add a regression test that asserts pairing succeeds when the ASN leg is persisted strictly before the PayPal leg. The existing `PairTransferCandidatesAliasBridgeTest` is the right home — add an "ASN first" case.

### BL-02: `KnownCounterpartyIbanResolver` returns a non-deterministic Account when the user owns multiple accounts of the alias's target kind

**File:** `Modules/Import/Internal/Services/KnownCounterpartyIbanResolver.php:52-56`

**Issue:**
```php
return Account::query()
    ->where('user_id', $userId)
    ->where('kind', $alias)
    ->first();
```
There is no `orderBy`. SQLite's `first()` on an unordered query returns whichever row the storage engine picks — typically the lowest rowid but not contractually so. When the user owns two `bank`-kind accounts (entirely realistic: joint ASN + personal ASN, or a future ABN AMRO migration on the same instance), `resolveAccount('NL08ABNA0526650664', $userId)` returns an arbitrary one.

This routes the ICS bulk-settlement `transfer_out` to the wrong partner account in `PairTransferCandidates` (BL-01 makes this worse) and routes the resolver's `IcsSettlementResolver::resolveOne()` to mutate the *wrong* `card_statements` row when two ICS accounts exist.

The contract docstring (lines 27–30) declares "user's own Account whose kind matches the alias" — singular — but the schema permits N accounts per kind per user. The seeder for `DefaultKnownCounterpartyIbansSeeder` stores `target_account_kind` only, with no Account `id` pin and no slug tiebreaker.

The unit test `KnownCounterpartyIbanResolverTest` masks this: every fixture seeds exactly one account per kind.

**Fix:**
Either (a) make the `known_counterparty_ibans` row carry a `target_account_id` (preferred — it locks the mapping to a specific Account at seed time and survives kind expansion), or (b) order the lookup deterministically and document the contract:
```php
return Account::query()
    ->where('user_id', $userId)
    ->where('kind', $alias)
    ->orderBy('id')
    ->first();
```
Option (a) requires a migration extension (additional `target_account_id` FK nullable, with the seeder filling it on first run after Accounts exist). Option (b) is a one-line patch but only kicks the can — multi-account users still get an arbitrary-but-stable pick.

Add a unit test: "resolver returns the lowest-id account when the user owns two of the alias's target kind." Currently no test exercises this multi-account-per-kind case.

### CR-01: `ClassifyTransactionType` swallows `MissingPaypalTransactionTypeMapException` for parent rows whose adapter classified them as `parent` but lacks a `TRANSACTION_TYPE` entry

**File:** `Modules/Import/Internal/Pipeline/Stages/ClassifyTransactionType.php:139-152`

**Issue:**
```php
try {
    $mappedType = $this->eventTypes->transactionType($parentEventType, $language);
    return $tx->withType($mappedType);
} catch (UnknownPaypalEventTypeException) {
    // Unknown parent event type OR missing TRANSACTION_TYPE
    // mapping — fall through to the subtractive default.
    ...
}
```
`MissingPaypalTransactionTypeMapException extends UnknownPaypalEventTypeException` (asserted in `PaypalCsvEventTypeMapTest.php:144-153`). The classifier catches the supertype, which silently absorbs the narrower "code-internal inconsistency" exception alongside the legitimate "unmapped event type" case.

The intent in `PaypalCsvEventTypeMap`'s docstring is the opposite: the narrower exception means a `parent`-classified event type slipped past the rollup walker but never had a `TRANSACTION_TYPE` row added — a developer bug, not a user-data condition. The current catch silently falls through to the amount-sign default, hiding the bug.

A future entry added to `MAP` as `'parent'` but forgotten in `TRANSACTION_TYPE` will silently misclassify in production rather than throw at parse time as the funding-leg expansion the phase delivers depends on (the test invariant "every parent has a transactionType" is enforced *between MAP entries*, not at runtime against arbitrary CSV rows).

**Fix:**
Catch the narrower exception explicitly and re-throw / log it, while only swallowing `UnknownPaypalEventTypeException`:
```php
} catch (MissingPaypalTransactionTypeMapException $e) {
    // Code-internal inconsistency — a 'parent' event has no
    // TRANSACTION_TYPE entry. Surface as a hard failure so the
    // developer sees it; this is NOT a user-data condition.
    throw $e;
} catch (UnknownPaypalEventTypeException) {
    // Unknown parent event type — user-data condition.
    // Fall through to the subtractive default.
}
```
…and add the corresponding `use Modules\Ingestion\Public\Exceptions\MissingPaypalTransactionTypeMapException;` import.

### CR-02: `ConfirmImport` gates the post-commit card-statements upsert on `inserted > 0 || enriched > 0`, missing the legitimate "all-duplicates-but-new-statement-summary" case

**File:** `Modules/Import/Public/Actions/ConfirmImport.php:189`

**Issue:**
```php
if ($dispatchChain && ($result->inserted > 0 || $result->enriched > 0)) {
    $this->cardStatementUpserter->upsertForImportRun($importRunId, $user);
    ...
}
```
ICS PDF imports persist a `statement_summaries` row *before* the recorder runs (per the PdfStatementParser path). If a user re-imports the same ICS PDF after manually deleting the matching `card_statements` row (for any reason — debugging, schema drift recovery, partner-app reset), `inserted = 0` and `enriched = 0` because every transaction row is a fingerprint-duplicate. The `card_statements` upsert never fires, even though the underlying `statement_summaries` row *would* produce a fresh `card_statements` insert (its UNIQUE constraint is `(user_id, account_id, period_start, period_end)`, not import_run-keyed).

Worse: the gate also skips the recurring-detection dispatch in the same `if`, which is a separate downstream concern but the same defect shape.

**Fix:**
Decouple the upsert call from the `inserted/enriched` gate. The upsert is itself idempotent (asserted by its own test) so calling it for an all-duplicates import is safe and produces 0 inserts when card_statements already exists:
```php
if ($dispatchChain) {
    // The upserter is idempotent — safe to call on every confirm.
    $this->cardStatementUpserter->upsertForImportRun($importRunId, $user);

    if ($result->inserted > 0 || $result->enriched > 0) {
        // chain dispatch + recurring dispatch
    }
}
```
…and either move the chain dispatch out of the same `if` (if the resolver should also re-run on a "no new rows but missing card_statements" recovery) or split the conditions explicitly.

Tighten the existing test `'zero-row ConfirmImport (no inserts and no enrichments) does NOT call the upserter'` (`CardStatementUpsertOnImportTest.php:86-126`) into a clearer "re-confirm short-circuits via status='confirmed' path" assertion — the current test names the wrong invariant.

### WR-01: `DefaultKnownCounterpartyIbansSeeder` does NOT use `withoutGlobalScopes()`, relying on `UserScope`'s unauthenticated fall-through

**File:** `Modules/Import/Database/Seeders/DefaultKnownCounterpartyIbansSeeder.php:47-57`

**Issue:**
```php
KnownCounterpartyIban::query()->firstOrCreate([...]);
```
`KnownCounterpartyIban` uses `BelongsToUser`, which adds the `UserScope` global scope. `UserScope::apply()` catches `NotAuthenticatedException` and falls through cleanly — but this is the only thing preventing a cross-user leak when the seeder is invoked from an HTTP-authenticated context.

The Categorization seeder (`DefaultCategorizationRuleSeeder.php:57-77`) does `Category::withoutGlobalScopes()` and `CategorizationRule::withoutGlobalScopes()` explicitly. The Known-Counterparty-IBAN seeder does not. If a future code path calls this seeder from an authenticated HTTP request acting as user A while seeding user B (e.g. a future admin "re-seed user" action, or simply a developer in `php artisan tinker --as=foo` running the seeder for a different user), `firstOrCreate` will match against user A's row even though the WHERE includes `user_id => $user->id` — the scope adds *another* `user_id` filter on top, possibly with a different value, producing zero results and a fresh INSERT that violates the per-user UNIQUE.

**Fix:**
Mirror the Categorization seeder's defensive posture:
```php
KnownCounterpartyIban::query()->withoutGlobalScopes()->firstOrCreate([...]);
```
Across both rows. Add a regression test asserting that running the seeder for user B while `actingAs(userA)` produces user B's rows correctly.

### WR-02: `IcsSettlementResolver::pairLookupAvailable()` is dead-code dressed as a public API to suppress a PHPStan unused-property lint

**File:** `Modules/Chains/Internal/Resolvers/IcsSettlementResolver.php:121-136`

**Issue:**
```php
public function pairLookupAvailable(): bool
{
    return get_class($this->pairLookup) === PairLookup::class;
}
```
The PHPDoc on the property (lines 109–115) and the method (122–129) both admit the property is unused by the algorithm and only exists "for downstream waves." `get_class(...) === PairLookup::class` is a strict-equality check that returns `false` for any subclass/test-double, defeating the "is wired" intent. The method exists ONLY to suppress PHPStan's `onlyWritten` lint.

This is dead code with a comment-only justification. It also breaks the constructor's interface-stability claim — the comment promises wave 3 will consume it, but consumers should reach for the resolver via its real interface, not introspect "did the container wire my collaborator?"

**Fix:**
Drop the `PairLookup $pairLookup` constructor parameter and `pairLookupAvailable()` method entirely until the consuming code (wave 3 refund-after-close cross-pair check or PayPal funder lookup) actually exists. Adding a constructor parameter for a future wave violates YAGNI and forces every test to inject a real PairLookup or stub for no benefit. If the wave-3 plan is firm, add the parameter when wave 3 ships and ship the wiring change in the same PR — that's a 5-line diff with no test churn cost.

If the parameter must stay for plan-locked-signature reasons, suppress the lint via a `// @phpstan-ignore-next-line property.onlyWritten` annotation on the constructor property line — far less confusing than a defensive accessor with broken semantics.

### WR-03: `IcsSettlementResolver::findCandidateStatement()` uses `Carbon::diffInDays(..., true)` then casts to int — drops sub-day precision asymmetrically

**File:** `Modules/Chains/Internal/Resolvers/IcsSettlementResolver.php:528-536`

**Issue:**
```php
$periodEnd = CarbonImmutable::parse(self::toString($row->period_end ?? null));
$distance = abs((int) $periodEnd->diffInDays($posted, true));
```
`diffInDays(..., true)` returns a float (e.g. `2.3`); `(int)` truncates toward zero. For two candidate statements where one period_end is `2026-04-30 23:59:59` (distance 1.5 days from a 2026-05-02 posted_at) and another is `2026-05-01 00:00:00` (distance 1.0 days), the integer truncation collapses both to distance 1, then the `<` comparison picks whichever appeared first in the SQL `orderBy('id')` result — i.e. the older-id row, even when the newer-id row is actually closer.

For real ICS-card monthly statements this is unlikely to matter (statements don't overlap), but the period-only window query (line 515) selects *all* open / partially_settled statements in the ±10-day window, and the tie-break logic silently mis-picks when two statements have the same integer-day distance.

**Fix:**
Compare in seconds (or use Carbon's float diff directly) before casting:
```php
$distance = abs($periodEnd->diffInSeconds($posted, true));
if ($distance < $bestDistance) { ... }
```
`$bestDistance` should be `PHP_FLOAT_MAX` instead of `PHP_INT_MAX` for the float comparison.

```php
    'Reversal of General Account Hold' => 'skip',
],
```
The comment correctly notes these are English strings that ship un-localised even in NL exports. But the structural placement under `'nl'` means an English-language PayPal export (no `'en'` key in `MAP`) would still raise `UnknownPaypalEventTypeException` for these same strings. The forward-compatibility is partial.

**Fix:**
For v1 (NL is the only observed locale), this is fine. When a second locale ships, the four English-string skips should move to a `'_global'` fallback bucket the `classify()` method checks AFTER the language-specific lookup misses, so EN exports also benefit. Out of v1 scope; flag for the wave that adds non-NL locale support.
