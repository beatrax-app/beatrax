## Architecture decision — Option B (resolver rewire, not virtual-row synthesis)

Two architectures were considered for closing the ICS settlement chain end-to-end:

- **Option A — synthesize a virtual `transfer_in` row on the ICS card account at PDF import time.** The ICS PDF adapter would emit one synthetic aggregate row per statement period (amount = statement total; counterparty_iban = the user's ASN IBAN; description tagged `[synthetic settlement]`). The existing `IcsSettlementResolver::resolveForUser()` algorithm stays unchanged.

- **Option B (chosen) — rewire `IcsSettlementResolver::resolveForUser()` to iterate ASN-side `transfer_out` rows whose counterparty resolves via the alias bridge to an `ics_card` account.** The card_statement is looked up on the target ICS account. Skips adapter changes; localizes the change to the resolver.

**Option B is chosen for three reasons:**

1. **Ledger purity** — Option A would pollute the ledger with synthetic aggregate rows that don't correspond to any real transaction the user actually made. The Mijn ICS PDF DOES NOT carry a per-row settlement entry — the bulk settlement only exists on the ASN side. Forcing a synthetic row to exist on the ICS side would mean the ledger no longer faithfully reflects the source statements; the user could see a transaction on the ICS card account that never appeared on any printed statement.

2. **Single source of truth** — Plan 03's `ResolvesKnownCounterpartyIban` is now the canonical "real IBAN → user's synthetic-IBAN account" mapping. Option B reuses it once more (a third consumer alongside `ClassifyTransactionType` from Plan 04 and `PairTransferCandidates` from Plan 04). Option A would either need its own mapping logic in the ICS adapter or would have to inject the resolver into the adapter — a much wider blast radius than rewiring one resolver.

3. **Adapter scope discipline** — `IcsPdfAdapter` is a pure parser (PDF text → DTOs). Adding cross-account synthesis to it would couple it to the user's account model (it would need to know the ASN account's IBAN to set the synthetic row's counterparty), breaking the adapter's single responsibility. Adapters parse; resolvers correlate. Option B respects that boundary.

The resolver's algorithm (find matching open card_statement, compute delta against expenses, apply state machine transition, write per-expense chain_links) stays unchanged from the existing implementation — ONLY the candidate-iteration changes from "ICS-side `transfer_in`" to "ASN-side `transfer_out` whose alias resolves to ics_card".

    **Implementation `CardStatementUpserter`**:

    - Constructor-injects `Illuminate\Database\DatabaseManager` and `Modules\Core\Public\Contracts\Clock`.
    - `upsertForImportRun(int $importRunId, User $user): int`:
        1. Query `statement_summaries` JOIN `accounts` WHERE `statement_summaries.user_id = $user->id` AND `statement_summaries.import_run_id = $importRunId` AND `accounts.kind = 'ics_card'`.
        2. For each row whose `period_start` AND `period_end` are non-null:
            - Compute `total = (int) closing_balance_minor` (NEGATIVE per existing sign convention).
            - Compute `open = abs(total)` (POSITIVE).
            - Build the insert payload: (user_id, account_id, import_run_id, period_start, period_end, total_amount_minor=total, open_balance_minor=open, state='open', timestamps via Clock::now()).
        3. Use `insertOrIgnore` on `card_statements` keyed on the UNIQUE (user_id, account_id, period_start, period_end). The `insertOrIgnore` semantics align with `firstOrCreate` — existing rows' `state` column is NOT mutated on re-runs.
        4. Return the count of rows actually inserted. Compute by counting candidate rows pre-insert and counting `card_statements` rows post-insert for the same import_run_id, returning the delta. (insertOrIgnore in Laravel returns the affected-row count from the underlying driver — verify against the driver's reported value.)

    **Idempotency contract**: re-running the upserter against the same import_run_id produces zero new card_statements rows. Existing rows' `state` is preserved (so a card_statement that the state machine moved from `open` to `partially_settled` does NOT get reset to `open` if the upserter re-runs against the same import_run_id).
