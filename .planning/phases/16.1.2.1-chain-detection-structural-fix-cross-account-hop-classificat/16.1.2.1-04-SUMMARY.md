## Decisions Made

- **Two-arm ordering: alias bridge runs FIRST, literal equality is the fallback.** Both consumers (classifier + listener) place the alias-bridge arm before the literal own-IBAN equality check. This ordering is load-bearing for the cross-account-hop case (where the partner account uses a synthetic IBAN literal like `'PAYPAL'`) and is locked by unit test 4 (`alias arm takes precedence over the literal-equality fallback`) via a deliberate post-CT-construction `BANKA->delete()` to prove the alias arm has no dependency on the literal-arm target row being present. The reverse ordering would still work for the canonical hop case (literal arm misses on `'LU89751000135104200E'` → alias arm fires) but the chosen ordering matches the design intent that "alias is the primary signal, literal is the fallback for the legacy bank-to-bank case."
- **Anonymous-class spy on instance property, not closure-`use (&$count)`.** The "resolver never consulted" assertion in pair-feature test 3 wraps `KnownCounterpartyIbanResolver` in a public-counter anonymous class implementing the Public contract, bound via `$this->app->instance(...)`. The closure-`use (&$count)` shape is not legal PHP for anonymous-class constructors (primitives cannot be passed by reference and propagate writes to the outer scope), so the counter must be an instance property. Pattern documented in the plan and verified to match `Modules/Community/tests/Unit/OpenExternalUrlActionTest.php:36-37`.
- **End-to-end Test 1 dispatches the PayPal side first.** The empirical PayPal Activity Download CSV does not carry a per-row counterparty IBAN — the funding source IBAN flows through child events, not the parent (`Bankstorting`) row itself. Dispatching the PayPal side first triggers a clean short-circuit (empty counterparty_iban → listener returns early); dispatching the ASN side second fires the alias-bridge fallback which resolves the partner. This matches the real import order produced by `RecordTransactions` against a real PayPal CSV.
