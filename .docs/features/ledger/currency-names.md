# `Ledger` — what a currency is called, and which currencies there are

Two pickers print a currency: the reporting-currency select in
`/settings` and the per-account select beside it. Both label their
options through `Modules/Ledger/Public/Support/CurrencyDisplayName`,
which answers from a bundled transcript of ICU's own currency names —
one name per currency per shipped locale — rather than from a
translation file or from `ext-intl` at render time.

The set of currencies is the set the bundled FX snapshot can price. A
reporting currency no rate can reach is one every roll-up would have to
leave out, so the two are generated from one another and a test fails
while they disagree.

## Why the names are transcribed rather than asked for

`ext-intl` is present in every shipped binary, and on the desktop it
carries full ICU locale data — ICU 77.1, 881 locales, `Zweedse kroon`
for a Dutch reader. **The mobile binaries carry the code and not the
data.** Both `ios-4.0.0-php8.5.9-icu` and `android-4.0.0-php8.5.9-icu`
ship a 2.3MB `libicudata.a` against a full package's ~30MB, holding 250
entries: `root`, `en`, 130 `en_XX` regionals and 114 `curr/en_XX`.
There is no `nl`, and no `curr/` bundle for any other language.

```
strings mobile-app/nativephp/android/app/src/main/staticLibs/arm64-v8a/libicudata.a \
  | grep -E '^icudt[0-9]+l/' | sort -u
```

A currency-name lookup against that data does not fail. ICU resolves an
absent locale up its parent chain to `root` and answers in **English**,
with no error and no exception — so a Dutch reader on the phone would
be shown "Swedish Krona" and nothing anywhere would report a problem.
That is the failure this repository already has a guard against
(`tests/Contracts/AColumnSeededWithWordsResolvesInTheReadersLocaleArchTest`),
and a runtime lookup would pass every check on a developer machine and
on CI while being wrong on the device.

So the answer is the one `Locale::groupMark()` and its siblings already
give for the same gap: ICU is the **source**, consulted where its data
is complete, and the tree carries the answer. Here the answer is too
large for a `match` arm, so it is a file.

Asking ICU at runtime *where it can answer* was considered and
rejected. It would have made the same account read `Bahreinse dinar` on
the desktop and `BHD` on the phone beside it, and a phone that words
things differently from the desktop is the defect
[`MoneyFormatTest`](money-formatting.md#the-invariants-the-tests-hold)
exists to prevent.

## The transcript

`Modules/Ledger/Resources/currency-names.json` — locale, then code,
then the name:

```json
{
    "nl": { "SEK": "Zweedse kroon", "…": "…" },
    "sv": { "SEK": "svensk krona",  "…": "…" }
}
```

It is generated by `scripts/generate_currency_names.php`, which must be
run on a host whose ICU carries full locale data. Re-run it after
replacing `Modules/FX/Resources/rates-snapshot.json`;
`ACurrencyIsNamedInEveryLocaleTest` fails while the two disagree.

**The test does not hold the transcript to the host's ICU word for
word, and cannot.** CLDR rewords currencies between releases: against a
CI runner's ICU, ten of the 806 entries differ — Spanish drops the
qualifier (`yuan` for `yuan renminbi`, `yen` for `yen japonés`),
Slovenian writes `poljski novi zlot` for the zloty, and Serbian moved
`Evro` to `evro`. A transcript generated once and committed would
otherwise turn an unrelated system-library upgrade into a red build.
What the test holds instead survives every version: **where ICU says a
language has its own word for a currency, the transcript must not be
answering that language in English** — which is the defect the
transcript exists to prevent, rather than a preference between two
correct spellings. ICU 77.1 and 78.3 happen to agree on all 806, so the
shipped desktop binary and a current developer machine generate the
same file byte for byte.

Three things in the generator are load-bearing:

- **The lookup disables ICU's fallback.** With it on, a currency a
  locale does not name resolves to `root` and comes back in English,
  which is exactly the string that must not be written into another
  language's file. With it off, a locale answers only for what it
  itself declares.
- **ICU keeps Norwegian under `no`.** The `nb` bundle holds a
  `%%Parent` pointer and nothing else, so a lookup by the app's own
  locale code returns **no name at all** — and a resolver that answered
  an absence with English would have read as one that worked.
- **ICU's `sr` is Cyrillic.** This app ships Serbian in Latin script
  (`Locale::Sr`, pinned by
  `tests/Contracts/ALocaleIsWrittenInTheScriptItShipsInArchTest`), so
  the generator reads `sr_Latn`. That one is not a missing name but a
  wrong one, which is the failure that reads as a working one.

The generator also asserts that Dutch and English name SEK
differently before it writes anything. Every other step in it answers
something on a host whose ICU data is filtered to English, because
English is the one language such a host does have; without that control
it would write twenty-six identical English files and report success.

## What resolves at runtime

```php
CurrencyDisplayName::forCode(string $code): string
```

The reader's locale, then English, then **the code itself**. It never
falls back to another reader's language: a code the transcript does not
carry — an importer stamps the statement's own denomination on the
account it mints, and the snapshot cannot price every currency a
statement arrives in — reads as `BHD`, which is true in every language.

`Modules/Ledger/Public/Support/CurrencyNames` reads and memoises the
file, and is also where the seeder and the seed migration get the list
of currencies from, so the choosable set and the named set cannot
drift. `CurrencyNames::forget()` exists for a test that must not read
what another left.

## What this replaced

`Modules/Ledger/Resources/lang/*/currencies.php` — twenty-six files of
four hand-written names — is **gone**, and so is `currencies.name`, the
column those names were seeded into and both pickers printed verbatim.
That column is what offered a Dutch reader "Pound Sterling", and
`CurrencyDisplayName` fell back to it when a locale had no line, so
seeding twenty-seven more currencies would have put English in front of
twenty-five languages by construction.

The two migrations that write `name` keep writing it: the column is
`NOT NULL` until `2026_09_12_000001_seed_every_currency_the_snapshot_can_price`
drops it, and a fresh install runs them in order.

One English word changed: CLDR calls GBP **British Pound** where the
hand-written line said "Pound Sterling". The wording is now CLDR's in
English exactly as it is in the other twenty-five languages, which is
the point of having one source.

## The minor unit is not ICU's to decide

ICU 78 dropped the forint and the rupiah to **zero** fraction digits
where ICU 77 and ISO 4217 give them two. The bundled desktop binary is
ICU 77.1 and a developer machine may be on 78, so a scale read from ICU
is a scale that changes when a host's system libraries are upgraded —
and what a stored integer *means* cannot move. The scale stays with
`CurrencyScale`, over the ISO 4217 data `brick/money` carries and
`composer.lock` pins. See [minor units and zero-decimal
currencies](minor-units-and-zero-decimal-currencies.md#where-the-scale-comes-from).

The rendered figure is safe for the same reason:
`brick/money`'s locale formatter pins `MIN_FRACTION_DIGITS` and
`MAX_FRACTION_DIGITS` to the amount's own scale before it hands the
number to ICU, so a forint renders `HUF 1,234.50` on an ICU 78 host
too.
