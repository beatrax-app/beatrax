# The Argon2id cost, and why the suite does not pay it

Three places in this codebase stretch a human secret into a key with Argon2id:

| Site | What it derives | Where the parameters end up |
| --- | --- | --- |
| `Modules\Auth\Internal\Lock\AppLockKdf` | the wrap key that opens the app-lock data key | nowhere — only the salt is stored, in `user_app_lock_configs.kdf_salt` |
| `Modules\Auth\Internal\Lock\PinHasher` | the PIN verifier | inside the `$argon2id$…` string itself |
| `Modules\Core\Public\Services\BackupEncryptor` | the stream key for an encrypted backup | in the file's own header |

All three derive at the cost named by `Modules\Core\Public\Contracts\KdfCost`.

## What ships

`Modules\Core\Internal\Encryption\ProductionKdfCost` is the only implementation
under `Modules/` or `app/`, and `CoreServiceProvider` binds it unconditionally.
It returns libsodium's `MODERATE` pair:

| Parameter | Value |
| --- | --- |
| `opslimit` | `3` (`SODIUM_CRYPTO_PWHASH_OPSLIMIT_MODERATE`) |
| `memlimit` | `268435456` — 256 MiB (`SODIUM_CRYPTO_PWHASH_MEMLIMIT_MODERATE`) |
| algorithm | `SODIUM_CRYPTO_PWHASH_ALG_ARGON2ID13` |

That is roughly half a second per derivation on a developer laptop. It is
memory-hard on purpose: a six-digit PIN has about twenty bits of entropy, so
the only thing standing between a stolen `user_app_lock_configs` row and the
data key is how expensive each guess is.

`BackupEncryptor::encryptWithKey()` is the deliberate exception and does **not**
take this cost. Its secret is already 256 uniformly random bits, so stretching
buys nothing and cost `(1, 8192)` is what the keyring read path pays.

## How it is pinned

`Modules/Core/tests/Unit/TheShippedArgon2idCostIsPinnedTest.php` and
`Modules/Auth/tests/Unit/TheAppLockDerivesAtTheShippedCostTest.php` are the
guard. Between them they assert:

- a **known-answer vector** — a fixed passphrase and salt derive one exact
  32-byte key. One assertion catches a lowered `opslimit`, a lowered
  `memlimit`, a swapped algorithm, and a shortened output, and it cannot be
  regenerated by accident the way an equality against a constant can be
  relaxed.
- the same vector through `AppLockKdf` as an application booted from
  `bootstrap/app.php` resolves it — the wiring, not just the numbers.
- that a hash from `PinHasher` starts `$argon2id$v=19$m=262144,t=3,p=1$`.
- that a `BackupEncryptor` header records `3` and `268435456`.
- that `KdfCost` resolves to `ProductionKdfCost` in an application built
  without the test harness, and that no second implementation has appeared
  under `Modules/` or `app/`.

Weaken the shipped cost and five of those seven cases go red.

## Why the suite is allowed to be cheap

Deriving at 256 MiB thousands of times is most of the suite's wall clock: the
`AuthFeature` testsuite ran 250 s, of which about 218 s was key derivation —
`AppLockProvisioner::enable()` alone costs three derivations.

`Tests\Helpers\CheapKdfCost` returns libsodium's floor, `(1, 8192)`, about
17,000 times faster. `Tests\TestCase::setUp()` binds it over the contract for
every test in the repository, since every module's `TestCase` extends that one.

Two properties make that substitution safe rather than a hole:

1. **No shipped class can select it.** There is no environment check, no config
   flag and no constructor default anywhere in `Modules/` or `app/`; the single
   binding names `ProductionKdfCost` and nothing else. `CheapKdfCost` lives
   under `tests/`, a composer `autoload-dev` root, so it is not in a bundle
   built without dev dependencies at all.
2. **Nothing stored depends on the cost that wrote it.** A PIN hash carries its
   own parameters, and so does a backup header, so a fixture written at either
   cost verifies under the other. Only the app-lock wrap key has implicit
   parameters, and it is derived and used within one test.

`BackupEncryptor`'s `MAX_OPSLIMIT` / `MAX_MEMLIMIT` ceiling stays fixed at
`MODERATE` for exactly that reason — it bounds what an unauthenticated header
may ask this process to allocate, and must not follow the write cost down.
See [`Core` — architecture](../features/core/architecture.md#the-argon2id-parameters-a-backup-header-may-ask-for).

## Changing the cost

Raise it, never lower it. The pinning tests will fail; regenerate the two
vectors by deriving them at the new parameters and update the expected hex,
the table above, and the `m=`/`t=` string in the `PinHasher` case. Existing PIN
hashes and backups keep opening, because they carry their own parameters.
Existing app-lock wraps do **not** — they would need
`AppLockProvisioner::rewrapForNewPin()` or an equivalent migration, so a change
there is a behavioural change and needs a specification change first.
